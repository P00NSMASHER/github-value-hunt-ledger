# Pair 3 — EXPERIMENT persistent state

## Validated reusable lessons
- Task 16: For broad operational-engine targets, code-level capability conjunctions outperformed title/README search. The useful conjunction was constrained solver (`OR-Tools`/`CP-SAT`) + domain legality (`FAR117`/duty) + passenger/rebooking terms + replay/determinism. This surfaced `mizuharaa/olus`, while obvious “airline disruption optimizer” searches mostly surfaced narrower aircraft-only or demo systems.
- Task 16: Deterministic-replay engineering is a high-signal maturity discriminator when it is evidenced by both an explicit nondeterminism inventory and golden tests that cross a persistence/restart boundary. `olus` pins mutable event fields, captured weather, RNG inputs and CP-SAT replay settings, then tests byte-identical replay output excluding documented wall-clock timing.
- Task 16: README integration claims must be traced into the exact optimization model. `olus` claims FAR117 hard constraints in its main recovery optimizer, but source inspection showed the main aircraft CP-SAT model audits legality post-solve; hard FAR117 filtering exists in the separate crew-overbooking CP-SAT. This distinction prevented an inflated evaluation.
- Task 17: Capability-conjunction search transferred successfully from airline recovery to financial reconciliation. The useful conjunction was exact Decimal money + canonical multi-source normalization + fee/refund semantics + split-group matching + idempotency/dedupe + explicit ambiguity/exception states. This surfaced and validated `Etherlabs-dev/multi-processor-reconciliation`, while generic reconciliation searches produced dashboards, assessments, and narrower explainable matchers missing part of the requested capability set.
- Task 17: For money-bearing engines, verify the same invariant at three layers when available: algorithm-level tests, persistence/database constraints, and CI/benchmark execution. In `multi-processor-reconciliation`, Python tests cover matching semantics, PostgreSQL rejects duplicate raw events and unbalanced journals, and the exact head revision has a successful CI run that executes schema/seed, pytest, n8n import, workflow validation and a synthetic reconciliation benchmark.
- Task 17: “Reference implementation” should not be treated as an automatic reject or as production proof. The repository explicitly disclaims verified client deployment, but source/tests/schema/CI substantiate a real engine. The correct calibration was STRONG for benchmark capability and NOT verified for enterprise scale.
- Task 18: Temporal decision engines should be verified through transition order plus negative time/provenance invariants, not forecast accuracy. `Vzlentin/calibre` exposes one legal loop (`resolve -> settle -> predict -> reconcile -> calibrate -> order`) and tests publication-time admission, original-issuance retention for late feedback, no rewrite of issued decisions, and fail-closed settlement before inventory mutation.
- Task 18: Exact-revision verification must precede crediting indexed repository descriptions. Search-engine/indexed documentation for `Vzlentin/calibre` still described a richer SQL/API/deployment architecture, while exact head `264b6fc...` had been replaced on 2026-09-09 with a smaller copied core whose README explicitly says the larger target architecture remains future work. This prevented a material false promotion.
- Task 19: Capability-conjunction search transferred a third time, now to human-governed dispatch. The productive conjunction was route solver + Gini/workload fairness + persisted appeal/manual-override state + deterministic explanation logic + persistent decision logs. This surfaced the zero-star `KesavamurthyT/Fair-Dispatch-Transparent-Fair-Route-Allocation`, whereas generic fair-routing searches mostly surfaced routing-only optimizers or fairness descriptions without contestability/audit state.
- Task 19: Governance features must be verified at the state-transition boundary, not by model/table existence. The candidate genuinely persists appeals, performs assignment reassignment on manual override and logs decisions, but deeper tracing showed that appeal approval does not automatically trigger remediation, the override’s before/after fairness calculation does not recompute driver-aggregated burden, and the main explanation path does not yet query actual manual-override state.
- Task 19: Test names are not evidence of the named invariant. `test_fairness_reduces_gini` exercises the fairness path but never asserts that final Gini is lower than initial Gini. Exact-head CI was also red even though the CVRP subset in checked-in local output passed. Strong scoring therefore requires assertion-level inspection plus exact-revision CI status, not filenames or local summaries.
- Task 20: Safe adaptive optimizers should be verified as a promotion transaction, not by the existence of an optimizer and a validator in the same repository. In `cls1277/RACE-Sched`, the active rule is snapshotted as baseline, generated code must parse/compile in a restricted environment, candidate and baseline run on matched deterministic episodes, rejected candidates never enter the ready queue, and only an accepted best rule reaches `RuleManager.update_rule()`; the no-accepted-candidate branch leaves the current rule unchanged.
- Task 20: “Hard validation” has multiple levels and must be named precisely. RACE-Sched strongly gates candidate code and restricts online choice to simulator-provided legal actions, but it does not provide an independent whole-schedule feasibility proof before promotion. The benchmark fit remained STRONG only after narrowing the claim from formal plan validation to candidate-execution/legal-action gating plus paired sandbox acceptance.
- Task 20: Lineage quality is graded, not binary. RACE-Sched records baseline name, candidate indices, iteration, plan/evaluation/critic metadata, rule-selection events, accepted-rule version/timestamp and eval metadata, but does not expose a first-class immutable parent→child repair DAG; inspected code also logs critic `suggested_changes` without clearly feeding those suggestions into the next planner history. This prevented overclaiming “repair lineage.”
- Task 21: Causal promotion decision value should be decomposed into three separately verified layers: treatment-identification/data provenance, held-out randomized policy-ranking evidence, and dollar utility under explicit campaign economics. `Nudge-Causal-Promotion-Intelligence-System` has all three, but the exact -11.85% versus +5.27% ROI comparison is model-valued rather than realized P&L, so the held-out Hillstrom Qini evidence is essential independent support rather than decoration.
- Task 21: Trace baseline semantics through the actual artifact handoff, not just similarly named source classes. The reusable `src/models/naive_baseline.py` implements pseudo-uplift with treatment as a feature, while the Phase 1 notebook used by the downstream budget pipeline trains a treated-only response model and exports that raw `p_convert` as `naive_score`; the latter is the benchmark-relevant correlational baseline.

## Failed search patterns
- Generic repository-title queries such as “airline disruption optimizer/recovery” produced many aircraft-only projects, UI demos, or agent wrappers without the requested crew legality + passenger recovery + uncertainty + replay combination.
- Research-paper repositories can look unusually deep but must be checked for the actual imported implementation. `kahyakursat1-cloud/hybrid-cpsat-qiga-airline-recovery` had strong paper/experiment claims, but inspected experiment scripts imported `src.*` modules that were absent from the repository tree, so it was not accepted as the engine result.
- Task 17: Generic “reconciliation platform/engine” search produced many invoice dashboards, assessment projects, and accounting demos with duplicate/unmatched labels but no fee-aware + refund + split-settlement semantics backed by tests.
- Task 17: Explainability/property-testing alone is not enough for this benchmark. `dylanpulver/recon` is technically disciplined but explicitly limits grouping to many-to-one and does not supply the full refund/fee/multi-source semantics requested.
- Task 18: Generic “forecast-driven inventory control” searches mostly returned forecast + safety-stock simulators without publication clocks, late-observation provenance, immutable issuance semantics or settlement-state boundaries. `Surge77/stockout` is especially useful negative evidence because its current README explicitly says the earlier conformal/newsvendor inventory layer was deleted; forecasting rigor alone is not an inventory decision engine.
- Task 19: Generic “fair route allocation” / “driver fairness” search was noisy: mature VRP engines often stop at balancing objectives/constraints, while hackathon-style fairness systems often stop at dashboards or README claims. Requiring appeal/override/log symbols in the same code search sharply improved precision.
- Task 19: A governance table plus endpoint is insufficient evidence of a closed-loop control. Do not credit an appeal as remediation until its approved state is traced into an actual re-plan/state transition, and do not credit “before/after fairness” until metrics are recomputed from the post-action entity-level state.
- Task 20: Generic “production scheduling optimizer” and “FJSP repair” searches produced many solvers that stop at generating a repaired schedule. `Zhang-Henry/CoEvoSkills` was especially useful negative evidence: it validates repair strategies but, if none is fully valid, explicitly returns the candidate with the fewest issue types. A validator adjacent to a solver is therefore not evidence of fail-closed promotion.
- Task 20: Hard-validation search terms can surface technically deep but domain-misaligned systems. `mahmoudelfeelig/Planora` has strong validators, disruption hashes and extensive evidence, but it is academic timetabling rather than manufacturing production planning; retain its validation patterns as analogs, not as the benchmark answer.
- Task 21: Generic “causal uplift marketing” searches returned many estimator tutorials and well-built uplift packages without an explicit economic decision surface showing the correlational policy crossing into negative ROI. Model quality alone is not evidence of decision value.
- Task 21: A causal model scoring both its own target set and a competitor target set can produce a consistent same-yardstick comparison but is not independent realized-profit evidence. Do not promote a dollar table on that basis alone; require randomized/held-out outcome evidence or an independent policy-value estimator.

## Useful terminology / signatures
- Operational replay: `NONDETERMINISM.md`, `golden replay`, `deterministic=True`, `num_search_workers=1`, fixed `random_seed`, frozen weather/input snapshots, persistence/restart equality.
- Airline recovery conjunction: `CrewLegalityEngine`, `FAR117`, `crew_overbooking`, `rebooking`, `CP-SAT`, `uncertain horizon`, `regret`, `cascade predictor`.
- Red-team signature: compare README phrase “hard constraint” against actual `model.add(...)` / candidate-variable construction and solution extraction.
- Financial reconciliation conjunction: `Decimal`, `fee_aware`, `partial_refund`, `split_payment`, `ambiguous_candidates`, `ambiguous_split`, `duplicate_input`, `idempotency_key`, `CursorConflict`, `recon_exceptions`.
- Money-engine verification signature: successful CI at exact head revision + database invariant tests + deterministic/synthetic benchmark result, not README business-outcome claims.
- Temporal inventory conjunction: `available_at`, observation clock, `deliveries_since`, original-origin keyed score windows, `settle_periods`, complete simulation demand, `decision_bound`, `order_up_to`, no order reissue, gap/tail settlement.
- Architecture-drift red-team signature: compare current exact-head tree/README against search-indexed feature claims and recent large replacement/rewrite commits before crediting persistence/API/deployment surfaces.
- Fair-dispatch conjunction: `fairness_threshold_gini`, `max_fairness_iterations`, `ManualOverride`, `AppealStatus`, `DecisionLog`, `before_metrics`, `after_metrics`, `had_manual_override`, `agent_timeline`, deterministic explanation categories.
- Governance-loop red-team signature: trace appeal status → remediation/replan; override mutation → entity-level metric recomputation; override/appeal state → explanation inputs; decision-log persistence → mutability/tamper properties; test name → actual assertions.
- Safe-promotion conjunction: active baseline object + bounded/compiled candidate + matched baseline/candidate evaluation + explicit acceptance predicate + hot-swap/update mutation + `no accepted candidate` branch + fallback/disable behavior + persisted candidate/eval events.
- Lineage red-team signature: distinguish event trace, versioned accepted artifact, causal parent→child repair graph and immutable audit; search for whether critic/repair feedback is actually consumed by the next candidate-generation step rather than merely logged.
- Causal-promotion conjunction: treated-only `p_convert`/`naive_score` + CATE model + held-out `Qini`/RCT metric + `budget_sweep` + `naive_roi` + `break_even_uplift` + common campaign economics.
- Causal-value red-team signature: distinguish target-selection score from evaluation score; ask whether the dollar comparison is realized, doubly robust/off-policy, randomized/holdout-based, or merely model-valued; preserve explicit cost/margin assumptions.

## Candidate search skills
### Capability-Conjunction Search + Claim Tracing — evidence on 5 distinct tasks; eligible for promotion
WHEN TO USE: Broad systems benchmarks where the target is defined by several rare co-occurring capabilities and repository names are likely generic.
PROCEDURE: Search code for 3–4 rare implementation signatures from different requirement families; deep-inspect the candidate; trace every integration-critical README claim into solver/source/tests; inspect persistence/CI evidence when the domain has money, safety, compliance or reproducibility boundaries.
WHY IT WORKED: Task 16 found a 1-star generic-named airline recovery engine with the requested capability spread and exposed a material README overstatement. Task 17 independently transferred the same method to finance, where a conjunction of Decimal + refund/fee + split + dedupe + exception semantics surfaced a low-attention exact-fit reconciliation engine and red-team review preserved its bounded-split/non-production caveats. Task 19 independently transferred it to fair dispatch, where solver + fairness + contestability + explanation + decision-log signatures surfaced a zero-star exact-fit implementation and enabled targeted adversarial tracing of each governance seam. Task 20 transferred it to adaptive production scheduling: baseline object + candidate gate + paired evaluator + hot-swap + failure branch surfaced the safety transaction and exposed the weaker repair-lineage claim. Task 21 transferred it to causal retail promotion: correlational baseline + treatment-effect estimator + held-out causal metric + explicit budget/ROI semantics surfaced a zero-star exact-fit engine while the red-team separated model-valued ROI from independent outcome evidence.
STATUS: Evidence threshold is satisfied. Eligible for SEARCH_SKILLS promotion; this state update does not modify the central skill file.

### Transition-Order + Temporal-Invariant Verification — evidence 1/2
WHEN TO USE: Inventory, scheduling, planning, campaign-control or other decision systems where correctness depends on what was knowable when and on irreversible state transitions rather than on predictive accuracy alone.
PROCEDURE: (1) Find the exact legal transition sequence. (2) Trace publication/availability clocks into admission logic. (3) Verify late feedback keeps original decision/issuance identity instead of becoming recent history. (4) Verify already-issued decisions are immutable under later actuals. (5) Verify settlement/state mutation validates the full required interval before changing state. (6) Pin exact head and compare it with indexed docs/history so removed architecture is not credited as current capability.
WHY IT WORKED: Task 18 separated `Vzlentin/calibre` from ordinary inventory forecasting projects and, during red-team, caught that public search snippets still described a richer pre-reset SQL/API stack that the current exact revision no longer contains.
STATUS: Do not promote to SEARCH_SKILLS.md yet. Requires success on at least one additional distinct benchmark task or Hunt 15 approval.

### Governance-Loop Boundary Verification — evidence 1/2
WHEN TO USE: Optimization/decision systems that claim human contestability, manual override, explainability or auditability around automated decisions.
PROCEDURE: (1) Trace the automated decision into its persisted record. (2) Trace appeal/contest state to the exact operation it can change; do not equate status change with remediation. (3) Trace manual override through the actual operational mutation and then recompute metrics from the affected entity-level post-action state. (4) Trace governance state into explanation inputs rather than merely checking that an explanation schema has a field for it. (5) Classify decision logs by persistence and mutability; ordinary rows are not tamper-evident evidence. (6) Inspect assertions in named fairness/governance tests and check exact-head CI separately.
WHY IT WORKED: Task 19 preserved the candidate as a genuine fair-dispatch engine while uncovering three material seams that README/schema inspection alone would miss: approval without automatic replan, misleading override before/after fairness snapshots, and incomplete override-to-explanation wiring.
STATUS: Do not promote to SEARCH_SKILLS.md yet. Requires success on at least one additional distinct benchmark task or Hunt 15 approval.

### Promotion-Transaction Boundary Verification — evidence 1/2
WHEN TO USE: Adaptive optimization, scheduling, planning or generated-policy systems that claim a safe baseline/candidate validation-and-deployment loop.
PROCEDURE: (1) Identify the exact active/baseline state object. (2) Trace candidate construction through parse/compile/domain guards before comparison. (3) Verify baseline and candidate are compared on matched scenarios or equivalent controlled evidence. (4) Trace the acceptance predicate into the only state-mutation/hot-swap site. (5) Trace `no candidate`, rejected candidate, timeout/error and runtime-failure branches to confirm they retain or restore a safe policy. (6) Grade lineage separately: logged events < versioned accepted artifacts < explicit parent→child repair ancestry < immutable/tamper-evident audit. (7) Check whether critic/repair feedback is actually consumed by the next generation step.
WHY IT WORKED: Task 20 separated `cls1277/RACE-Sched` from ordinary FJSP repair code and found both the real safety transaction (baseline snapshot, restricted candidate, paired evaluation, accepted-only hot-swap) and the two overclaim hazards (no formal whole-plan validator; repair lineage is a trace rather than an explicit causal graph).
STATUS: Do not promote to SEARCH_SKILLS.md yet. Requires success on at least one additional distinct benchmark task or Hunt 15 approval.

### Causal Policy Value + Evaluator-Independence Check — evidence 1/2
WHEN TO USE: Uplift, personalization, promotion, pricing or other causal-decision systems claiming that causal targeting improves economic value versus response/propensity/correlation-based decisions.
PROCEDURE: (1) Trace the naive policy to the exact score/artifact that actually selects actions. (2) Trace causal estimates to held-out/randomized or otherwise defensible policy-ranking evidence. (3) Trace both policies through an explicit utility function with the same costs/margins/budget. (4) Identify who evaluates each target set: realized outcomes, randomized estimator, doubly robust/off-policy estimator, or the candidate model itself. (5) If the candidate model is the common evaluator, treat the dollar result as modeled decision value and require an independent outcome layer before STRONG. (6) Stress-test documented cost/margin assumptions because break-even conclusions may move even when ranking quality does not.
WHY IT WORKED: Task 21 found `Himanshu-Laddhad/Nudge-Causal-Promotion-Intelligence-System`, verified the exact treated-only correlational baseline, CATE/Qini pipeline and +5.27% versus -11.85% same-budget modeled ROI, while independent held-out Hillstrom RCT evidence supported the selected S-Learner's ranking advantage and prevented the modeled dollar table from being mistaken for realized campaign profit.
STATUS: Do not promote to SEARCH_SKILLS.md yet. Requires success on at least one additional distinct benchmark task or Hunt 15 approval.
