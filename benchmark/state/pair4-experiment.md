# Pair 4 — EXPERIMENT persistent state

## Validated reusable lessons
- DECISION-CLAIM → RUNTIME-SIDE-EFFECT TRACE: Confirmed independently on Tasks 25 and 26. When a repository claims a decision-changing mechanism or algorithm, trace the claim through the public API/dispatch path into executable implementation, then into the state/output mutation and finally into semantic tests. Task 25 showed that uncertainty/VoI calculations and post-processing labels did not enforce deferral or information acquisition at runtime. Task 26 showed the same failure mode in a different domain: RMOL advertises/tests dynamic programming, but the public service method is empty and the DP implementation body is commented out; its forecasting and unconstraining tests are also hard-coded passes. Feature names, docs, enums and test names are therefore evidence of intended surface only, not executable capability. This lesson has now succeeded on two distinct benchmark tasks and is eligible for SEARCH_SKILLS promotion; it was not promoted in this run to avoid racing shared-file edits.

## Failed search patterns
- Task 23: Broad queries built only from "self-driving lab", "optimizer", "campaign" and "autonomous laboratory" mostly surfaced orchestration/optimization frameworks without evidence that the campaign authority distinguishes scientific confirmation, recovery, context acquisition, escalation and stopping. Do not treat generic closed-loop execution as a governance-state match without source-level transition evidence.
- Task 24: Railway scheduling searches centered on "optimization", "robustness" or "re-planning" alone surfaced many projects that recompute a schedule but do not preserve accepted/underway work. A previous solution supplied as an OR-Tools `AddHint`/warm start is not evidence of a lock: it can be displaced whenever the new objective prefers something else.
- Task 24: README claims of "robustness" are weak evidence. Require executable perturbation or stochastic evaluation and inspect the pass/fail semantics; a robustness percentage can hide tolerated failures, as RailSync explicitly counts a scenario feasible when at most one non-critical unplanned failure remains.
- Task 25: Generic "predictive maintenance" / "maintenance optimization" searches were mostly forecasting and fresh-schedule work. The high-signal conjunction was scarce maintenance slots/capacity + imperfect repair/replace + explicit uncertainty/confidence + value-of-information/another observation. Even with that near-exact terminology, paper/README matches can overstate executable decision semantics.
- Task 25: Do not infer operational deferral or active information acquisition from analytics. In PPDM, the confidence threshold that marks later actions N/A was found in plotting/post-processing, while the evaluator still emits an argmax action; `steps_to_avoid` is computed/logged but the inspected loop did not prove that observation acquisition is actually delayed or triggered by it.
- Task 26: Searching only for protection levels, EMSR, exact DP, bid prices or overbooking surfaced strong downstream capacity-control libraries that assume demand is already known. `arikanatakan/revmng` is a useful comparator with stronger worked-example validation and exact DP, but its README explicitly excludes demand forecasting and censored-booking unconstraining, so downstream RM sophistication alone does not satisfy an end-to-end latent-demand task.
- Task 26: Documentation and test-file names can materially overstate maturity. RMOL's public surface advertises DP and contains `OptimiseTestSuite`, `ForecasterTestSuite` and `UnconstrainerTestSuite`, yet source tracing found an empty DP service method, an all-commented DP core, hard-coded-pass forecast/unconstraining tests, and optimizer assertions that are mostly no-throw checks. Searchers should inspect the call path and assertion body, not count feature/test names.

## Useful terminology / signatures
- Task 23: High-signal implementation signatures were `DecisionRecorded`, `campaign_id` + monotonic iteration identity, `evidence_run_ids`, explicit `stop_reason`, `intervention_required`, resume/replay from append-only events, optimizer-state restoration, and refusal to continue across an unknown physical outcome.
- Task 23: High-signal scientific-governance vocabulary was exploration/confirmation/replication/failure-recovery/human-escalation/stopping plus transition guards. Searching this vocabulary separately from optimizer terms exposed the difference between scientific authority and execution recovery.
- Task 23: A missing first-class `acquire_context`/context-acquisition transition is meaningful negative evidence when the benchmark asks for a campaign authority that can deliberately seek more context rather than merely retry or stop.
- Task 24: High-signal lock-preserving scheduling signatures were `locked_assignments`, a scenario model carrying task→block pins, propagation of those pins into the re-solve, and a hard equality such as `model.Add(x[(task_id, locked_block_id)] == 1)`.
- Task 24: High-signal robustness signatures were `ScenarioRobustnessEngine`, deterministic seeded Monte Carlo over failure-time/survival curves, explicit per-scenario failure accounting, `PlanBContingency`, disruption-diff outputs, and an adversarial test where a higher-priority emergency cannot displace locked baseline work.
- Task 25: High-signal maintenance-decision signatures were slot-capacity action masks, actions `{hold, imperfect repair, replace}`, repair-count/reset dynamics, `prob_thresh`, Monte-Carlo policy sampling, `mutual_information`, `VOI`, `steps_to_avoid`, and a future-uncertainty surrogate. The combination is much more selective than "predictive maintenance" alone.
- Task 25: A claimed abstention/information-acquisition mechanism should be traced through metric → threshold/rule → runtime control-flow side effect → negative/edge-case test. A value calculated or plotted without changing execution is evidence of analysis, not of an enforced decision gate.
- Task 26: High-signal end-to-end revenue-management signatures were `SegmentSnapshotTable`, price/product gross-booking snapshots, availability snapshots, a censorship flag triggered by unavailable inventory, `HistoricalBookingHolder`, `Detruncator::unconstrain`, EM latent-demand reconstruction, booking-class mean/stddev forecasts, `generateDemandSamples`, `setCumulatedProtection`, `setCumulatedBookingLimit` and bid-price vectors. The conjunction exposes the upstream state correction that many modern RM libraries intentionally omit.
- Task 26: A useful maturity red-team signature is disagreement between advertised dispatch and implementation body: `optimize<OPT_DP>` → `optimalOptimisationByDP()` → empty/commented implementation, or a named test whose asserted variable is hard-coded true. These patterns should immediately downgrade evidence quality even when other engine paths are real.

## Candidate search skills awaiting second-task confirmation
- STATE-MACHINE + AUDIT-LOG CONJUNCTION: When a task asks for governed autonomous decisions, search for explicit domain-state/transition vocabulary and durable decision/event persistence as a conjunction. Then red-team each requested action independently; do not infer scientific recovery/escalation/context acquisition from generic retries, resume or human-intervention plumbing. Task 23 used this procedure to identify OpenSDL's strong replay/governance substrate while correctly withholding STRONG because the full requested action repertoire was not implemented.
- PERTURBATION + INVARIANT TEST: When a scheduling/repair/re-planning task requires preserving an accepted baseline, search for an explicit disruptive scenario and then inspect whether the invariant is encoded as a hard constraint and tested under pressure from a better-scoring/higher-priority alternative. Reject warm starts, hints and objective penalties as substitutes for locks. Separately inspect robustness success semantics so tolerated failures are not mistaken for proof. Task 24 used this procedure to distinguish RailSync's tested hard lock from a comparator whose prior plan is only an `AddHint` warm start.
- CENSORED-STATE → LATENT-STATE → CONTROL HANDOFF: When searching for inventory/revenue/capacity systems where observed demand can be censored by stockout or closed availability, require a source-level chain from censor detection through latent-demand reconstruction and forecast distribution into the actual control decision (protection/booking/order/bid-price). A sophisticated optimizer that accepts already-clean demand is only a downstream component. Task 26 used this procedure to distinguish RMOL's rare end-to-end booking-state→EM unconstraining→forecast→protection path from newer capacity-control libraries that explicitly leave forecasting/unconstraining out of scope. Await a second cross-domain confirmation before promotion.
