# Pair 5 — EXPERIMENT persistent state

## Validated reusable lessons
- Task 30: README-level "verification" claims are not enough. High-signal implementation checks are: (a) executor output explicitly treated as a claim, (b) completion fail-closed unless a verifier/auditor confirms original requirements, (c) blocking constraints prevent `complete`, (d) verifier/auditor mutation is detected or restored, and (e) resume reconstructs planning context from durable recorded state. These discriminators separated a true verification loop from generic orchestration/checkpoint frameworks.
- Task 31: For ticket-driven autonomous software orchestration, inspect four implementation transitions rather than generic "agent orchestration" claims: tracker state -> dispatch/reconciliation; worker exit/stall -> retry/backoff; issue identity -> collision-safe isolated workspace/path boundary; validation evidence -> review/merge state. OpenAI Symphony implemented and tested all four strongly enough to survive red-team review, while also exposing important caveats: retry/block state is process-local, workspace separation is not equivalent to a hardened sandbox, and some quality gates are WORKFLOW policy rather than an independent verifier.
- Cross-task reinforcement from Tasks 30 and 31: the useful transferable habit is to locate the actual state transition that accepts work as complete/reviewable, then inspect recovery and evidence around that transition. This is stronger than searching for reviewer/auditor terminology alone. The exact Task-30 role×persistence×proof search recipe is not yet considered independently confirmed because Task 31 did not require a manager/executor/auditor role split.
- Task 32: For self-improving systems, the useful trusted-state transition is candidate skill -> held-out verifier -> trusted registry -> runtime eligibility. `kenhuangus/ASG-SI` implements this explicitly: only 100%-passing held-out candidates are marked verified and inserted, while runtime reuse filters to verified skills and every candidate verification is written as an audit record with per-case outcomes and a program hash. Auditability and rollback must be evaluated separately; the inspected prototype does not implement a durable skill-version rollback/disable mechanism even though its README frames modular skills as reversible.
- Cross-task reinforcement from Tasks 30-32: acceptance-path inspection transfers from task completion to capability promotion. The high-signal question is always "what exact code path changes trusted state, and what evidence can or cannot unlock it?" Task 32 adds a second discriminator: a trustworthy promotion gate does not imply durable rollback, so trusted-state entry and trusted-state reversal need separate verification.
- Task 33: For computational metrology, a high-value traceability substrate is the conjunction of (a) explicit uncertainty/correlation identity, (b) propagation through arbitrary functions and (c) persistent machine-readable state. `usnistgov/rmellipse` implements all three strongly enough to distinguish it from a scalar uncertainty calculator: shared `umech_id` labels carry full-correlation semantics, `RMEProp` propagates sensitivity/Monte-Carlo state through decorated Python functions, and HDF5/object round-trip tests preserve measurement uncertainty state and importable function identity. Exact reproducibility/provenance is a separate claim: module/name serialization does not freeze code/environment hashes, and the repository explicitly flags pre-1.0/Monte-Carlo limitations.
- Task 34: For heterogeneous scientific-workflow provenance, the valuable intersection is (a) real adapters/interceptors spanning multiple execution or ML systems, (b) a common lineage object carrying parent/child workflow identity plus inputs/outputs/runtime context, and (c) persistence/query tests that cross a framework boundary. `ORNL/flowcept` implements this with Dask and MLflow adapters, common workflow/task provenance state and a Dask+PyTorch nested-lineage test. Runtime observability and persistence must still be separated from stronger claims of immutable/tamper-evident provenance or exact replay.

## Failed search patterns
- Broad repository searches centered only on phrases like `agent harness`, `manager verifier`, or `long horizon agent` produced high generic-framework noise and many systems with memory/checkpointing but no independent original-requirements audit boundary.
- Searching for "auditable" alone over-selected logging/trace/evidence-recording systems where the executing agent can still effectively self-certify completion.
- Task 31: Broad searches for `coding agent orchestrator` or `kanban coding agent` returned many thin wrappers that spawn a CLI in a worktree but lack reconciliation, retry semantics or an evidence-to-review gate. Require at least two of: tracker-state reconciliation, retry/backoff, path/workspace safety, CI/review proof, or explicit rework semantics before deep inspection.
- Task 31: README claims of "isolated workspace" are insufficient evidence of security isolation. Distinguish deterministic per-issue workspace/path-safety from container/OS sandboxing and do not upgrade one into the other.
- Task 32: Broad `self-improving agent` searches over-select prompt optimizers and memory systems that improve aggregate scores but do not have a candidate-skill promotion boundary. Search the actual registry insertion/read-filter code instead.
- Task 32: Do not infer rollback from audit logs, hashes, git history, modular skills or a README claim that capabilities are reversible. Require a concrete disable/version-select/restore path if rollback is important.
- Task 33: `uncertainty calculator` and `Monte Carlo uncertainty` searches alone over-select one-shot numerical tools that do not preserve correlation identity or a machine-readable calculation chain. Require the uncertainty-object + arbitrary-function + serialization intersection before deep inspection.
- Task 33: Do not equate persistent HDF5 or function module/name metadata with exact provenance. If reproducible traceability is load-bearing, separately require source/environment/version hashes or another immutable execution manifest.
- Task 34: Generic `workflow provenance` searches mix workflow engines, metadata catalogs and tracing libraries. Do not deep-inspect unless at least two heterogeneous framework adapters plus a shared runtime lineage schema are visible. Also do not infer immutable evidence from a provenance database or a W3C-PROV-oriented vocabulary; separately verify integrity/attestation if that property matters.

## Useful terminology / signatures
- Role axis: `manager`, `executor`, `auditor`, `verifier`, `reviewer`.
- Persistence axis: `resume`, `checkpoint`, `task state`, `recorded rounds`, `latest state`, `durable run`.
- Proof axis: `original requirements`, `stable task contract`, `independent evidence`, `executor text is only a claim`, `blocking constraints`, `complete clean aligned`, `read-only auditor`, `workspace mutation`, `completion guard`.
- Source inspection signature: search for the code path that converts verifier output into an accepted completion state, not merely the prompt that asks a verifier to review.
- Task-31 orchestration signatures: `reconcile_running_issues`, `retry_attempts`, worker `DOWN`, stall timeout, exponential/backoff retry, stale retry token, active/terminal tracker states, `workspace_key`, symlink/path escape, persistent workpad, ticket-provided `Validation`/`Test Plan`, PR feedback sweep, Human Review, Rework, Merging.
- Ecosystem-lineage signal: multiple independent projects explicitly advertising compatibility with the same named orchestration specification can reveal a canonical reference implementation worth deeper inspection.
- Task-32 promotion signatures: `verify_skill`, `heldout_tasks`, strict `pass_rate`, `candidate.verified`, the sole trusted-registry insertion call, runtime `get_verified_skills`/equivalent filters, verification-report hashes, and explicit rollback/version-select APIs when claimed.
- Task-33 metrology signatures: `umech_id` or other shared uncertainty identity; covariance/sensitivity and Monte-Carlo state; `propagate`/decorator paths around arbitrary functions; round-trip serialization of measured values, covariance/MC state and function identity; GUM terminology; explicit distinction between traceability state and exact code/environment provenance.
- Task-34 provenance signatures: concrete `adapters`/`interceptors` for Dask, MLflow, TensorBoard, PyTorch or equivalent heterogeneous systems; `workflow_id`, `parent_workflow_id`, `campaign_id`, `used`, `generated`, code-repository/environment metadata; adapter persistence/query tests; nested cross-framework workflow tests; explicit separation between runtime lineage capture and cryptographic provenance integrity.

## Candidate search skills awaiting second-task confirmation
### Role × persistence × proof conjunctive search
WHEN TO USE: Finding long-running or high-stakes agent/control architectures where the real value depends on reliable completion rather than generic agent capability.
PROCEDURE: Search using at least one term from each of role separation, durable state/resume, and evidence/original-requirements verification. Once a candidate is found, inspect the actual acceptance/completion guard, resume reconstruction path, failure persistence, and tests before reading broader benchmark claims.
WHY IT WORKED ON TASK 30: It surfaced AMAP-ML/LongHorizon-Harness and discriminated it from ramannanda9/agent-harness (strong checkpoint/orchestration but no equivalent independent original-contract auditor gate) and lordaeternus/agent-execution-harness (strong evidence/claim gates, but a lighter agent-instruction harness rather than the same manager/executor/auditor long-horizon runtime architecture).
STATUS: Awaiting confirmation on at least one additional distinct benchmark task; Task 31 reinforced the acceptance-path inspection principle but did not independently confirm the exact three-axis role search. Do not promote yet.

### Descendant cluster -> canonical spec -> transition verification
WHEN TO USE: Several low-attention repositories advertise compatibility with or implementation of the same named agent/orchestration specification.
PROCEDURE: (1) use descendants as discovery beacons rather than assuming they are the best artifact; (2) pivot to the named canonical spec/reference; (3) pin exact revision; (4) inspect the concrete control transitions required by the target task; (5) search tests for those transitions and their failure modes; (6) compare descendant-added features separately rather than attributing them to the canonical system.
WHY IT WORKED ON TASK 31: Harmonica, Stokowski and other issue-driven orchestrators repeatedly pointed to the Symphony specification. Pivoting to openai/symphony exposed the canonical Elixir reference, its retry/reconciliation state machine, collision-safe workspace lifecycle, extensive tests and proof-to-review WORKFLOW policy.
FAILURE MODES: descendant marketing can overstate what the canonical spec requires; a spec may exist without a maintained reference implementation; independent projects may all copy the same weak claim; popular canonical projects can distract from a technically superior descendant.
STATUS: One-task evidence only. Await a second distinct benchmark success before promotion to SEARCH_SKILLS.md.

### Promotion-boundary plus rollback split
WHEN TO USE: A self-improving agent framework claims reusable skills, governed learning, auditable promotion or reversible capability changes.
PROCEDURE: (1) locate candidate-skill creation; (2) locate held-out/replay verifier and pass threshold; (3) trace the only transition that inserts a candidate into the trusted registry; (4) trace the runtime read path and confirm unverified entries cannot execute; (5) inspect evidence/audit records; (6) separately locate an actual disable/version-select/restore transition rather than inferring rollback from modularity or logs.
WHY IT WORKED ON TASK 32: It identified ASG-SI's real 100%-pass held-out promotion gate and runtime verified-skill filter, while simultaneously falsifying the stronger implication that the prototype has a production-grade rollback subsystem.
FAILURE MODES: same-distribution held-out tasks can overstate generalization; verifier and executor may share the same assumptions; audit hashes may not be cryptographically anchored; a git branch or log history may be mistaken for an operational rollback control.
STATUS: One-task evidence only. Keep local until a second distinct benchmark task confirms transfer or Hunt 15 approves promotion.

### Metrology traceability invariant intersection
WHEN TO USE: Searching for uncertainty/metrology software where value depends on preserving traceable uncertainty through a calculation chain rather than producing a one-time uncertainty number.
PROCEDURE: (1) require an uncertainty object model with explicit correlation/covariance identity; (2) verify propagation through arbitrary user calculations rather than only a fixed formula UI; (3) require persistent machine-readable serialization and inspect round-trip tests; (4) trace correlation semantics into source/tests; (5) separately inspect exact code/environment provenance so persistence is not mistaken for deterministic replay.
WHY IT WORKED ON TASK 33: It elevated `usnistgov/rmellipse` over generic uncertainty calculators and exposed a concrete NIST implementation with shared-mechanism correlation, arbitrary-function uncertainty propagation and HDF5/object round-trip behavior, while also bounding its provenance and Monte-Carlo maturity limits.
FAILURE MODES: one-shot calculators may have excellent statistics but no persistent chain; identical mechanism labels may encode only full correlation rather than arbitrary partial correlation; serialized function names may silently resolve to changed code; project claims of traceability may describe intent rather than a complete calibration-chain authority model.
STATUS: One-task evidence only. Keep local until a second distinct benchmark task confirms transfer or Hunt 15 approves promotion.

### Provenance adapter × lineage-schema × cross-framework-test intersection
WHEN TO USE: Searching for scientific/AI provenance systems where commercial value comes from observing existing heterogeneous execution stacks without replacing them.
PROCEDURE: (1) identify at least two concrete framework/runtime adapters or interceptors in source; (2) locate the common workflow/task lineage model and require parent/child identity plus input/output/runtime metadata; (3) find persistence/query tests for each major adapter; (4) require at least one test or example where lineage crosses a framework boundary, not just two disconnected adapters; (5) check publication/history evidence for scale and maturity; (6) separately test whether integrity, immutability or exact replay is actually implemented rather than inferred from the word provenance.
WHY IT WORKED ON TASK 34: It distinguished `ORNL/flowcept` from framework-native workflow engines and lower-level tracers by combining Dask/MLflow adapter code, common workflow lineage fields, persistence tests and a Dask+PyTorch parent/child lineage test, while bounding paper-reported performance and non-cryptographic provenance claims.
FAILURE MODES: adapters may be present but untested; different adapters may write incompatible schemas; persistence may exist only in optional modes; W3C-PROV terminology may be declarative rather than fully enforced; runtime lineage may be mutable and therefore unsuitable as evidence without an added integrity layer.
STATUS: One-task evidence only. Keep local until a second distinct benchmark task confirms transfer or Hunt 15 approves promotion.
