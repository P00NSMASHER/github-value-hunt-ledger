# Pair 7 — EXPERIMENT persistent state

## Validated reusable lessons
- Task 44: verifier quality is best judged at fail-open boundaries, not from “backup verified” prose. Source/tests that distinguish PASS vs FAIL vs SKIP vs UNKNOWN, and that explicitly refuse to turn missing evidence/environment faults into green success, provided high-signal evidence.
- Task 44: verify the exact operational depth independently of the SPEC/README. `pg_hardstorage` has a real scratch restore plus `pg_verifybackup`, but its current sandbox source explicitly says it does not boot PostgreSQL or run `pg_amcheck`/smoke SQL. Scoping the claim to code prevented an overpromotion.
- Task 45: for portable evidence systems, the highest-signal verification sequence was NORMATIVE CONTRACT -> IMPLEMENTATION -> NEGATIVE/GOLDEN VECTORS -> DIFFERENTIAL IMPLEMENTATION. `swarrm-verify` was strong because the bundle contract's root/signature/manifest requirements map to a concrete Rust verifier, hostile/fuzz fixtures, and shared cross-implementation golden vectors; spec-only candidates remained weaker.
- Task 45: internal cryptographic integrity, export-set completeness, and external trust are separate claims and must stay separate. A self-contained bundle can verify E1 integrity while completeness is UNKNOWN without a signed manifest and stronger trust remains dependent on out-of-band roots/high-water evidence. Preserving this distinction prevented a false “self-trusting proof” promotion.
- Tasks 44 + 45: FAIL-OPEN BOUNDARY ARCHAEOLOGY now has two independent confirmations. In Task 45, stripped/absent completeness evidence produces an explicit UNKNOWN downgrade (or strict failure under `--require-manifest`) and malformed carried evidence fails, rather than silently becoming VERIFIED. This matches the Task 44 pattern where missing/ambiguous verification evidence must not become green success.
- Task 46: inspect the provenance of every input that can unlock PASS/CLEAN. A field named `verified` or an event named `ok` is not independent evidence if the verifier merely trusts a caller-authored literal. `BackupAttest` can emit clean/exit-0 from self-reported `verified=yes` plus a fresh `ok` drill without reading backup bytes or executing a restore; the drill identifier is not even cross-checked against the manifest.
- Task 46: derived metrics must use the same admissibility set as the core validity/chain logic. `BackupAttest` correctly excludes an orphan incremental from an assembled recovery chain but its RPO calculator counts every timestamp, including that orphan, as a recoverable point. Its tests lock in a 27h gap from an unusable backup where the chain-reachable gap is 39h. Cross-module invariant-set disagreement is a high-signal false-green indicator.
- Task 46: a polished repository and a substantial test count can increase false-promotion risk when tests validate implementation consistency rather than the intended real-world proposition. Read the assertions for semantic contradictions; do not treat “29 tests, all passing” as proof that the recovery claim itself is sound.
- Tasks 44 + 45 + 46: FAIL-OPEN BOUNDARY ARCHAEOLOGY has now transferred from strong-positive verification to a deliberate reject case. The same method that found explicit fail-closed behavior in Tasks 44/45 exposed self-attested green state in Task 46, strengthening confidence that it is useful for calibration rather than only finding positives.
- Task 47: missing economic authority must remain UNKNOWN rather than silently becoming zero/default. `freight-audit` turns an absent `approved_accessorials` field into an empty map and treats a positive invoice accessorial absent from parsed contract categories as a full-dollar WARN; with no rate confirmation at all, detention logic can still price a recovery at the default $75/hour even though the result is BLOCK. This is a domain-transfer confirmation of the authority-origin check from Task 46.
- Task 47: diagnostic findings are not necessarily additive economic claims. The engine sums all `money_impact_cents`, so a single $125 unauthorized liftgate can also be counted as the same $125 total mismatch, yielding $250 aggregate impact for a $125 invoice delta. The billing tests encode the same overlap for linehaul. Before promotion, every asserted dollar needs a unique economic claim identity or an explicitly non-additive explanation hierarchy.
- Task 47: review status must be part of the aggregation invariant. API/web paths record usage by summing positive/negative findings before any human decision; the decision endpoint does not restate usage; the UI totals raw loads independently of review/decision state; and optional percentage-of-value billing consumes the pre-review aggregate. Therefore “potential,” “reviewed,” “confirmed,” and “recovered” values must be separate states, not labels over one shared sum.
- Tasks 46 + 47: AUTHORITY-ORIGIN / INVARIANT-SET CONSISTENCY now has two independent domain confirmations: self-attested verification state in recovery tooling and missing/ambiguous contractual authority plus review-state contamination in freight audit. The common test is to trace the provenance and admissibility of every fact/dollar that can enter an asserted outcome, then compare that accepted set across validation, aggregation and billing/reporting modules.
- Task 48: source-health semantics are an authority-origin problem. Sawfleet’s admin UI paints the latest upstream `job_runs.status === success` green, but the repository cannot independently establish source completeness/freshness and exposes no stale, partial/degraded, zero-row anomaly, schema-drift or expected-window semantics. A green upstream status is therefore not evidence that the intended permit universe was observed.
- Task 48: production-shaped downstream workflows must not be confused with a production-grade source plane. Sawfleet has a real permit marketplace, outreach, scheduling, named jurisdictions and run history, yet the actual scrapers/source contracts are external to the repository. The clearest source-boundary warning is explicit upstream placeholder contamination: a fabricated `permit-<number>@permit.local` contact can be injected to satisfy the external schema and must be stripped by the application before use.
- Task 48: a strong public-data ingestion comparator should version source identity, connector, admitted fields/mapping, cursor/window, freshness and legal/status metadata, preserve raw provenance, and separate production sources from candidates/holds. `ahdithanu/buildsignals` exposed those controls directly; this made the missing Sawfleet source contract measurable rather than merely an aesthetic criticism.
- Tasks 46 + 47 + 48: AUTHORITY-ORIGIN / INVARIANT-SET CONSISTENCY now has three cross-domain confirmations: self-attested recovery status, missing/ambiguous contract authority and externally asserted source-health state. In all three, the decisive question is whether the system independently establishes the fact that unlocks the asserted outcome and whether downstream modules use the same admissible evidence set.
- Task 49: regulatory calculator currentness must be verified at the input-semantics level, not inferred from recent commits or current-looking threshold tables. `RC2_SBA_Navigator.html` instructs users to supply a 3-year average receipt figure and describes a 12-month employee window, while current federal-contracting authority uses five completed fiscal years for receipts and 24 calendar months for employees; named SBA financial-assistance programs retain a separate 3-or-5-year election. A generic calculator that collapses these contexts can produce a categorical result from the wrong measurement period even if its NAICS dollar threshold is otherwise current.
- Task 49: repeated stale rule language across executable UI and adjacent explanatory content is stronger evidence of a systemic authority-version defect than a single typo. RC2's calculator labels, `calcSizeStd()` result text and separate NAICS article all repeat the 3-year/12-month model. Conversely, a disclaimer to “verify with SBA” does not make a deterministic yes/no output rule-current.
- Tasks 46 + 47 + 48 + 49: AUTHORITY-ORIGIN / INVARIANT-SET CONSISTENCY now has four cross-domain confirmations. Task 49 extends the pattern from data/status provenance to rule provenance: the fact authorizing a decision can be an effective-dated legal rule, and repository recency is not a substitute for tracing that rule to the correct authority and program context.

## Failed search patterns
- Task 44: a broad GitHub repository search for `postgres restore verification pg_amcheck scratch backup recovery verifier` returned no candidates. Product/category phrases were too weak; direct code/protocol signatures and obscure-repository comparisons were materially more productive.
- Task 45: broad phrases such as “offline evidence bundle signatures hashes” produced mixed supply-chain/attestation noise. The search became productive after switching to implementation signatures (`verify_bundle`, inclusion/consistency proof, signed export manifest, hostile/golden/fuzz fixtures) and then deliberately checking low-attention verifier repositories.
- Task 45: a strong specification without resolvable implementation/tests is insufficient for STRONG. `ArdurAI/ardur` had a promising offline-bundle contract, but implementation/test evidence was not established as deeply as the selected candidate during this run.
- Task 46: broad `recovery verifier` / `backup validation disaster recovery` searches produced substantial tutorial, infrastructure and documentation noise. A shorter repository query (`backup verifier`) plus immediate inspection of the green transition was more productive.
- Task 46: repository “quality gates” can be orthogonal to domain verification. `BackupAttest/scripts/verify.py` sounds relevant by filename but only checks SVG/README/style properties; filename/function-name search must be followed by body inspection before crediting verification depth.
- Task 47: a long product-style query combining `freight invoice audit accessorial detention surcharge` produced no useful repository hits, while the shorter category query `freight audit invoice` surfaced the relevant family. After discovery, architecture signatures (`approved_accessorials`, `_detention_rate`, `money_impact_cents`, `_usage_amounts`, `record_usage`, `bill_tenant`) were much higher signal than more product keywords.
- Task 47: “has review workflow” is not evidence that money totals are review-safe. The decisive evidence came from tracing write timing and aggregation code across API -> usage -> decisions -> billing/UI, not from the presence of a reviewer endpoint or review labels.
- Task 48: broad `permit property lead platform` searches surfaced many shallow websites, demos and README-only repositories. The productive switch was to code-level source-plane terms (`source health`, `job_runs`, source names, sync paths, manifests/registries) plus deliberate zero-star inspection.
- Task 48: a list of named jurisdictions in UI code is not source configuration. Searching Sawfleet’s source keys found display-name/icon mappings but no versioned connector endpoints, field maps or coverage contracts; do not award source-depth credit from presentation-layer enumeration.
- Task 49: broad repository searches for “SBA calculator” were sparse/noisy. Exact stale/currentness phrases such as `3-year average revenue`, `average annual receipts`, calculator field IDs/functions, and a direct first-party authority cross-check surfaced the useful candidate and defect faster.
- Task 49: recent repository maintenance, a current-looking NAICS table, and a “verify with SBA” disclaimer are weak proxies for regulatory currentness. The period rule must be checked against a dated first-party authority and the exact product context; otherwise a valid exception rule can be overgeneralized into the wrong federal-contracting result.

- Task 44: commit/test phrases around “fabricated skipped exit 0”, “fail open”, “bad bind-mount”, “remote DOCKER_HOST”, “permissions”, and “unverifiable latest” are useful anchors for evidence-verifier archaeology.
- Task 45: `evd/bundle/v1`, `verify_bundle`, `export_manifest`, `target_checkpoint_hash`, `receipt_hashes`, SET-EQUALITY, `checkpoint_chain`, `consistency_from_prev`, inclusion proof, `NOT VERIFIED`, completeness UNKNOWN, `--require-manifest`, golden fixtures, hostile corpus, fuzz corpus, differential/parity test, from-scratch second implementation.
- Task 45: cross-implementation disagreement that previously exposed a concrete cryptographic/spec bug (for example an RFC-6962 leaf-prefix mismatch) is unusually strong evidence that the second verifier is doing real independent work rather than merely wrapping the first.
- Task 46: `verified=yes`, `outcome=ok`, `last_ok`, `Report.clean`, exit 0, `_recoverable_points`, orphan exclusion, drill `backup_id`, opaque digest, “does not restore anything”, and “trusts the verified flag” are useful signatures for distinguishing metadata hygiene from actual recovery verification.
- Task 46: compare positive-set membership across modules: `build_chain`/admissibility vs RPO/coverage/settlement metrics. A record excluded as invalid in one module but counted as proof/value in another is a strong semantic bug candidate.
- Task 47: `approved_accessorials`, contract completeness, absent-vs-empty map, `_detention_rate`, default rate, `money_impact_cents`, `net_money_impact_cents`, `_usage_amounts`, `record_usage`, `overpayment_caught_cents`, `recoverable_revenue_cents`, `value_cents`, review/decision status, percentage-of-savings billing.
- Task 47: search for overlapping explanatory findings that refer to the same economic delta (`TOTAL_MISMATCH` + line/accessorial overcharge, aggregate variance + component variance). If the model has no claim identity/dedup layer, raw sum-of-findings is unsafe for asserted value.
- Task 48: `job_runs`, latest-by-source, `records_found`, `records_inserted`, `records_updated`, source health, stale success, 200-but-empty, partial/degraded/failed, expected window, freshness watermark/SLA, source registry, connector, field mapping, cursor, candidate/hold, schema drift, synthetic placeholder contact, `@permit.local`.
- Task 48: positive source-plane signatures include immutable raw record/version capture, explicit production-vs-candidate source state, source-specific field mapping, canary/retry logic that cannot write production data, and persisted run counts/errors/cursor/freshness.
- Task 49: `13 CFR 121.104(c)`, five completed fiscal years, 3-or-5-year election, Business Loan/Disaster Loan/Surety Bond/SBIC exception, 24 calendar months, `calcSizeStd`, `calc-revenue`, `3-year average revenue`, effective-dated rule pack, federal-contracting context.
- Task 49: useful adversarial pattern: choose a current candidate threshold and a five-year receipt sequence whose five-year average and latest-three-year average fall on opposite sides of that same threshold. This tests whether the period defect can actually flip the categorical decision rather than merely producing a documentation mismatch.

## Candidate search skills
- FAIL-OPEN BOUNDARY ARCHAEOLOGY (3 validated tasks: #44, #45, #46): after finding a verifier/auditor, search source tests and commit history for prior or current paths where missing evidence, ambiguous state, stale selection, stripped completeness material, infrastructure faults, or self-attested status can become skip/success. Require explicit negative behavior before STRONG. Task 46 demonstrates the skill also supports evidence-backed REJECT decisions. This method is already present in shared `SEARCH_SKILLS.md`; no benchmark-phase edit is needed.
- CONTRACT -> NEGATIVE-VECTOR -> DIFFERENTIAL-IMPLEMENTATION TRIANGULATION (1 validated task: #45): start from the normative artifact/interoperability contract, map each mandatory integrity/trust binding to implementation code, then locate hostile/golden/fuzz vectors and a genuinely separate implementation or differential test. Prefer candidates where the differential path has actually caught a bug. Await a second distinct benchmark confirmation before promotion.
- AUTHORITY-ORIGIN / INVARIANT-SET CONSISTENCY (4 validated tasks: #46, #47, #48, #49): for every input that can unlock PASS or asserted value/health/eligibility, identify who authored/authorizes it and whether the system independently establishes the correct authority; then compare the accepted evidence/rule set across validation, derived metrics, UI/reporting and billing/decision output. Self-attested status, missing-authority-as-zero/default, externally asserted health without coverage/freshness, cross-module set disagreement, or stale rule semantics under a current-looking UI blocks evidence-grade promotion. It exceeds the two-task evidence threshold for later shared-skill promotion; leave `SEARCH_SKILLS.md` unchanged during the frozen pair run.
- VALUE-STATE AGGREGATION AUDIT (1 validated task: #47): trace each dollar from source authority -> diagnostic finding -> unique economic claim -> adjudication status -> aggregate label -> billing. Test missing authority, overlapping findings, WARN/BLOCK rows and pre-decision write timing. Require POTENTIAL/REVIEWED/CONFIRMED/RECOVERED states to be distinct when the product language or pricing depends on them. Await a second distinct task before any shared-skill promotion.
- SOURCE-COVERAGE CONTRACT AUDIT (1 validated task: #48): for public-data lead/intelligence products, trace each advertised source from UI label back to a versioned connector/source contract. Require official source identity/endpoint, admitted fields or mapping revision, expected coverage/window, freshness watermark/SLA, explicit EMPTY/PARTIAL/DEGRADED/FAILED/STALE semantics, and negative tests for 200-but-empty/schema drift. If the downstream product only trusts an external `success` row, treat completeness as unverified. Await a second distinct benchmark confirmation before any shared-skill promotion.
- RULE-PERIOD / AUTHORITY-VERSION AUDIT (1 validated task: #49): for deterministic legal/regulatory/eligibility calculators, trace every measurement window, threshold type, exception branch and categorical output to a dated first-party authority. Explicitly test the general rule against named-program exceptions and construct a boundary case where stale-vs-current periods cross the same threshold. Recent commits and disclaimers do not establish substantive rule currentness. Await a second distinct benchmark confirmation before any shared-skill promotion.
