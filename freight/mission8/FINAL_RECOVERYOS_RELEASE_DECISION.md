# RETALLY RecoveryOS | Final consolidated release decision
**Snapshot: 2026-10-08. Decision: NO-GO for hosted customer financial processing.**

## Executive decision
RETALLY has demonstrably repaired **nonproduction** payment preparation, authorization and replay defects and now possesses one executable end-to-end **localhost** authenticated application-level acceptance suite. It has not proven the positive financial flow through Floot's hosted M8 staging HTTP gateway, authenticated real buyer/carrier/bank authority, actual recovered cash, refunds or contingency fee conservation. No paying-customer financial processing, production deployment or automatic carrier/payment action is authorized.

Production RecoveryOS `c719b60c-9b3b-4193-a543-0be9d3ceaef2` is published; isolated M8 staging `41bb5a26-a38a-4a93-ae8d-a07f9e11f77b` is unpublished. Their independently read PostgreSQL cluster identities differ: production `7693746749463444100` (Neon `wispy-frost-74208542`), M8 `7694301220230018932` (Neon `mute-scene-87269526`). Production had 0 payment instructions / 0 payment events at verification. M8 retained 11 synthetic instructions, 11 allocations, 0 authorizations, 0 events and 0 bank-verified cash rows.

**Nothing in this package merges a PR, deploys to production, changes a scheduled task, contacts a customer, sends a payment, or closes a historical finding.**

**Important application defects independently reproduced and corrected in unpublished code:**
- Missing authorization guard for certain new event-state transitions (Phase 5 helper regression, reachability through real API not established).
- Event read/check/insert race corrected with same-instruction DB transaction/row-lock pattern; verified at progressively higher but nonhosted levels.
- Duplicate economic capacity / wrong-currency source / altered idempotency terms originally accepted under the per-request calculation; candidate enforces certified entitlement/allocations and controls.
- Authorization read-before-insert race corrected via instruction-row lock; original duplicate-constraint result and repaired stable 100-call behavior independently exercised.
- **M11 critical application integration defect A:** double `JSON.stringify` of financial instruction body made PostgreSQL receive a JSON string; isolated authenticated handler test failed `invalid tenant scope`. Fixed by passing the structured object.
- **M11 critical application integration defect B:** expected snake_case response from `Kysely.CamelCasePlugin` returned camelCase; stored instruction could commit while handler returned `Financial allocation reconciliation failed`. Fixed with correct response field lookup; same frozen M11 suite now passes.

Both M11 defects were visible only when the real TypeScript handler, Kysely dialect, authentication and DB function ran together. This is why isolated SQL green checks cannot establish production readiness.

## One decision matrix
- **GO:** Continue fictional/synthetic financial engineering, read-only auditing of current nonproduction resources, code review, customer-facing *sample* demonstrations clearly labeled as samples, and ordinary nonfinancial website work whose claims are substantiated.
- **CONDITIONAL ONLY, not yet authorized here:** A purely offline/manual *real-customer* document review after independent verification of legal contracting identity, written customer scope/authority, confidentiality/data retention/security controls, encrypted access, licensed source rights and human sign-off. Do not claim this is already operationally accepted.
- **NO-GO:** Upload actual client financial data to unapproved RecoveryOS processing, call carrier/bank endpoints, automatically submit disputes or refunds, authorize payment or calculate collectible contingency fees from unverified credits, import old customer data into staging, or merge/deploy any research financial PR without independent release approval.

## Minimum remaining human-controlled acceptance gates (not another laboratory initiative)
1. **Hosted M8 access:** Obtain approved test-browser/identity provenance to use authentic M8 staging (without circumventing the `403` sandbox control), then run the existing M11 positive sequence against actual authenticated hosted `/_api` endpoints. Capture response IDs, persisted DB state, at least 100 same-key callbacks, conflicting references, cross-tenant and authorization boundaries. Until then hosted acceptance remains BLOCKED.
2. **Source parity + release:** Review PRs #306, #315, #318, #325, #331 in dependency order with independent code/security review; reconcile against production and the parallel Phase 4 research lane. Verify exact deployed code and database migrations in independently backed-up, segregated staging. Require a final hosted fail-closed security suite and explicit authorized release decision.
3. **External claim authority:** For each purported recovery, acquire customer authorization, authenticated invoice/carrier source, legally valid tariff/contract, independently evidenced bank/cash credit or remittance and a reconciled economic identity. `SETTLED` from mock provider is not cash. Keep all unsupported recovered amounts at zero.
4. **Ledger and contingency fees:** Prove exact-cent allocations and releases under partial payments, failures, reversed credits, refunds, currency changes (if any), and eligible, earned, collected and refunded fees, with reconciled customer balances. No automatic release after a reversal without an independently tested release process.
5. **Commercial/security pilot:** Verify business entity and trade-name authority, signed legal engagement/contingency terms, confidentiality/retention/access controls, bank/fee disclosures, manual dispute procedures, exception queue and operator training. Use a **human-approved, capped first pilot** only after the preceding applicable gates pass.
6. **Historical register:** Prioritize financial high-severity research findings, but keep all original 26 open until original-scope evidence warrants individually updating them.

Treat **all** of these as mandatory for hosted customer-financial go-live: exact reviewed/merged commit; externally independently authenticated financial provenance; hosted positive authenticated end-to-end parity; tenant isolation and replay stress tests; proven settlement/reversal/refund/fee ledger conservation; completed legal/customer security authority; explicit approved production release and postdeployment smoke. A generic repository release-gate green result does **not** override a blocked/failed hosted financial gate. Any FAIL/BLOCKED/UNVERIFIED is **NO-GO**.
