### Concrete capability
A staffing/placement operating and accounting system that connects effective-dated placement economics to approved time and then routes the same frozen economic authority into customer AR, vendor/AP and employee payroll. The rate authority is not a mutable 'current rate' lookup: approved placement-rate rows are versioned/effective-dated and the approved time entry stores `rate_snapshot_id`, which downstream money paths reuse.

### Evidence inspected beyond README
- `modules/placements/api/rates.php`: explicit effective-dated rate API; draft rows can be edited, approved rows return a conflict and require correction rather than mutation.
- `modules/placements/lib/rate_approve.php`: approval closes the previous approved row at `new effective_from - 1 day`, links supersession, stamps approval actor/time, adjusted bill rate/net-to-vendor and economics snapshot JSON, and audits the change.
- `modules/time/lib/time.php`: `timeResolveRateSnapshot(placementId, workDate)` selects the approved placement-rate row whose effective window contains the work date. Approved time carries `rate_snapshot_id`; downstream financial totals use the locked row and fail when an approved entry lacks a usable snapshot.
- `modules/time/lib/settlement_create.php`: approved/unextracted time can settle into billing/AP/payroll; customer billing uses adjusted bill rate/bill rate, AP uses pay rate, and created money records retain time-entry/rate-snapshot lineage with idempotency/transaction locking.
- `tests/time_settlement_smoke.php`: checks approved-only extraction, missing-snapshot refusal, FOR UPDATE/transaction/idempotent behavior, AR creation with per-day lines + `rate_snapshot_id`, AP creation, and payroll grouping/period mapping; UI copy also explicitly says the create action makes drafts rather than silently sending/posting/paying them.

- `tests/gusto_integration_smoke.php`: static/pure runtime integration checks cover HMAC verification, OAuth state replay protection, submit guardrails, employee matching, calculate/submit sequence, optimistic locking, paid-event handling and audit wiring. ### Rare / undernoticed value

### Buyer / painful problem
Staffing, labour-hire, consulting and contractor-placement firms where rate changes, retro corrections, approved hours, customer billing, worker/vendor pay and external accounting/payroll systems can diverge. Finance/controller teams lose margin when historical rate authority is overwritten, approved hours never reach one side of the ledger, or provider 'success' is treated as final without readback.

### First paid wedge
**Contract Labor Margin Close Audit**: for one closed month, ingest placements/rate history, approved time, customer invoices/payments, AP/payroll output and provider readback; recompute expected bill/pay from event-time authority and return a dollar-ranked exception ledger for historical-rate drift, approved-but-unbilled/unpaid work, invoice/payment mismatches, payroll mismatches, partial/unallocated cash and stale provider states.

### Monetization
Fixed-price diagnostic -> managed monthly close assurance -> recurring SaaS/embedded reconciliation. Value can be priced against recovered margin/leakage, faster close and reduced manual reconciliation.

### Build/domain advantage
Likely saves many months of design and implementation around effective-dated placement economics, time-to-money lineage, AR/AP/payroll settlement routing, external-provider idempotency, two-eye payroll controls and money-state audit semantics.

### Red-team / strongest objection
Provider `PAID` is **not yet reversal-safe finality**. `api/gusto_webhook.php` maps `Payroll.reversed` to `gusto_submission_status='reversed'`, but only the `paid` branch changes the canonical payroll-run status/`paid_at`; the reversal branch does not revert or otherwise invalidate the internal paid state. Likewise, QBO `CAPTURED`/`SETTLED` application is strong provider evidence but I did not verify an equivalent refund/chargeback reversal path that unwinds AR allocation. Therefore this repo proves strong temporal authority and downstream readback plumbing, but not fully settled, later-reversal-safe finality.

A second caveat: legacy approved time with a missing snapshot can be repaired by resolving the current effective-dated history for the work date. That is useful recovery behavior but should not be mistaken for original event-time provenance in an audit if rate history itself has since been corrected.

`field completion/evidence + approved work + event-time bill/pay authority + AR/AP/payroll derivation + external provider/payment readback + reversal-safe finality`

The prior `cbd-portal` finding supplies unusually good domain logic for when employee pay hours and client charge hours differ. CoreFlux supplies the missing event-time frozen rate authority and routes that authority into both sides of the books. Together they materially strengthen the existing Job-to-Gross-Margin Leakage thesis into a cross-vertical **Work-to-Gross-Margin Close Assurance** product for staffing, construction labour, field service and other labor-heavy verticals.

## Claims tested / falsified
- **Verified:** effective-dated client/worker rate records are not enough; the stronger pattern is to pin the approved work event to an approved rate version/snapshot and propagate that lineage downstream.
- **Verified:** CoreFlux implements this snapshot lineage into AR/AP/payroll and external QBO/Gusto identities rather than merely documenting it.
- **Falsified:** provider `paid` can be treated as terminal truth. CoreFlux's own Gusto path exposes the counterexample: a later `Payroll.reversed` changes the provider-status field but does not undo the canonical internal `paid` state/`paid_at`.
- **Falsified:** a rate-card table plus an invoice module implies authority-preserving billing. RCS_HRMS has effective-dated rate cards but the inspected invoice backend accepts line economics from POST without proved server-side rate authority lineage.

## Emerging technology signal
**Authority-aware margin close / proof-carrying economics** is strengthening. Independent systems increasingly model event-time economic authority, downstream money-state lineage and external provider state separately. The valuable architecture is not 'ERP automation'; it is a deterministic chain from approved operational fact to expected economics to receivable/payable/payroll to externally observed settlement, with the ability to invalidate success later.

## Negative knowledge / failure memory
1. Mutable/current-only `bill_rate` + `pay_rate` on a placement/engagement is insufficient for retrospective assurance.
2. Effective-dated rate cards are still insufficient unless the actual approved event/downstream money records preserve which version governed them.
3. A provider webhook `paid` state is not terminal if reversal/refund/chargeback events do not reopen or offset internal money state.
4. Static integration/smoke assertions are useful structural evidence but are not equivalent to live provider integration or external CI.
5. Staffing repos named ATS/interview/payroll often stop at CRUD or calculators; prioritize signatures around `rate_snapshot_id`, supersession/effective dates, immutable approval, AR allocation, provider IDs and reversal events.
