### Concrete capability verified

This repository implements a rare combination of money-state safety properties that directly closes part of Run 12's CoreFlux gap:

1. **Lost-webhook recovery uses independent provider inquiry, not the internal paid flag.** A scheduled reconciler selects stale `Pending` attempts, asks Paymob by the stored special reference, stores the returned provider transaction, and routes it through the same transaction processor/ledger path as webhooks.
2. **Unknown provider outcomes fail open-to-retry, not closed-to-false-failure.** Network errors, 5xx responses and repeated auth failures leave the attempt `Pending`; only an answered inquiry that finds no transaction can expire an already-expired checkout.
3. **Refund initiation is one-shot under ambiguity.** `request_refund` writes a durable `refund_requested_at` marker before the outbound call. The low-level refund client explicitly says never retry because a lost response may still mean Paymob processed the refund. A second refund inside the confirmation window is refused.
4. **The outbound refund request is not ledger authority.** The signed Paymob callback or an independently fetched signed child refund transaction is what can create the accounting reversal.
5. **Refund posting creates a real ERPNext Payment Entry.** `ledger.post_refund` creates a submitted money-out Payment Entry linked back to the Payment Request and checks the posted amount against the verified provider refund delta.
6. **Cumulative refund resends do not silently create money.** A parent resend carrying only cumulative refund information triggers Transaction Inquiry for the actual child refund. If the child cannot be proven, or if its signed delta does not reconcile to Paymob's cumulative total, the system posts no reversal and creates a human-review audit item.
7. **Partial refunds accumulate through explicit states.** Legal state transitions are `Paid -> Partially Refunded -> Refunded`; impossible transitions are refused.
8. **Duplicate/replay safety is implemented at several boundaries.** Stored transactions are idempotent on `processed`; the reconciliation path reuses a previously stored-but-unprocessed transaction; duplicate successful charges against one Payment Request are serialized by a row lock and audited as a refund-owed condition rather than posting another internal receipt.

### Why unusual

Most gateway integrations collapse at least one of these distinctions: request sent vs provider confirmed; webhook missing vs payment failed; cumulative refund amount vs signed refund delta; payment recorded vs money reversed; replay vs second genuine charge. This implementation makes those distinctions executable and test-backed.

### Strongest objection / red team

This is a **payment integrity component, not a complete vertical ERP**, and it does not solve event-time staffing bill/pay authority by itself. It also does not prove post-refund bank settlement or a later external reversal of an already-confirmed refund. The `Refunded` state is terminal in this component. Therefore it closes the PSP/refund side of the Run 12 gap but not the entire `event-time authority -> AR/AP/payroll -> final bank/payroll settlement -> later return` chain.

### Buyer / painful problem / paid wedge

- Buyer: staffing/labour-hire, contractor, field-service or B2B operators using ERPNext or a similar money-state architecture.
- Pain: internal invoices/payments can look paid while the PSP callback was lost, a refund response was ambiguous, a duplicate charge occurred, or a refund was reported without enough evidence to safely reverse the ledger.
- First paid wedge: **Payment Finality & Refund Integrity Audit** — reconcile ERP payment state against PSP inquiry/webhook/refund evidence and surface `paid-but-unconfirmed`, `confirmed-but-unposted`, duplicate-charge, refund-pending, refund-proof-gap and refund-ledger mismatch exceptions.
- Money path: prevent duplicate refunds/payments, prevent false paid state, surface money-out reversals correctly, reduce manual reconciliation and close risk.

### Combination

**CoreFlux event-time bill/pay authority + paymob_integration provider inquiry/refund truth + alyf-de/banking bank statement truth + Summae close oracle** creates a stronger Work-to-Gross-Margin Close Assurance chain:

`approved work -> pinned rate authority -> expected AR/payroll/AP -> PSP confirmed receipt/refund -> bank statement realization -> independent close/replay -> exception / reopen / offset`.

## CLAIMS TESTED

### Hypothesis: provider timeout can safely be treated as failure
**FALSIFIED.** Paymob integration tests and source explicitly preserve `Pending` on network/5xx ambiguity; only an answered negative inquiry may expire an attempt. This strengthens CAP-018's `UNKNOWN != FAILED` requirement.

### Hypothesis: sending a refund request is enough to reverse internal accounting
**FALSIFIED.** The stronger pattern is request marker -> provider callback/inquiry -> verified refund delta -> accounting reversal. Both Paymob and Paystack evidence support this separation.

### Hypothesis: a cumulative provider refund field is sufficient authority for the refund amount
**FALSIFIED.** Paymob's implementation treats the cumulative total as an alert/reconciliation signal and requires the signed child refund delta before posting. A disagreement is held for human review with no money movement.

### Hypothesis: one integration now solves the full Run 12 question
**NOT YET.** Paymob materially solves the AR/PSP ambiguity and refund side, but it does not preserve staffing bill/pay authority and does not automatically undo a later reversal of an already-confirmed refund/payroll success. CoreFlux + Paymob + bank evidence is a stack, not yet one end-to-end system.
