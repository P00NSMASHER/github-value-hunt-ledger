### What it actually is
A WhatsApp-first financial operating system for Nigerian small businesses with invoices, receipts, customers/suppliers, stock, double-entry ledger, financial statements, provider payments/settlements, bank reconciliation, audit history and correction-by-counter-posting. README explicitly labels it pre-launch and says no live provider has yet been exercised, so production-provider behavior remains unproven.

### Verified capability
The important capability is **late external counter-event -> immutable reversal evidence -> receivable reopen -> correct post-settlement liability/recovery accounting**.

`apps/api/src/commands/payment-adjustment-commands.ts` implements three distinct money-back events: refund, payment reversal and chargeback. It does not mutate the original payment allocation. `unwindAllocations` reverses each affected allocation in full; when only part is being clawed back it creates a fresh retained allocation for the still-valid remainder. It then rebuilds invoice projections from the subledger and returns the exact invoice IDs reopened. Conflicting cases such as overpaid payments, refund-plus-chargeback ambiguity, or amounts exceeding standing allocations are refused rather than guessed.

The provider event path is tested against real PostgreSQL, not only mocks at a pure-domain layer. `adjustments.integration.test.ts` stores provider event payloads, runs attribution/pump/jobs, and then asserts invoice state, payment lifecycle, standing allocations, ledger totals, settlement rows and reconciliation exceptions.

Concrete tested semantics include:
- successful payment -> invoice `paid`, balance due zero, one standing allocation;
- pre-settlement refund -> invoice reopened and provider clearing reversed;
- post-settlement refund -> invoice reopened while prior settlement evidence remains, with the refund hitting bank rather than retroactively rewriting settlement;
- partial refund -> invoice becomes partially paid, original allocation is fully reversed, and the retained remainder is a new positive allocation;
- a provider-side reversal after settlement is **not** silently treated as the pre-settlement reversal type; it is routed to reconciliation because that economic situation needs a refund/chargeback treatment instead;
- open dispute moves no money and creates an exception;
- lost dispute before settlement -> chargeback through provider clearing, customer owes again;
- lost dispute **after settlement** -> customer invoice reopens, AR is restored, and the merchant gets a `PROVIDER_CHARGEBACK_PAYABLE` liability rather than a fake second receivable or a rewritten settlement;
- duplicate lost-dispute notifications create one chargeback row and one posting.

`packages/db/src/repos/chargebacks.ts` derives PRE-vs-POST settlement from the accounting/settlement model, not from caller assertion. Post-settlement chargeback posts `DR Accounts Receivable / CR Provider Chargeback Payable`; direct bank-debit recovery instead credits bank; missing required provider accounts fail before writing a chargeback fact.

The settlement tests go one step further: a later provider settlement can contain a `CHARGEBACK` deduction that clears the open chargeback payable, while an explicit bank-debit variant needs no payable. Chargeback records are treated as immutable history. This is very close to the counter-event/finality state machine needed by CAP-016/CAP-018.

### Test / CI evidence
The exact inspected revision has successful GitHub Actions checks including PostgreSQL integration, Playwright E2E and Docker deployment checks. The integration suites explicitly exercise provider payment, refund, reversal, dispute, chargeback, settlement, allocation and ledger behavior.

### Strongest objection
The project is **pre-launch** and its README states no live provider has been exercised. Some provider-reversal reachability is explicitly synthetic: the test suite itself documents that Paystack may not emit a direct post-settlement reversal event in the tested shape, and routes such a state to human reconciliation when it occurs after settlement. Therefore the accounting/state-machine implementation is strongly verified, but production event-shape/provider coverage is not.

### Commercial interpretation
Do not sell Rekoda itself as the thesis. The valuable reusable capability is a **reversal-safe receivable and settlement control plane**.

First paid wedge: extend Money-State / Work-to-Gross-Margin Close Assurance so a closed-period audit can prove:
`payment apparently succeeded -> settlement occurred -> later refund/chargeback/return -> invoice/AR reopened -> provider liability/bank deduction posted -> later settlement deduction clears liability`.

This plugs the exact AR-side gap exposed by CoreFlux, where a later payroll/provider reversal could leave canonical success unchanged.

### Capability delta
A later externally observed counter-event can now be modeled as an immutable financial fact that invalidates prior finality, reopens only the affected economic allocation, and preserves the original payment/settlement history.

### Graph edge
Strongly strengthens **CAP-016 Money-State Integrity** and **CAP-018 Provider-to-Bank Settlement Ambiguity**, and directly supplies new fault cases for **EXP-010**.

### Radar signal
Independent support for **RAD-006 Authority-Aware Money Assurance**. The pattern is no longer only `expected vs actual`; it includes explicit *revocation of previously valid actual state* without rewriting history.

### Experiment impact
EXP-010 should include:
- paid -> post-settlement lost dispute -> invoice reopen + provider payable;
- later settlement deduction -> payable cleared;
- direct bank-debit chargeback variant;
- partial refund -> allocation reversal + retained fresh allocation;
- duplicate dispute/reversal notification;
- unsupported mixed refund + chargeback -> REVIEW/no double posting.

### Negative knowledge
`provider_status = reversed` is not enough. Correct accounting depends on **when settlement occurred**, what portion of the original allocation remains authoritative, and whether the provider later recovers through a settlement deduction or direct bank debit.

### meteroid-oss/meteroid
- URL: https://github.com/meteroid-oss/meteroid
- Exact revision: `c72f3f05715a122c70e14b51e42fecd111b57e87`
- Date inspected: 2026-09-20
- Status: **strong comparator / component**
- Score: **27/30** — A4 / B5 / C5 / D4 / E5 / F4
- Public license: AGPL-3.0.

#### Verified value
Meteroid independently implements the same late-finality principle in a mature subscription billing/payment engine. `reverse_transaction_tx` explicitly applies a post-settlement reversal and reopens its invoice under row lock. Full GoCardless-style chargebacks / late failures, Stripe cumulative refunds, dispute-withdrawal deltas and reinstatement are modeled separately. Bare failure events cannot claw back an already-settled payment; a settled transaction can leave success only through amount-bearing reversal logic.

The integration suite proves:
- settle -> full chargeback -> transaction `Refunded`, invoice fully unpaid, full amount due restored;
- duplicate chargeback is idempotent;
- partial refund leaves the transaction settled but invoice partially paid for exactly the refunded amount;
- the reopened partial balance is actually collectible by a new payment;
- dispute funds withdrawn reopen only the disputed amount;
- dispute funds reinstated re-close the invoice;
- chargeback cancellation restores the settlement and re-closes the invoice;
- redelivery after reversal/reinstatement is a no-op.

This is excellent independent validation that **success must be revocable and re-collectable**. It is less rare than Rekoda (~1.2k stars), so its primary value here is as a mature comparator/oracle rather than hidden vertical gold.

#### Strongest objection
It is horizontal billing infrastructure rather than the target obscure vertical ERP. It also does not by itself supply staffing/labour event-time bill/pay authority.

#### Verified value
This is a low-attention Rust commerce engine with order/payment/refund/AP money guards. Regression tests document and fix a subtle chargeback bug: putting a completed payment into `Disputed` previously released its share of the order total and allowed a second full capture; resolving the dispute back to `Completed` could then leave the order double-captured. The current implementation treats disputed money as still consuming capture capacity until the dispute actually resolves. Tests also cover cancelled-order payment refusal, payment/order currency identity, full/partial refunds, and concurrent duplicate idempotency keys. The changelog further documents real AP payment runs with status-guarded transitions and allocations.

#### Strongest objection
The inspected evidence is strongest around **contested-money capture capacity**, not the full late-loss -> independent settlement/bank observation -> receivable reopen chain proven in Rekoda/Meteroid. Keep as a useful commerce invariant source, not the new leader.

## CLAIMS TESTED

### 1. “A later chargeback can safely reopen an invoice without deleting the original payment.”
**Verified.** Rekoda reverses allocations with explicit counter-rows, rebuilds invoice projection, and retains original payment/receipt/settlement history. Meteroid independently proves the same economic behavior with transaction amount-refunded state plus invoice recomputation.

### 2. “Post-settlement chargeback is the same accounting event as pre-settlement reversal.”
**Falsified.** Rekoda explicitly distinguishes them. Before settlement, provider clearing reverses. After settlement, the customer receivable reopens **and** the merchant owes the provider via a liability unless the provider directly debited bank.

### 3. “A dispute should immediately release capture capacity.”
**Falsified.** StateSet regression tests demonstrate the double-capture bug that results. Contested money remains economically live until the dispute is resolved.

### 4. “The prior run's AR-side finality gap is still unsolved.”
**Mostly falsified.** Rekoda and Meteroid now provide strong independent implementations of late payment counter-events that reopen/offset AR and can later restore/re-close state. The remaining unsolved part is payroll/AP finality tied to event-time labor authority.

## EMERGING TECHNOLOGY SIGNALS

### Revocable finality / counter-event accounting
A stronger reusable pattern is now visible across independent systems:

`authoritative obligation -> payment claim -> provider success -> settlement -> later counter-event -> reopened/offset obligation -> recovery/reinstatement -> re-close`

The important capability is not refund support. It is **revocable finality with historical continuity**: the system can say “this payment really was valid at T1, then became economically invalid at T2” without rewriting T1.

This strengthens RAD-006 and CAP-016/CAP-018 materially.

## FAILURES / NEGATIVE KNOWLEDGE

- Generic `refund()` / `chargeback` fields are not sufficient. Require proof that an already-paid invoice or payable is recomputed/reopened from authoritative allocations.
- A bare `failed` event after settlement is unsafe as a clawback authority; mature implementations require an amount-bearing reversal/counter-event.
- Disputed money should not automatically free original capture capacity while the outcome remains unresolved.
- The timing plane matters: pre-settlement reversal, post-settlement refund, post-settlement chargeback payable, direct bank debit and later settlement deduction are economically different events.
- Provider status alone is not independent cash truth; the next stack still needs bank/statement/settlement observation when material.
- Rekoda is pre-launch. Its source/test quality is strong, but no live provider behavior should be promoted as production-proven until staging/live authorized evidence exists.
