### What it actually implements
EruoFood is a marketplace/food operating system with an unusually strong merchant-payable and settlement subsystem. The key capability is not generic payments; it is a historically reconstructable payable that can survive later provider ambiguity and reversal.

**Event-time economic authority / immutable earning:**
- `payments_payable_accruals` is append-only in PostgreSQL. Earnings and refund adjustments are separate row types; UPDATE/DELETE are blocked by a trigger and corrections require compensating accruals.
- One earning per order and one refund adjustment per refund are protected by partial unique indexes, so duplicate delivery/webhooks cannot create money twice.
- Money uses signed integer minor units with a DB invariant `net = gross - commission - fee` and sign constraints.
- `commission_rate_bps` is persisted on the accrual specifically so a later commission change cannot retroactively alter what the merchant was owed.
- More strongly, `PayableAccrualService` does **not** recompute commission from current configuration when an order completes. It reconstructs gross/commission/fee from the immutable capture ledger posting written when the money arrived, then derives the effective basis-point rate from those historical amounts. If the authoritative capture posting is missing, nothing is accrued.

**Payable authority is not caller-supplied:**
- `SettledOrder` carries identifiers, not amounts.
- `recordSettledOrder()` finds the captured payment, reads the capture ledger, constructs the append-only accrual, and optionally moves escrow -> merchant payable in the same transaction.
- A refund creates a distinct negative `refund_adjustment` and compensating payable/escrow posting rather than editing history.

**Settlement state machine / UNKNOWN handling:**
- `SettlementRunService::computeDraft()` derives a run from unsettled accruals; the caller cannot provide the payout amount.
- Accruals are reserved when a draft is built so concurrent settlement drafts cannot both consume the same orders.
- Approval and execution are separate acts; tests enforce a four-eyes rule.
- Before calling a bank/provider, the system commits a durable payout-attempt row. A process death during the transfer therefore leaves an identity that reconciliation can query later.
- `GatewayOutcome::Processing` and `Unknown` leave the run unfinished and keep accruals reserved because the money may already have moved.
- An `Unknown` run may **not** be retried. The state machine permits only reconciliation; it cannot transition directly back to Pending/Processing/Succeeded.
- Later provider inquiry can resolve UNKNOWN to Succeeded, or to Failed. Only a provider-confirmed Failed outcome releases the lines and makes the merchant payable again; an unresolved inquiry becomes a terminal `ReconciliationRequired` human case.

**Reversal / re-open without history rewrite:**
- A completed settlement can be reversed only by a compensating ledger posting. The original settlement posting remains untouched.
- Reversal releases the settlement lines, making the underlying append-only accruals available to a later settlement run again.
- Because those accruals contain the original capture economics and commission-rate snapshot, a later re-settlement derives from the original event-time authority rather than today's commission configuration.
- Tests verify the original posting remains, a second compensating posting is added under the same settlement reference, and the ledger remains balanced.

### Red-team / strongest objection
This does **not fully solve** the previous question. The late reversal in the inspected settlement path is exposed as an explicit application action (`reverse(actor, runId, reason)`); I did not find source evidence that an independently observed post-success bank return/webhook automatically invokes that reversal. Provider inquiry is strong for resolving an initially UNKNOWN payout, but a payment that was genuinely confirmed Succeeded and only later returned still requires the counter-event to reach the application through a separate integration/manual path.

That distinction matters: EruoFood already has the correct *internal* authority-preserving re-open primitive, but it has not yet proven the final external observation edge demanded by CAP-018 / EXP-010.

### Commercial implication

`completed economic event -> historical earning/rate authority -> payable -> approved payout -> provider outcome -> later counter-event -> compensating ledger -> reopened payable -> re-payment under original authority`.

## CLAIMS TESTED

1. **A past payable can preserve its original economic authority instead of re-reading current configuration — SUPPORTED.** EruoFood reconstructs the earning from the immutable capture ledger and stores the effective commission rate on the append-only accrual.
2. **UNKNOWN provider outcome can be prevented from becoming a duplicate payout — SUPPORTED.** Unknown is non-retryable; provider inquiry must resolve it or it becomes a human reconciliation case.
3. **A completed settlement can be reopened without erasing historical success — SUPPORTED.** Reversal is compensating and releases the original accrual lines.
4. **The same system automatically observes a late external bank/provider return after prior confirmed success and triggers the reopen — NOT PROVEN.** This remains the missing edge.
5. **A returned payout necessarily means platform cash returned — FALSIFIED across independent implementations.** Layr-Labs, like CocoScout previously, distinguishes a connected-account bank payout failure from a Stripe transfer reversal; the economic payable and physical cash location are separate facts.
