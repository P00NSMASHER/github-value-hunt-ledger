# Hunt 01 run 18 — post-terminal payout readback / revocable-finality gap

Date: 2026-09-20
Lane: Vertical ERP Gold / authority-aware money assurance
Status: **NO NEW MASTER CANDIDATE; strong component + negative knowledge**

## Highest-value question
Can an independent provider/bank readback detect a late return after a payout is already terminal/PAID, even when the reversal webhook is permanently lost, correlate it to the exact prior payout, and reopen the original entitlement without current-rate drift or duplicate repayment?

## Discovery methods
1. Direct code-signature search: `payout.reversed`, `payout.failed`, `reconcile`, `retrieve`, terminal `PAID/COMPLETED` states.
2. Scheduled reconciliation / cron archaeology: looked for pollers that intentionally query already-successful payouts rather than only pending/processing ones.
3. Vertical analog search: music creator payouts, travel-driver payouts, cleaner/gig-worker payouts, publishing/creator marketplaces.
4. Adversarial transition comparison: compare state written by success handler with states accepted by late failure/reversal handler.

## BEST NEW FIND — phyzikaldaking/epic-music-space
Pinned revision: `8cf5e9750cfdbe61587fbcf429508d6e1a0ad6f3`
Disposition: **STRONG COMPONENT / WATCH, 25/30**

### What is implemented
`apps/web/src/app/api/cron/payout-reconcile/route.ts` is a real scheduled reconciliation backstop, not a webhook-only design. It explicitly documents the case where Stripe's `transfer.reversed` webhook is permanently lost and the local `Payout` row remains `PAID`. The cron:
- scans recent `PAID` Stripe payouts with a stored `stripeTransferId`;
- retrieves each exact Stripe transfer independently;
- detects `transfer.reversed` / fully reversed amount;
- changes the local payout from `PAID` to `FAILED` and pages ops;
- separately repairs stale PENDING rows by asking Stripe truth or by re-queueing with a stable idempotency key.

This is the first Node 01 implementation found in this sequence that deliberately polls an already-successful payout state to detect provider drift after the webhook boundary. The lookback is bounded to 72 hours, so it is not indefinite finality observation.

The normal Stripe webhook path independently handles `transfer.reversed`, matches by exact `stripeTransferId`, creates a `PayoutFailure`, and marks the payout failed. The transfer worker uses idempotent Stripe transfer creation and refuses to send a second time while the payout is still `PAID`.

Exact-head commit status reports successful Railway deployment statuses for the inspected revision. This is deployment evidence, not test-suite proof of the reconciliation invariant.

### Red-team result / why not MASTER
The semantics are narrower than the prior Familiarise target. In Epic Music Space, `transfer.reversed` is documented as a platform clawback from the artist, commonly due to a refund/dispute. The webhook mirrors that clawback into the revenue ledger as debit splits that net against a future payout. In that case the artist entitlement should *not* simply be reopened and repaid.

More importantly, the scheduled PAID-drift path only flips the payout to `FAILED`; it does not create the same `PayoutFailure` artifact or prove a deterministic entitlement-reopen/repayment path. The payout source rows (`RevenueSplit`) are marked `PAID` on the original payout and the inspected reconciliation code does not reset them. Therefore this repository proves **post-terminal independent observation**, not the full **same-original-earning reopen** invariant.

A second caveat: the current drift sweep observes only 72 hours of recent PAID payouts. A reversal arriving outside that window can still be missed if its webhook is permanently lost.

### Commercial value
Useful donor for CAP-018 / EXP-010: add a post-terminal readback observer to Payout Close Assurance so a provider cannot remain contradicted by a stale local `PAID` state merely because a webhook vanished.

## STRONG NEGATIVE ORACLE — jedreekPrograms/dofast
Pinned revision: `284bc515c71477d890bb67ce49b7bb8c049694d4`
Disposition: **technically strong vertical payout system, but fails the target late-transition invariant**

Dofast is a low-attention gig-worker/task marketplace (3 stars, 0 forks, no public license metadata at inspection) with unusually careful payout provenance, wallet reservation/restore semantics, provider event identity, row locking, Stripe Connect validation, and settlement reconciliation.

Its provider settlement service correctly restores the exact reserved wallet amount when a SUBMITTED payout receives a definitive provider failure. However, the transition guard is explicit: it accepts SUBMITTED→PAID or SUBMITTED→FAILED, and treats same-terminal duplicates as idempotent; a PAID→FAILED provider event is rejected as a conflict. The Stripe-specific preflight has the same rule.

This is valuable negative knowledge because the architecture looks sophisticated enough to create false confidence. It proves that provider event IDs, row locks, idempotency, exact transfer identity, and reserve/restore accounting are **not sufficient** for revocable finality if terminal-state transition policy forbids a later counter-event.

### New automated red-team rule
For any payout candidate, compare:
1. the state written by the success path; and
2. the states accepted by every later failure/reversal/reconciliation path.

If success writes `PAID/COMPLETED` but the counter-event path accepts only `SUBMITTED/PROCESSING/PENDING`, classify it as **terminal-finality blind** regardless of how good its idempotency or ledger code looks.

## CLAIMS TESTED

### Claim: independent polling can detect a payout contradiction after local PAID
**SUPPORTED, bounded.** Epic Music Space intentionally scans recent PAID payouts, retrieves exact Stripe transfer state and corrects local PAID→FAILED after a lost reversal webhook. The observation window is 72 hours.

### Claim: sophisticated provider settlement code necessarily supports late terminal reversal
**FALSIFIED.** Dofast has exact provider identities, settlement events, wallet reserve/restore and strong validation, yet explicitly refuses PAID→FAILED as a contradictory provider event.

### Claim: post-terminal detection automatically restores the original economic entitlement
**FALSIFIED.** Epic Music Space's drift observer changes payout status but does not prove that original paid RevenueSplit rows are reopened. Its normal reversal semantics can represent a buyer-side clawback rather than a failed worker/artist bank payout.

## EMERGING TECHNOLOGY SIGNAL
The stronger pattern is now **redundant financial observation**, not merely webhook handling:

`economic authority -> obligation -> payout effect -> local terminal state -> independent provider readback -> counter-event classification -> compensating/reopen semantics -> re-close`

The remaining scarce primitive is the conjunction of **post-terminal independent readback** and **authority-preserving obligation reopen**. We now have each half in different repositories (Familiarise for historical earning + reopen; Epic Music Space for terminal-state polling) but not one verified end-to-end implementation.

## FAILURE / NEGATIVE KNOWLEDGE
1. Polling only PENDING/PROCESSING is not independent finality; it is delivery repair.
2. Exact provider IDs + webhook dedupe + row locks do not help if the state machine forbids PAID→FAILED/REVERSED.
3. A `transfer.reversed` event must be economically classified before reopening entitlement; it may mean buyer refund/clawback, not failed worker receipt.
4. Bounded terminal sweeps create a new blind spot after the lookback horizon.
5. Flipping a terminal status to FAILED is insufficient unless the exact economic source rows are reopened/offset in a provable way.

## CROSS-LANE REFERRAL
Money-State / Payment Integrity should combine Familiarise's event-time earning authority and `COMPLETED -> REVERSED -> READY` reopen with Epic Music Space's independent post-PAID provider readback. EXP-010 should include two distinct reversal reasons: (a) bank/provider return where worker/provider remains owed; (b) upstream refund/dispute clawback where worker/provider entitlement should decrease. The observer must not apply the same accounting treatment to both.
