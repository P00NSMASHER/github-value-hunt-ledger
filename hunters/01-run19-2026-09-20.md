### Concrete capability
A read-only Stripe Connect reconciliation/monitoring engine that queries connected-account provider truth independently of the host application's payout state. Its `reconcile()` path reads balances and **lists payouts for every supplied connected account on every run** over a configurable time window. Payout retrieval is direct from Stripe with the `Stripe-Account` header and pagination; it is not conditioned on whether the host application thinks a payout is pending, paid, completed, failed or otherwise terminal.

The engine separately supports an `EVENT_GAP` detector when the host supplies its processed event IDs. This can flag a Stripe `payout.failed` event that exists at the provider but never entered the application's event history. The default reconciliation window is 30 days; payout lookback can be explicitly configured. Stripe event-gap visibility is naturally bounded by Stripe's event-retention window.

### What was actually verified beyond README
- `src/reconcile.ts`: payouts are fetched unconditionally for configured connected accounts; refunds/events are optional only where application state is needed for comparison.
- `src/stripe/stripeDataSource.ts`: direct `stripe.payouts.list(...)` calls per connected account, created-range filter, Stripe-Account header, pagination and bounded concurrency.
- `test/stripe/stripeDataSource.test.ts`: verifies per-account payout listing and mapping of a provider `failed` payout.
- `test/core/detectFailedPayouts.test.ts`: verifies failed payouts become critical findings, canceled payouts warnings, and paid payouts do not produce false positives.
- `test/core/detectEventGaps.test.ts`: verifies an unprocessed `payout.failed` becomes a critical `EVENT_GAP` when application processed-event state is supplied.
- Repository tree contains broader tests for reconciliation, monitoring, state stores, Stripe mappers/data source, synthetic fixtures and webhook handling.
- The inspected commit had no GitHub commit-status checks attached; tests were inspected in source but were not independently executed in this run.

### Why unusual
Most payout "reconciliation" code inspected in this lane only revisits local nonterminal rows such as `processing`, `submitted`, `pending` or `in_transit`. This project instead treats provider payout history as an independent observation plane. That makes it capable of surfacing a provider-side failed payout even when the vertical application has stopped polling because its own row is already terminal.

### Buyer / painful problem / first paid wedge
- Buyer: staffing/contractor marketplaces, creator platforms, ticketing/event platforms, home-service marketplaces and other Stripe Connect operators.
- Painful problem: an internally `PAID`/`COMPLETED` payout can be contradicted later by provider reality, or the provider can emit a financially important event the application never processed.
- First paid wedge: **Payout Finality Sentinel** — import the operator's locally completed payout IDs/provider references, independently read provider payout/event truth, and produce a dollar-ranked list of terminal-state contradictions and event gaps before duplicate repayment, stale liabilities or vendor complaints occur.
- Time to first revenue: short if offered as a read-only audit/monitor against an existing Stripe Connect deployment; no money-moving permission is needed.
- Build compression: useful provider-readback, paging, connected-account handling, issue classification, stateful alert deduplication and synthetic/test scaffolding are already present.
- Moat: not the Stripe API calls themselves; the defensibility would come from joining this independent observer to event-time entitlement authority and deterministic remediation across heterogeneous vertical ERPs.

### Strongest objection / red-team result
It is deliberately **read-only**. It detects provider truth but does not map that truth into a vertical system's historical earning/payable, does not reopen the obligation, and does not by itself distinguish `BANK_RETURN_STILL_OWED` from `REFUND/CLAWBACK_NOT_OWED`. That economic classification is critical: both can look like payout trouble while requiring opposite accounting treatment.

The default 30-day window is also a policy horizon, not permanent finality. Payout lookback can be configured more broadly, but event-gap detection is bounded by provider event retention. Therefore this should be treated as an independent sensor, not a complete close-assurance engine.

### Combination opportunity
**Familiarise historical earning authority + stripe-connect-reckon terminal provider readback + reason-aware counter-event logic** is the strongest current composition:

`event-time rate authority -> immutable earning -> payout success -> independent provider scan -> contradiction by exact payout/event identity -> classify bank return vs economic clawback -> compensate ledger -> reopen or reduce entitlement -> safe re-close`

This directly attacks the prior lost-post-success-webhook gap without forcing the vertical ERP itself to poll every supposedly terminal provider effect forever.

## COMBINATIONS DISCOVERED

### Payout Finality Sentinel
A practical composite product now looks feasible without waiting for one repository to contain every primitive:

1. Read the vertical ERP's immutable earning/payable artifact and exact provider payout ID.
2. Independently scan provider payout history regardless of the ERP's local terminal state.
3. Compare external provider state with local money state and processed-event history.
4. If contradicted, classify the counter-event economically:
   - `BANK_RETURN_STILL_OWED` -> compensate prior payout accounting and reopen the same historical earning/payable.
   - `REFUND_CLAWBACK_NOT_OWED` -> reduce/reverse economic entitlement instead of re-paying.
   - ambiguous identity/reason -> quarantine for human review.
5. Re-pay only from the stored original earning/rate authority; never consult current rates for the historical event.
6. Continue independent observation until a configured finality policy is satisfied.

This can attach first to staffing/labour-hire or marketplace products where a single failed payout is both operationally painful and financially auditable.

## CLAIMS TESTED

- **Independent provider payout observation does not need to be gated by local payout state.** `stripe-connect-reckon` lists provider payouts directly for each connected account over the configured window.

- The full target remains unproven in one repository: terminal external polling + exact historical earning authority + reason classification + automatic conditional reopen + safe re-payment under the original authority.

## FAILURES / NEGATIVE KNOWLEDGE

1. The word **reconcile** is weak evidence. Inspect the query selector: if it only loads `pending`, `processing`, `submitted` or `in_transit`, the system is blind after local success.
2. Webhook replay and direct object readback are different. Replaying missed events helps within event-retention windows; listing/retrieving provider payout objects is a separate observation plane.
3. Terminal-provider polling without local economic context cannot decide remediation. A generic failed payout finding is not sufficient evidence that the historical worker/vendor entitlement should be reopened.
4. A `reverse` method can represent a clawback, not failed delivery. Always inspect what economic object moves after reversal.
5. A finite polling window creates a hidden finality horizon. Any production assurance product must make that horizon explicit and configurable rather than silently equating age with truth.
