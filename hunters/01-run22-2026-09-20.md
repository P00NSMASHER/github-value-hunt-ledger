# Hunter 01 — Run 22 — 2026-09-20

## Mission focus
Test whether the prior South Africa finding (`EPIUSECX/cohenix_local_za`) represents a repeatable commercial category: jurisdiction-specific operational software that turns regulatory/domain authority into deterministic ERP workflow, regulator-facing artifacts, reconciliation, and tests. Search was deliberately broadened back toward Vertical ERP Gold rather than continuing payout-only component hunting.

## Discovery methods used
1. **Direct jurisdiction/problem search** — ERPNext/Frappe country localization, e-invoicing, payroll/tax compliance, and export/import compliance.

3. **Analog search** — looked for the same authority -> deterministic workflow -> external/regulator readback pattern in a different jurisdiction and in a different boring regulated business process (Indonesia VAT/e-invoice and India EXIM).
4. **Low-attention search** — inspected low-star Kenyan payroll/localization projects and active regional ERP extensions rather than popularity-ranked ERP repositories.

## BEST NEW FIND

### agile-technica/erpnext-indonesia-localization
- URL: https://github.com/agile-technica/erpnext-indonesia-localization
- Exact revision: `82d5be95f3c89b9c58cdc05e0bbd6d319c72f5ac`
- Public metadata at inspection: 47 stars, 20 forks, AGPL-3.0, active release line; v1.4.1 merge dated 2026-06-19.
- Status: **STRONG / WATCH FOR PROMOTION**
- Score: **25/30** — A4 B4 C5 D4 E4 F4

### Concrete capability
A working ERPNext Indonesia localization whose strongest seam is a bidirectional **ERP invoice -> Coretax DJP -> ERP official-state reconciliation** workflow.

The source is materially stronger than its README:
- `coretax_xml_exporter.py` selects submitted Sales Invoices not yet carrying an official tax-invoice number / generated XML marker; maps company, buyer tax identity, transaction code, facility-stamp context, item/unit data, price/quantity/discount, tax base, alternate tax base, VAT amount/rate, and luxury-goods tax into Coretax XML; and records the export against the invoice.
- `coretax_importer.py` reads the regulator-generated spreadsheet output, resolves the original ERP invoice by `Referensi`, validates required fields and allowed external states, and writes back `tanggal_faktur_pajak`, `nomor_faktur_pajak`, and `coretax_status`.
- Allowed imported external states are explicitly constrained to `APPROVED`, `AMENDED`, or `REJECTED`; an APPROVED record must have an official tax-invoice number.
- Checked-in tests exercise export selection/preview, successful/failed export paths, importer success/failure/rollback behavior, missing fields, and regulator-output mapping.
- Exact-head GitHub checks continue to run successfully for security analysis; the repository contains a substantial test suite even though I did not independently execute its complete Frappe test matrix in this run.

### External verification
Independent DJP sources confirm that Coretax became the VAT administration path for the January 2025 tax period and that Coretax supports tax-invoice upload through XML import. DJP later reported raising XML-upload capacity from 100 to 15,000 invoices per upload and increasing XML-import signing throughput. That independently validates the business workflow this repository implements; it does **not** by itself validate every field mapping in the repository.

Official sources inspected:
- https://www.pajak.go.id/id/berita/shifting-tax-invoice-e-faktur-coretax-2025
- https://www.pajak.go.id/id/siaran-pers/pembaruan-informasi-pasca-implementasi-coretax-djp

### Why unusual / commercially important
The reusable value is not generic Indonesian tax configuration. It is the closed operational loop:

`ERP transaction -> regulator-specific deterministic artifact -> external regulator processing -> imported official status/identifier -> corrected ERP state`

That is a real compliance operating primitive and a plausible template for other jurisdictions where e-invoice/tax systems sit outside the ERP.

### Buyer / painful problem / first paid wedge
- **Buyer:** Indonesian ERPNext implementers, finance/controllers at Indonesian ERPNext users, regional ERP service firms.
- **Pain:** manual tax-invoice export/import, mismatched ERP vs Coretax status, missing official invoice numbers, rejected invoices, and repeated mapping/configuration work.
- **First paid wedge:** **Coretax Readiness + Reconciliation Audit** — install in staging, validate company/customer/item/tax mappings, generate a frozen sample XML batch, reconcile the returned Coretax output to source invoices, and deliver a deterministic exception report.
- **Money path:** reduced manual compliance labor, fewer rejected/missing tax invoices, lower month-end reconciliation effort, and faster ERP implementation.
- **Build compression:** materially compresses regulator-specific schema/workflow discovery plus Frappe integration and regression test work.

### Red-team / strongest objection
This does **not** yet prove the stronger South-Africa-style temporal-authority architecture. I did not find explicit effective-from/effective-to or rule-pack/version identity governing the Coretax field/rule mappings. The app is current-regime integration, not demonstrably bitemporal compliance authority.

There is also a failure-boundary concern worth testing: exporter mapping marks invoices as XML-generated before file generation completes. The direct synchronous wrapper throws on a failed export, which should roll back in a normal Frappe transaction, but the >500-invoice queued path should be fault-injected to prove a caught generation exception cannot commit `is_xml_generated=1` without a durable XML artifact.

### Rights / provenance
Public repository license is AGPL-3.0. Per the hunt's standing user assertion, repository-owned code is treated as separately commercially authorized for this research. That assertion does not extend to DJP/Coretax specifications, trademarks, hosted tax services, taxpayer data, or regulator terms.

### Capability / graph / radar / experiment delta
- **Capability delta:** regulator round-trip state reconciliation becomes a concrete reusable primitive: internal source record -> deterministic regulator artifact -> official output -> source-record state correction.
- **Graph edge:** strengthens CAP-008 structured invoice compliance and RAD-008 machine-readable regulatory/source authority; also complements CAP-019 source-observation concepts because official status must remain distinct from local intent.
- **Radar signal:** independent second-jurisdiction evidence for **compliance-as-executable-domain-pack**, but temporal rule versioning is weaker than `cohenix_local_za`.
- **Experiment impact:** a reusable jurisdiction-pack benchmark can now include `VALID_EXPORT`, `REJECTED_EXTERNAL`, `AMENDED_EXTERNAL`, `MISSING_OFFICIAL_NUMBER`, `ROW_IDENTITY_MISMATCH`, and `EXPORT_ARTIFACT_FAILURE_AFTER_LOCAL_MARK` cases.
- **Commercial impact:** supports a narrow implementation/audit service that can sell before building a new ERP.
- **Negative knowledge:** successful regulator format integration is not the same as historical rule authority; every pack should prove the exact rule/spec revision that governed a historical artifact.

### finbyz/exim
- URL: https://github.com/finbyz/exim
- Exact revision: `7179d0cbc6580898157b1ed1d0b9ce1f3becb999`
- Public metadata: 10 stars, 29 forks; README states GPL v3; GitHub metadata reports license as `NOASSERTION`/Other, so public-license provenance should be rechecked from the actual `license.txt` before reuse decisions.
- Status: **WATCH / HIGH DOMAIN VALUE**
- Score: **24/30** — A4 B5 C5 D5 E2 F3

#### What was actually verified
This is a genuinely deep India export/import operating layer, not a CRUD shell. Source contains:
- **Advance Authorisation** import/export ledgers with item/quantity/value consumption and over-utilization guards.
- Sales- and Purchase-Invoice hooks that append export/import consumption to the license.
- **BRC Management** that ties shipping-bill amounts to payment receipts/BRC amounts and has partial/completed states.
- **Forward Booking** with underlying exposure, amount utilization, cancellation, maturity, gain/loss calculation, and automatic Journal Entry posting.
- Export benefit calculations for **Duty Drawback** and RoDTEP-labelled (`meis_*`) values, including percentage-of-FOB and per-unit cap logic.
- Pre-shipment/post-shipment, LC/contract-term, shipping, document-check, claim and related ERP workflow surfaces.

Independent DGFT material confirms the underlying business domain is real and economically consequential: Advance Authorisation permits duty-free import of inputs tied to export products and carries export-obligation periods; current RoDTEP schedules publish item-specific percentage-of-FOB rates and per-unit caps. RBI material independently confirms forward hedges are tied to underlying exposures and maturity/cancellation rules.

Official sources inspected:
- DGFT Advance Authorisation / export-promotion material: https://content.dgft.gov.in/Website/dgftprod/816a9d11-d7a1-46c8-8098-47afade7f6e6/Annual%20MIS%20Report%20on%20Export%20Promotion%20Schemes-%20%202025.pdf
- DGFT RoDTEP Appendix 4RE: https://content.dgft.gov.in/Website/dgftprod/13be3318-2140-49c1-acfd-6fbd1f3f8b28/Appendix%204RE%20%281%29.pdf
- RBI forward-contract guidance: https://www.rbi.org.in/commonman/Upload/English/Notification/PDFs/05RM290613FL.pdf

#### Why not promoted
The domain compression is excellent, but the authority/testing layer is materially weaker than the workflow depth:
- benefit rates appear as mutable invoice/item fields rather than an effective-dated, source-identified DGFT rate pack;
- code search found mostly test stubs / CI test-discovery scaffolding rather than a convincing invariant regression suite;
- `BRCManagement.cal_total()` initializes a local `total_bank_charges` but does not visibly aggregate it into `self.total_bank_charges`, while status logic later uses the document field — a concrete reconciliation edge to test;
- `create_jv_with_gst()` appears to save/submit the Journal Entry inside one branch and then save/submit it again unconditionally, a potential double-submit defect that needs reproduction before treating this as financial authority.

Commercially, this is a high-value **domain/workflow donor** and could support an India EXIM implementation service, but it is not safe enough to become a compliance/money oracle without a versioned authority layer and adversarial tests.

## COMBINATIONS DISCOVERED

### Compliance Domain Pack Control Plane
The South Africa and Indonesia findings now suggest a reusable commercial architecture:

`official authority/source -> versioned jurisdiction pack -> deterministic ERP transformation -> regulator artifact -> external regulator result -> ERP reconciliation -> evidence receipt`

`cohenix_local_za` is stronger on effective-dated statutory calculation. `erpnext-indonesia-localization` is stronger on regulator round-trip artifact/state reconciliation. A productized control plane should combine both rather than copying either architecture literally.

A second adjacent product line is **India EXIM Compliance Assurance** using FinByz's workflow vocabulary as the domain map while independently sourcing/versioning DGFT/RBI authority. The key product advantage would be replacing mutable item-level scheme rates with source/version/effective-date identities and proving every claim/utilization against the rule version valid for the shipment date.

## EMERGING TECHNOLOGY SIGNALS

**Compliance-as-executable-domain-pack is now a real multi-jurisdiction signal, but should remain a sub-thesis under RAD-008 rather than receive a new radar score yet.**

The commercial moat appears to be the conjunction of:
1. current and historical source authority;
2. deterministic executable rules;
3. regulator-specific artifact/protocol generation;
4. external result reconciliation;
5. regression fixtures tied to authoritative source revisions.

Most discovered localizations have only 2-4 of these five. That gap itself is product opportunity.

## FAILURES / NEGATIVE KNOWLEDGE

- Do not equate a country localization with a compliance authority. Hard-coded current-year values are a maintenance liability without explicit effective dates and source identity.
- Do not accept "tests exist" from CI scaffolding; count concrete semantic fixtures and inspect whether the discovery step can self-match.
- Do not treat regulator upload success as historical rule correctness. The artifact needs a rule/spec version receipt.
- Do not use mutable item-level RoDTEP/Drawback fields as authoritative historical rates without a dated DGFT schedule identity.
- In regulatory round-trip systems, fault-inject the seam between "local row marked exported" and "durable external artifact created"; caught exceptions can strand local state if transaction boundaries are not explicit.

## SEARCH POLICY UPDATE

For country/regulatory ERP hunting, require a five-part conjunction before deep inspection:
1. **authority identity** — source/version/effective date;
2. **deterministic rule execution** — not a form or static field list;
3. **regulator artifact/protocol** — XML/JSON/file/report/submission object;
4. **external readback/reconciliation** — approved/rejected/amended/returned state or official identifier;
5. **semantic regression fixtures** — authoritative boundary cases, not only UI or import-success tests.

A repository missing two or more legs is a workflow donor, not a compliance authority.
