## Why it matters
This is the closest Node 01 has found to the full **Compliance Domain Pack Control Plane** inside one complete ERP. It combines:

- event-time taxpayer/branch registration authority;
- event-time tenant settings that are stamped into issued document events rather than re-read later;
- deterministic ZATCA UBL generation from immutable sales events;
- invoice hash / previous-hash / ICV / QR / signing machinery;
- explicit ZATCA clearance/reporting results modeled as external legal facts;
- fail-closed ambiguity semantics for transport failure versus actual regulator refusal;
- VAT return calculation and frozen filing records;
- substantive integration tests over tax, registration, ZATCA onboarding/clearance, returns, credit notes, and installed statutory rate configuration;

The surrounding ERP is not a toy tax adapter. Its README lists double-entry ledger, sales, purchases, inventory, POS, payments, prepaid entitlements, booking, CRM, branches, HR, Saudi HR/GOSI, payroll, reports, messaging, conversations, notifications and files. Tenants receive separate PostgreSQL databases and the architecture uses a custom event log/projection model.

## Concrete verified capability
### 1. Event-time authority is preserved instead of re-reading current identity/configuration
`modules/tax_sa/src/taxpayer.rs` explicitly treats Saudi taxpayer registration as an event because an old invoice must use the registration that existed when it was issued. Later branch/address/VAT-registration changes become later events rather than rewriting old tax artifacts.

The same source states that VAT rate, posting accounts and related tenant settings are read inside the issuing-command transaction and stamped into the event so a later setting change cannot restate an already-issued document.

This is a meaningful temporal-authority primitive.

### 2. Regulator artifacts are deterministic and replayable
`modules/tax_sa/src/documents.rs` rebuilds Saudi tax documents from the immutable sales event log. The source explicitly requires replay of the same history to reproduce byte-identical documents because the invoice hash was sent to the authority.

The document projection:
- uses registration as it stood at the relevant position in history;
- renders ZATCA UBL/XML;
- stops rather than silently skipping a document if rendering fails;
- computes the invoice hash, ICV/previous-hash chain and QR;
- records invoices issued before registration as `unregistered` rather than omitting them;
- models corrections as new credit-note tax documents instead of mutating the original invoice.

### 3. External regulator truth is represented separately from internal state
`modules/tax_sa/src/clearance.rs` treats a ZATCA verdict as an external event because it is a legal fact that cannot be reconstructed locally.

Crucially:
- timeout / HTTP 503 / certificate transport failure are **not** recorded as a ZATCA decision;
- the document remains pending for a later sweep;
- acceptance stores the clearance/reporting action plus ZATCA-stamped artifact/warnings;
- refusal is terminal for that document and correction requires a new document rather than editing the refused one.

This is a strong `UNKNOWN != REFUSED` boundary and is directly relevant to CAP-008/CAP-019-style evidence semantics.

### 4. VAT filing is frozen as filed, rather than perpetually recomputed
`modules/tax_sa/src/http.rs` documents that rerunning a filed period returns the number that was filed. A second filing of the same period is a conflict because an amendment is a different legal act. The route records the filing-period numbers as they stood.

That is the same broad architecture seen in money assurance: historical fact and later correction are separate events.

### 5. Semantic tests are substantive
`modules/tax_sa/tests/tax_sa.rs` installs the actual ledger/sales/purchases/tax schemas and projectors against a database. Among other cases, it verifies:
- Saudi standard VAT rate installation at 1500 bps;
- re-install does not overwrite a tenant-configured rate;
- VAT return behavior and filed-return preservation;
- ZATCA onboarding/clearance state behavior;
- refusal versus undecided/retry semantics;
- tax document behavior through the integrated sales/purchases stack.

`modules/tax_sa/tests/sandbox.rs` is intentionally ignored by default because it needs authorized ZATCA compliance credentials, but its purpose is explicitly to run the ordinary renderer/signer against ZATCA's sandbox and treat actual authority acceptance as the final interoperability oracle.

## External authority verification
Independent ZATCA sources confirm the important surrounding regulatory facts:
- Saudi Arabia's standard VAT rate changed from 5% to 15% effective 1 July 2020, subject to transitional rules.
- E-invoicing Phase 2 began 1 January 2023 in waves and requires integration with ZATCA/FATOORA.
- Phase 2 tax invoices are submitted to FATOORA in XML for clearance; ZATCA validates them and returns the cleared XML after applying the authority stamp/QR requirements.

This independently supports the repository's choice to model clearance as an external legal fact rather than an internal status flag.

## Strongest objection / red-team result
This repository is **not yet a complete immutable legal-source authority bundle**.

The strongest missing edge is the statutory rule/spec provenance itself. The test suite seeds the Saudi standard rate at 15% and the system freezes the chosen rate/config into the issued event, but I did not verify a formal rule object carrying fields such as:
- source URI / authority publication identity;
- source content hash;
- ZATCA XML Implementation Standard / validation-rule version;
- `effective_from` / `effective_to` for each statutory rule;
- supersession lineage.

That distinction matters. Event-time freezing prevents a future configuration change from rewriting the past, but if the configuration was wrong on the day of issuance, the system can faithfully preserve the wrong rule.

A second limitation is evidence scope: the ZATCA sandbox tests prove that the project has a live-validation path, but those tests are ignored by default and were not executed in this run. Exact-head CI proves the local/integration suite, not current remote ZATCA acceptance of every artifact.

The public BSL file also contains unresolved licensor placeholders. This does not reduce the technical finding under the user's separate authorization assertion, but it is real provenance metadata and should stay visible.
