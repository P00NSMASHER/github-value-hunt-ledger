## Question

Does the Saudi ERP's deterministic ZATCA invoice path bind each issued artifact and regulator response to the exact effective official ZATCA rule/specification bundle that governed it?

## Result

**No. The implementation preserves the business/configuration context, exact invoice bytes, invoice hash, signature material and ZATCA verdict, but it does not preserve an explicit immutable identity for the official ZATCA authority bundle.**

The official authority is real and versioned. ZATCA's current developer page publishes the Electronic Invoice Data Dictionary and Electronic Invoice XML Implementation Standard, both dated 19 May 2023. The downloadable XML standard identifies itself as **version 1.2**, records versions 1.0 (2021-05-28), 1.1 (2022-06-24) and 1.2 (2023-05-19), and says the implementation standard and Data Dictionary are interdependent. ZATCA separately publishes the Security Features Implementation Standards dated 19 May 2023; that PDF also identifies itself as **version 1.2** and records the same version lineage.

This is a multi-artifact authority surface, not a single self-identifying ruleset. ZATCA's SDK page further warns that passing the toolkit does not mean an invoice was approved by ZATCA and does not replace compliance with the Regulation, invoice specifications and security features. Therefore SDK conformance and external regulatory acceptance are separate evidence planes.

Official evidence:

- ZATCA E-Invoice specifications page: https://zatca.gov.sa/en/E-Invoicing/SystemsDevelopers/Pages/E-Invoice-specifications.aspx
- XML Implementation Standard v1.2 (2023-05-19): https://zatca.gov.sa/ar/E-Invoicing/SystemsDevelopers/Documents/20230519_ZATCA_Electronic_Invoice_XML_Implementation_Standard_%20vF.pdf
- Security Features Implementation Standards v1.2 (2023-05-19): https://zatca.gov.sa/ar/E-Invoicing/SystemsDevelopers/Documents/20230519_ZATCA_Electronic_Invoice_Security_Features_Implementation_Standards_vF.pdf
- ZATCA SDK qualification boundary: https://zatca.gov.sa/en/E-Invoicing/SystemsDevelopers/ComplianceEnablementToolbox/Pages/DownloadSDK.aspx

## Implementation inspection

### What the ERP does preserve

The renderer deliberately emits canonical UBL bytes, hashes those bytes, signs the hash, and preserves the exact submitted/stamped XML. It hard-codes `cbc:ProfileID` as `reporting:1.0`, preserves invoice number/UUID/date/time, and builds the ZATCA chain and signature envelope.

Source: https://github.com/suhailhijry/modular-erp/blob/31524f3e9339d411fa85f4bd657668d6ec2aed02/modules/tax_sa/src/zatca/ubl.rs

The wire model separates a ZATCA verdict from transport ambiguity. It submits only `invoiceHash`, `uuid` and signed invoice bytes. The response model records validation messages, clearance/reporting status and the cleared invoice. A 401/403, 503 or unreadable response remains an unanswered transport/authentication condition rather than becoming a document refusal.

Source: https://github.com/suhailhijry/modular-erp/blob/31524f3e9339d411fa85f4bd657668d6ec2aed02/modules/tax_sa/src/zatca/wire.rs

The projection schema stores `invoice_hash`, canonical XML, QR, signature, signed XML, stamped XML, remarks and settlement time. It does not define fields for the ZATCA XML-standard version, Data Dictionary version/digest, security-standard version/digest, SDK/validator release, authority-bundle receipt or effective interval.

Source: https://github.com/suhailhijry/modular-erp/blob/31524f3e9339d411fa85f4bd657668d6ec2aed02/modules/tax_sa/schema/install.sql

### What is missing

1. **`reporting:1.0` is not authority provenance.** It identifies the UBL profile emitted by this renderer, not the ZATCA XML/Data Dictionary/Security bundle version that authorized the transformation.
2. **The external API body carries document identity, not ruleset identity.** The submission binds hash + UUID + bytes; the stored answer binds status/messages/stamped XML. Neither binds ZATCA standard v1.2 or another effective ruleset.
3. **The event metadata comment and struct disagree.** The comment says `config_version` and `rule_version` make historical decisions explainable, but the exact pinned `Metadata` struct contains `config_version` and no `rule_version` field. Even a generic internal rule-version hook is therefore not demonstrated at this revision.
4. **Official publication is versioned but not delivered here as one immutable manifest.** The inspected ZATCA pages expose separate dated documents and a separately downloaded SDK. The ERP does not snapshot or hash those inputs into one receipt.

Source for metadata mismatch: https://github.com/suhailhijry/modular-erp/blob/31524f3e9339d411fa85f4bd657668d6ec2aed02/crates/erp-eventlog/src/envelope.rs

## Claim tested

**Claim:** deterministic historical replay plus external acceptance proves which official rules governed the invoice.

**Result:** falsified.

Deterministic replay proves that the ERP can reproduce its own historical bytes. ZATCA clearance/reporting proves the authority accepted or acknowledged those bytes at that interaction. Neither alone identifies the exact documentary/validator authority bundle used by the ERP, and the SDK page explicitly says toolkit verification is not ZATCA approval.

## Concrete control primitive

Add an internal immutable **ZATCA Authority Receipt** rather than inserting nonstandard provenance fields into the signed UBL:

- receipt ID;
- official artifact title and canonical ZATCA URL;
- published version and publication date;
- SHA-256 of every retrieved official artifact (XML standard, Data Dictionary, security standard, resolution/bylaw and SDK/validator bundle);
- effective-from/effective-to or an explicit `effective_until_unknown`;
- validator/SDK release identity and executable digest;
- acquisition timestamp and supersession lineage;
- ERP renderer revision;
- taxpayer-registration event identity;
- invoice hash and UUID;
- ZATCA response/stamped-document hash.

Persist the receipt ID in the internal issue event and `zatca_document` projection, and carry it into replay/conformance jobs and audit exports. Do not modify the signed UBL with an extension unless the governing specification explicitly permits it.

## Acceptance fixture

1. Freeze authority receipt A for the current v1.2 ZATCA bundle.
2. Issue, sign and hash invoice X; persist receipt A beside its immutable artifact.
3. Record a genuine ZATCA verdict/stamped document.
4. Install authority receipt B with at least one changed load-bearing rule or validator artifact.
5. Rebuild X. The system must reproduce X under A, not silently use B.
6. Issue new invoice Y under B.
7. Reject any audit export where X or Y lacks the receipt, any receipt artifact digest cannot be reproduced, or a response hash is detached from the exact invoice hash.
8. Keep `toolkit_passed`, `ZATCA_accepted`, `transport_unknown` and `ZATCA_refused` as distinct states.

## Capability impact

This does not add a new candidate or close `CAP-008`. It sharpens the missing acceptance criterion:

> A historically replayable regulated artifact must bind both its business/configuration authority and the exact official external rule/specification bundle; document hashes, profile IDs and regulator verdicts are necessary but not interchangeable with that bundle identity.

## Commercial implication

A **ZATCA Historical Authority & Replay Audit** can now test a precise control instead of offering generic compliance review: prove which official source bundle, validator build, ERP renderer revision, taxpayer identity and external verdict produced every retained invoice.
