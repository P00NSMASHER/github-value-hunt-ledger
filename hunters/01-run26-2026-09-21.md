## Question

Can a second regulated vertical—not a regulator SDK—carry an official schema version through a generated filing artifact, regulator acknowledgement and durable historical record?

## Result

**Partial, but not end-to-end.** The LAN Management System is a real ISP line-of-business system, not a KSeF demo: it combines subscriber/customer records, recurring network-service billing, finance, invoices, network inventory/config generation, notifications, helpdesk and scheduling. Its current KSeF code embeds an official FA(3) identity in generated XML and can retain regulator-assigned identifiers, hashes, statuses and UPO files. Received purchase invoices also have explicit database fields for the form system code, schema version and invoice hash.

However, the exact inspected public revision does not contain the application write path that creates or updates the outgoing `ksefbatchsessions` and `ksefdocuments` records or saves a UPO. Code search found the tables, readers, UI and migration/backfill logic, but no `INSERT INTO ksefdocuments`, `INSERT INTO ksefbatchsessions`, substantive status update, or `saveUpo` implementation. The repository declares `n1ebieski/ksef-php-client`, but its use is not present in the inspected source. Therefore the public revision proves a schema-aware generator and evidence consumer, not a self-contained regulator round trip.

This is a useful negative result: **a durable-looking regulator schema does not prove the evidence-producing integration is in the repository, versioned with the ERP, or replayable.**

## What is implemented

### 1. Generated invoices identify FA(3)

`getInvoiceXml()` emits:

- namespace `http://crd.gov.pl/wzor/2025/06/25/13775/`;
- `KodFormularza kodSystemowy="FA (3)" wersjaSchemy="1-0E"`;
- `WariantFormularza` 3;
- issue-time `DataWytworzeniaFa`;
- LMS software name/version in `SystemInfo`.

The checked-in XSD has the same target namespace and imports the Ministry data-type schema. This is materially stronger than a generic `version=3` flag because the output bytes self-identify the official logical form.

Generator: https://github.com/chilek/lms/blob/c58d607c62ca57e57289f33690f747cee109ae39/lib/KSeF/KSeF.php#L348-L357  
Checked-in XSD: https://github.com/chilek/lms/blob/c58d607c62ca57e57289f33690f747cee109ae39/lib/KSeF/schemat_FA(3)_v1-0E.xsd

### 2. The operational database models regulator state

Outgoing records include batch-session identity, environment, status and timestamps; document records include the source invoice, ordinal, KSeF number, document hash, status/description/details and permanent-storage date. A migration backfills permanent-storage date for status `200` records from the batch-session update time.

Received purchase invoices go further: `ksefinvoices` stores KSeF number, issue and permanent-storage dates, correction identity, parties, amounts, invoicing mode, invoice type, `form_system_code`, `form_schema_version`, `form_value`, invoice hash and correction hash.

Schema: https://github.com/chilek/lms/blob/c58d607c62ca57e57289f33690f747cee109ae39/doc/lms.pgsql#L3129-L3243  
Backfill: https://github.com/chilek/lms/blob/c58d607c62ca57e57289f33690f747cee109ae39/lib/upgradedb/postgres.2026031200.php

### 3. UPO evidence is retained and exposed

The invoice view resolves the latest relevant KSeF record, retrieves the UPO by the regulator-assigned KSeF number and lets an operator download or render it. The included UPO stylesheet expects the official-looking `http://upo.schematy.mf.gov.pl/KSeF/v4-3` namespace and displays the logical-structure name, form code, session reference, seller NIP, invoice number, KSeF number, send/assignment dates and document hash. It explicitly treats presence of a KSeF number as evidence of acceptance because the UPO file has no separate status field.

UI/controller: https://github.com/chilek/lms/blob/c58d607c62ca57e57289f33690f747cee109ae39/modules/invoiceksefinfo.php  
UPO rendering: https://github.com/chilek/lms/blob/c58d607c62ca57e57289f33690f747cee109ae39/lib/KSeF/upo-ksef-v4-3-to-html.xsl

### 4. Incoming artifacts have rollback-aware file handling

The received-invoice path saves the exact XML under tenant/date/KSeF-number-derived storage, parses it, tracks newly written paths, and exposes rollback that removes those files if the wider import fails. That is a useful artifact/database split-brain guard.

Source: https://github.com/chilek/lms/blob/c58d607c62ca57e57289f33690f747cee109ae39/lib/KSeF/KSeF.php#L2202-L2295

## Independent authority verification

The Polish Ministry of Finance says it published the target FA(3) logical structure in the Central Repository of Electronic Document Templates on **25 June 2025**, and that FA(3) replaced FA(2) on **1 February 2026**. The namespace date and template number embedded by LMS match that official identity.

Official FA(3) page: https://ksef.podatki.gov.pl/informacje-ogolne-ksef-20/struktura-logiczna-fa-3/

The Ministry's implementation roadmap states that KSeF 2.0 became the only operating system on **1 February 2026**, became mandatory for remaining enterprises on **1 April 2026** except the smallest firms, and is scheduled to cover those previously exempt firms on **1 January 2027**.

Official roadmap: https://ksef.podatki.gov.pl/etapy-wdrozenia-ksef/

The official downloads page separately publishes FA(3) examples, an FA(3) information brochure, and a description of UPO_KSeF elements; it was modified on **31 August 2026**. This confirms that the schema, API contract and UPO description are distinct authority artifacts rather than one automatic receipt bundle.

## Red-team result

### Missing public submission writer

The public repository contains readers and schemas for outgoing session/document state but no source path that creates those records, updates their real regulator status, or writes UPO files. The only `UPDATE ksefdocuments` code found is a schema migration backfill of `permanent_storage_date`. The KSeF helper has `getUpoFile()` and `upoFileExists()` but no UPO save method.

This means the most important provenance edge—**which executable and dependency version turned local invoice XML into this session/status/UPO record**—is missing from the inspected public source.

### No KSeF semantic tests

The checked-in `tests/` tree contains generic configuration/database/pagination tests but no KSeF tests. More importantly, the Travis configuration comments out `phpunit`; its active checks are dependency installation, database schema loading, PHP/template lint, PHPCS and JSHint. This is build/static evidence, not semantic proof that generated FA(3) XML validates, that status transitions are safe, or that a UPO hash matches the exact submitted bytes.

Tests: https://github.com/chilek/lms/tree/c58d607c62ca57e57289f33690f747cee109ae39/tests  
CI: https://github.com/chilek/lms/blob/c58d607c62ca57e57289f33690f747cee109ae39/.travis.yml

### No immutable authority receipt

For outgoing invoices, the schema version exists inside generated bytes but not as a separate database field beside `ksefdocuments`. For incoming invoices, a version label is stored, but no official XSD digest, canonical authority URL, publication/acquisition date, API/validator release, executable client version, or supersession lineage is persisted. The UPO itself can name a logical structure and bind a document hash, but the ERP does not prove which local XSD/renderer/client bundle produced and validated the artifact.

## Commercial implication

The concrete wedge is an **ISP KSeF Evidence-Chain Audit** rather than generic e-invoicing implementation:

1. inventory every invoice by embedded FA namespace/version, LMS revision, environment, local hash, session, KSeF number and UPO;
2. flag locally generated invoices with no durable artifact, accepted/status-200 rows with no readable UPO, UPO hashes detached from retained XML, and offline hashes without later finality;
3. validate exact retained bytes against a content-addressed official XSD bundle;
4. record the missing sender/client executable identity and version;
5. replay historical invoices across the FA(2) → FA(3) transition without silently substituting today's renderer.

## Capability impact

- `CAP-008`: strengthened negative acceptance criterion. An embedded schema version plus a regulator acknowledgement is insufficient if the evidence-producing submission component is absent or unversioned.
- `CAP-019`: strengthened artifact-chain criterion. Durable storage must include both exact bytes and the executable/authority identities that produced, validated and transmitted them.
- No new capability was added and no candidate was promoted.

## Cheapest falsifiable next test

Obtain the actual deployed submission worker/module used with LMS and freeze a synthetic production-like fixture:

`LMS invoice → FA(3) XML → local SHA-256 → API client version/digest → KSeF session → KSeF number → UPO → UPO document hash`.

The fixture passes only if the UPO hash matches the exact retained XML, every database transition can be replayed from the public worker source, a timeout remains nonterminal, and the record contains an immutable official XSD/API manifest identity. Without the missing writer/module, do not infer the round trip from the schema alone.
