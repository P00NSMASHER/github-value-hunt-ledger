## Question

Can an independent .NET/NuGet implementation connect all three of the assignment's required legs in executable source and tests: an effective rule version, historical evaluation under that version, and provenance to the external authority that supplied the rule?

## Result

**No implementation met all three legs.** The strongest target, Payroll Engine, meets the first two unusually well and exposes the precise missing control for the third.

Its exchange schema gives each regulation a version number unique within the regulation name plus a `validFrom` date. Its version tests create three versions of one payroll rule and prove that version selection changes historical payrun output at the effective boundary: January resolves version 1 and value 1000, February resolves version 2 and value 2000, and March resolves version 3 and value 3000. A separate edge fixture tests `validFrom == evaluationDate` and a future version that must remain inactive. The temporal payroll fixture independently tests bitemporal knowledge cutoffs: identical value dates resolve differently depending on which facts existed at the evaluation date.

The repository also contains a concrete Swedish-tax-table integration path: download Skatteverket's annual fixed-width table, import roughly 7,100 records into a named lookup, and calculate withholding from income bracket, municipal table number and taxpayer column. This is not just a README claim; the regulation YAML contains the lookup expression and the test YAML drives a January 2026 payrun.

But the authority edge breaks exactly where historical proof is needed. The official table file is deliberately excluded from source control, the import command does not bind a year/version/hash/authority URL to the regulation version, and the tax assertions in the checked-in test are commented-out TODOs pending a manual run with the downloaded file. A later annual import resets lookup values in place. The generic schema can carry arbitrary attributes, but this example does not require or test an authority receipt. Therefore an old payrun may be reproducible against versioned engine logic while the exact official data artifact that supplied its tax values remains unidentified or overwritten.

**Disposition: 24/30 — WATCH / strong transfer donor, not authority-grade.**

### 3. Historical evaluation is bitemporal, not merely annual

`TemporalPayroll` separates value date from evaluation date. A salary adjustment valid from April but entered in May is invisible to a February knowledge cutoff and visible to a September cutoff. Its seven expected-output cases cover retro and forecast perspectives, including a later-expired forecast value.

Fixture: https://github.com/Payroll-Engine/PayrollEngine/blob/2ddb5c770b0a955936562355a1021f06e922886a/Examples/TemporalPayroll/Payroll.tp.yaml

This is the strongest transfer primitive from the run: a regulation can select an effective rule version while inputs are independently filtered by what was knowable at the historical evaluation date.

## Red-team result

### The imported authority artifact is not durable evidence

The example tells operators to download `taxrate-monthly.txt` and explicitly recommends keeping the file out of the repository. `LookupTextImport` then fills a stable lookup whose first slice uses update/reset semantics. No checked-in source shows a required SHA-256, authority URL, publication/acquisition timestamp, tax year, record-format revision or immutable source-artifact ID flowing into the regulation version or payrun result.

The absence matters because Skatteverket publishes multiple years side by side. A regulation version can faithfully select lookup logic while the lookup's current rows came from the wrong annual file.

### The tax result is not semantically pinned

The January 2026 tax test contains salary and taxpayer cases, but its expected withholding wage type and collector values are commented TODOs to be filled after a first run with the real downloaded table. This proves the integration shape, not correctness against an official authority artifact.

### Package version is not rule-source version

NuGet lists `PayrollEngine.Client.Services` 1.0.0, updated 2026-04-21, and documents independent evaluation, period and regulation dates. That package identity versions executable client code; it does not identify which Skatteverket table or record specification populated a historical regulation lookup.

NuGet package: https://www.nuget.org/packages/PayrollEngine.Client.Services

## Claim tested

**Claim:** an independently implemented .NET/NuGet payroll or benefits system carries effective rule identity, historically correct evaluation and durable external-authority provenance in one tested path.

**Result:** falsified for the bounded sample.

Payroll Engine proves that the first two legs are practical and testable in the NuGet ecosystem. Its strongest real-authority example then demonstrates the missing third leg: a URL in documentation plus a mutable manual import is not a historical authority receipt.

## Commercial implication

The immediate wedge is a **Payroll Rule Authority Receipt** for regulation-driven payroll engines. For every imported official table or parameter pack, preserve:

1. authority and canonical source URL;
2. tax year/effective interval and published format revision;
3. exact source bytes and SHA-256;
4. parser/map digest and engine/package revision;
5. target regulation name/version and immutable imported-row-set digest;
6. semantic conformance fixtures whose expected outputs come from official worked examples;
7. payrun result linkage back to that receipt.

This would turn Payroll Engine's already-strong regulation-version and bitemporal machinery into historically provable compliance execution.

## Capability impact

- `CAP-008`: materially strengthened. The new acceptance criterion is **rule version + effective date + content-addressed authority receipt**, not rule version alone.
- `CAP-019`: strengthened. A historical payrun receipt must bind both the selected regulation version and the exact external parameter artifact that populated its lookups.
- No new capability was added and no candidate was promoted.

## Cheapest falsifiable next test

Create two official-style annual Skatteverket tables, A and B, with one deliberately different bracket. Import A into regulation version 1, calculate and close a historical January payrun, then import B into version 2 using the existing reset behavior. The test passes only if replay of January still resolves A, the payrun points to A's authority receipt and content hash, and a wrong-year or altered file fails before calculation. Today the checked-in example does not establish those guarantees.

## Stop reason

The bounded coverage question is answered after three deep inspections. One strong NuGet implementation satisfies effective rule version and historical evaluation with source-level tests, but the only inspected real-authority data path does not preserve or test immutable authority provenance. More generic .NET tax wrappers would not close that specific gap without a content-addressed source-to-payrun receipt.
