## BEST NEW FIND
**Name:** Freight production isolation question is not yet an executable repository claim

The repository contains scope-bound proof objects, manifests, a scoped SQLite audit reference store, and a scoped SQLite settlement reference store, but it does not contain an actual authenticated multi-tenant HTTP/API service or object-store authorization implementation to test. A repository search for common service/object-store surfaces (`FastAPI`, `Flask`, `boto3`, `object_store`) returned no matching implementation, consistent with the release/security documents' explicit claim boundary.

This matters because the prior Run 11 question cannot be closed by adding more unit tests to the reference stores. `FRT-SEC-001` requires negative tests against the **actual pilot data service**. Until such a service/deployment exists, end-to-end authorization, denied cross-scope attempts, object-store isolation and authorization-derived scope remain NOT_PROVEN rather than FAILED or PASSED.

## Claims tested
1. **Claim: proof-layer and persistence scoping proves production tenant authorization.** FALSIFIED. Scope correctness and principal authorization are different claims.
2. **Claim: the repository currently contains an API/object-store layer on which FRT-SEC-001 can be closed.** NOT SUPPORTED by the inspected tree/search; the security documents explicitly leave this deployment-specific gate open.
3. **Claim: more generic Freight repository hunting is warranted while this remains open.** REJECTED by the registered gap policy. `FRT-SEC-001` is engineering-owned and search is disabled; EXP-001 remains the higher-value blocker.
4. **Claim: current scoped reference stores are useless without an API.** FALSIFIED. They remain strong executable invariants for the future service, but should be treated as lower-layer acceptance oracles rather than end-to-end authorization proof.

## Commercial implication
The product should not spend another hunt cycle pretending to close enterprise multi-tenant security in the research repository. For an initial controlled, read-only, single-buyer pilot, the existing scope-bound proof/reference stores remain useful. Shared-service claims must wait for the actual data-service deployment and its authorization tests. The highest-value commercial evidence remains one authorized frozen buyer population carried through actual settlement.

## COMBINATIONS DISCOVERED
The security proof chain should be represented as separate planes:

`authenticated principal -> authorized buyer/BU scope -> scoped API/object locator -> scoped persistence transition -> append-only audit of allow/deny decision -> proof object / settlement edge`.

The current repository strongly exercises the middle persistence/proof layers. It does not yet implement/prove the first, second, third or deployed audit-service layers.

## EMERGING TECHNOLOGY SIGNALS
Strengthens `RAD-001` and `RAD-006` qualitatively: proof-carrying money systems need **authorization provenance** in addition to tenant-qualified data identity. A correct tenant column is not evidence that the caller was entitled to select that tenant.

## FAILURES / NEGATIVE KNOWLEDGE
- Do not equate scope-bound repository constructors with authenticated authorization.
- Do not count same-database buyer isolation tests as deployed API/object-store isolation.
- Do not build a speculative production API merely to satisfy a research checklist before buyer/deployment requirements exist.
- Do not resume generic Freight discovery: the gap registry currently has no `ACTIVE_SEARCH` Freight gap.
- Keep `FRT-SEC-001` open until there is an actual pilot data service to attack with cross-scope negative tests and denial-audit assertions.
