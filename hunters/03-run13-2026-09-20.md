## BEST NEW FIND
**Name:** Freight pre-parser CSV fail-closed / memory-amplification seam

The current `freight/input_guard.py` is intentionally a pre-parser guard, not a sandbox. It rejects oversized files, archives, unsafe filenames, XML DTD/entity constructs, NULs, invalid UTF-8, unrecognized EDI headers and overlong EDI segments, and it supplies a formula-neutralization helper for derived spreadsheet exports.

A concrete fail-closed hole remains in the CSV branch:

```python
list(csv.reader(io.StringIO(text)))
```

The branch catches `UnicodeDecodeError` only. It does not catch `csv.Error`, does not set an explicit CSV field-size policy, and materializes the complete parsed CSV into a Python list before any downstream parser sandbox exists.

### Falsifiable reproduction
In the current CPython runtime used for this inspection, `csv.field_size_limit()` returned `131072`. A CSV containing one 200,000-character field is below Freight Recovery's default `max_text_line_chars=1_000_000` and far below `max_file_bytes=25_000_000`, but Python's `csv.reader` raises:

`Error: field larger than field limit (131072)`

Because `inspect_input()` catches only `UnicodeDecodeError`, this condition is not converted into the module's typed `REJECT` result; it propagates as an exception. That violates the stated fail-closed interface even though it does not create a false ACCEPT.

A separate bounded-memory probe used a 1,000,000-byte CSV consisting of 500,000 one-character fields. `list(csv.reader(...))` peaked at about 9.19 MB under `tracemalloc` — more than 9x the raw input size. The exact amplification varies by runtime/data shape, but the important invariant is structural: the guard keeps the entire parsed cell graph in memory. A buyer file can therefore be within the 25 MB byte limit and still cause substantially larger pre-parser memory consumption.

## Recommended engineering acceptance patch
Do not silently raise the global interpreter field limit. The safer acceptance target is:
- add an explicit policy field such as `max_csv_field_chars`;
- stream `csv.reader` rows rather than wrapping it in `list(...)`;
- reject any field/row/cell-count over explicit bounded policy;
- catch `csv.Error` and return typed `REJECT` with a stable reason such as `invalid_or_oversized_csv`;
- add regression cases for field-size overflow, very high cell count, quoted multiline fields and malformed encodings;
- keep the downstream parser-sandbox requirements open until an actual deployment runtime exists.

The pre-parser should itself be safe to run outside the parser sandbox; it should not require an adversarial file to reach a resource-heavy parser merely to decide that the file is unsupported.

- A library default (`csv.field_size_limit`) should not silently define the business/security acceptance envelope.
- Fail-closed means predictable typed rejection, not merely "did not ACCEPT"; unhandled parser exceptions can cause retry loops or ambiguous source state.
- Do not close `FRT-SEC-002` from unit preflight alone. Production parser sandbox/network/credential isolation remains a separate deployment claim.
