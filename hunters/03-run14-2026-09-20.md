**Name:** Freight CSV shape preflight + typed parser rejection

**Why it matters:** the known `FRT-SEC-002` CSV seam was an internal acceptance-path defect, not a repository-search problem. The old guard eagerly materialized `list(csv.reader(...))`, had no explicit CSV field/logical-row/cell limits, and allowed `csv.Error` to escape the intended typed `ACCEPT`/`REJECT` boundary. The revised guard makes CSV resource limits explicit and performs a conservative shape preflight before `csv.reader` can materialize an over-wide logical row.

**Score:** N/A — internal capability/security hardening, not an external repository candidate.

**Implemented evidence:**
- `IngestPolicy` now has explicit positive limits for `max_csv_field_chars`, `max_csv_rows`, `max_csv_cells_per_row`, and `max_csv_total_cells`.
- physical line-length checking no longer uses `splitlines()` or whole-line list materialization;
- CSV shape is scanned first with quote/newline awareness so oversized fields, overly wide rows, excessive logical rows, and excessive total cells become deterministic typed rejection reasons;
- `csv.reader(..., strict=True)` runs only after the shape preflight succeeds and any `csv.Error` becomes `csv_parse_error` instead of escaping;
- a quoted comma/newline regression proves legitimate CSV quoting survives the preflight;
- a monkeypatched parser regression proves an over-wide row is rejected before `csv.reader` is invoked.

## COMBINATIONS DISCOVERED

The safer buyer-file path is now:

`authorized source -> byte/extension/magic gate -> explicit CSV shape bounds -> typed syntax validation -> isolated domain parser (future deployed boundary) -> normalized evidence -> authority/expected/actual comparison -> settlement proof`.

The shape preflight deliberately remains separate from the later parser sandbox. It reduces pre-parser amplification but does not establish OS/container isolation, CPU/time ceilings, network denial, or credential isolation.

## CLAIMS TESTED

1. **Every accepted-shape CSV should return a typed result rather than leaking parser exceptions.** Supported by the new `csv.Error -> csv_parse_error` regression.
2. **Cell-count limits must apply before a pathological logical row reaches `csv.reader`.** Supported by the monkeypatched-reader regression: a row above the configured width is rejected without invoking the parser.
3. **Quoted commas/newlines must not be mistaken for extra cells/logical rows.** Supported by a quoted multiline two-cell/one-row acceptance regression.
4. **The repository is now production parser-isolated.** NOT supported. `FRT-SEC-002` remains open until the hostile-input suite passes in the deployed parsing path with bounded CPU/memory/time, low privilege, no ambient credentials, and unintended network access disabled.

## EMERGING TECHNOLOGY SIGNALS

This modestly strengthens `RAD-001` proof-carrying operational software: source ingestion itself should emit deterministic evidence states. A typed rejection with explicit policy reason is stronger operational evidence than a parser crash or retry timeout.

## FAILURES / NEGATIVE KNOWLEDGE

- byte limits alone do not bound parser object amplification;
- checking row width only after `csv.reader` returns the row is too late for a single pathological row;
- Python/library parser defaults must not silently define commercial ingestion policy;
- fail-closed means a stable typed `REJECT`, not merely “not accepted” because an exception escaped;
- this preflight must not be represented as the future parser sandbox.

## CROSS-AGENT REFERRALS

Security/data-ingestion lanes should reuse one exact negative: configure a small per-row cell limit, replace the downstream parser with a sentinel that fails if called, and prove an over-wide quoted/unquoted input is rejected before parser invocation. This is a reusable way to distinguish “limit checked after allocation” from a real pre-allocation guard.
