## Falsifier 1 — semantically false acknowledgment strings mint authorization
`CharterRequest` annotates the acknowledgment fields as `bool`, but `from_dict()` performs no runtime boolean validation. `build_charter()` then evaluates `all(acknowledgments.values())`.

A deterministic in-memory reproduction using the exact current semantics showed:

```text
acknowledgments = {
  buyer_acknowledges_scope: "false",
  buyer_acknowledges_blind_protocol: "false",
  buyer_acknowledges_report_totals_separate: "false",
  buyer_acknowledges_no_guaranteed_recovery: "false",
  freight_acknowledges_no_external_action_without_buyer_approval: "false"
}
all(acknowledgments.values()) == True
launch_status == "READY"
=> charter_state == "KICKOFF_AUTHORIZED"
```

This is not hypothetical Python typing behavior: every non-empty string is truthy. The current test suite checks literal JSON/Python `False` but has no negative for `"false"`, `"0"`, integer `1/0`, `null`, array/object, or other wrong-type acknowledgment values.

**Verdict:** current type annotations do not fail closed at the authorization boundary.

## Falsifier 2 — scalar scope is silently converted into character scope
`from_dict()` currently performs:

```python
normalized["carrier_scope"] = tuple(data["carrier_scope"])
normalized["mode_scope"] = tuple(data["mode_scope"])
```

A scalar JSON string therefore becomes a tuple of one-character strings. Reproduction:

```text
tuple("carrier-1")
=> ('c','a','r','r','i','e','r','-','1')
```

The later validation only requires a non-empty tuple whose members are non-empty strings, so the malformed scalar survives. This weakens the claimed frozen-scope artifact because invalid shape can be normalized into apparently valid evidence.

## Falsifier 3 — self-consistent activation hash does not prove launch-gate authority
`pilot_launch_gate.evaluate_launch()` is the component that actually evaluates readiness, rights, deployment/separate-environment evidence, request flags and `as_of_date`.

However, `pilot_activation_packet.build_packet(readiness_input, launch_decision)` accepts a caller-supplied decision dictionary and passes it to `build_brief()`. The activation packet then hashes its own body. `pilot_charter._validate_activation_packet()` verifies that self-hash plus a small set of packet fields, but it does not prove that the `READY` decision came from `evaluate_launch()` or bind the exact launch inputs/evidence used by that evaluation.

I constructed a syntactically valid READY activation-packet body directly and recomputed its canonical SHA-256 under the current algorithm. The resulting self-consistent hash was:

`c680340235ddf88ed4fbe45d49428d97173e32abd74653993e0b07f61bf95f68`

Nothing in `_validate_activation_packet()` distinguishes that caller-constructed self-consistent packet from one produced after a successful authoritative launch evaluation.

**Important boundary:** SHA-256 here proves packet-body integrity only. It does not prove issuer authority, evidence provenance, freshness, or that `pilot_launch_gate.evaluate_launch()` was actually executed.

## Combined exploitability of the trusted-state transition
The two seams compose:
1. construct a self-consistent activation packet whose `launch_status` is `READY` and route is plausible;
2. provide all five acknowledgment values as non-empty strings such as `"false"`;
3. provide carrier/mode scope as scalars if desired;
4. current charter semantics can reach `KICKOFF_AUTHORIZED` and set `customer_data_authorized=true` without typed affirmative acknowledgments and without a proven authoritative launch-gate evaluation.

This is a **trusted-state integrity defect**, not a credential/access exploit. No external system or secret material is involved.

## Required engineering contract
Hunter write-discipline limits this run to durable evidence/referral rather than editing shared Freight implementation files. The engineering fix should satisfy all of the following before `KICKOFF_AUTHORIZED` is trusted:

### A. Strict request typing
- input must be an object/dict;
- each acknowledgment must satisfy `type(value) is bool`;
- `carrier_scope` and `mode_scope` must be JSON arrays / Python list-or-tuple, never scalar string/bytes;
- each scope member must be a non-empty string after trim;
- `fixed_fee_usd` must be a finite real number, reject `bool`, NaN and infinity;
- required string/date fields must be exact strings and fail closed before coercion.

### B. Authoritative launch receipt
The trusted gate should emit one receipt that binds at minimum:
- launch-gate schema/revision identifier;
- canonical digest of readiness input;
- canonical digest of component-rights registry;
- canonical digest of rights evidence manifest;
- canonical digest of the selected deployment evidence OR separate-environment evidence;
- complete `LaunchRequest` (`data_path`, multi-tenant requirement, parser-runtime requirement);
- `as_of_date` / freshness evaluation cutoff;
- resulting status, route, blockers, conditions and warnings;
- receipt hash over all of the above.

A receipt self-hash alone is still not an external identity signature. Therefore the safer immediate in-process design is for the Activation Packet builder to invoke the authoritative gate over raw/pinned inputs (or re-evaluate a supplied receipt against those exact inputs) rather than accepting a free-form decision JSON as launch authority.

### C. Transitive binding
The Activation Packet must bind the verified launch-receipt hash; the Pilot Charter must verify/bind that hash before a READY state can authorize customer data. Recomputing only downstream self-hashes must never convert an unverified/fabricated READY verdict into authorization.

## Mandatory regression negatives
1. `"false"`, `"0"`, `1`, `0`, `null`, `[]`, `{}` for every acknowledgment -> reject, never merely pending/authorized.
2. scalar string/bytes carrier or mode scope -> reject.
3. `fixed_fee_usd=true`, NaN, +Inf, -Inf -> reject.
4. caller-fabricated READY decision + recomputed Activation Packet hash -> cannot authorize.
5. valid gate receipt with one evidence digest changed -> cannot authorize.
6. stale/as-of mismatch -> cannot authorize.
7. request-flags mismatch (`requires_parser_runtime` or multi-tenant requirement changed) -> cannot authorize.
8. valid current gate receipt + exact typed acknowledgments -> can authorize.

## Claims / limits
**VERIFIED / FALSIFIED:**
- Python dataclass annotations are not runtime validation here.
- current `all()` semantics accept non-empty false-looking strings as affirmative.
- current scalar scope coercion can turn malformed input into non-empty string tuples.
- current Activation Packet self-hash proves internal consistency, not launch-gate provenance.

**NOT CLAIMED:**
- no claim that an external attacker can reach this code path in production;
- no claim that a deployed buyer-data service currently uses the charter artifact as its sole authorization mechanism;
- no claim that a cryptographic signature infrastructure is required for the controlled pilot; authoritative in-process re-evaluation plus exact evidence digests may be sufficient at this stage.

## Negative knowledge
- Python type hints are documentation unless runtime validation enforces them.
- Truthiness is not consent/acknowledgment semantics.
- Coercion before shape validation can turn invalid evidence into apparently valid evidence.
- A deterministic self-hash proves integrity of the object it covers, not who was authorized to create its trusted state.
- Downstream hashes cannot repair missing provenance upstream.
