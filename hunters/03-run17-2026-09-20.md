### Finding: accepted amendments can be minted from truthy non-booleans

`AmendmentRequest` annotates `buyer_acknowledges_change` and `freight_acknowledges_change` as `bool`, but `from_dict()` performs no runtime type validation. `build_amendment()` computes:

```python
accepted=request.buyer_acknowledges_change and request.freight_acknowledges_change
```

Consequently non-empty strings such as `"false"` are truthy and enter the accepted amendment path. This repeats the unsafe primitive previously found at the initial Pilot Charter boundary, but now affects the post-kickoff change-control path.

### Finding: replacement Charter verification trusts a self-consistent object rather than an authoritative Charter transition

`_verify_charter()` verifies the replacement Charter self-hash, requires a handful of non-empty strings, and requires `external_action_authorized is False`. It does **not** verify the Charter through the authoritative Charter builder / trusted launch receipt, nor does it require semantic consistency among `charter_state`, `launch_status`, and `customer_data_authorized`.

After verification, the amendment uses:

```python
kickoff_suspended=not bool(replacement_charter.get("customer_data_authorized"))
customer_data_authorized=bool(replacement_charter.get("customer_data_authorized"))
```

Therefore a self-hashed replacement Charter containing `"customer_data_authorized":"false"` is treated as **authorized** and unsuspended because the string is truthy.

A local synthetic falsifier reproduced the consequence: a valid base Charter plus a role-change replacement Charter with the string `"false"` in `customer_data_authorized` passed the current replacement verification and produced the equivalent of:

- `amendment_state = SUPERSEDED_BY_REPLACEMENT`
- `kickoff_suspended = False`
- `customer_data_authorized = True`

### Finding: “new Activation Packet required” is currently only a different-string gate

Material scope changes and out-of-band fee changes set `requires_new_activation=True`, which is correct in intent. But the enforcement is currently:

```python
if requires_new_activation and replacement_charter["activation_hash"]==base_charter["activation_hash"]:
    raise ValueError(...)
```

`_verify_charter()` only requires `activation_hash` to be a non-empty string; it does not verify that it is a SHA-256 digest of a real Activation Packet, that the packet exists, or that the authoritative launch gate produced the underlying READY decision from current readiness/rights/security evidence.

A local synthetic material-scope-change falsifier therefore succeeded with a self-hashed replacement Charter whose `activation_hash` was simply a different arbitrary non-empty string (`different-but-not-a-real-activation-packet`). That satisfies the current “new activation” comparison without proving launch/readiness revalidation actually occurred.

This is stronger than the prior initial-Charter provenance finding because the Amendment object explicitly claims:

- readiness revalidation required,
- launch revalidation required,
- new Activation Packet required,

while the operative transition does not currently require evidence that those revalidations happened.

### Additional malformed-shape seam

`from_dict()` does `tuple(normalized["carrier_scope"])` / `tuple(normalized["mode_scope"])` before shape validation. A scalar string such as `"carrier-1"` is therefore converted to a tuple of characters and can satisfy the later per-element non-empty-string check. Shape must be validated before coercion.

## Existing test coverage / missing negatives

The inspected tests correctly cover:

- literal Boolean `False` acknowledgment staying pending,
- hash tampering,
- role change requiring replacement but not new activation,
- material scope change requiring readiness/launch/new activation flags,
- same activation hash rejection for material change,
- valid replacement Charter flow,
- out-of-band fee requiring new activation / price-band behavior.

They do **not** cover:

- acknowledgment values `"false"`, `"0"`, `1`, `0`, `null`, list, or object,
- scalar-string carrier/mode scope,
- replacement `customer_data_authorized` wrong types,
- `launch_status=BLOCKED` combined with an “authorized” replacement object,
- fabricated-but-rehashed replacement Charter,
- arbitrary non-receipt `activation_hash`,
- stale/mismatched readiness, rights, security, request-flag, or gate-revision evidence.

## Engineering acceptance contract

Before Pilot Amendment can be a trusted customer-data authorization transition:

1. Validate the exact runtime schema before coercion; reject unexpected types.
2. Require both amendment acknowledgments to be the literal Boolean `True`, not truthy values.
3. Require carrier/mode scopes to arrive as non-empty arrays/tuples of non-empty strings; reject scalar strings.
4. Require `customer_data_authorized` to be a literal Boolean and require its value to be consistent with the authoritative Charter state and launch status.
5. Verify a replacement Charter through an authority-bound receipt, not only by self-hash.
6. When `requires_new_activation=True`, require the actual new Activation Packet / launch receipt and verify that its canonical digest exactly equals the replacement Charter `activation_hash`.
7. Bind the new activation receipt to the exact readiness input, rights registry/manifest, security/deployment or separate-environment evidence, request flags, evaluation cutoff, gate revision, status, blockers, and conditions.
8. Treat `requires_readiness_revalidation` and `requires_launch_revalidation` as evidence-backed predicates, not descriptive output flags.
9. Add negative tests for truthy false strings, scalar scopes, fabricated replacement Charter, arbitrary activation string, stale/wrong evidence digest, blocked launch with claimed authorization, plus at least one valid role-only and one valid material-change path.

## Commercial / security significance

The Pilot Amendment exists specifically to ensure a frozen buyer population cannot be silently widened or otherwise changed after authorization. A self-consistent amendment must therefore not be able to make a materially changed scope operative without actual re-authorization. Otherwise the system can produce a machine-readable statement that confidential customer data remains authorized even when no authoritative new Activation Packet was ever issued.

The safest trust chain is:

`typed amendment request -> literal bilateral acknowledgment -> authoritative revalidation when required -> exact-input-bound launch receipt -> verified Activation Packet -> authoritative replacement Charter -> amendment supersession`

Self-hashes remain useful integrity evidence, but they do not establish decision provenance.
