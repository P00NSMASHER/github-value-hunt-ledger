## BEST NEW FIND — data-room source admission can be semantically false yet accepted

`freight/pilot_package.py` declares `SourceEntry.read_only`, `authorized`, and `contains_secrets` as booleans, but Python dataclass annotations do not enforce runtime types. `build_data_room_manifest()` tests `if not entry.authorized` and `if require_pilot_read_only and not entry.read_only` using truthiness.

Therefore non-empty strings such as `authorized="false"` and `read_only="false"` are both truthy and pass the two gates. The resulting manifest can literally serialize `"authorized":"false"` and `"read_only":"false"` while still being accepted and hashed as a valid data-room artifact.

This directly contradicts the documented fail-closed rule in `freight/PILOT_DATA_ROOM.md` that sources do not enter when authorization is undocumented or pilot access is not read-only.

A smaller type seam also exists in `retention_days`: Python `bool` subclasses `int`, so `retention_days=True` passes `isinstance(..., int)` and becomes a one-day retention value unless exact type/domain validation is added.

### Concrete negative

A source shaped like:

```python
SourceEntry(
    source_id="invoice-1",
    buyer_id="buyer-1",
    business_unit="bu-1",
    source_type="invoice",
    source_hash=<valid sha256>,
    read_only="false",
    authorized="false",
    contains_secrets=False,
    retention_days=30,
)
```

passes the current `build_data_room_manifest()` authorization and read-only checks because both non-empty strings are truthy.

## STRONGER INTEGRITY SEAM — final package does not re-verify the data-room hash against its entries

`DataRoomManifest` is directly constructible. `build_pilot_package()` accepts a `DataRoomManifest` object and copies `data_room.manifest_hash` into the final package, but it never recomputes/validates that digest against the manifest's buyer, BU, and entries. It also does not re-run the source authorization/read-only/secret/retention checks.

Consequences:

1. a caller can directly construct a `DataRoomManifest` with entries that were never accepted by `build_data_room_manifest()`;
2. the supplied `manifest_hash` can be stale, unrelated, or even malformed;
3. `build_pilot_package()` can still emit a self-consistent `package_hash` that commits only to the supplied `data_room_hash` string, not provably to the actual entries it just inspected.

So the current package chain proves deterministic consistency only when all callers honor the intended builder path. It does not itself establish transitive data-room integrity.

## ENGAGEMENT-STATE ADJACENT CHECK

The same trust shape exists one layer upstream in `freight/engagement_state.py`: the resolver is documented as the downstream answer to whether customer-data work may proceed, but it verifies self-hashes plus a small subset of fields rather than authoritative Charter/Amendment provenance. `_verify_charter()` also computes `authorized=bool(charter.get("customer_data_authorized"))`, so a self-hashed hand-built Charter with `charter_state="KICKOFF_AUTHORIZED"` and `customer_data_authorized="false"` is interpreted as authorized.

This means hardening only the Charter/Amendment *builder functions* is insufficient. Every downstream verifier that accepts serialized artifacts must validate exact schema, literal boolean semantics, transitive upstream authority, and the relevant content digest.

## TEST COVERAGE REVIEW

`freight/test_pilot_package.py` covers:
- valid package scope/hash flow through official builders;
- literal boolean `authorized=False` rejection;
- cross-buyer source rejection;
- literal `contains_secrets=True` rejection;
- missing incumbent source.

It does not cover:
- `authorized="false"` / `read_only="false"` / numeric truthy values;
- `retention_days=True`;
- direct construction of an invalid `DataRoomManifest`;
- stale/mismatched/malformed `manifest_hash` passed into `build_pilot_package()`;
- a package whose `data_room_hash` is valid-looking but does not bind the current entries;
- requirement for a current authoritative engagement-resolution receipt before customer data is admitted.

`freight/test_engagement_state.py` composes artifacts through the official builders and therefore does not test constructor/self-hash laundering at the resolver boundary.

## REQUIRED ACCEPTANCE CONTRACT

Before real confidential buyer files are admitted:

1. Require exact runtime booleans (`type(x) is bool`) for `authorized`, `read_only`, and `contains_secrets`; do not use truthiness as authorization.
2. Require `type(retention_days) is int`, with explicit configured min/max bounds.
3. Add `verify_data_room_manifest()` that canonicalizes the exact schema and recomputes `manifest_hash` from buyer, BU, and entries.
4. Have `build_pilot_package()` call that verifier and fail closed before using `data_room.manifest_hash`.
5. Validate all source-entry fields again at the serialized-artifact boundary, or use one canonical parser that returns a verified object incapable of bypassing validation through direct construction.
6. Require a current engagement-resolution/authorization receipt whose buyer+BU match the data room before source admission; a manifest's own `authorized` bit is not proof that the buyer authorized this engagement or path.
7. Add adversarial tests for truthy false-like strings/numbers, direct-constructor bypass, stale/mismatched hash, cross-scope receipt, suspended amendment, and one valid authorized path.
