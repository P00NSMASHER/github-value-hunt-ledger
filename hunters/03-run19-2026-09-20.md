# Node 03 Freight Stack — Run 19 — 2026-09-20

## BEST NEW FIND

**Name:** Data-room source hashes are not transitively bound to inspected bytes

**Why it matters:** `freight/input_guard.py` independently computes SHA-256 from the actual buyer-file bytes and returns it as `InputInspection.sha256`, but `freight/pilot_package.py` accepts `SourceEntry.source_hash` as caller-supplied metadata and validates only that it looks like a lowercase 64-character SHA-256. The data-room builder does not accept an `InputInspection`, does not recompute source bytes, and does not bind a locator/object-version/byte-length to the measured digest. The final Pilot Package then trusts the data-room manifest digest. This creates a time-of-check/time-of-use and evidence-provenance seam: the system can prove that metadata containing hash H was frozen without proving the later-parsed bytes are the bytes that produced H.

**Score:** N/A — internal acceptance/security finding, not an external repository candidate.

**Evidence inspected:**
- `freight/input_guard.py` blob `b74076fd5051780f745d829591e4725bd6db38c1`: `inspect_input(filename, data)` computes `sha256=_sha256(data)` from actual bytes.
- `freight/pilot_package.py` blob `48712d36db5361c6308208b9d8d5db6282e71e6e`: `SourceEntry` carries `source_hash` plus optional `source_locator`; `build_data_room_manifest()` validates only hash shape and source metadata, then hashes those supplied fields. No byte input, object version, byte length, ETag/version ID, or `InputInspection` receipt participates in source admission.
- `freight/PILOT_DATA_ROOM.md` blob `57e335d56d47577b516aead0325939726acae1ae`: the documented blind-order chain says the data-room manifest is built before population/truth and describes deterministic content binding, but the current canonical implementation binds declared digest metadata rather than independently measured immutable source bytes.
- `freight/test_pilot_package.py` blob `51b599758c22976454d1a1f7d197ddab05edc8e3`: tests synthesize hashes with `H(text)` and pass them directly into `SourceEntry`; no test mutates a source after inspection or proves a parser consumes the inspected byte object.
- Repository freight surface contains `input_guard.py`, `pilot_package.py`, and their separate test modules but no canonical intake module that connects the measured `InputInspection.sha256` to `SourceEntry.source_hash` before read/store/parse.

**Commercial implication:** before a real blind Freight Audit Acceptance Test, source admission should create one authoritative content receipt from the exact bytes entering the evidence room. Otherwise a mutable file path/object key can change between inspection/manifest creation and parsing while all downstream hashes remain internally self-consistent.

## OTHER STRONG CANDIDATES

### Mutable-locator TOCTOU
`source_locator` is optional metadata and no storage/object version is bound to it. A file/object at the same locator can therefore represent different bytes at different times unless an external immutable-storage control exists. Current repository evidence does not prove that control.

### Source-role independence remains unproven
Required data-room source types are checked by type presence, while duplicate protection is by `source_id`. There is no explicit rule preventing one identical content digest from being represented under multiple logical roles. This may be legitimate in some cases, but the blind incumbent-output role should not be allowed to masquerade as an independent invoice/authority source without an explicit policy.

## COMBINATIONS DISCOVERED

The correct source-admission chain should combine the already-working byte inspector with the proof-package system:

`current buyer/BU engagement authorization -> read exact source bytes once -> input guard ACCEPT -> system-computed SHA-256 + size + format -> immutable object/version receipt -> SourceEntry generated from that receipt -> data-room manifest -> population/truth/incumbent seal -> parser reads only the same immutable version/digest -> final package`.

This closes the missing edge between hostile-input inspection and proof-carrying commercial evidence.

## CLAIMS TESTED

**Supported:** the pre-parser can produce a deterministic SHA-256 from actual bytes.

**Falsified:** a valid `DataRoomManifest.manifest_hash` by itself proves which physical bytes were inspected or later parsed. The current builder receives only metadata objects.

**Not proven:** the pilot runtime prevents same-locator byte replacement, verifies object version/ETag at parse time, or requires the parser to consume exactly the admitted content receipt. No deployed intake runtime is present in this repository to establish those claims.

## EMERGING TECHNOLOGY SIGNALS

This strengthens RAD-001 / proof-carrying operational software. The useful primitive is not merely `hash in manifest`; it is a transitive content receipt: **measured bytes + scope + authority + immutable version + parser-consumption proof**. A declared digest and a downstream self-hash are weaker because they can be internally consistent while referring to different physical content.

## FAILURES / NEGATIVE KNOWLEDGE

- Hash syntax validation is not content measurement.
- A content digest supplied by the caller is not equivalent to a digest computed at the trust boundary.
- A mutable locator/path plus digest metadata is vulnerable to TOCTOU unless a specific immutable version is pinned and revalidated.
- Separate `input_guard` and `pilot_package` modules do not establish a security chain unless one authoritative intake transition connects their receipts.
- Do not claim deployed content binding from the current repository; the actual buyer-data service remains the place where this must be proven.

## CROSS-AGENT REFERRALS

Security/proof-package/payment lanes should use the same falsifier: inspect bytes A, record digest A, replace the object at the same logical locator with bytes B, recompute all downstream self-hashes, and verify the trusted workflow still refuses B unless its exact immutable version was separately admitted. This pattern applies to invoices, contracts, bank exports, remittances, proof attachments, and commission inputs.
