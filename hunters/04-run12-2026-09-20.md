# Hunter 04 Run — 2026-09-20 — Scope Recovery authority-path verification

## Run objective
Close the highest-value missing edge in EXP-005: determine whether a production-shaped public construction/public-works implementation binds an independently approved field measurement to the exact commercial authority at the bill-bearing transition, rather than merely exposing measurement and billing as adjacent screens.

## Explicit hypothesis
A public production-shaped construction/public-works system exists where the **bill-bearing transition itself** reloads an independently approved measurement, validates exact work-order/contract-line ownership, measurement date/billing-period inclusion, cumulative authorized quantity, and then binds that evidence to the bill. A weaker but still valuable outcome is a well-tested measurement→claim authority component that improves EXP-005 even if full cash finality remains elsewhere.

**Falsification condition:** the correct authority exists only in a selector/UI/preview, caller-supplied IDs or values can bypass it, approval is created as part of bill approval rather than before billing, or alternate mutation endpoints can change money-bearing lines without re-establishing the authority join.

## Specialist pass — CODE INSPECTOR

### Candidate A — `datadrivenconstruction/OpenConstructionERP`
**Exact revision:** `5622fe9a63e3811ebfa1d11c405d1635b5967cdf` (2026-09-19).
**Public license:** AGPL-3.0; user standing separate repository-code authorization applies. External datasets/assets remain separate.

### What is genuinely implemented
- `ProgressEntry` is an append-only field observation per BOQ position, with numeric range constraints, actor, timestamp, optional GPS/photos, and a monotonic sequence so latest-observation ordering is deterministic.
- `populate_claim_from_progress()` joins a claim's contract lines to BOQ-position progress inside the same project, derives period quantity/value from field percent complete and contract-line value, skips unlinked/no-progress/foreign-currency lines, and computes gross/retention/net.
- `commit_preview_to_claim()` reloads each referenced ContractLine from the claim's contract, rejects a foreign contract line before mutation, recomputes monetary value server-side, clamps a caller override to the contract-line ceiling, replaces claim lines idempotently, recomputes cumulative values, rolls totals, and emits an event.
- The claim state machine is explicit: draft → submitted → approved → certified → paid (with rejection paths). Generic claim PATCH is blocked from changing status; dedicated transition endpoints are required.
- DB-backed PostgreSQL integration tests cover latest-observation selection, no-progress/unlinked/foreign-currency cases, project isolation, idempotence, server recomputation/clamping, foreign-contract-line rejection, retention/net math and event emission.

### What breaks the authority thesis
1. `ProgressEntry` has no verified/approved measurement state. The bridge trusts the latest append-only observation; it does not require an independently approved measurement.
2. The commit endpoint accepts an edited set of claim lines. Although money is recomputed and bounded by the contract line, the server does not re-prove that the submitted percentage/value is equal to or bounded by an authoritative ProgressEntry. Thus the field observation can become advisory rather than controlling evidence.
3. `POST /progress-claim-lines/` is a direct alternate mutation path: it checks parent-claim access/editability but, in the inspected route, does not re-establish that the supplied `contract_line_id` belongs to that claim's contract before creating the line.
4. `DELETE /progress-claim-lines/{line_id}` verifies access and deletes the row but, in the inspected route, does not call the parent claim's editability guard. That creates an apparent path to mutate the line breakdown after approval/certification/payment, subject to the caller having the route permission.
5. `mark-paid` is an internal claim-state transition; no independently observed bank clearing is part of this construction module.

### Candidate B — `cscl-git/egov-coexistence`
**Exact revision:** `ac415b47f0388a5fd5ab711e1b1e578f32992d48`.
**Public license:** GPLv3 plus repository-specific terms; user standing separate repository-code authorization applies to repository-owned code.

### What is genuinely implemented
- Measurement books bind to WorkOrder/WorkOrderEstimate and contain measurement date/status/approval metadata.
- Measurement details bind quantities/rates to WorkOrderActivity.
- The measurement service calculates cumulative quantities from prior non-cancelled measurement books, includes approved revision quantities in the authorized ceiling, and detects approval-limit crossing.
- `getApprovedMBList(workOrderId, workOrderEstimateId, asOnDate)` is exactly the kind of authority selector ScopeSignal needs: it requires APPROVED measurement status, exact WO/estimate identity, an as-of date cutoff, and excludes already billed non-cancelled measurements.

### The decisive falsification
The current contractor-bill creation path does **not** use that strong selector as the authoritative bill gate. `CreateContractorBillController` receives a transient nested measurement-book object from the bill flow. `ContractorBillRegisterService.create()` creates/saves a new MB with status `CREATED`, links it to the bill and work-order estimate, and bill approval later approves that bill-created MB. The current path therefore does not prove **pre-existing independently APPROVED measurement → bill**. Code search did not find a current call site that made `getApprovedMBList` the bill-bearing gate.

The archived first-party `egovernments/egov-smartcity-suite@361238c743d046080d66b7fcbe44673a8a784be2` exhibits the same pattern, so this is useful lineage evidence rather than merely municipal fork drift.

**Exact revision:** `5d0b45c32ef295a610775b1bb806ceb767465955` (2026-06-19, unsigned).
**Public-facing license:** no root LICENSE was found at this revision; user standing separate repository-code authorization still governs repository-owned code for this research.

### What is genuinely implemented
This is not merely HLD text. The repository includes Go services, repositories, SQL migrations/queries, generated DB code and RPC handlers for measurement books, measurement entries, progress bills, certificates, payment applications, retention and deductions. Measurement books have a DRAFT/VERIFIED/closed-style lifecycle surface; progress bills carry billing periods, RA numbers, amounts, retention/recovery/tax/net, contractor identity, a measurement-book reference and downstream invoice reference.

### Why it fails the authority standard
- `CreateBill()` accepts `GrossAmount`, `PreviousAmount`, `CurrentAmount`, `RetentionPercent`, `RetentionAmount`, recoveries, deductions, tax, `NetAmount`, `WorkCompletionPercent`, contractor identity and `MeasurementBookRef` directly from caller input and persists them into a DRAFT progress bill.
- `UpdateBill()` likewise allows those monetary/progress fields and the measurement reference to be replaced from caller input.
- `measurement_book_ref` is a free text column in the inspected progress-bill schema, not a foreign key to an authoritative measurement-book record.
- Submit/Certify/Approve service methods simply call repository transitions. The SQL updates do not require a prior state in their `WHERE` clause and do not validate an approved/verified MB before moving the bill status.
- Measurement-book `VerifyMB` exists, but the inspected progress-bill transitions do not reload or assert that referenced MB or its project/date/status/line quantities.

## Specialist pass — ECOSYSTEM / HISTORY ANALYST
Three independent implementation families now converge on the same conceptual objects—BOQ/work-order line, field/progress measurement, progress/RA claim, certification, retention/deductions and payment state—but repeatedly diverge on where authority is actually enforced. ## Claims tested / falsified
- **Claim: “If a codebase has an `APPROVED unbilled measurement` selector, bills must originate from approved measurements.” — FALSIFIED.** eGov contains the selector but the inspected contractor-bill path creates a new MB in CREATED state and later approves it with the bill.
- **Claim: “A server-recomputed progress→claim bridge prevents unmeasured billing.” — FALSIFIED.** OpenConstructionERP's commit path allows edited claim lines and does not re-prove the entered percentage against the progress observation.
- **Claim: “A claim state machine makes an approved/certified/paid claim immutable.” — FALSIFIED at route level.** OpenConstructionERP blocks generic status PATCH and guards create/update line paths, but the inspected delete-line route lacks the parent editability guard.
- **Claim: “A rich measurement/progress-billing schema implies bill authority.” — FALSIFIED.** Samavaya stores a free-text measurement reference and caller-authored economic values, while lifecycle SQL transitions do not require the prior state or validate the referenced MB.
- **Claim: “No useful result unless a new 27+ repo is found.” — FALSIFIED.** The negative architecture pattern directly strengthens EXP-005 and provides high-value adversarial acceptance cases.

## EXP-005 adversarial fixtures added by this run
1. `GOOD_SELECTOR__NOT_ON_BILL_PATH`: approved/unbilled measurement selector exists but bill transition never invokes it.
2. `LATEST_FIELD_OBSERVATION__UNAPPROVED`: latest field progress drives claim value despite no independent approval state.
3. `PROGRESS_PREVIEW__CLIENT_EDITED_BEFORE_COMMIT`: preview comes from measurement/progress, but caller changes percentage/value before commit and authoritative transition does not re-prove it.
4. `RAW_CLAIM_LINE__FOREIGN_CONTRACT_LINE`: alternate line-create route receives a ContractLine ID from another contract.
5. `CERTIFIED_OR_PAID_CLAIM__LINE_DELETE`: destructive line mutation attempted after the parent claim leaves editable state.
6. `FREE_TEXT_MEASUREMENT_REF__NO_FK`: bill stores an MB reference string without authoritative measurement identity/status verification.
7. `LIFECYCLE_JUMP__NO_PRIOR_STATUS_PREDICATE`: SUBMIT/CERTIFY/APPROVE update query has no expected-current-state predicate.
8. Existing downstream fixture remains: `INTERNAL_PAID_OR_RECONCILED__NOT_EXTERNAL_FINALITY`.

## Failure / negative knowledge
- Stop rewarding the mere presence of `APPROVED`, `VERIFIED`, `MeasurementBook`, `RA Bill`, `Certified`, `Paid`, or `Reconciled` vocabulary.
- A correct authority selector is not evidence unless the money-bearing transition calls it.
- Preview validation is not authority if commit accepts edited values without re-validation.
- A primary service method is not sufficient; enumerate all raw POST/PATCH/DELETE mutation routes around the same economic object.
- State-machine constants are not sufficient; mutation endpoints and DB update predicates must enforce expected prior state.
- A text/reference field named after an authoritative object is not lineage unless it is resolved and checked against identity/status/date/scope at the transition.
- No positive repository this run proved the full chain: independently approved field measurement + exact commercial-line ownership + billing-period inclusion + cumulative authorized quantity + immutable certified claim + independent external settlement/finality.

## Search-method outcome / policy update
The strongest reusable refinement is **authority-location verification**, an extension of `STRAT:acceptance-path-transition-inspection`:

1. Find the best-looking authority selector/validator.
2. Trace exact call sites into the money-bearing transition.
3. Enumerate every alternate create/update/delete route for the same economic state.
4. Check expected-current-state predicates in the DB update, not only service-layer labels.
5. Construct a bypass test where the evidence is valid-looking but belongs to the wrong authority, wrong period, wrong state, or is altered after preview.

This is evidence-backed this run but does not require a new SEARCH_SKILLS.md entry; it refines an existing strategy and central skill promotion remains integrator-owned.
