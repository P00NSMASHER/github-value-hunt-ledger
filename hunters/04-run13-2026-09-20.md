# Hunter 04 Run — 2026-09-20 — bill-authority replay / independent RA verifier

## Run objective
Close the remaining EXP-005 construction authority gap by looking for a bill-bearing transition that binds one independently approved field measurement to an authoritative commercial line and cannot be replayed or bypassed. In parallel, test whether a low-attention independent RA-bill verifier could become a near-term ScopeSignal audit component even if it is not itself the system of record.

## Explicit hypothesis
Recent construction systems may encode the missing authority join at the database transition — exact measurement row lock + multi-role approval provenance + BOQ/project lock + cumulative ceiling + atomic bill-item insertion — but a candidate should not score STRONG unless the same economic state cannot be reached by alternate mutation paths, the measurement cannot be consumed twice after commit, required schema is reproducible from the repository, contractor/period authority is unambiguous, and meaningful negative tests exist.

A secondary hypothesis is that an independent BOQ/RA-bill verifier can be commercially useful before full evidence-to-cash authority is solved, provided it fails closed on malformed numeric input and is kept separate from entitlement/finality claims.

## Discovery modes used
1. **Direct problem search:** construction measurement book, approved measurement, RA/running-account bill, cumulative BOQ quantity, contractor billing verification.
2. **Low-attention repository search:** obscure/public-works construction billing and measurement projects, including recent small repositories with little attention.
3. **Code-signature search:** `measurement_book_entry_id`, `consume_billable_measurement`, `measurement_assignment_allows`, `RABill`, `MeasurementBook`, direct CRUD routes and row-level security.
4. **Commit/history archaeology:** exact migration-introduction commits and exact-head Actions history.
5. **Independent falsification:** synthetic execution of the inspected independent-verifier arithmetic/quantity logic on normal, over-limit, negative and NaN quantities.

## Specialist decomposition
- **Discovery Scout:** broad/problem/low-attention/code search.
- **Code Inspector:** authoritative transition, schema, direct mutation/RLS paths, quantity/identity/date invariants.
- **Test/History Validator:** versioned migrations, source history, Actions, test surfaces and reproducibility.
- **Commercial Analyst:** buyer, first paid wedge, build compression and what can be sold without overstating entitlement/recovery.
- **Independent RED-TEAM/VERIFIER:** replay, alternate insert/update, wrong contractor, wrong period, schema drift, malformed numeric input and false-finality boundaries.

## Candidate A — `raahul2701/nirman`

### New capability discovered
The current tree contains a hardening migration, `20260906_accounting_integrity_consume_billable_measurement.sql`, adding `consume_billable_measurement(p_measurement_id, p_ra_bill_number)` as a `SECURITY DEFINER` function.

The function:
- locks the exact measurement row `FOR UPDATE`;
- requires `measurement_assignment_allows(..., 'executive_engineer')`;
- requires a billable measurement with non-null billable/JE/AE approval provenance and calculated quantity;
- locks the exact BOQ row by measurement BOQ + same workspace/project;
- rejects invalid BOQ/project relation;
- rejects cumulative quantity above the BOQ ceiling;
- derives rate from the locked BOQ row rather than caller input;
- inserts a bill item carrying the exact measurement ID;
- advances BOQ completed quantity;
- writes a measurement audit event.

Commit archaeology shows the function was introduced in `6899826fa90e2b9f878a1ee2dca5919f39207560` with the message `fix: protect billable measurement consumption`, then only whitespace-cleaned in a later commit. This is unusually relevant because it shows the project was explicitly trying to move authority into a DB transaction rather than leaving it in UI/service code.

### RED-TEAM / VERIFIER findings
**1. Row locking is not one-time consumption.**
The function locks the measurement during one transaction but does not change the measurement to a consumed state, set a consumed flag, or otherwise make it ineligible after success. The inspected versioned `ra_bill_items` schema does not declare `measurement_book_entry_id` UNIQUE. Therefore, after the first transaction commits, a later call can source the same still-billable measurement again unless an unobserved database constraint exists. The BOQ ceiling may eventually stop overconsumption, but that is not equivalent to exactly-once measurement consumption.

**2. Alternate direct mutation path remains visible.**
The inspected RLS policy allows a project field user or the matching contractor to insert/update `ra_bill_items` directly. The current repository search found the old table/policy migration and the new consume function but no later revoke/policy that forces all bill-item creation through the function. A correct secure RPC is therefore not yet an unbypassable economic transition.

**3. Contractor authority is ambiguous.**
The function derives a contractor from same workspace/project `project_assignments` with active/pilot status and `LIMIT 1`. It does not bind the measurement to an exact work order/contract line or prove that the selected contractor owns the measured scope. On a project with multiple active contractor assignments, this is not sufficient authority.

**4. Billing period is not enforced.**
The earlier schema contains `measurement_date`, but the consume function never compares it with a bill period. `p_ra_bill_number` is caller-supplied text, not a period authority object.

**5. Versioned schema replay is unresolved.**
The hardening function references `measurement_assignment_allows`, `status='billable'`, `billable`, `billable_by`, `je_verified_by`, `ae_reviewed_by` and `calculated_quantity`. Current-repository search found those measurement-authority names only in the consume migration (apart from unrelated subscription/licensing uses of `billable`), while the earlier versioned table definition constrains measurement status to `draft|submitted|checked|approved|rejected`. No versioned migration defining the newer approval columns/function was found in the inspected migration set. This does **not** prove production lacks those columns, but clean-repository migration replay is not established and the function may depend on unversioned/manual database state.

**6. Evidence quality is weak.**
No direct test of `consume_billable_measurement` was found. Exact-head Actions show one production-deploy workflow run and it failed; no cause was inferred. The repository root exposes environment-named files, which were deliberately not opened under the hunt safety boundary.

### Score
A 4 / B 5 / C 5 / D 5 / E 2 / F 2 = **23/30 WATCH**.

### Independent verdict
**DO NOT PROMOTE STRONG.** The DB transition is an important architecture reference and a much better positive pattern than UI-only measurement awareness, but replay, bypass, contractor/period authority and migration/test gaps prevent it from serving as ScopeSignal's entitlement/billing oracle.

### EXP-005 value
Add two high-value negative fixtures:
- `ROW_LOCK_WITHOUT_CONSUMED_IDENTITY__SEQUENTIAL_REPLAY`: same measurement is consumed twice in separate committed transactions.
- `SECURE_RPC_EXISTS__DIRECT_TABLE_INSERT_BYPASS`: sanctioned function is correct, but alternate table/RLS mutation can create equivalent money-bearing state without the same checks.

Also add:

## Candidate B — `jbhp9fysxx-droid/construction-billing-verification-engine`

### Why it is interesting
This tiny low-attention Python project is explicitly positioned as an **independent RA Bill Verification Engine before approval** rather than a construction ERP replacement. Its implemented row validator independently checks:
- project/item existence in the approved BOQ;
- claimed rate against BOQ rate;
- arithmetic `claimed_qty × claimed_rate = claimed_amount`;
- cumulative claimed quantity against approved BOQ quantity;
- same-month resubmission semantics by replacing that month rather than double-counting it.

Its ledger updater uses `(project_id, item_code, month)` as the upsert key, recomputes chronological cumulative quantity and stores the RA-bill number. This aligns with a service-first ScopeSignal wedge: independent pre-approval checking against buyer-provided frozen BOQ/claim data.

### Practical falsification test
The inspected logic was reproduced exactly enough to test four cases:
- ordinary in-limit quantity: **accepted**;
- over-limit quantity: **rejected as BOQ_QTY_EXCEEDED**;
- negative quantity with matching negative amount: **accepted unexpectedly**;
- `NaN` quantity with `NaN` amount: **accepted unexpectedly** because Python comparisons such as `abs(NaN) > tolerance` and `NaN > boq_qty` are false.

The source performs `float(...)` conversion but no explicit `math.isfinite(...)`, non-negative quantity or positive-amount guard before money/ledger logic. A malformed/malicious negative or non-finite numeric value can therefore evade the currently inspected validation logic and contaminate the cumulative ledger.

### Tests/history/provenance
- No automated test files were found by repository search.
- Exact head has no GitHub Actions runs.
- Validator history is essentially the initial v1.0.0 implementation; no negative-input hardening lineage was found.
- No root `LICENSE` was found at the exact revision. The user's standing separate commercial authorization may govern repository-owned code for this hunt, but public-facing provenance still remains no-license/unclear.
- The engine checks claim-vs-BOQ math; it does **not** prove independently approved field measurement, contract/work-order ownership, entitlement, certification or cash finality.

### Score
A 5 / B 4 / C 4 / D 3 / E 2 / F 4 = **22/30 WATCH**.

### Independent verdict
**Retain as an independent comparator / negative-control seed, not as a money-authority engine.** It is commercially useful precisely because it is independent and simple, but it needs explicit finite/nonnegative numeric validation plus a planted-fault test suite before it can be trusted as a blind acceptance-test component.

### Commercial wedge
A lightweight **RA Bill Pre-Approval Acceptance Test** can be sold without replacing the customer's ERP: freeze an approved BOQ + cumulative ledger + candidate RA bill, independently recompute item/rate/arithmetic/cumulative quantity, produce a reviewer evidence pack, and keep any unsupported quantity/authority outside recoverable-dollar claims. ScopeSignal's richer evidence plane can later add field measurement, change authority, notice, certification and settlement.

## Commercial analysis
**Buyer:** specialty subcontractor/GC commercial manager, QS/PMC, owner rep, public-works auditor, construction controller.

**Painful problem:** a candidate RA bill can be arithmetically valid yet unsupported by the approved field quantity, wrong contractor/work-order line, wrong period, superseded baseline or already-consumed measurement. Existing systems often keep these facts in adjacent screens without enforcing one authoritative economic join.

**First paid wedge:** **Scope-to-Cash / RA Bill Acceptance Test** over 20–50 changes or bills. Start with approved BOQ/work order + RA bill + cumulative history; add measurement/certification/payment evidence when available. Output only evidence-backed findings and REVIEW states — not speculative recoverable dollars.

**Money path:** prevent overbilling, find underclaimed/omitted authorized work, reduce manual QS checking, catch duplicate/replayed measurement and strengthen dispute evidence.

**Build compression:** current findings supply independent verifier logic, hard database-transition patterns and high-value adversarial fixtures without requiring a greenfield ERP.

**Moat:** negative-case authority corpus + cross-system lineage verification, not a generic construction form or another LLM takeoff feature.

## Technology/radar interpretation
This run strengthens **RAD-001 proof-carrying operational software** and **RAD-006 authority-aware money assurance** without changing their central scores. The emerging primitive is not merely an `APPROVED` status or a row lock. It is:

`source evidence -> exact authority identity -> expected prior state -> one-time consumption -> bounded economic mutation -> durable lineage -> independent downstream outcome`

Construction repositories repeatedly implement only a subset. The repeatable missing controls — one-time evidence consumption, exact contract-line identity, period authority, alternate-route closure and versioned schema replay — are themselves a potentially defensible ScopeSignal acceptance standard.

## Claims tested / falsified
- **Claim: `SELECT ... FOR UPDATE` makes a measurement exactly-once billable. — FALSIFIED by source inspection.** The lock serializes concurrent transactions; without consumed-state mutation or uniqueness, it does not prevent a later committed replay.
- **Claim: a correct SECURITY DEFINER billing function makes the bill path authoritative. — NOT ESTABLISHED / challenged.** Direct table inserts remain allowed by the inspected RLS surface.
- **Claim: project-level contractor identity is enough. — REJECTED.** `LIMIT 1` among active project contractors does not prove ownership of the measured commercial line.
- **Claim: versioned source proves production schema authority. — NOT ESTABLISHED.** The consume migration references approval columns/functions not found in the inspected versioned migration set.
- **Claim: a simple independent BOQ verifier safely handles numeric input after `float()` conversion. — FALSIFIED by synthetic test.** Negative and non-finite quantities can pass the inspected conditions.
- **Claim: an independent RA-bill checker can still have commercial value without being entitlement authority. — SUPPORTED.** The narrow fixed-price pre-approval audit is useful if output is constrained to arithmetic/BOQ/cumulative facts plus REVIEW for missing authority.

## Failure / negative knowledge
1. **Row lock ≠ consumed identity.** Require a state change/claim token/unique evidence-to-bill binding and test sequential replay, not only concurrency.
2. **Secure RPC ≠ unbypassable path.** Enumerate direct table/API/serializer/RLS mutation surfaces that can create the same money state.
3. **Project identity ≠ commercial-line authority.** Exact contract/work-order-line ownership must be reloaded at the transition.
4. **Bill number ≠ bill period.** Measurement event date needs an authoritative period/window check.
5. **A migration file ≠ reproducible schema.** Search all referenced columns/functions and test clean migration replay before crediting the invariant.
6. **`float()` parsing ≠ valid money/quantity.** Require finite numbers, permitted sign/domain, decimal/rounding policy and planted NaN/Inf/negative tests.
7. **Independent arithmetic checker ≠ entitlement/finality oracle.** Keep its claims narrow and preserve REVIEW/$0 for missing measurement/contract/payment authority.

## Search policy update

1. inspect the sanctioned trusted transition;
2. verify exact authority identities and expected prior states;
3. test **sequential replay after commit** as well as concurrent replay;

Do not promote this as a new shared SEARCH_SKILLS entry yet; it is an evidence-backed lane refinement of an existing validated skill and should prove itself on another distinct task before central promotion.
