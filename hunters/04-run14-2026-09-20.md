### Concrete capability
PMIS implements a substantial public-works commercial-authority chain from sanctioned estimate/tender award into the agreement BOQ and then into Running Account bills. Its RA-bill service does **not** trust the caller's rate/description when a package has an agreement BOQ: each bill line must name the package BOQ line; `resolveForBilling()` reloads that exact line, rejects a line from a different package, computes already-billed quantity from non-rejected/non-cancelled bills, rejects quantity above the agreement remainder, and returns the authoritative agreed rate. Bill amount is then recomputed from present quantity × agreement rate. Source: `app/server/src/services/ra-bill.service.ts`, `app/server/src/services/boq.service.ts`, `app/server/src/models/boq.model.ts`.

The database schema preserves exact `project_id`, `package_id`, `contractor_id`, `division_id`, bill period, BOQ item IDs, cumulative/current quantities, agreed rate, workflow identity, Tally voucher reference and payment reference. `ra_bill_items.boq_item_id` is a real FK to `package_boq_items`; `ra_bills.measurement_book_no`, however, is only text. Source: `app/server/src/db/schema.sql`.

### Why this matters
This repository is unusually production-shaped and its exact head is CI-green, yet its MB→RA integration demonstrates several ways an application can *look* evidence-backed while the money transition remains weak.

### Verified source/schema behavior
1. `measurement_book` contains real physical-measurement fields, a `boq_item_id`, `measured_by`, `measured_at`, verification metadata, status and `ra_bill_id` FK. Quantity is non-negative at schema level.
2. The status vocabulary is `recorded | verified | billed | disputed | cancelled`; there is no separate `APPROVED` measurement state.
3. The UPDATE RLS policy is documented as “allow verification (status flip) but not data mutation,” but SQL RLS is row-scoped, not column-scoped: the policy shown does not itself constrain changed columns. Authenticated measurement-book UPDATE is granted for permitted roles.
4. The client query layer exposes direct `linkMbToRa()` and `unlinkMb()` operations that set or clear `ra_bill_id`.
5. `createRaBill()` accepts a caller-provided `billAmount` and optional MB IDs, inserts the RA bill first, then links the supplied MB rows.
6. On RA approval, `auto_link_mb_on_approve()` links **all verified, currently unlinked measurement rows in the same project**. It does not filter by exact BOQ/contract line, measured date/bill period, subcontractor/work order, or the rows that actually supported the bill.
7. `sum_mb_for_ra()` sums all rows linked to the RA bill without a measurement-status predicate. The scheduled recalculation function can rewrite `approved` or `paid` RA-bill amounts from those linked rows.
8. The drift trigger audits a post-bill MB quantity/rate change but explicitly does **not** block it.

Sources: `scripts/supabase/10_measurement_book.sql`, `scripts/supabase/32_mb_ra_linkage.sql`, `scripts/supabase/177_mb_automation.sql`, `src/app/queries/mbRaQueries.ts`, `src/app/queries/financeQueries.ts`.

### Test/history verification
`tests/app/mbRa.test.ts` verifies list mapping and mocked link/unlink success, but the inspected tests do not prove wrong-project, wrong-BOQ, wrong-period, disputed/cancelled, or post-approval mutation failure cases. The exact head's GitHub Actions CI run `35421957870` completed successfully, including test, unit coverage, mocked E2E, RLS security tests, typecheck/build/smoke and DB/security gates. That is precisely why this is valuable negative knowledge: broad green CI does not prove the missing commercial-authority invariants when they are absent from the test corpus.

### Independent red-team verdict
**REJECT STRONG.** The implementation demonstrates four separate false-confidence traps:
- **verified ≠ independently approved**;
- **same project ≠ same contract/work-order/BOQ authority**;
- **linked evidence ≠ evidence that supported the bill at approval time**;
- **CI/RLS green ≠ money-state authority proven**.

Do not treat the broad callable recalculation path or mutable post-bill MB behavior as payment/entitlement proof.

# COMBINATIONS DISCOVERED

The strongest reference architecture is now clearer:

**PMIS agreement/tender chain** supplies exact package/contract-line + agreed-rate authority and a realistic certification/deduction workflow.

**Nirman/DIGIT-style field measurement** supplies the missing independently reviewed physical quantity plane, but must be hardened beyond the currently known replay/period/ownership gaps.

**ScopeSignal verifier** should join them with an immutable evidence key:
`measurement_id → exact contract/work_order_line_id → measured_at → approved_by/state → single bill_item_id`.

Required transition invariants:
1. measurement is independently APPROVED;
2. measurement belongs to the exact contract/work-order/BOQ line;
3. measurement date is within the billed period or explicitly authorized exception;
4. quantity/rate are reloaded from authoritative records, not caller fields;
5. `measurement_id` can be consumed at most once (unique constraint or equivalent durable state), surviving sequential replay as well as concurrency;
6. only one sanctioned mutation path can create the money-bearing bill line;
7. downstream payment intent remains separate from independent bank/treasury observation and later reversal/return state.

This is a stronger product architecture than copying any single ERP.

2. Stop treating “verified” as equivalent to an independently approved commercial measurement without explicit semantics.
3. Same-project auto-linking is too coarse for construction money authority; require exact commercial-line identity.
