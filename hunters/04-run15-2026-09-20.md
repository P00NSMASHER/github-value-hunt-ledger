### CODE INSPECTOR — sanctioned path
`backend/apps/billing/services/billing_service.py` implements a notably strong *intended* path:
- `create_measurement_book()` runs transactionally and reloads each `TenderItem` by both caller-selected item ID **and the work order's tender**, so the normal service path rejects an item from another tender.
- Quantity is caller-provided, but rate/description/unit and estimated quantity are reloaded from the authoritative TenderItem.
- Overbilling is checked against prior `approved`/`submitted` measurement-book quantities.
- `create_ra_bill()` refuses any Measurement Book whose status is not exactly `approved`.
- The RA bill inherits `work_order` from the Measurement Book, derives its bill-period string from the Measurement Book's `period_from`/`period_to`, and creates each RA-bill line from the Measurement Book's persisted item quantity/rate/amount rather than accepting arbitrary bill-line economics in that service call.

This is one of the cleaner public examples found of `approved field-commercial evidence → server-derived bill` in the sanctioned service path.

### SCHEMA / STATE VERIFIER
`backend/apps/billing/models.py` and `backend/apps/billing/migrations/0002_initial.py` show:
- Measurement Book lifecycle: `draft → submitted → verified → approved/rejected`, with `verified_by`, `approved_by`, verification/approval timestamps, exact `work_order`, period bounds and MB items.
- An already approved Measurement Book cannot be reverted to another status through its model `save()`.
- MB items carry exact `work_order_item`, measured/verified identities, measurement date, quantity, rate and cumulative quantity.
- RA Bill carries exact `measurement_book` and `work_order` FKs; RA Bill Item carries an exact `mb_item` FK.
- **However, neither RA Bill→Measurement Book nor RA Bill Item→MB Item is unique.** The migration adds indexes but no `OneToOneField`, `UniqueConstraint`, consumed flag, or equivalent one-time economic-consumption invariant.

Therefore the same approved Measurement Book / MB item can apparently be claimed again in a later sequential transaction. Transaction/row locking in quantity creation does not cure that replay boundary.

### API / BYPASS INSPECTOR
The most important red-team evidence is in `backend/apps/billing/api/views.py` plus `serializers.py`:
- `MeasurementBookViewSet`, `MBItemViewSet`, `RABillViewSet`, `RABillItemViewSet`, and `DeductionViewSet` are all generic DRF `ModelViewSet`s.
- The repository has safe custom actions (`create_from_workorder`, `create_from_mb`) that call `BillingService`, **but the generic create/update/delete surfaces remain available alongside them**.
- The corresponding serializers use `fields = '__all__'` and do not make the economic/authority fields generally read-only.

This creates several materially plausible bypasses that the sanctioned service path does not close:
1. **`APPROVED_MB__SEQUENTIAL_REBILL`** — no one-time consumption/unique binding prevents the same approved MB from generating another RA bill later.
2. **`SAFE_SERVICE__GENERIC_RABILL_CREATE_BYPASS`** — a caller can reach the generic RABill ModelViewSet rather than `create_from_mb`, bypassing the approved-MB check and server-derived gross/net construction unless another unseen layer blocks it.
3. **`SAFE_SERVICE__GENERIC_RABILLITEM_CREATE_BYPASS`** — generic RA-bill-item creation can accept caller-selected `mb_item`, quantity/rate/amount fields rather than forcing server derivation.
4. **`APPROVED_MB__GENERIC_MBITEM_MUTATION`** — MeasurementBook itself blocks status reversion after approval, but MBItem has no corresponding parent-approved immutability rule. A generic MBItem update can therefore potentially alter fields under an already approved MB before later billing.
5. **`DIRECT_APPROVED_MB_CREATE`** — the generic MeasurementBook ModelViewSet + all-fields serializer does not itself implement a verified→approved transition gate; a caller can plausibly post/update status and economic summary fields directly instead of using a governed approval transition.

These are source-level bypass findings, not claims that a deployed instance has been exploited. They are exactly the kind of alternate-mutation-path failure `EXP-005` needs to test.

## Search-policy update
For ScopeSignal authority hunting, every apparently strong service/RPC should now be audited as a **closed-world mutation problem**:
1. locate the sanctioned money transition;
2. inspect exact authority identities and prior-state gates;
3. check DB uniqueness/consumed-state for sequential replay, not only row locks;
4. enumerate every generic CRUD/serializer/table/RLS mutation surface for the same economic object;
5. test whether parent approval makes child evidence immutable;
6. inspect exact-head CI and negative tests separately from source design.

Useful signatures: `ModelViewSet`, `fields = '__all__'`, direct `.objects.create`, `ForeignKey` versus `OneToOneField`/`UniqueConstraint`, parent-approved immutability hooks, consumed IDs, and negative replay tests.
