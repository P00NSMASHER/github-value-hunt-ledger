## CODE INSPECTOR — unusually strong intended path
`src/modules/subcontract/measurements/measurements.service.js` implements several load-bearing controls:
- measurement creation reloads exact `workOrderId` scoped to company;
- measurements cannot be recorded before the work order is beyond draft/issued/in-approval and a verified mobilization record exists;
- `workOrderItemId` is reloaded and must belong to the exact selected work order;
- authoritative unit/rate come from the work-order item, not the caller;
- cumulative measured quantity is checked against `contracted_qty` before measurement creation;
- new measurements begin in `draft` and retain exact work-order, work-order-item, vendor, measurement date, quantity, rate and amount lineage;
- only rejected/sent-back measurements can be revised; no generic economic UPDATE route was found.

`src/modules/subcontract/raBills/raBills.service.js` is stronger than several prior ScopeSignal comparators:
- `getPendingMeasurements()` selects only exact-work-order measurements with `status: "certified"`, `is_latest_revision: true`, and no RA-bill item whose bill is still economically live (anything other than cancelled/rejected).
- `createRaBill()` repeats the exact-work-order + `certified` + not-already-live-billed predicates inside a Prisma transaction; a caller cannot directly supply bill-item quantity or rate.
- gross bill amount is the sum of persisted measurement amounts; retention/tax/advance/deductions are then computed centrally.
- created RA-bill items retain stable `measurement_id` lineage.
- global code search found `rABill.create` and `rABillItem.createMany` only in this RA-bill service (normal create plus controlled revision), unlike the generic-CRUD bypass seen in InfraLedger.
- routes expose one RA-bill POST path calling this service; there is no generic PATCH/DELETE CRUD surface in the inspected route file.

This is real progress versus prior candidates: exact evidence identity, exact work-order identity, server-derived economics, app-level sequential replay exclusion, and a relatively closed application mutation surface coexist in one path.

## VALIDATOR / STATE-MACHINE VERIFIER — decisive falsification
The intended path is not currently proven reachable through the repository's own validated HTTP API.

`measurements.service.js` defines these status transitions:
- `draft -> submitted | cancelled`
- `submitted -> checked | rejected | sent_back`
- `checked -> approved | certified | rejected | sent_back`
- then approved/certified -> archived.

But `measurements.validation.js` allows the status API body to contain only:
- `draft`, `checked`, `certified`, `rejected`.

`measurements.controller.js` always applies that validator before calling `updateMeasurementStatus()`, and `measurements.routes.js` exposes that controller as the status mutation route.

Therefore a freshly created `draft` measurement cannot legally request `submitted` through the validator, while requesting `checked` or `certified` passes the validator but is rejected by the service's transition graph. Global search found no other `updateMeasurementStatus` call path and no other `workMeasurement.update` path that advances this lifecycle.

**Constructed counterexample:** create a valid measurement (state=`draft`) and POST any validator-accepted next status. `checked`/`certified` are rejected by the service because `draft` can only move to `submitted`/`cancelled`; `submitted` cannot pass request validation. Thus the repository's own normal API cannot establish the `certified` state required by `createRaBill()` unless data are seeded/mutated outside the inspected route path.

This is a materially different failure mode from prior generic-CRUD bypasses: **authority can be perfectly checked at the money transition and still be non-operational because the trusted evidence state is unreachable.**

## PERIOD / ONE-USE VERIFIER
Two additional gaps prevent promotion:
1. **Bill-period authority is not tied to evidence time.** `createRaBill()` accepts caller-supplied `periodStart`/`periodEnd`, but its measurement query filters by ID, exact work order, certified status and prior bill usage; it does not require `measurement_date` to fall inside the requested period. A certified January measurement can therefore satisfy the inspected bill-creation predicates for a June bill period.
2. **One-use is application-level, not durable at the DB boundary.** The active-bill relationship predicate blocks ordinary sequential re-use after the first bill item exists, which is better than Nirman's and InfraLedger's previously inspected paths. However, code/schema search found no `@@unique([measurement_id])` / equivalent unique one-use constraint, no explicit row lock on the selected measurements and no Serializable isolation setting. Two concurrent transactions can therefore plausibly both observe `ra_bill_items: none` before either creates its bill item. This is a source-level race concern, not a reproduced database race, so label it **UNVERIFIED BUT PLAUSIBLE** rather than TESTED.

## Independent RED-TEAM / VERIFIER verdict
