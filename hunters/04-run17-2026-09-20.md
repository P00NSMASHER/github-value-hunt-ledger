### CODE INSPECTOR — positive evidence
1. **Trusted measurement state is production-reachable.** `save_measurement_book()` creates/edit Draft measurement books. `certify_measurement_book()` is a whitelisted application transition that stamps the current user and sets status `Certified`; `get_wo_measurements()` includes only Certified books in measured-to-date. This is materially stronger than the prior Constructor ERP candidate whose trusted state was unreachable through its validated API.
2. **Reachability is tested.** `test_measurement_book.py::test_certify_feeds_measured_and_locks_editing` creates a Draft MB through the production save API, certifies it through the production certify API, proves the Certified quantity enters measured-to-date, and proves normal editing is blocked until explicit revert. Separate tests prove Draft is the initial state, certification is idempotent, multiple Certified books accumulate, and revert intentionally reopens editing.
3. **Work-order bill draft lines are server-derived.** In `save_bill()`, Work Order bills ignore client-supplied bill lines and call `doc.fetch_lines()`. `fetch_lines()` iterates the Work Order schedule-of-values lines, loads Certified measured-to-date, subtracts previously submitted bill quantity, takes the stored Work Order rate, and computes `this_period_amount = qty × rate`.
4. **Commercial source must be committed.** `SubcontractorBill.validate()` requires a Work Order bill to reference a submitted Work Order (`docstatus == 1`).
5. **Accounting transition is real.** Submitted Subcontractor Bills generate an ERPNext Purchase Invoice; tests cover generation, cancellation behavior, payment-entry linkage, retention and prior-billed roll-forward.
6. **Positive integration tests exist.** `test_wo_bill_derives_from_measurement_book` proves 40 certified units at Work Order rate 85 become gross 3,400 and a submitted bill creates a Purchase Invoice. `test_previously_billed_rolls_forward` proves a submitted 40-unit bill followed by an additional 30 certified units gives the next fresh bill `previous_qty=40`, `this_period_qty=30`.

### SCHEMA / AUTHORITY INSPECTOR — decisive gaps
#### 1. Deterministic stale-draft sequential replay at submit
`previously_billed_by_line()` counts only **submitted** Subcontractor Bills. `fetch_lines()` is called when the draft bill is saved/fetched, but `SubcontractorBill.validate()` / `before_submit()` do **not** call `fetch_lines()` or otherwise recompute measured-to-date minus newly submitted predecessors. `submit_bill()` simply reloads the stored draft and calls `doc.submit()`.

Constructed source-level counterexample:
1. Certified measured-to-date for WO line L = 40; no submitted bills.
2. Save Draft Bill A → derived `this_period_qty=40`.
3. Save Draft Bill B before A is submitted → also derived `this_period_qty=40`.
4. Submit A → 40 becomes submitted/billed.
5. Submit stale B afterward → submit-time hooks do not re-derive lines against the now-updated prior-billed state, so the stored 40 remains eligible for submission.

This is a **sequential post-commit replay**, not merely a speculative simultaneous race. The repository has a positive roll-forward test where the second bill is created only after the first has submitted, but no inspected test for two drafts materialized before the first submit.

VERDICT: exactly-once economic consumption is **not established**.

#### 2. Bill authority is aggregate, not evidence-specific
`Subcontractor Bill Line` stores Work Order line, measured-to-date, previous quantity, current quantity and rate, but not a stable Measurement Book / Measurement Book Entry identity. Bills therefore consume a cumulative aggregate rather than one immutable accepted evidence record.

VERDICT: no durable `measurement_id -> bill_item_id` lineage / one-time evidence consumption was verified.

#### 3. Certified evidence can be reverted and rewritten after it has supported billing
`revert_measurement_book()` intentionally changes Certified back to Draft and clears the certifier; the repository's own test proves the reverted MB becomes editable again. The inspected revert path does not first prove that no submitted bill depends on that Certified evidence, and submitted bill lines do not preserve the exact MB/version that supported them.

Adversarial scenario: certify MB=40 → submit a bill using the resulting 40 → revert the MB → edit quantity/evidence → recertify. The financial document remains while the currently authoritative field-evidence object can now tell a different story.

VERDICT: post-bill evidence immutability/version binding is **not established**.

#### 4. Temporal authority is absent
The bill schema has a posting/date field but no bill-period start/end identity tied to Measurement Book dates. `get_wo_measurements(work_order)` sums all Certified books for the Work Order with no date cutoff. A backdated bill draft can therefore derive from a later-dated Certified measurement unless another external control intervenes.

VERDICT: `measurement_date <= authoritative bill cutoff / within billed period` is **not enforced by the inspected path**.

#### 5. Exact field-entry ownership validation is weaker than the UI picker suggests
`save_measurement_book()` accepts entry `work_order_line` values and the MeasurementBook controller validates project/company anchoring, but the inspected save/controller code did not re-load each entry's Work Order line to prove it belongs to the selected Work Order or independently cap cumulative measured quantity to the Work Order line quantity. The bill derivation itself iterates the actual Work Order lines, which limits direct wrong-line monetization, but the upstream evidence store can still contain structurally invalid measurement references.

VERDICT: evidence-store integrity is weaker than the positive billing path.
