## CODE INSPECTOR — positive evidence
1. **Bills bind exact measurement-item paths, not merely aggregate quantity.** `BillData.mitems` stores paths of billed measurement items in `[cmb][measurement][measurement item]` form. `Bill.update()` resolves each stored path back to the exact measurement item and derives schedule-item quantities from the measurement's calculated totals.
2. **Prior-bill roll-forward is explicit.** `Bill.update()` imports prior-bill quantity into the current bill, computes normal/excess quantity and rate treatment, and calculates `bill_since_prev_amount` from current cumulative net less the previous bill's net total.
3. **Cross-reference identity is preserved through structural renumbering.** `DataModel.update_static_paths()` rewrites bill measurement paths when CMB/measurement/item positions shift after insertion/deletion. This is a real lineage mechanism, not just a displayed reference string.
4. **Already-billed measurement items are excluded from a second normal bill selection.** `DataModel.update()` builds a global `LockState` by unioning every bill's `get_billed_items()`. `BillDialog` computes `locked = get_lock_states() - this_bill_selected`; its toggle callback refuses selection when `locked[path] == True`. Thus an item already referenced by another bill is unavailable for ordinary re-selection while editing/creating a bill.
5. **The implementation is directly about public-works quantity accounting.** README describes schedule → measurements/CMB → bills, selected measurement items, part/excess rates, previous-bill support, PDF/XLSX output, deviation statements. Changelog records RA-bill form support and prior fixes for bills breaking when schedule/measurements were modified.

## SCHEMA / HISTORY INSPECTOR — decisive limitation
CMB Automiser's item identity is an in-memory/project-file path, not an immutable database evidence ID. The path-rewrite machinery is useful for local referential consistency, but it is not append-only provenance or multiuser transactional consumption.

The most important failure is stronger than that:

### Billed evidence can be edited in place
The ordinary measurement-view `edit_selected_row()` path does not check whether the item is already bill-locked. It calls `DataModel.edit_measurement_item()`, whose implementation mutates the referenced measurement object and then calls `self.update()`. Because existing bills resolve their stored `mitems` back to the current measurement object during update, editing a measurement item that already supports a bill can retroactively change the existing bill's derived quantity/amount.

### Billed evidence can be deleted and historical bill support silently disappears
`MeasurementsView.delete_selected_row()` directly calls `DataModel.delete_row_meas(path)` without a bill-lock gate. Before deletion, `update_static_paths(path, False)` walks every bill; when a billed measurement path is in the deletion set it removes that path from `bill.data.mitems`. The measurement object is then deleted and `self.update()` recomputes bills.

This is a crisp negative oracle: the system tracks exact billed measurement-item identity and prevents ordinary *second selection*, but a later source-evidence edit/delete can rewrite the historical money record instead of creating a versioned correction/counter-event.

### UI lock is not lifecycle immutability
The measurement tree displays a `Billed?` lock flag, and bill selection honors that flag. However the main application callbacks `OnMeasDeleteClicked` and `OnMeasEditClicked` call the measurement view delete/edit functions directly; the inspected edit/delete implementations contain no lock-state rejection. A visual/selection lock is therefore not equivalent to a governed evidence-mutation boundary.
