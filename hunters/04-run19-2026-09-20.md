### Why it matters
SiteMate independently implements two patterns that EXP-005 needs:

1. **Copy-on-write commercial baseline versioning.** Approved/submitted/locked BOQs are snapshotted before business-field edits. The prior BOQ is copied to an inactive locked historical record, a revision record is created, the active BOQ version increments, and the active record reopens as Draft. BOQ-line create/write/unlink operations also trigger this snapshot behavior.
2. **Append-oriented economic consumption with explicit counter-events.** `construction.boq.consumption` stores exact BOQ line, `source_model`, `source_id`, quantity, amount, date and user. The model revokes database `UPDATE` and `DELETE` on the ledger table. Vendor-bill posting locks BOQ lines with `SELECT ... FOR UPDATE`, appends positive consumption for invoices, and appends negative consumption for refunds rather than mutating an existing entry. Tests explicitly exercise negative refund-style consumption and subsequent restored capacity.

This is a stronger correction model than the mutable-history behavior seen in CMB Automiser and BuildSuite: a reversal can be represented as a new economic event instead of silently rewriting the original one.

## CODE / SCHEMA INSPECTOR — positive evidence
### Copy-on-write BOQ snapshots
`models/boq.py` defines `version`, `previous_boq_id`, a Draft→Submitted→Approved→Locked→Closed state vocabulary, and `create_revision_snapshot()`. For business changes to Submitted/Approved/Locked BOQs, the implementation copies the old BOQ to an inactive Locked historical BOQ, creates a `construction.boq.revision`, increments the live record's version, points `previous_boq_id` to the snapshot and reopens the live record as Draft. BOQ-line create/write/unlink also invoke the snapshot before changing governed lines.

### Append-only consumption intent
`ConstructionBOQConsumption` stores:
- exact `boq_line_id` with `ondelete='restrict'`;
- `source_model` and `source_id`;
- quantity and amount;
- date and user.

Its `init()` executes `REVOKE UPDATE, DELETE ON construction_boq_consumption FROM PUBLIC;`, which is a meaningful database-layer historical-integrity measure rather than a UI-only lock.

### Money/event transition with locking and counter-events
`models/account_move.py::action_post()`:
- locks every affected `construction_boq_line` using `SELECT ... FOR UPDATE` before validating and appending consumption;
- derives positive consumption from invoice lines;
- uses a negative sign for refunds;
- appends the resulting ledger records before calling the ordinary accounting post transition.

This is an explicit correction-as-counter-event pattern: a refund adds negative quantity/amount instead of editing the original consumption row.

### Tests
`tests/test_security_boq.py` verifies direct consumption inside limits, rejection when amount/quantity exceeds limits, incremental limit enforcement, and negative consumption as a refund that restores capacity for a later positive consumption. This gives the append/reversal semantics real regression evidence, unlike many construction billing repos inspected in previous runs.

## Independent RED-TEAM / VERIFIER — decisive provenance failure
**DO NOT PROMOTE TO STRONG.** The ledger is append-oriented, but its counter-events are not sufficiently provenance-bound.

### Arbitrary callers can create ledger events
`security/ir.model.access.csv` grants both `group_site_engineer` and `group_project_manager` `perm_create=1` on `construction.boq.consumption`. The model's `create()` validates budget bounds, but it does not resolve or authenticate `source_model`/`source_id`, does not require the referenced source to exist or be in a terminal/accounting state, and defines no uniqueness constraint over `(source_model, source_id, boq_line_id)`.

### Negative counter-events are generically creatable
The test suite deliberately creates a negative consumption record directly with a synthetic `source_model='test.model'` and arbitrary source ID, then treats the resulting restored capacity as valid. That proves negative append semantics, but also demonstrates the missing provenance gate: a negative event is accepted because it is negative, not because it is an authoritative refund/reversal of a specific prior source event.

### Append-only is therefore not enough
An immutable log can still be economically false if actors can append unsupported negative events. EXP-005 must require **provenance-bound counter-events**: the reversal must point to a real prior event/source, be type-compatible with it, have bounded quantity/amount, be unique/idempotent, and be emitted only from an authoritative correction transition.

### No source-event idempotency
There is no inspected `_sql_constraints` or equivalent uniqueness over `source_model + source_id + boq_line_id`. `account.move.action_post()` is normally governed by Odoo's one-way posting state, which reduces ordinary duplicate invocation risk, but the ledger itself does not make source-event replay impossible and its generic create permission bypasses that lifecycle assumption.

### BOQ snapshot caveat
The copy-on-write BOQ versioning is useful, but the economic consumption row still references the live `construction.boq.line` identity rather than an immutable BOQ-line-version ID. When an approved BOQ is revised, the old BOQ is copied to new historical line objects while the original active BOQ/line identities continue into the new Draft version. Thus downstream consumption tied to the original line ID is not automatically bound to the copied historical baseline version that was authoritative when the event occurred. The snapshot preserves a historical copy, but the event→exact-baseline-version edge is not explicit.

### CI / deployment evidence
The exact head has one successful GitHub Actions run, but that workflow is deployment-only: it SSHes to a server, pulls the repository and restarts Odoo. It does **not** run the repository test suite. Therefore exact-head deploy success is operational evidence, not test evidence.

## SEARCH POLICY UPDATE
Refine the existing historical-evidence mutation audit with a **provenance-bound counter-event audit**:
1. Identify whether corrections/reversals append new rows rather than mutate accepted rows.
2. Verify the correction row points to a real authoritative prior event or source object/version.
3. Verify that source lifecycle/state is checked at the transition creating the correction.
4. Require uniqueness/idempotency for the source event or correction edge.
5. Require quantity/value bounds so one reversal cannot exceed the event being reversed unless a governed adjustment type permits it.
