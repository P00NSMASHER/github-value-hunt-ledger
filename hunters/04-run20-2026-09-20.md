## Candidate B — OpenConstructionERP finance ledger reversal subsystem
**Canonical:** https://github.com/datadrivenconstruction/OpenConstructionERP

**Revision:** `5622fe9a63e3811ebfa1d11c405d1635b5967cdf`

**Public license/provenance:** AGPL-3.0; public GitHub repository. User standing repository-code commercial authorization also applies per system instruction.

**Category:** construction-adjacent immutable accounting counter-events.

### CODE INSPECTOR
The ledger model stores `project_id`, transaction reference, source type/id, `is_reversal`, exact `reversal_of_id` FK, and an idempotency key. `reverse_ledger_transaction()` appends new reversal rows instead of changing the originals, mirrors every leg of the prior journal, swaps debit/credit amounts, links each reversal row to the exact original row, and uses a deterministic reversal idempotency key plus DB unique-index race backstop.

### HISTORY VALIDATOR
Commit `d3bbd8b71f29c73064738f1d6579abce6b6efa1c` (2026-06-15) fixed a real historical defect where only the first debit/credit legs were reversed; current code now mirrors every journal leg. Separate history also records fixing oversized reversal idempotency keys. This is meaningful production-shaped archaeology, not just README claims.

### TEST VALIDATOR
Unit tests prove balanced/unbalanced posting, basic immutable reversal behavior, exact account/amount mirroring and missing-transaction rejection. A targeted search did not find regression tests for same transaction reference reused in different projects or cross-project reversal scoping.

### RED-TEAM / VERIFIER — scope alias counterexample
**Verdict: WATCH / NEGATIVE CONTROL, NOT STRONG.** The router authorizes the caller-supplied `project_id`, then calls `reverse_ledger_transaction(transaction_ref, project_id=...)`. Inside the service, both the already-reversed lookup and original-entry lookup are filtered by human-readable `transaction_ref` and reversal flag but not by project. The reversal idempotency key is derived from `transaction_ref + ':rev'`, also without project scope. Because the ledger has only a non-unique `(project_id, transaction_ref)` index, the same transaction reference can legitimately exist under multiple projects.

Source-level counterexample: if Project A and Project B both contain `TXN-001`, a reversal request authorized for Project A is not source-proven to select only A's original rows; the service query can match both projects, then the write path applies the caller's project to the generated reversal rows. Conversely, an existing reversal under one project can alias an otherwise independent reversal request under another project. This was not executed as a live exploit; it is a source/schema authority failure.

## Combinations discovered

`immutable measurement_version_id`
→ `exact project/contract/work-order/BOQ-line + baseline_version`
→ `unique accepted effect(project, source_document, source_item, source_version, effect_type)`
→ `exactly-once bill_item consumption`

## Failures / negative knowledge
- A `reversal_of_id` field is insufficient when the lookup that chooses the original event is not scoped.
- A deterministic idempotency key is unsafe as an authority identity if it omits project/tenant scope.
- Append-only + unique can still point to a nonexistent prior event if referential integrity is not enforced somewhere authoritative.
- Human-readable refs should not be assumed globally unique across construction projects.
- Schema/source evidence does not substitute for direct replay/cross-scope regression tests.

## Search policy update
For every future correction/reversal design, inspect four independent identity layers:
1. **lookup scope** — how the original event is selected;
2. **idempotency scope** — what fields form the replay/correction key;
3. **DB uniqueness** — what duplicate source effects/reversals the database rejects;
4. **referential integrity** — whether the counter-event must point to a real prior accepted event in the same authority scope.

Always add an adversarial case where two projects reuse the same human-readable reference. Do not promote this as a new central `SEARCH_SKILLS.md` skill yet.
