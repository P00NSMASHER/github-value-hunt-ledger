## Active hypothesis
**Hypothesis:** A production-shaped government-contractor ERP may contain a strong exact Measurement Book→RA Bill identity and server-derived billing path, but the more valuable failure mode is authority drift: the trusted measurement state may be reachable through an unsafe creation path, the approval→bill transition may not be atomic, and a later redesign may create a new primary billing path that bypasses Measurement Book authority entirely.

**Status:** SUPPORTED at source/schema/history level in `coolabhi991/ap-os@b68e9686e008fffa6dafdcabc9196b08cfcb32f3`.

**Supporting evidence:**
- Legacy Measurement Book billing requires an `APPROVED` MB, reloads persisted MB rows server-side, and persists `RunningBill.measurementBookId` under a database unique constraint, giving an unusually strong one-MB→one-bill identity.
- `updateMB()` makes Approved MBs immutable and auto-invokes bill creation when status transitions to `APPROVED`.
- However, MB approval is committed inside one Prisma transaction and `createRunningBillFromApprovedMB()` is called only after that transaction returns, so approval and bill creation are not one atomic transaction.
- `createMB()` accepts caller `status`, passes it through `parseStatus`, and can directly create an `APPROVED` MB; its POST controller passes `req.body` directly and the route is guarded only by authentication. This path does not auto-create the corresponding bill.
- The current primary Form 58 path is explicitly documented in source as replacing Measurement Book for new UI billing. It sets `measurementBookId: null` and can create new Site Bill Item master rows from the billing request itself.
- The payment endpoint can directly create `RunningBillPayment`, update `amountReceived`, and derive `PARTLY_PAID/FULLY_PAID` without requiring a source BankTransaction; a bank-origin pointer exists only when the payment came through Transaction Allocation.

**Contrary evidence / caveat:**
- The legacy MB path has several excellent controls: Approved-only state, immutability after approval, server-side quantity/rate derivation, non-deletable MB-sourced bills, and a schema-level unique MB→RunningBill edge.
- The current Form 58 path does preserve historical rates by snapshotting SiteBillItem rate into bill lines, and it scopes SiteBillItems to Site/Sub Work.
- The identified approval→bill seam is a source-level atomicity failure; no live failure was induced.

### What is genuinely strong
The old Measurement Book→Running Bill chain is one of the better source-level authority patterns found in this lane:
- MB statuses are `DRAFT → SUBMITTED → APPROVED`.
- Approved MBs cannot be edited or deleted.
- `createRunningBill()` reloads the exact MB by `id + companyId`, requires `status === APPROVED`, rejects empty MBs, and derives bill rows from persisted MB items rather than caller-supplied bill economics.
- `RunningBill.measurementBookId` is backed by a database unique index, so an MB cannot be linked to two RunningBill rows even under sequential/retry paths.
- MB-sourced bills cannot be deleted, preventing a simple delete-and-rebill replay.

This is real build compression for a reference design: trusted state, immutable accepted evidence, server-side derivation, durable source identity, and one-to-one consumption are all represented.

### Authority drift #1 — trusted state can be created directly
`createMB()` stores `status: parseStatus(input.status)`. A caller may therefore create a new MB already marked `APPROVED`; the creation path does not invoke `createRunningBillFromApprovedMB()`. The controller passes `req.body` directly to the service and the route applies authentication but no inspected transition-specific validator.

This means the state machine is not closed-world: `APPROVED` is both a governed transition target and a creatable initial state.

### Authority drift #2 — approval and bill creation are not atomic
`updateMB()` commits the MB mutation in `prisma.$transaction(...)`; only after the transaction returns does it call `createRunningBillFromApprovedMB()`. If the process or downstream bill creation fails after approval commits, an `APPROVED` but unbilled MB can exist despite the source comment asserting that approval should never commit without billability.

The schema unique constraint protects duplicate MB→bill consumption once a bill row exists; it does not make the approval and bill insertion one atomic effect.

### Authority drift #3 — the controlled path is legacy
The running-bill source explicitly labels Form 58 as the **current, primary** path and the Measurement Book flow as **legacy, retired from the UI**. `createRunningBillFromForm58()` sets `measurementBookId: null` and derives bill lines from `SiteBillItem` master rows. A new row may be created from bill-request description/unit/rate and then becomes a Site Bill Item master row for future bills.

Thus a strong legacy evidence chain does not prove the current money-bearing workflow still requires independently approved field measurement. The system evolved past its strongest authority invariant.

### Authority drift #4 — payment state can outrun bank evidence
The repository's blueprint says banking is the heart / financial truth, and the DTO preserves a `sourceBankTransaction` pointer when a payment was created from Transaction Allocation. But `POST /running-bills/:id/payments` also permits a direct manual payment. `recordRunningBillPayment()` creates a RunningBillPayment and updates `amountReceived`, `outstandingAmount`, and the derived status to `PARTLY_PAID`/`FULLY_PAID` without requiring a source BankTransaction. Therefore internal paid state is not synonymous with independently observed bank settlement.

### Line-identity caveat
Legacy MB items are identified by `boqItemNo` / optional Sub Work rather than a stable contract BOQ-line foreign key. Source comments explicitly note that MB item IDs are deleted/recreated on save and that audit history is keyed by `boqItemNo` because item IDs do not survive edits. This weakens immutable per-line evidence/version identity even though an approved MB itself becomes immutable.

## Emerging technology signal
This run strengthens the same authority-aware operational software thesis with a new failure class: **authority drift across product evolution**. A system can possess an excellent one-time evidence→money invariant and later route new work around it without deleting the old code. Static architecture review can therefore over-credit controls that are no longer authoritative in the active path.

No radar-score increase from this run alone.

## Failure / negative knowledge
- Database uniqueness on source evidence does not make the transition that creates source state + money state atomic.
- A status transition can be well controlled while direct object creation still mints the trusted state.
- Historical/legacy controls do not deserve production authority credit when a newer primary route bypasses them.
- Stable document identity at the parent MB level does not equal stable per-line evidence/version identity when child IDs are recreated on edit and matched by strings.
- An internal `FULLY_PAID` label can remain weaker than an independently observed bank event even inside a system whose stated design treats banking as the source of truth.
- No-test repositories can still be valuable adversarial oracles, but evidence quality must remain capped.
