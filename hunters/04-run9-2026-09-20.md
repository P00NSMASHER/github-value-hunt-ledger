# Hunter 04 — Run 9 — 2026-09-20

## Run objective
Close the highest-value missing edge in ScopeSignal/EXP-005: determine whether a construction system makes **approved field measurement an authoritative, server-side prerequisite for billed quantity/value**, then trace the resulting bill into approval and payment state.

## Explicit hypothesis
A commercially useful ScopeSignal bridge should enforce, on the authoritative server path:

`authorized BOQ/work-order line -> field measurement -> required approval state -> bill quantity/value derived from that measurement -> bill approval -> payable/payment state`

Client-only warnings, hidden UI buttons, or a bill that merely mentions a measurement do not satisfy the hypothesis.

## FINDING A — DIGIT-Works follow-up: authoritative measurement-to-purchase-bill gate FALSIFIED

### Artifact
- Repository: `egovernments/DIGIT-Works`
- Exact revision: `7c44e963c7aced16d648971ae66eb938cbe8fdc4`
- Prior status remains: strong component for contract-bounded measurement.
- New narrower claim status: **REJECTED / FALSIFIED** — purchase-bill creation is not proven to be server-gated by APPROVED measurement.

### What was verified
- `ExpenseCalculatorService.createPurchaseBill` validates a caller-provided purchase bill and invokes `PurchaseBillGeneratorService`; unlike the wage-bill path, it does not first load approved measurement records.
- `ExpenseCalculatorServiceValidator.validateCreatePurchaseRequest` checks request/basic bill fields but does not validate measurement IDs, measurement workflow status, measurement quantity, measurement-to-bill linkage, or an approved-measurement ceiling.
- The `PurchaseBill` model contains contract/project/bill-details/workflow/payment-related fields but no authoritative measurement reference field.
- `PurchaseBillGeneratorService` calculates from caller-provided bill details plus contract/charge information. In the inspected path, no measurement status is fetched to derive the authoritative billed quantity.
- The browser UI does fetch measurement information through `useMBDataForPB`, but that helper defines a valid measurement as anything whose `wfStatus` is **not `DRAFTED` and not `REJECTED`**. It does not explicitly require `APPROVED`.
- The purchase-bill UI uses measurement-derived totals as a warning/confirmation boundary, not as a demonstrated unbypassable backend invariant.
- The inspected expense-calculator backend test tree contains only `TestConfiguration.java`; no substantive regression test was found proving an approved-measurement purchase-bill gate.

### Evidence classification
- Server-side bill creation from provided bill details: **IMPLEMENTED**.
- Client measurement summary / warning: **IMPLEMENTED**.
- APPROVED-only server-side measurement prerequisite: **FALSIFIED / NOT IMPLEMENTED in inspected path**.
- Direct regression test of such a gate: **NOT FOUND**.

### RED-TEAM verdict
**REJECT the bill-gate claim.** Keep DIGIT as a strong measurement component and an excellent EXP-005 negative control.

The critical lesson is that **UI measurement awareness is not authority**. A downstream commercial-assurance product should explicitly flag purchase bills that lack approved-measurement provenance or exceed an independently reconstructed approved-measurement ceiling.

### Negative knowledge
- `status != DRAFTED && status != REJECTED` is not equivalent to `status == APPROVED`.
- A confirmation modal is not a commercial control if the backend accepts a direct caller-provided amount/line structure.
- “Measurement exists in the same product” does not establish `measurement -> billed quantity` provenance.

## FINDING B — senecaSparsh/nirman

### Repository / provenance
- URL: https://github.com/senecaSparsh/nirman
- Exact revision: `0e40fbada98a7448c4d74b1cbd4252da76c9183e`
- Date inspected: 2026-09-20
- Attention level: one GitHub star observed; repository created 2026-08-15 and actively pushed through 2026-09-19.
- Public license metadata: none observed at the inspected revision. The user's standing separate commercial authorization for directed public GitHub repository code applies to this investigation; do not infer rights to independently owned statutes, datasets, services, trademarks or other third-party material.
- Status: **STRONG COMPONENT / REFERENCE — 26/30**; not MASTER-ready yet.

### What it contains
A functioning construction subcontractor commercial chain:

`BOQ -> Measurement Book DRAFT -> VERIFIED -> APPROVED -> approved + unbilled MB entries -> RA bill -> SUBMITTED -> APPROVED -> AP/retention/TDS accounting -> PAID`

Important server-side properties inspected:
- MB creation requires positive measured quantity and rejects cumulative VERIFIED/APPROVED quantity above the BOQ estimated quantity.
- MB verification requires `DRAFT`; MB approval requires `VERIFIED`.
- Non-tier-1 measurers cannot verify/approve their own entry.
- `createRaBill` queries only MB entries with `status: "APPROVED"` and `raBillLineId: null` for BOQ items present on the work order.
- Bill quantity is derived from those MB entries; bill rate is derived from the work-order line's agreed rate. The caller does not provide arbitrary bill line quantities/rates through the inspected public RA-bill POST input.
- MB entries are atomically claimed to RA-bill lines with an `raBillLineId: null` predicate; a concurrent partial claim aborts with conflict rather than silently double-billing.
- RA-bill approval requires `SUBMITTED`, updates work-order cumulative quantities/amounts, creates project cost and posts accounting entries for WIP/AP/TDS/retention.
- RA-bill payment requires `APPROVED`, marks the bill `PAID`, updates work-order paid totals and posts `Dr AP / Cr Cash` internally.
- Code search found a single `raBill.create(...)` source path in the repository, strengthening confidence that the service method is the central creation path.

### Tests / verification depth
- `self-approval-guards.test.ts` contains service-level tests for MB self-verification/self-approval separation-of-duties controls.
- RA API route tests cover authentication, permissions, validation and route behavior, but mock `createRaBill`; they do **not** independently prove the APPROVED-only MB gate.
- `subcontractor.test.ts` is shallow for the commercial state machine (payment-mode constants only).
- No direct regression test was found for the exact negative invariant `DRAFT/VERIFIED/REJECTED MB cannot enter an RA bill`.
- Current-head repository workflow activity was observed, but the inspected current workflow evidence did not prove the RA-bill logic suite itself ran. Do not silently upgrade source implementation to tested correctness.

### Why unusual / commercially valuable
The uncommon part is not another construction ERP screen. It is a fairly explicit **quantity-authority chain** in source: approved field evidence becomes the allowed input to an RA bill; billed quantity is derived server-side; measurement rows are claimed to a bill; bill approval creates accounting consequences; payment settles the payable.

This supplies a strong design reference for ScopeSignal's missing `proof -> authoritative money state` bridge.

### Buyer / painful problem
- Buyer: GC, EPC, quantity-surveying team, construction finance/controller, owner PMO, subcontractor-payables audit team.
- Pain: billed subcontractor quantities can drift from approved field measurements, be attributed to the wrong work order, fall outside the billed period, duplicate prior quantities, or reach internal “paid” status without independently verified cash settlement.

### First paid wedge
**Subcontractor RA Bill Assurance Audit**:
1. ingest 20-50 RA bills, work orders/BOQ lines and measurement-book entries;
2. reconstruct each billed quantity from approved measurements;
3. recompute value from authorized work-order rates;
4. flag unapproved/no-measurement quantities, cross-work-order attribution, out-of-period measurements, repeated claims, cumulative BOQ excess, deduction mismatches and internally marked-paid items without external clearing evidence;
5. produce an evidence packet per exception.

### Build/domain advantage
High. The inspected state machine supplies a concrete reference for MB states, cumulative quantity control, RA-bill calculation, atomic claim semantics, retention/TDS/advance deductions, bill approval and payable settlement.

### RED-TEAM / VERIFIER objections
Nirman survives as STRONG, but **not as a complete proof-to-cleared-cash system**:

1. **Key gate is implemented but not directly regression-tested.** The service source filters `APPROVED` and unbilled MB rows, but no located test directly attempts to bill DRAFT/VERIFIED/REJECTED rows.
2. **Work-order state is too permissive.** `createRaBill` rejects CANCELLED/CLOSED but does not require ISSUED/ACTIVE, so a DRAFT work order appears billable if qualifying MB rows exist.
3. **Potential cross-work-order attribution ambiguity.** MB rows are tied to project/BOQ item and later to an RA-bill line; they are not directly bound to a subcontractor work-order line at measurement creation. If the same BOQ item participates in multiple work orders, first claimant may not necessarily be the economically correct work order.
4. **Billing period is not enforced against measurement date.** `periodFrom <= periodTo` is checked, but the inspected MB query does not constrain `measureDate` to that period.
5. **Atomic claim prevents double billing, not wrong billing.** `raBillLineId: null` is an excellent race/deduplication control but says nothing about entitlement or correct commercial owner.
6. **`PAID` is internal bookkeeping, not cleared-bank proof.** `payRaBill` changes internal state and posts GL based on an authorized action/payment reference. No external bank/treasury settlement confirmation was verified.
7. **Tier-1 self-approval is allowed by design.** OWNER/ADMIN can auto-approve in some paths; this may be operationally reasonable but is not strict segregation of duty.
8. **Jurisdiction-specific rules require separate validation.** TDS percentages/statutory treatment should be configurable and separately validated; repository code is not legal authority.

### Final verifier verdict
**ACCEPT STRONG, 26/30, as an implementation/reference component.**

Promote the architectural pattern, not the unsupported stronger claim. The verified claim is:
> Within the inspected RA-bill creation path, bill quantity/value is server-derived from APPROVED, unbilled measurement-book entries and authorized work-order rates, with atomic measurement-to-bill claiming and downstream internal accounting/payment state.

Do **not** claim:
> the system proves correct work-order entitlement, enforces measurement-period inclusion, or confirms externally cleared cash.

### Combination opportunities
`BIMChange-Agent/OpenTakeoff -> ScopeSignal contract/notice evidence -> DIGIT-style contract-bounded measurement -> Nirman-style APPROVED-measurement-to-RA-bill derivation -> Prova/Beam/Motif/LienGuard-style outcome proof`

The combined design should improve on Nirman by adding explicit measurement->work-order ownership, period inclusion, superseded-baseline handling, external payment confirmation and held-out negative tests.

## FAILURES / NEGATIVE KNOWLEDGE
- Stop treating client-side warnings as commercial authority.
- Stop accepting “not draft/rejected” as a proxy for approved.
- An atomic no-double-bill lock does not prove correct work-order/subcontractor attribution.
- A bill period field is meaningless for proof if source measurements are not filtered/validated against it.
- Internal `PAID` plus GL posting is not equivalent to bank-cleared payment.
- Another generic IPC/pay-app UI is low-value unless it proves a missing authority invariant.
