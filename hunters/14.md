### open-eid/SiVa
- URL: https://github.com/open-eid/SiVa
- Exact commit / revision: `0c9c5f2490b1a27798b47906bbaa6adb4d26daad`
- Date inspected: 2026-09-19
- Status: strong / trust-validation component
- Score: **25/30** — A3 first revenue, B4 ceiling, C5 domain compression, D4 rarity, E5 evidence/completeness, F4 rights clarity. Revenue is indirect because this is a validation subsystem rather than a standalone managed-service wedge, but it closes a high-value proof-integrity gap.
- Concrete capability: Production-oriented digital-signature validation service for XAdES/CAdES/PAdES/ASiC and timestamp-bearing containers. It validates trusted certificate chains, timestamp message imprints, OCSP/CRL evidence, revocation-token status and revocation freshness; it uses trusted-list certificate sources and exposes detailed diagnostic/report schemas.
- Rare / undernoticed value: Recovery Proof already has RFC 3161 token creation/offline verification patterns, but its queue still lacks production-grade trust-chain/revocation semantics. SiVa contains years of real validation-policy engineering around exactly the dangerous distinction between “timestamp signature parses” and “timestamp/revocation evidence is actually trusted and temporally valid.”
- Likely buyer / painful problem: regulated SaaS/MSPs/audit evidence services that need cryptographically defensible evidence packages; auditors and insurers need more than a self-signed or locally trusted timestamp claim.
- Monetization / first paid wedge: Use the validation patterns as the verification side of a managed Continuous Assurance Evidence package: externally timestamp the signed restore/compliance bundle, then independently validate chain/trust/revocation/freshness before the evidence is accepted as current. First paid wedge is an evidence-integrity add-on to a recovery-readiness audit, not a standalone signature-validation product.
- Build-time/domain advantage: Estimated 2–4+ months saved on certificate/timestamp/revocation validation semantics, trusted-list plumbing, freshness edge cases, diagnostic schemas and negative-test design.
- Evidence inspected: `README.md` at the pinned revision; `RevocationFreshnessValidator.java`, which requires timestamp/revocation token signature integrity, valid/trusted chain and good certificate status, compares timestamp production time to CRL `nextUpdate` / OCSP production time, and warns when OCSP freshness exceeds 15 minutes; `TokenUtils` search confirms the trusted-chain predicate; docs/config search confirms European trusted-list/LOTL sources and explicit stale-trust-list handling; unit/integration/system-test structure is documented.
- Actual public license / third-party rights: EUPL v1.1. Validation depends materially on DigiDoc4J / the Open-EID DSS fork and European trusted-list infrastructure; those third-party code/data/trust-service terms remain separate diligence items.
- User-asserted commercial-permission posture: Per the standing hunt instruction, assume separate commercial permission exists for SiVa repository-owned code/content despite the public EUPL terms; do not extend that assumption to DigiDoc4J/DSS, EU trusted lists, certificates, trust-service APIs or other independently owned material.
- Combination opportunities: `audit-labs/evidence-seal` or another RFC3161 issuer/client produces the token → SiVa-style trust/revocation validation decides whether that token is acceptable → Production Readiness Checklist/OpenWright binds the verified timestamped digest to the exact evidence/config → Evidentia/OSCAL packages the result.
- Next action: Build a synthetic timestamp-validation fixture with valid chain, untrusted root, expired TSA cert, revoked signer, stale CRL, stale/future OCSP, wrong message imprint and unavailable revocation material; define which states must hard-fail versus remain explicitly indeterminate.
