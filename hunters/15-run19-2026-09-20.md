### What is actually implemented
Wazuh now persists the agent identity under which state was last synchronized (`synced_agent_id`) and compares that against the process-global identity that stamps outgoing sync sessions. Current syscollector identity tests explicitly distinguish four materially different states:
- marker absent after an in-place upgrade -> **adopt current ID without a fleet-wide resync**;
- current ID equals prior synchronized ID -> **no-op** (the common re-enrollment/key-rotation case where identity did not change);
- current identity unavailable/unknown -> **do nothing**, never interpret absence as change;
- current ID differs from the prior synchronized ID -> **resend enabled inventory on the correct protocol lane and only advance the marker after successful recovery**.

The tests also explain why a failed marker read must remain UNKNOWN instead of being folded into "never recorded": falsely adopting the new ID in that window would suppress the required resync permanently. The associated merged recovery work covers syscollector, SCA and FIM rather than one narrow table.

### Why this matters to Recovery Proof
The prior CAP-010 identity rule — "different fresh hard IDs => conflict" — is too coarse. Wazuh demonstrates a legitimate **same-workload/new-agent-generation** transition: after deletion on the manager, an endpoint can re-enroll under a new agent ID while the local workload and its inventory remain the continuing subject. Treating every fresh agent-ID change as a new workload would duplicate the census; treating it as ordinary field drift would lose the generation boundary and could carry stale proof forward.

The correct Recovery Identity Authority needs a first-class edge such as:

`SAME_SUBJECT -> IDENTITY_SUCCESSION(old_agent_id, new_agent_id, reason=re_enrollment) -> REPROVE_REQUIRED`

A successful succession must preserve old->new history, invalidate proof tied to the prior generation until state is republished/re-observed, and must not silently mint a second workload.

### Evidence beyond README
- Current `src/wazuh_modules/syscollector/tests/sysCollectorImp/syscollector_identity_tests.cpp` contains explicit tests for absent marker adoption, unchanged ID no-op, unknown ID no-op, failed marker read non-adoption, and changed-ID resend on the correct protocol lane.
- Current source carries separate synchronized-ID markers and comments documenting why identity freshness and lane state are tracked separately.
- PR #38623 records end-to-end testing on real Amazon Linux 2023 and Ubuntu 22.04 agents after deletion/re-enrollment: inventory was restored under new agent IDs and the recovery path had to distinguish first-scan/VD semantics from ordinary synchronization.

### Strongest objection
Wazuh's agent ID alone does not prove that the re-enrolled endpoint is the same business workload. The source demonstrates **how a known endpoint system handles its own identity generation change**, not a universal cross-source merge rule. Recovery Coverage Authority must authorize succession only when a stronger or independently governed continuity witness exists (for example cloud instance identity, VM inventory identity, or approved replacement lineage).

### Commercial implication
This materially improves the Backup Coverage Census / Recovery Proof SLA product: endpoint reinstall/re-enrollment can become a governed **generation transition** instead of denominator churn, while stale recovery proof is invalidated until the new generation is re-observed and re-proven.

## MINIMAL ADVERSARIAL IDENTITY CORPUS FOR EXP-004
The following corpus is now specific enough to implement before any further broad CMDB search.

1. **Concurrent strong-ID contradiction**
   - Observation A: cloud instance `i-A`, hostname `web-01`, public IP X.
   - Observation B: cloud instance `i-B`, same hostname/public IP X, both fresh and concurrently valid in the same issuer/account scope.
   - Expected: `IDENTITY_CONFLICT`; automatic merge forbidden even if weak features strongly agree.

2. **Legitimate agent succession**
   - Stable workload witness: same cloud/VM native identity.
   - Endpoint/EDR agent ID changes from `agent-old` to `agent-new` through an explicit re-enrollment/reinstall lifecycle event.
   - Expected: one canonical workload with `IDENTITY_SUCCESSION(old,new)`; prior agent-generation proof becomes stale and new-generation observation/re-proof is required.

3. **Credential rotation without identity rotation**
   - Same source-authoritative agent ID; key/password/token changes.
   - Expected: no new subject and no identity succession. Proof freshness may be separately evaluated, but census cardinality is unchanged.

4. **Cloneable hardware identifier collision**
   - Two concurrent VMs/containers expose the same DMI/SMBIOS/hardware UUID while runtime/container/native IDs differ.
   - Expected: `IDENTIFIER_COLLISION`; hardware ID downgraded from unique authority in that scope and may not merge the subjects.

5. **Copied local identity cache**
   - Device/database image copied to new hardware; cached local UUID remains old while an independent hardware/control-plane witness changes.
   - Expected: `SOURCE_DISAGREEMENT`; cached local identity cannot override fresh independent control-plane identity.

6. **Identity source unavailable**
   - Metadata/provider read fails or source collection is partial during a suspected ID change.
   - Expected: `UNOBSERVED/PARTIAL`; do not adopt a new identity, do not tombstone the old one, and do not make the coverage denominator green.

7. **Duplicate canonical hard ID**
   - Two already-canonical workloads acquire the same source-authoritative stable ID in an overlapping validity interval.
   - Expected: hard `DUPLICATE_AUTHORITY_CONFLICT`; block proof aggregation until reviewed/split/corrected.

8. **Retired/replaced workload with explicit lineage**
   - Old cloud/VM identity terminates; approved replacement has new native identity and an explicit owner/governed replacement link.
   - Expected: not a merge. Preserve `REPLACED_BY` lineage; old subject retires at an explicit effective time and new subject receives its own proof obligation.

## Identity contract refinement
The identifier schema should no longer have a single `strength=hard|weak` field. It needs at least:
- `issuer/source` and tenant/account/region scope;
- `identifier_kind`;
- `cardinality_assumption` (`one_to_one`, `cloneable`, `unknown`);
- `lifecycle_class` (`lifetime_bound`, `installation_generation`, `credential`, `generated_persistent`, `ephemeral`);
- `observed_at`, `valid_from`, `valid_to`/freshness;
- `observation_provenance` (control plane, hardware read, local cache, agent, scanner);
- `generation` or explicit predecessor/successor edge when applicable;
- contradiction state and adjudication provenance.

### Proposed fail-closed states
`MATCHED`, `AMBIGUOUS_REVIEW`, `IDENTITY_CONFLICT`, `IDENTIFIER_COLLISION`, `IDENTITY_SUCCESSION_PENDING_REPROOF`, `SOURCE_DISAGREEMENT`, `UNOBSERVED/PARTIAL`, `RETIRED`, `REPLACED_BY`.
