## BEST NEW FIND — carabiner-dev/ampel

Repository: https://github.com/carabiner-dev/ampel
Exact revision: `5cf19bc2786cbd73a8423383a966fbf842222d23`
Public license: Apache-2.0
Category: evidence admission / policy evaluation / signed verification-result attestation
Score: **28/30 — A4 B5 C5 D4 E5 F5**

### Concrete capability

Ampel is unusually close to a reusable proof-admission kernel for CAP-007:
- verifies signed evidence before policy evaluation;
- supports policy-level or policy-set-level signer identities;
- rejects/discards evidence whose signer does not match pinned identities;
- tests that policy-pinned identities override looser CLI identity inputs;
- rejects unsigned/unverified evidence by default;
- only permits explicitly supplied unverified evidence under an explicit `AdmitUnverified` mode, and that mode does not override pinned signer identities;
- enforces optional policy expiration;
- can emit signed result attestations in its native format, SLSA VSA, or in-toto SVR form;
- binds the result attestation to the evaluated subject and a policy-origin ResourceDescriptor;
- explicitly refuses to summarize a `SKIP` as VSA/SVR because no verification took place.

The implementation tests are stronger than the README. `pkg/verifier/implementation_test.go` includes wrong-identity, mixed-identity, all-unverified, unsigned, policy-over-CLI-precedence, and explicit-unverified cases; `TestCheckPolicy` checks expired-policy rejection. `pkg/attest/attest_test.go` checks output predicate dispatch and subject binding. `pkg/attest/svr.go` rejects skipped results and writes policy origin into the verification-result predicate.

### Important fail-open boundary

Ampel also exposes a valuable negative control: **CLI process success is not the same as proof success.** Its documented/default CLI semantics exit 0 on `SKIP` unless `--fail-skip` is set. This is intentional because no applicable policy failed. At the same time, the SVR/VSA attestation path refuses to attest a skipped result.

For Recovery Proof this must be hardened into an invariant:

`PASS/PROVEN != process exit 0`

A Recovery Proof adapter must consume the semantic result state or require `--fail-skip`; it must never treat a bare zero exit code as evidence that any required recovery obligation actually applied.

### Standards caveat

Ampel currently emits in-toto SVR **v0.1** (`https://in-toto.io/attestation/svr/v0.1`). The current in-toto Simple Verification Result specification is v0.2 and now requires `verifier.policies` as an array of ResourceDescriptors. Do not copy Ampel's current wire format unchanged for a new Recovery Proof evidence contract; use the current v0.2 shape and preserve exact policy digests.

### Commercial impact

Ampel materially compresses the build for a **Proof Admission Gateway** inside Recovery Proof:
- buyer: regulated SaaS/MSP/platform/security/compliance team;
- painful problem: evidence can be correctly signed yet still be the wrong evidence, signed by the wrong authority, skipped by applicability rules, or evaluated under stale policy;
- first paid wedge: wrap one customer's Recovery Proof drill so the final `PROVEN` state requires signed admissible evidence, pinned signer identity, non-skipped applicable policy, and a signed standard verification result;
- money path: higher-value audit evidence, reduced manual evidence review, reduced false-green risk, stronger insurer/auditor defensibility;
- build compression: months of signer/evidence admission, policy evaluation and result-attestation plumbing already exist;
- moat remains the Recovery Proof negative-control corpus and exact authority semantics, not Ampel itself.

### Strongest objection

Ampel alone is not enough for CAP-007. It has policy expiration, but the inspected surface does not replace the TUF/Uptane-style highest-seen anti-rollback and snapshot-consistency authority already identified. It also intentionally allows SKIP to be a successful process exit by default. Recovery Proof must compose Ampel-like admission with the existing TUF/Uptane currentness envelope and a mandatory semantic non-SKIP gate.

## OTHER STRONG CANDIDATE — in-toto/in-toto

Repository: https://github.com/in-toto/in-toto
Exact revision: `e352b43ad7cb8915d84c36d791aa61346152a0a3`
Public license: Apache-2.0
Score: **27/30 — A3 B5 C5 D4 E5 F5**

Why it matters: classic in-toto supplies the missing **authorized-functionary + threshold + artifact-agreement** model. Its `in_toto_verify` path verifies layout signatures, layout expiration, authorized link signatures, distinct-functionary thresholds, sublayouts, artifact agreement/rules and inspections before declaring verification passed.

Key source/test evidence:
- unauthorized/invalid link signatures are ignored rather than counted;
- fewer than the required distinct authorized functionaries causes `ThresholdVerificationError`;
- two subkeys under the same master do not count as two independent threshold votes;
- expired signing keys are skipped in the GPG threshold test path;
- functionaries at a threshold must agree on materials/products or verification fails;
- root layout expiry is a hard failure;
- all checks complete before the final pass state.

Transfer to Recovery Proof: define the obligation as a signed layout-like object in which each required evidence class names its authorized functionary set and threshold. A validly signed restore report from an unauthorized role must not count.

Limit: in-toto explicitly leaves key lifecycle/revocation policy outside its isolated verification workflow, and classic layout verification does not itself supply TUF-style monotonic policy-version rollback protection. Pair it with CAP-007's TUF/Uptane authority envelope rather than treating it as a complete currentness layer.

## IMPORTANT CURRENT NEGATIVE ORACLE — sigstore/cosign

Repository: https://github.com/sigstore/cosign
Current inspected revision: `0c66ecdff337f647bbcb0259efe61a81e33a76e8`
Public provenance: Sigstore open-source project; repository license should be preserved separately if promoted.
Role in this run: current implementation + repeated historical false-green class, not a new standalone product candidate.

### Why this matters

A high-value failure class recurred in 2026: **valid signature != correct attestation type**.

GitHub Advisory GHSA-w6c6-c85g-mmv6 / CVE-2026-39395 reported that affected `cosign verify-blob-attestation` versions could report success for malformed payloads or mismatched predicate types under certain verification modes. Patched versions are 3.0.6 and 2.6.3.

The current revision now performs an explicit post-verification predicate-type check on both new-bundle and legacy paths: it converts the attestation for the requested predicate type and hard-fails when the resulting payload is nil, reporting expected vs observed predicate type.

This is especially important because the same conceptual error existed earlier in Sigstore policy-controller / CVE-2022-35930: at least one validly signed attestation could produce a false positive even when no attestation of the requested type existed. Current policy-controller code at `e0d5d701087c020419738d69e2d2eac2ca715c4b` explicitly iterates the wanted attestation predicate types, only appends matching checked attestations, and hard-fails with `no matching attestations` if none survive. Its tests include a `wrong predicate keyless attestation, error` case.

**Emergence conclusion:** attestation-type confusion is not a one-off historical bug. It is a recurring verifier failure class across adjacent Sigstore verification surfaces, separated by years. It belongs in the permanent CAP-007/EXP-004 adversarial corpus.

Safety note: only the defensive failure pattern and patched/current behavior were recorded. No exploit workflow or vulnerable target instructions are retained.

## STANDARD SIGNAL — in-toto Simple Verification Result v0.2

Current specification: https://github.com/in-toto/attestation/blob/main/spec/predicates/svr.md
Predicate type: `https://in-toto.io/attestation/svr/v0.2`

The current vetted SVR standard is a useful output envelope for Recovery Proof because it records:
- the subject artifact/resource;
- a versionable verifier identity;
- the exact policy artifacts used (`verifier.policies`, now required in v0.2);
- verification time;
- the properties the verifier asserts were checked.

The specification explicitly treats SVR as a concise result, not a self-contained reproduction package. Therefore a Recovery Proof SVR should be an index/summary pointing to the deeper signed Recovery Proof bundle, not the only evidence retained.

Commercial implication: emitting a standard SVR alongside the richer Recovery Proof evidence package would improve interoperability with supply-chain/evidence tooling without weakening the domain-specific proof contract.

## INDEPENDENT SYNTHETIC INTEGRATION TEST

To answer the prior run's exact question, I built a minimal local Ed25519 proof-admission model combining the identified semantics:
- root-signed policy metadata;
- monotonic policy version / highest-seen check;
- expiration;
- snapshot ID binding;
- exact subject digest;
- exact predicate/evidence type;
- authorized functionary set;
- distinct-signer threshold.

Eight cases were executed:

| Case | Expected | Observed |
|---|---|---|
| correct current bundle, 2 authorized signers | PROVEN | PROVEN |
| policy bytes changed after signing | reject | `POLICY_SIGNATURE_INVALID` |
| validly signed expired policy | reject | `POLICY_EXPIRED` |
| validly signed lower-than-highest-seen version | reject | `POLICY_ROLLBACK` |
| evidence from different snapshot generation | reject | `SNAPSHOT_MIX` |
| correctly signed evidence from unauthorized functionary | reject | `WRONG_AUTHORITY_ROLE` |
| correctly signed evidence with wrong predicate/type | reject | `WRONG_PREDICATE_TYPE` |
| only one valid signer where threshold=2 | reject | `THRESHOLD_SHORTFALL` |

Result: **8/8 expected outcomes.** This is a synthetic contract test, not a claim that the external repositories were executed together. It demonstrates that the combined CAP-007 + EXP-004 gate is small enough to implement and independently falsify.

The strongest proof-admission composition is now:

`TUF/Uptane currentness envelope`
→ `in-toto-style authorized roles + threshold + artifact agreement`
→ `Sigstore-style exact predicate/type + signer identity verification`

A final Recovery Proof result may become `PROVEN` only if all layers are current, applicable, type-correct, role-authorized, semantically correct and durably preserved.

## CLAIMS TESTED / FALSIFIED

1. **Falsified:** a valid cryptographic signature is enough to make evidence admissible. Wrong predicate/type has produced real false-green verifier bugs in both 2022 and 2026.
2. **Falsified:** process exit code 0 is sufficient proof that a policy passed. Ampel intentionally exits 0 on `SKIP` by default.
3. **Supported:** role/functionary authorization plus distinct threshold can be enforced before pass; in-toto implements and tests this.
4. **Supported:** a skipped/non-applicable policy should not be emitted as a positive standard verification result; Ampel refuses VSA/SVR output for SKIP.
5. **Supported by synthetic test:** currentness, snapshot consistency, exact evidence type, authorized role and threshold can coexist in one small fail-closed PROVEN gate.

## FAILURES / NEGATIVE KNOWLEDGE

- Do not infer `PROVEN` from a successful process exit; semantic PASS must be explicit.
- `SKIP` / not-applicable is not PASS.
- Signature validity does not imply signer authority.
- Signer authority does not imply evidence-type admissibility.
- Correct evidence type does not imply current policy version.
- Current signed policy does not by itself imply snapshot consistency.
- A concise SVR/VSA result is not sufficient reproducibility evidence; retain the deeper proof bundle.
- Do not emit Recovery Proof SVR v0.1 just because a current implementation does; the current in-toto spec is v0.2 and requires policy references.
- Classic in-toto key verification is intentionally isolated and is not a substitute for external revocation/currentness authority.
