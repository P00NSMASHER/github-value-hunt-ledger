## EXP-004 RUN 22 — local integrated admission matrix

### Execution substrate

A local isolated SQLite restore test-double was used because this automation runtime has no Docker, Podman, PostgreSQL server/client or container runtime, and its container network cannot resolve GitHub for cloning. This is therefore **not** a FireDrill Docker/PostgreSQL E2E execution and does not complete EXP-004.

The test-double deliberately mirrors FireDrill's verified E2E semantics and evidence shape:
1. write a SQL backup containing 5,000 ledger rows plus a canary token;

4. close/delete the isolated database and require sandbox destruction before proof publication;
5. serialize a FireDrill-compatible evidence record;
6. wrap that evidence in a DSSE in-toto Statement using FireDrill's exact predicate type and PAE construction;
7. apply the CAP-007 authority/admission envelope;

### Authority/admission contract executed

The local verifier used deterministic Ed25519 keys and required:
- root signature over the exact canonical policy bytes;
- unexpired policy;
- policy version not below local highest-seen version;
- exact snapshot ID agreement between policy and evidence catalog;
- exact recovery-evidence SHA-256 binding;
- exact DSSE digest binding;
- FireDrill DSSE signature from the policy-authorized evidence signer;
- exact FireDrill recovery predicate type;
- two distinct authorized functionary approvals where threshold = 2;
- explicit semantic `PASS` (not process exit 0);
- recovery evidence `verified=true`;
- every semantic check passed and none skipped;
- cleanup/sandbox destruction proven.

Only after those checks did the harness emit an in-toto Statement v1 with predicate type `https://in-toto.io/attestation/svr/v0.2`, a versioned verifier ID, required policy ResourceDescriptor with exact SHA-256, verification time and recovery-proof properties.

## SVR REPLAY / PUBLICATION TEST

The correct case produced a current SVR v0.2 summary plus the full proof bundle. A separate replay verifier then checked:
- SVR predicate type;
- required nonempty `verifier.policies`;
- exact policy-envelope digest referenced by the SVR;
- exact subject/evidence digest;
- presence of the full underlying DSSE evidence, policy, evidence catalog and approvals.

Results:
- untouched correct bundle -> `REPLAY_OK`;
- mutate the policy bytes after the SVR was issued -> `SVR_POLICY_DIGEST_MISMATCH`;
- remove an underlying proof component while leaving the SVR intact -> `MISSING_FULL_PROOF_BUNDLE`.

This experimentally validates the intended split: **SVR is a concise positive result/index; the complete proof package remains required for independent replay.**

## BEST NEW FIND / CAPABILITY DELTA

**Name:** Fail-closed SVR Publication Gate for Recovery Proof.

**Value:** the admission kernel is small enough to execute as a deterministic pre-publication state machine. Recovery evidence can be semantically correct yet still remain non-PROVEN for policy tamper, expiry, rollback, snapshot mix, wrong authority, wrong predicate, threshold shortfall or SKIP. Conversely, one coherent current bundle can produce a current-standard SVR whose policy reference survives independent digest replay.

**Working capability score:** 29/30 as architecture/experiment value, **not** a new repository promotion. The score reflects build compression and assurance value; commercial adoption remains unproven.

## CLAIMS TESTED / FALSIFIED

1. **Supported in integrated execution:** currentness, exact evidence type, signer authority, distinct threshold, snapshot consistency and semantic applicability can coexist in one small deterministic gate.
2. **Falsified:** process exit 0 can stand in for proof PASS. The explicit SKIP case exited 0 yet could not publish `PROVEN`.
3. **Supported:** an SVR policy ResourceDescriptor can bind the exact policy-envelope bytes; post-publication policy mutation is independently detectable.
4. **Supported by local contract:** an SVR alone is insufficient for Recovery Proof replay; removing an underlying proof component prevents replay even when the SVR itself remains intact.
5. **Not yet proven:** that the same 9/9 matrix survives unchanged when the subject artifact is emitted by an actual FireDrill Docker/PostgreSQL run. Runtime lacked Docker/PostgreSQL, so this remains the next test rather than being silently upgraded to complete.

## COMBINATION DISCOVERED

`FireDrill semantic recovery artifact`
→ `TUF/Uptane-style currentness / highest-seen policy state`
→ `in-toto-style authorized functionary threshold`
→ `exact FireDrill predicate + authorized evidence signer`
→ `explicit PASS/FAIL/SKIP admission`
→ `SVR v0.2 positive summary referencing exact policy bytes`
→ `full proof-bundle replay`
→ `proof-sink durability / external trust`.

The crucial architectural rule is now experimentally sharper: **negative states should fail before positive-result publication, rather than publishing a signed “failure result” into the same trusted-positive channel.** Failure/UNKNOWN/SKIP can still be durably recorded as operational evidence, but they must not be represented as a positive SVR carrying recovery-proof properties.
