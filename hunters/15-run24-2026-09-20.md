## BEST NEW FIND

**Name:** Recovery Qualification Receipt v0 + behavior-closure transfer gate

**Why it matters:** Exact Git SHA is excellent provenance but too coarse as the only qualification-currentness rule: demanding a paid/slow recovery drill after every irrelevant documentation edit would over-invalidate, while inheriting a historical green result across unbounded dependency/workflow/runtime changes is unsafe. Recovery Proof therefore needs two identities at once:

1. **Exact provenance identity** — repository + immutable commit SHA.
2. **Derived behavior-closure identity** — a digest computed from the exact workflow/harness, runtime dependency locks, restore/verifier/proof code, E2E tests and setup/tool pins that can change the behavior being qualified.

A qualification may transfer only when the new subject is the exact qualified SHA **or** a trusted path recomputes an identical behavior-closure digest from the current executable/configuration. A receipt-carried or hand-declared digest is insufficient by itself; the identity must be derived from the code/configuration actually about to issue proof.

**Score:** **29/30 as a capability/experiment refinement, not a repository promotion.** A4 speed to revenue, B5 buyer value, C5 build/domain compression, D5 rarity/assurance advantage, E5 evidence/falsifiability, F5 operational clarity.

## Proposed Recovery Qualification Receipt v0

Minimum machine-readable shape:

```text
receipt_version
subject:
  repo
  commit_sha                 # exact provenance
  closure_digest             # derived behavior identity
closure_inputs:
  workflow_blob_sha
  makefile_blob_sha
  dependency_lock_digests    # go.mod + go.sum or ecosystem equivalent
  restore_engine_tree_sha
  verifier_tree_sha
  proof/report_tree_sha
  sandbox_tree_sha
  e2e_test_tree_or_manifest
  setup_script_digests
  external_tool_image_versions
execution:
  run_id
  job_id
  started_at
  completed_at
  stage_reached
  harness_result
  subject_semantic_result
  proof_sink_result
  cleanup_result
qualification:
  exact_subject_match
  closure_match
  verdict
```

Recommended stage ordering:
`NONE -> CHECKOUT -> HARNESS_READY -> SUBJECT_STARTED -> SUBJECT_COMPLETE -> PROOF_PERSISTED -> CLEANUP_COMPLETE`.

Recommended terminal qualification states:
- `QUALIFIED`
- `NO_CURRENT_QUALIFICATION`
- `HARNESS_FAILED`
- `RECOVERY_FAILED`
- `PROOF_PERSISTENCE_FAILED`
- `CLEANUP_FAILED`
- `INVALID_RECEIPT`

All states except `QUALIFIED` are non-`PROVEN`, but the failure locus must remain visible.

## Transfer rule
A previous qualification can satisfy currentness only when one of these is true:

1. `current.commit_sha == qualified.commit_sha`; or
2. a trusted recomputation over the **current** behavior-bearing subject produces `current.closure_digest == qualified.closure_digest`.

The closure digest must not be accepted merely because an upstream manifest says it is the same. The qualification gate should derive/recompute the identity from the current execution artifacts/configuration before using it. This joins the Recovery Proof qualification boundary with the broader consequence-boundary lesson that declared executor identity is weaker than derived executor identity.

Any closure mismatch produces `NO_CURRENT_QUALIFICATION` until a new E2E receipt exists, unless a narrower machine-verifiable closure rule explicitly proves the changed component is outside the qualified behavior. Start conservative; optimize neutral-drift precision only after negative-control coverage exists.

## FAILURES / NEGATIVE KNOWLEDGE
- Git SHA alone is provenance, not a semantic equivalence proof.
- Historical green E2E cannot qualify a revision whose behavior closure has changed.
- A declared `closure_digest` is not trustworthy unless recomputed from the current executor/verifier/configuration.
- Unit/lint/fuzz success cannot replace a real restore drill.
- Harness failure before subject start must not be reported as failed recovery.
- Closure lists that are too broad cause expensive neutral-drift invalidation; lists that are too narrow create stale-proof risk. Begin fail-closed and add precision only with covered-change and neutral-change regression cases.
