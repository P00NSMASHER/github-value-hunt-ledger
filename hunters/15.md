### gitdr-io/gitdr — recovery success and proof persistence are separate control states
- URL: https://github.com/gitdr-io/gitdr
- Exact commit / revision: `c9d15a2bfc18460ea46ba864410a4f9ca012f278`
- Date inspected: 2026-09-20
- Category: Repository / Reusable Component / Business Opportunity
- Status: **exceptional strong / MASTER referral**
- Score: **28/30 — A5, B5, C5, D5, E4, F4.**
- Concrete capability: scheduled Git recovery drill that restores repositories from signed manifests, compares source-advertised ref state to bundle state and restored state, and emits a signed drill report beside the backup evidence. Crucially, the engine models a broken restore and a successfully restored estate whose signed report could not be durably stored as two different failures; neither returns clean success.

The latter must fail on source-vs-bundle history even though artifact restoration itself succeeds.
- Proof-path value: `ErrDrillFailures` and `ErrReportNotStored` are joined rather than collapsed. The CLI returns a distinct exit state when restores pass but the proof cannot be filed, making the evidence-delivery path itself an observable assurance control rather than an afterthought.
- Buyer / painful problem: GitHub/GitLab-heavy SaaS teams, MSPs and regulated engineering organizations that can show backup jobs but cannot prove exact repository history restores or that recovery evidence itself is durably retained.
- Monetization / first paid wedge: **Source-Code Recovery Proof SLA** — restore a deterministic sample/all repositories, verify signed source→bundle→restored ref equality, deliberately inject one damaged/missing-history case in a synthetic fixture, and report both recovery and evidence-retention status monthly/quarterly.
- Build-time/domain advantage: roughly 4–7 months of signed manifest/report contracts, reproducible Git history comparison, restore orchestration, missing-history negative controls and proof-storage failure semantics.
- Evidence inspected: `internal/pipeline/drill.go`, `internal/pipeline/drill_test.go`, `internal/cli/drill.go`, exact LICENSE at inspected commit. Implementation and tests were inspected beyond README; full live external-provider drill was not independently rerun in this hunt.
- Actual public license / provenance: GNU AGPL v3. User's separate commercial permission applies to repository-owned public code/content; Git hosting providers, customer repositories and credentials remain separately governed.
- Combination opportunities: add gitdr's **proof-persistence non-pass** to CAP-010/EXP-004 beside devicechain wrong-state controls, nearai verifier mutation, mukuroji non-Postgres semantics and SiVa/GuardSpine trust validation. Recovery should not be eligible for green status if the signed proof cannot be durably filed.
- Strongest objection: repository history is unusually content-addressable, so its exact ref equality proof does not generalize automatically to mutable databases or SaaS control planes.
- Next action: add `proof_sink_unavailable_after_successful_restore` as a mandatory EXP-004 control; the workload recovery may be recorded as successful, but overall assurance must remain non-green.

## Run learning / hypothesis — 2026-09-20 proof-14
- **Active hypothesis:** Recovery Proof needs two additional first-class assurance dimensions beyond restored data correctness: **proof-path durability** and **post-restore security-state correctness**. Confidence: high.
- **Supporting evidence:** gitdr refuses a clean exit when the signed proof cannot be stored; bombvault distinguishes destructive-probe protected/vulnerable/inconclusive; RustyAuth deliberately revokes restored sessions/rotates signing state; Olivares proves the evidence ledger and signer custody themselves survive host loss; Accounted/Verity show ACL/authorization state can make a data-correct restore unsafe.
- **Contrary evidence:** these controls are still fragmented across workload families. No single portable harness proves data correctness, history, immutable storage, proof persistence, verifier self-test, authorization/security state and evidence-ledger trust in one run.
- **Experiment impact:** extend EXP-004 with (6) proof sink unavailable after otherwise successful restore; (7) data correct but stale session/authorization/trust remains active; (8) evidence ledger restored but signer/checkpoint custody invalid. Overall assurance may be non-green even when workload restoration itself succeeded.
- **Negative knowledge:** stop treating report generation/storage as bookkeeping. A recovery engine can be operationally correct while the assurance system is unable to prove it. Also stop equating restored data with safe recovery when sessions, ACLs, signer state or authorization chronology are independently stateful.
- **Cross-lane referral to MASTER integrator:** evaluate `gitdr-io/gitdr@c9d15a2...` as a 28/30 CAP-010/EXP-004 proof-path-strengthening component and `rusty-auth/rustyauth@a1311b2...` as a security-state recovery pattern. Exact unanswered question: should the common Recovery Proof contract model `RECOVERED_BUT_UNPROVEN` as a distinct terminal state that is operationally successful but assurance-noncompliant?
- **Search method result:** productive were exact PASS/exit-state archaeology, destructive-control searches and security/control-plane restore semantics. Generic backup product searches remain low value; next search should target proof-sink failure, stale-session/revocation recovery, identity/control-plane resurrection and independent evidence-store failure.
