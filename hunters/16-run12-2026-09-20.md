### Concrete capability
Business Central now exposes a reusable, explicit allocation graph rather than a header-level three-way-match boolean. `PO Matching` constructs edges between invoice line, exact purchase-order line, and exact posted receipt line. `PO Matching Group` persists/reloads those edges and separately enforces invoice capacity, order-line remaining-to-invoice capacity, and receipt-line received-not-invoiced capacity. `Invoiceable Receipts` enumerates only receipt lines for the exact order number + order line whose received quantity remains uninvoiced, then subtracts capacity already consumed by the current group.

### Verified implementation evidence
Inspected:

- `.../POMatchingGroup.Codeunit.al`
- `.../InvoiceableReceipts.Codeunit.al`
- `src/Layers/W1/Tests/ERM/POMatchingGroupTests.Codeunit.al`

Verified **IMPLEMENTED + TESTED** invariants:
1. Exact IDs: edges use invoice-line, order-line and receipt-line `SystemId`; receipt validation also proves the receipt belongs to the exact `Order No.` + `Order Line No.`, not merely the same SKU.
2. Independent conservation budgets: an edge cannot exceed invoice-line quantity, the PO line's quantity remaining to invoice, or the receipt line's quantity received but not invoiced.
3. A pair budget cannot be reduced below receipt quantities already pinned to that invoice↔order pair.
4. `SaveMatchingGroups()` revalidates the merged graph against current source documents immediately before persistence; a previously-valid graph is rejected if external posting consumed capacity in the meantime.
5. Persisted allocations are loaded into a fresh group and count against new allocations, preventing a new session from silently reusing already-committed capacity.
6. A single receipt can be split across two invoice lines and stored as distinct per-invoice receipt edges.
7. Ambiguous receipt assignment is fail-closed: a bare order↔receipt edge errors if more than one invoice could own it rather than guessing.
8. Receipt rows are a second allocation layer and are intentionally excluded from invoice-cap summation so the same allocation is not double-counted simply because receipt evidence is attached.
9. Item-tracked receipt lines must be invoiced in full; partial pinning is rejected because the code cannot safely restate which lots/serials are represented.
10. Negative allocations are rejected.

### External currentness / ecosystem check
Microsoft Learn's 2026 Wave 1 documentation independently describes the same new matching surface: one invoice line can match multiple PO lines and posted receipt lines; partial receipts, missing receipts and multiple order references are supported. The feature's current documented limitations matter: it does not support blanket-order-linked orders and auto-receive is unavailable for already-partially-received lines. Treat BCApps as a strong allocation oracle, not a universal AP model.

### Strongest objection
Business Central's semantics are not universal procurement law. The matching feature excludes blanket orders and several other order types, and receipt-less matching can be allowed depending on configuration/workflow. SAP service procurement can make accepted Service Entry Sheets authoritative, but can also permit invoicing without an SES depending on PO verification flags. Therefore the reusable object is the **allocation graph and conservation invariants**, surrounded by a policy-resolved authority layer—not Business Central's exact workflow copied wholesale.

### Valuable semantics
`purchase_work_acceptance` implements a service/goods acceptance document linked to purchase-order lines, with acceptance state and optional enforcement on receipts and vendor bills. The README explicitly says only accepted products/services may be received/invoiced when enforcement is enabled. `purchase_blanket_order` gives each blanket line its own linked purchase-order lines and computes original, ordered, invoiced, received and remaining quantities; tests distinguish two same-product blanket lines via exact line/date selection and include company isolation.

### Red-team result — important line-collapse defect
The Work Acceptance gate is **not safe as an exact line-level oracle** in the inspected posting paths. Both receipt validation and vendor-bill validation aggregate accepted and posted quantities by `product_id`. Two distinct PO lines carrying the same product can therefore be substituted while aggregate product quantity still matches. This is precisely the class of false authority EXP-002 must reject. The module itself is marked **Alpha / development or testing only**.

### Commercial use
Retain the service-acceptance and blanket-order concepts as adversarial/reference fixtures, not as the production authority engine. Add a planted test with two same-product PO lines where WA accepts quantities `[4,6]` but invoice/receipt uses `[5,5]`; aggregate-by-product logic must fail our oracle even though OCA's current gate can accept the aggregate.
