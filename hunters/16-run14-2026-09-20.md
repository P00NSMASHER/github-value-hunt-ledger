### Concrete implementation evidence
`src/Layers/W1/BaseApp/Purchases/History/UndoReturnShipmentLine.Codeunit.al` implements a guarded reversal path for posted purchase return shipments:

1. **Already-reversed and already-invoiced states are blocked before mutation.**
   - The undo code filters out correction lines, raises `AlreadyReversedErr` if the selected posted return line is already a correction, and rejects undo when `Return Qty. Shipped Not Invd.` is not equal to the posted quantity. The explicit message states that Undo Return Shipment is allowed only for posted but not invoiced return shipments.
   - This is a critical semantic boundary: once financial consumption exists, a physical undo is no longer the legal counter-event path.

2. **The correction points back to the exact original inventory posting.**
   - `PostItemJnlLine` builds a correction item-journal line and sets `Applies-to Entry` to the original `Item Shpt. Entry No.` when available.
   - `InsertNewReturnShptLine` copies the original posted return line, emits a new line with the exact negative quantity/base quantity, sets `Appl.-to Item Entry` to the original item shipment entry, marks it `Correction = true`, and preserves the dimension set.
   - History is therefore additive: the original posted line remains and an explicit opposite-signed correction line is added.

3. **The exact return-order line is updated, not a same-SKU aggregate.**
   - `UpdateOrderLine` does an exact `Purchase Line.Get(Return Order, Return Order No., Return Order Line No.)` and passes that line plus exact quantities into `UndoPostingMgt.UpdatePurchLine`.
   - Warehouse undo lookup is likewise keyed by source document type, return order number and return order line number.

4. **The posting is one-time and quantity-bounded.**
   - The original line becomes `Correction = true`, and its `Quantity Invoiced` / `Qty. Invoiced (Base)` are set to the posted quantity while `Return Qty. Shipped Not Invd.` is zeroed after undo.
   - A second undo of the same economic posting is blocked. This is stronger than merely attaching a `reverses_event_id` field.

5. **Tests exercise the undo surface.**
   - The W1 SCM and Job test suites invoke `UndoReturnShipmentLine`; search results include a fixed-asset test whose THEN step explicitly verifies quantity after Undo Return Shipment.
   - The production code plus test surface and Microsoft Learn behavior agree on the main invariant: posted receipt/return quantity can be undone before invoicing by adding a corrective line and updating the related order line; invoiced flows require a financial correction path instead.

### First-party external corroboration
Microsoft Learn (current 2026 docs) states:
- Undo receipt/return shipment is for posted quantity that is **not yet invoiced**; undo inserts a corrective posted line and resets the related order's received/shipped-not-invoiced quantity.
- Purchase return orders can use **Get Posted Document Lines to Reverse** to copy exact posted lines and preserve exact cost reversing; manual exact cost reversing uses `Appl.-from Item Entry` to bind the return to the original purchase entry.
- Correct/cancel of a posted purchase invoice creates a corrective purchase credit memo; on a partial invoice cancellation the originating PO line's `Qty. to Invoice` and `Quantity Invoiced` are reset to their pre-partial-posting state.

### Why this matters beyond Business Central
The important reusable primitive is not “undo return shipment.” It is **reversal-capacity conservation**:

> Every original authority/allocation edge has a finite reversible residual. Counter-events consume that residual exactly once. Merely referencing the original edge is insufficient.

This is a second-order conservation law. Forward capacity prevents over-billing a receipt. Reverse capacity prevents over-crediting, double-cancelling, double-returning or repeatedly reopening the same authority.

## SYNTHETIC FALSIFIER — original-reference-only design is insufficient
A small synthetic authority ledger was built locally with exact Decimal quantities and explicit line/event IDs. The first version required every return/credit/cancel to reference an original edge and correctly blocked cross-line ownership and unavailable-source mutations. It still had a critical defect:

- Invoice edge `I1 = 5 units / $500`.
- Credit `C1 = 3 / $300` referencing I1 — individually valid.
- Credit `C2 = 3 / $300` also referencing I1 — individually `<= I1`, so a naïve per-event validator accepted it.
- Result: net billed state became **-1 unit / -$100**.

Thus `counter_event.original_edge_id` alone does not enforce reversal correctness.

The repaired model tracks `reversed_qty[original_edge]` and `reversed_amount[original_edge]` and requires cumulative counter-events to remain within the original edge's quantity/amount. It also prohibits full cancellation after partial credit and enforces exact line ownership and source availability.

### Repaired synthetic corpus result
Six adversarial invariants passed after adding per-edge reverse residuals:
1. receive 5 → bill 5 → refunding return 2 → credit 2 → re-receipt 2 produces physical 5, receipt authority 5, billed 3, billed amount $300;
2. cumulative credits 3 + 3 against one 5-unit invoice are rejected;
3. full cancellation after a partial credit is rejected unless modeled as the remaining residual only;
4. cumulative returns 3 + 3 against one 5-unit receipt are rejected;
5. a return referencing another PO line's receipt is rejected;
6. `UNAVAILABLE` source evidence cannot mutate authority.

The earlier physical-only-return case from Run 13 remains required: a stock movement that is not a commercial refund may reduce physical inventory while leaving commercial receipt authority unchanged.

## COMPARATOR — Tryton exposes a useful exact-origin boundary and a lineage weakness
- Repository: https://github.com/tryton/tryton
- Exact revision: `bdefd24bbc6cd7d0c574b16327d79a67461386a8`
- Status: **watch / negative-and-positive comparator**

### Positive semantics
`modules/purchase/purchase.py` links both invoice lines and stock moves to an exact `purchase.line` via their `origin`. `get_invoice_line()` sets `invoice_line.origin = self`; `get_move()` sets `move.origin = self`. Fulfillment invoice quantity is calculated from done supplier↔internal moves on that line, and cancelled invoice state is excluded when quantities are recomputed. This is strong exact-line forward state.

### Boundary / negative knowledge
Tryton's `ReturnPurchase` wizard copies the purchase header, sets the new purchase's `origin` to the original purchase header and negates line quantities. In the inspected implementation, the wizard does **not** visibly persist an original-purchase-line ID on each copied negative return line. The return therefore has clear header ancestry but weaker direct line-to-line reversal identity than BCApps' return-order-line / item-ledger-entry references or ERPNext's exact receipt-item lineage.

This does not make Tryton incorrect as an ERP. It makes it a useful negative oracle for our proof layer: **document ancestry plus same product is not enough to prove which original authority edge a counter-event consumed when several candidate lines exist.**
