- Published rights: repository root is MIT except separately identified Enterprise Edition material. The inspected payment-module paths are in the ordinary repository package tree; preserve notices and separately review any enterprise/provider dependencies.

### Concrete implementation evidence
`packages/modules/payment/src/services/payment-module.ts` now treats capture/refund amount guards as critical sections:

1. **Transaction context is mandatory.** `capturePayment_` and `refundPayment_` explicitly fail if no transaction manager exists; a `FOR UPDATE` issued on an autocommit connection is rejected as semantically unsafe because the lock would release immediately.
2. **The authoritative parent row is locked.** The implementation executes `SET LOCAL lock_timeout = '3s'` then `SELECT ... FOR UPDATE` on the exact `payment` row.
3. **Totals are re-read under the lock.** Capture relations or capture+refund relations are fetched again after the lock so a waiter sees the committed amount from the winner rather than the stale pre-lock snapshot.
4. **Residual is checked before the child event is inserted.** Refund computes `capturedAmount`, `refundedAmount`, then refuses `refunded + requested > captured` (with currency epsilon). Capture analogously refuses total capture beyond authorization.
5. **The critical write is inside the same transaction.** Only after the re-read/guard does it create the Capture/Refund record.
6. **Contention is bounded.** The 3-second local lock timeout makes inability to acquire the critical section an explicit failure rather than an unbounded hang; our own authority engine should map such a condition to retry/re-review, never to an absence or money-bearing conclusion.

### Concurrency tests
`packages/modules/payment/integration-tests/__tests__/services/payment-module/index.spec.ts` contains explicit races:
- authorization/captured amount = 500; two concurrent captures of 300 each; **exactly one** is admitted and final captured amount is 300;
- captured amount = 500; two concurrent refunds of 300 each; **exactly one** is admitted and final refunded amount is 300.

This is materially stronger evidence than a row-lock comment or a serial over-refund unit test: the repository contains the formerly failing concurrent pattern and asserts a one-winner outcome.

### Defect archaeology strengthens the evidence
Issue #16012 documented the prior check-then-act race at commit `917ddbe`: two workers could read the same refund total, independently pass the amount guard, create distinct refund rows, and use distinct provider idempotency keys. Fix commit `0b678b4...` specifically added row locking, fresh reads, transaction-context assertions, bounded lock waits, stable lock ordering for promotion-budget rows, and tests requiring exactly one concurrent capture/refund to be admitted.

### Red-team boundary — local serialization does not solve ambiguous external application
Medusa deliberately calls the payment provider **after** the local refund transaction. `refundPaymentFromProvider_` sends `idempotency_key = refund.id`. If that call throws, the public `refundPayment` path deletes the local refund row.

That is sensible for definite provider failure, but it exposes the next proof obligation for our money-bearing systems: if an external provider/ERP actually applies the credit/refund and the response is lost or classified only as a generic exception, deleting the local reservation can free reverse capacity; a later retry creates a new refund row and therefore a new idempotency key. Whether this can double-apply in a real Medusa deployment depends on provider-specific timeout/error semantics and was **not proven here**. Treat it as a boundary/risk, not a claim of a Medusa vulnerability.

Reusable rule for EXP-002: **atomically reserve reverse capacity first, but do not release that reservation on an ambiguous external result. Preserve one stable logical operation identity across retries until independent reconciliation proves NOT_APPLIED or APPLIED.**

## STRONG ANALOG — Commerce Layer RAIL0 makes reverse capacity an atomic on-chain bucket
- Repository: https://github.com/commercelayer/rail0
- Exact revision: `bcd481515d966b53667750b8860a1f0d0141c3cf`
- Status: **strong component / cross-domain concurrency oracle**
- Score: **27/30 — A3 B4 C5 D5 E5 F5**
- Published rights: MIT, Copyright 2026 Commerce Layer.

`contracts/src/RAIL0.sol` stores a finite `refundableAmount`. `refund` verifies `amount > 0 && amount <= refundableAmount`, computes `newRefundable`, and writes the decreased balance **before external token calls** under `nonReentrant`. Because the EVM executes each transaction atomically and reverts state if the later call fails, two submitted transactions cannot both consume the same pre-refund residual: the later transaction executes against the updated state or reverts.

The repository also binds each refund authorization nonce to both current live balances `(capturableAmount, refundableAmount)`. This matters because an earlier implementation used refundable balance alone; capture could restore that balance to a previously used value and repeat a nonce, permanently bricking later refunds. Issue #36 records the failure, and fix commit `793296de93e02ab22375aff7733fbd6ada3f4c2f` changed the nonce derivation.

Tests go beyond happy paths:
- `test_Refund_SurvivesARevisitedRefundableBalance` executes capture 50 → refund 50 → capture 50 (same refundable balance revisited) → refund 50 and proves the nonce differs and final refundable balance reaches zero;
- `testFuzz_RefundNoncesNeverRepeat` fuzzes capture/refund interleavings and asserts no refund nonce repeats; the test was explicitly run against the old derivation and failed there;
- accounting fuzz tests assert `capturable + refundable <= original amount` through capture/refund sequences;
- reentrancy tests cover guarded nested calls and multiple guarded operations in one transaction.

Transferable lesson: a reverse residual can be both **the guard and the state**, updated before side effects, while a state-derived operation nonce prevents stale/replayed external authorization from silently targeting a new balance state.

## WATCH — AWS Marketplace billing-adjustment reference code
- Repository: https://github.com/aws-samples/aws-marketplace-reference-code
- Exact indexed revision: `dc25d35b0dbe2558e7eb7eaa92bb6e6d2d0f939d`
- Status: **watch / provider-backstop reference**
- Score: **24/30 — A4 B4 C4 D3 E5 F4**

The billing-adjustments application uses a deterministic client token from `agreement_id:invoice_id`, performs live duplicate pre-checks against existing adjustment requests, holds rows for `NEED_REVIEW` if the safety-critical pre-check cannot verify the agreement, and relies on per-invoice `maxAdjustmentAmount` as a provider-side cap. Its docs explicitly warn that the API idempotency window is eight hours and that changing the client-token formula after refunds have been submitted can permit re-submission (bounded only by the provider max).

Useful combination: **local durable reverse residual + stable logical operation ID + external/provider max/backstop + post-write reconciliation**. Do not mistake a time-limited provider idempotency window for lifetime reversal authority.

## COMBINATION DISCOVERED
Strengthened EXP-002 control plane:

`CAP-019 source observation -> ReceiptAuthorityPolicy -> exact forward allocation graph -> per-original-edge forward/reverse residual -> SERIALIZED RESIDUAL RESERVATION (Medusa pattern or guarded conditional UPDATE) -> stable logical counter-event ID across retries -> external ERP/provider write -> reconciliation/APPLIED|NOT_APPLIED|UNKNOWN -> MiniGraf bitemporal replay -> CAP-007 proof gate -> CAP-016 settlement/accounting truth`.

A DB-native implementation can use either:
- `SELECT ... FOR UPDATE` + fresh read + guard + append-event/update-residual in one transaction; or
- a single conditional `UPDATE ... SET reverse_residual = reverse_residual - :amount WHERE edge_id=:id AND reverse_residual >= :amount`, treating 0 rows as a conflict/exhausted capacity.

The second form deserves benchmarking because it can turn the conservation rule into a database predicate without a separate read-check-write window.

## FAILURES / NEGATIVE KNOWLEDGE
- Application-level `if requested <= remaining` is not a concurrency invariant.
- Per-call idempotency IDs do not prevent two separately admitted operations; the admission itself must serialize on the common authority object.
- A lock without a transaction context can be semantically useless.
- A transaction lock held across a slow provider call creates a different reliability problem; reserve locally, then use a durable operation identity/outbox/saga boundary.
- Definite provider failure and **unknown-after-possible-apply** must not share the same cleanup path in our design.
- Time-limited idempotency windows are backstops, not durable authority history.
