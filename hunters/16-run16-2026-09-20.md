### What it contains
A small but unusually complete external-side-effect broker built around stable semantic operation identity, canonical request hashing, pinned target-safety contracts, durable effect state, attempts, leases, explicit `OUTCOME_UNKNOWN`, authoritative reconciliation and fail-closed retry policy.

The important capability is not generic job retry. It directly models the exact ambiguity that AP writeback now needs to handle: **the target may have committed, while the caller crashed or lost the response before recording the receipt.**

### Concrete implementation evidence inspected
1. **Stable logical operation identity and payload binding.** `src/effect_broker/canonical.py` hashes `{tool, arguments, contract_name, contract_version}` using strict canonical JSON. A `(tenant_id, operation_key)` deterministically derives one HMAC `downstream_key`, so crash recovery can reuse the target's same idempotency slot. Reusing an operation key with changed payload/contract is explicitly treated as a conflict rather than silently collapsed.
2. **Durable reservation before I/O.** `src/effect_broker/store/sqlite.py` persists effect identity, request hash, downstream key and pinned contract before dispatch. Unique identity collisions replay the same request only when the hash matches; changed payload raises `PayloadConflictError`.
3. **Attempt recorded before external effect.** `src/effect_broker/worker.py` moves the effect to `DISPATCHING`, writes an attempt, maintains a dispatch lease, then invokes the adapter.
4. **Ambiguous transport/process failure becomes durable UNKNOWN, not retryable failure.** Generic exceptions after possible dispatch transition to `OUTCOME_UNKNOWN`. Only a target-specific `AdapterError` documented as proven non-commit can become RETRYABLE/FAILED_FINAL.
5. **Safety-class-specific recovery.** `src/effect_broker/statemachine.py` and `reconcile.py` route UNKNOWN according to target capability:
   - `IDEMPOTENT`: re-dispatch only with the same stable downstream key and only while the declared key-retention horizon is still valid;
   - `RECONCILABLE` / `TRANSACTIONAL`: query the authoritative target first;
   - `UNSAFE`: never redispatch; route to manual review.
6. **Authoritative probe has three outcomes.** For reconcilable targets, probe `COMMITTED` -> success, `NOT_COMMITTED` -> safe PREPARED state, and unresolved probe -> MANUAL_REVIEW. UNKNOWN is not coerced into failure.
7. **Crash recovery uses leases, not operator inference.** Expired `DISPATCHING` leases are CAS-promoted to `OUTCOME_UNKNOWN`; heartbeats protect slow live workers. Late/zombie writes are fenced by version checks.
8. **Contracts are pinned and mechanically honest.** `contracts.py` refuses an idempotent contract without positive key-retention, a reconcilable contract without a settlement bound, and an unsafe target with any retry allowance. Contract versions are pinned into the effect at reservation time so later config reloads cannot retroactively change in-flight semantics.

### Crash-matrix proof
`examples/crash_matrix/runner.py` and `worker.py` provide a real process-death seam:
- broker state and target state are in separate durable SQLite databases;
- worker commits the target mutation, then executes `os._exit(137)` at `after_target_commit_before_receipt`;
- the production lease-sweep path discovers the abandoned dispatch and converts it to UNKNOWN;
- three concurrent recovery subprocesses race on the same effect; exactly one may win and stale/zombie writes are rejected;
- expected final behavior:
  - idempotent: one target effect, broker succeeds via same-key redispatch;
  - reconcilable: one target effect, exactly one target call, broker succeeds via probe and **does not redispatch**;
  - unsafe: at most one target effect, exactly one dispatch attempt, broker stops at MANUAL_REVIEW.

`tests/test_safety_classes.py` independently exercises lost-response recovery, five concurrent reconciliation attempts with exactly one winner/four version conflicts, authoritative probing without redispatch, pre-settlement unknown -> manual review, and unsafe no-duplicate behavior.

`tests/test_dispatch_leases.py` exercises target-committed/broker-receipt-missing recovery, fences a resurrected worker's stale receipt, proves a heartbeat prevents a slow healthy dispatch from being stolen, and proves an abandoned lease is reclaimed only once.

### Red-team limitations
- The supplied durable crash target is local SQLite, not a real ERP/PSP. The invariant is strongly demonstrated, but buyer-specific adapter correctness remains external.
- `COMMITTED` / `NOT_COMMITTED` authority is only as good as the target adapter's probe. An ERP query that cannot prove absence must return UNKNOWN, not NOT_COMMITTED.
- Idempotent redispatch is only safe inside the downstream target's retention horizon; the code explicitly stops at manual review after that horizon.
- The broker solves effect identity/reconciliation; it does **not** itself reserve AP amount/quantity reverse residual. For EXP-002 it should sit downstream of the Medusa/authority-ledger reservation, not replace it.
- A real deployment still needs adapter-specific authentication, authorization, network policy, customer tenancy and evidence-retention hardening.

### Commercial implication
This closes the major writeback design gap left by Run 15. A vendor-credit, cancellation or ERP correction can be modeled as one stable logical effect whose local authority reservation remains held while the external result is UNKNOWN. Process death, timeout or response loss do not justify creating a second logical counter-event.

Reusable AP rule:

`reserve exact reverse residual -> create/persist effect(operation_key, request_hash, pinned adapter contract) -> dispatch once -> APPLIED | proven NOT_APPLIED | UNKNOWN -> reconcile same effect identity -> release residual only on proven NOT_APPLIED; finalize consumption on APPLIED; UNKNOWN remains blocked/manual-review.`

The smallest paid wedge is a **safe AP writeback gateway** around approved credits/corrections: customers keep their ERP, while the gateway supplies stable intent IDs, crash recovery, evidence, reconciliation and no-blind-retry behavior.

## FAILURES / NEGATIVE KNOWLEDGE
- Transactional outbox != external-effect exactly-once.
- Caller idempotency key != shared economic-capacity serialization.
- Exception != NOT_APPLIED.
- Missing target object != NOT_APPLIED unless the target contract supplies a bounded, authoritative absence proof.
- Worker death after send must become UNKNOWN, not RETRYABLE.
- Reissuing with a fresh operation ID after UNKNOWN defeats idempotency even if each request individually uses a key.
- An idempotency guarantee is time-bounded if the downstream target forgets keys; retries after retention expiry need authoritative readback or manual review.
- A reconciler that hand-writes UNKNOWN in tests proves less than a production lease-recovery path; effect-broker's recent commit history usefully fixed that exact proof weakness.
