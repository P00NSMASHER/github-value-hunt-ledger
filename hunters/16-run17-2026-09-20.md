### Why it matters
This is the first inspected real-ERP adapter that materially narrows the unresolved `NOT_APPLIED` problem without relying on negative object lookup at all during the normal response-loss path.

Oracle NetSuite's REST contract supports asynchronous submission with `Prefer: respond-async` and a client-supplied `X-NetSuite-idempotency-key`. Oracle explicitly states the mechanism prevents duplicate record/task submission and helps recover “loose-running jobs after a connection failure.” A retry with the same key returns an `IDEMPOTENCY_ERROR` plus the `Location` of the previously submitted async job. The caller can then query job status, task status and task result by that stable job identity.

The useful architecture is therefore:

`stable logical counter-event -> same NetSuite idempotency key -> 202 + job Location OR duplicate-conflict + original job Location -> poll exact job/task -> retrieve exact task result -> reconcile economic state`

This is stronger than `POST -> timeout -> GET by approximate business fields -> if absent, retry`, because temporary index/replication absence is never promoted to NOT_APPLIED.

### Concrete implementation evidence inspected
1. **Async write request contract.** `apps/sim/tools/netsuite/utils.ts` builds batch write requests with `Prefer: respond-async`, the collection content type and optional `X-NetSuite-idempotency-key`.
2. **Recovery of the original provider operation.** When NetSuite returns the documented HTTP 400 idempotency conflict, the adapter requires all of the following before treating it as successful recovery: the original request actually carried an idempotency key; body contains `o:errorCode = IDEMPOTENCY_ERROR`; and the response has a valid NetSuite async-job `Location`. It then returns the original `jobId`/Location rather than minting a second operation.
3. **Fail-closed status handling.** `isIdempotentJobReplay()` accepts only HTTP 400. A 409 response carrying the same-looking error code is not silently normalized because that status is not the raw Oracle contract used by the adapter.
4. **Provider-location validation.** Async `Location` must be HTTPS, same-origin, no credentials/hash/query, and exactly `/services/rest/async/v1/job/{id}`. Cross-origin and malformed locations are rejected.
5. **No false-success on incomplete async acknowledgement.** A nominal 202 with no pollable job Location is returned as failure, not success.
6. **Provider readback surface.** `get-async-status.ts` retrieves job, task collection or exact task state and validates documented fields. `get-async-result.ts` retrieves the exact provider response for one job/task.
7. **Record identity support.** Batch PATCH requires an internal or external record ID; batch PUT requires a non-empty external ID and forbids an internal ID, aligning with NetSuite's external-ID/upsert synchronization model.

### Regression evidence
`apps/sim/tools/netsuite/utils.test.ts` contains explicit tests that:
- recover the original async job from a documented 400 `IDEMPOTENCY_ERROR` and original job Location;
- refuse to recover a similar-looking error returned at an undocumented status;
- reject cross-origin job Locations during recovery;
- reject malformed async Locations;
- reject 202 async responses lacking a pollable Location;
- reject unrelated Location-bearing errors instead of treating them as idempotent replay.

This is unusually good evidence for an ERP connector because the tests target the exact ambiguity/error-shape boundary rather than merely checking that an HTTP request was emitted.

### First-party Oracle triangulation
Current Oracle documentation independently confirms:
- REST async jobs return a job Location that can be polled for status/results;
- idempotent retry is intended to avoid duplicates and recover jobs after connection failure;
- a duplicate idempotency key returns the previously submitted job Location;
- external IDs are intended for synchronization and can be addressed as `eid:<external_id>`;
- batch update/upsert operations support internal/external IDs and async execution.

### What this proves — and what it does not
**Verified:** for the documented NetSuite async/idempotency contract, the correct response-loss strategy is *same-key replay to recover the provider job*, not absence polling followed by a fresh write.

**Verified:** the Sim adapter implements that raw-provider recovery contract and fails closed around status/error/Location shape drift.

**Not established:** live execution against a customer-authorized NetSuite tenant. The repository tests use mocked HTTP responses.

**Not established:** the retention horizon for REST idempotency keys. The retrieved current REST documentation explains duplicate recovery but did not state how long the idempotency key remains authoritative. Oracle separately documents 30-day validity for asynchronous SOAP job IDs, but that must not be silently transferred to the REST idempotency-key contract.

**Not established:** a universal `NOT_APPLIED` proof after the vendor's idempotency/job-retention window has expired. At that point EXP-002 must retain UNKNOWN/manual review unless an exact external reference or authoritative record read proves the state.

**Important batch caveat:** batch jobs can contain multiple tasks. A completed job is not enough for economic finality; the exact task result and resulting ERP record must be inspected. For AP writeback, prefer one logical correction per provider operation or retain exact task-to-authority-edge mapping.

### Commercial implication
This materially reduces the implementation risk of a **Safe ERP Writeback Gateway** for AP Leakage Assurance. NetSuite can be the first concrete ERP adapter because the vendor already supplies the hardest primitive: client-controlled idempotent async request identity that can rediscover the original job after response loss.

The first paid implementation wedge can remain read-only AP assurance, but a controlled-action add-on becomes more credible:

`approved credit/correction -> reserve reverse capacity -> effect-broker operation_key -> derive stable NetSuite idempotency key -> async submit -> recover/poll same provider job -> exact task result -> APPLIED / FAILED / UNKNOWN -> release or finalize capacity only after proof`.
