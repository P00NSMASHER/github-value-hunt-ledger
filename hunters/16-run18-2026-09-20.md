### Why it matters
Sage Intacct provides an independently developed provider contract for crash/response-loss recovery that is different from, but complementary to, NetSuite's async-job replay.

The XML gateway distinguishes two IDs:
- request-level `<controlid>` only correlates a request with its response and is explicitly **not uniqueness-checked**;
- each `<function controlid="...">` is the identity used for recovery/idempotence.

With `<uniqueid>true</uniqueid>`, Sage checks the function control ID to determine whether that function was already executed and completed. Sage's own mid-process-failure instructions say to persist unique function IDs and, after receiving no gateway response, **resubmit the original request with `uniqueid=true`**. The platform compares the function control IDs against cached requests/activity logs so each function is executed only once.

This is strong evidence that a second ERP supports the key EXP-002 property:

`one logical counter-event -> one durable provider function identity -> response loss/process ambiguity -> replay same request/identity -> provider suppresses repeat execution`

It differs from NetSuite in an important way: NetSuite's same idempotency key can recover the prior async job Location; Sage Intacct's documented contract is primarily **replay suppression by function identity**. Exact business/economic readback is still required before classifying the write APPLIED.

### First-party Sage contract evidence
- `https://developer.intacct.com/web-services/requests/`
  - request `controlid` is not checked for uniqueness;
  - `uniqueid=true` causes the gateway to check each function control ID for prior completed execution;
  - function `controlid` is explicitly recommended for transaction idempotence and recovery;
  - financial create/update requests are the exact class of operations for which Sage recommends `uniqueid=true`.
- `https://developer.intacct.com/web-services/error-handling/`
  - defines mid-process failure as a hardware/network/software failure where no XML response may arrive and only some functions may have been processed;
  - requires a unique function control ID;
  - prescribes resubmitting the original request with `uniqueid=true`;
  - states the system compares function control IDs with cached requests and activity logs to execute each function only once;
  - warns that a timeout can occur while processing still completes, so lack of response is not NOT_APPLIED.
- `https://developer.intacct.com/api/accounts-payable/ap-adjustments/`
  - an AP adjustment is a credit/debit memo modifying what is owed to a vendor;
  - create supports vendor, adjustment number, bill number, description, external ID, currency and one-or-more adjustment lines;
  - currency values beyond two decimals are rounded, with client-side two-decimal rounding recommended.

### Source evidence beyond README
**Stable function identity, but unsafe auto-generation if not persisted**
- `src/Functions/AbstractFunction.ts` stores `controlId`; if the caller does not supply one, the SDK generates a fresh UUIDv4.
- Consequence for EXP-002: crash/restart code must persist the logical effect ID and reconstruct the function with the **same** control ID. Rebuilding the function with no ID after a crash creates a new UUID and forfeits provider dedupe identity.

**Critical SDK default is fail-open for mutation replay unless overridden**
- `src/RequestConfig.ts` defaults `uniqueId = false`, `maxRetries = 5`, `maxTimeout = 30000`, and `noRetryServerErrorCodes = [524]`.
- `src/Xml/Request/ControlBlock.ts` serializes that setting directly to the `<uniqueid>` XML field.
- Current Sage Node/PHP SDK documentation independently publishes the same `uniqueId=false` default.
- This differs from the raw XML-gateway documentation, which says `uniqueid=true` is the raw request default. The official SDK therefore creates an integration footgun: mutation safety cannot depend on the raw gateway default because the SDK explicitly emits false unless configured otherwise.

**Automatic HTTP retry makes the configuration boundary economically important**
- `src/Xml/RequestHandler.ts` builds the XML request and automatically retries general HTTP 5xx responses using the same XML body and exponential delay.
- The retry is safe for write operations only when the adapter has explicitly set `uniqueId=true` and preserved the same function control IDs.
- The SDK deliberately defaults HTTP 524 to **no retry**; the Sage PHP docs explain this as a CDN connection cut where the system can still be processing. That is exactly the honest UNKNOWN boundary EXP-002 requires.

**AP write surface is concrete**
- `src/Functions/AccountsPayable/ApAdjustmentCreate.ts` writes the function's durable `controlid` and a `create_apadjustment` containing vendor/date/adjustment number/action/bill number/description/external ID/currency/GL behavior/custom fields/line items.
- `test/Functions/AccountsPayable/ApAdjustmentCreateTest.ts` verifies exact emitted XML, including stable function control ID and AP adjustment fields.

**Retry behavior is tested**
- `test/Xml/RequestHandlerTest.ts` explicitly tests a 502 followed by a successful retry and separately tests that 524 throws rather than retries.
- These tests do not themselves prove provider-side dedupe because they are mocked HTTP tests, but they verify the client execution path that makes `uniqueId=true` mandatory for write safety.

### Currentness / lifecycle caveat
Sage's current 2026 developer guidance says the REST API has been GA since February 2025, XML SDK enhancement development has stopped, new integrations should generally prefer REST, and new objects/features will be released through REST. XML remains supported, and Sage's XML reference says there are cases where legacy XML functions remain the only available way to perform a task.

Therefore this is a **strong provider-semantics reference and potentially usable adapter**, but it should be isolated behind a provider contract rather than becoming hard-wired portfolio infrastructure. REST parity should be investigated before a greenfield deployment.

## STRUCTURAL COMPARATOR — NetSuite replay-addressable versus Intacct replay-suppressed
Run 17 established NetSuite's stronger async-job pattern. The two providers now support a useful capability taxonomy:

1. **REPLAY_ADDRESSABLE** — stable client key can recover the *same provider operation handle/status/result*. NetSuite is the current exemplar.
2. **REPLAY_SUPPRESSED** — stable provider-recognized function identity prevents duplicate execution when the original request is replayed, but final business/economic readback may be a separate step. Sage Intacct XML is the current exemplar.
3. **RECONCILABLE** — no safe replay identity, but exact authoritative readback can prove what happened.
4. **UNSAFE / MANUAL** — neither replay nor bounded authoritative reconciliation is available.

This taxonomy is more actionable than a boolean `supports_idempotency` flag and can become a reusable integration moat.
