## BEST NEW FIND — QuickBooks Online provider request identity is usable for AP writeback, but the official Java SDK makes that identity ephemeral unless the caller persists it

**Repository:** `intuit/QuickBooks-V3-Java-SDK`

**Exact revision:** `c4d5dfad23ffebf0302356876d0dc389708513a9` (current `develop` head inspected; commit dated 2026-07-17)

**Category:** accounting-provider mutation identity / AP writeback safety

**Score:** 26/30 — A4 / B5 / C5 / D3 / E4 / F5

### Concrete capability
QuickBooks Online mutations accept a caller-controlled `requestid`; the official Java SDK exposes `Context.setRequestID(...)`, includes that value in the QBO request URL, and tests the exact URL construction. If no ID is supplied, `Context.getRequestID()` generates a random UUID-like value. Critically, `PrepareRequestInterceptor` clears the context request ID immediately after appending it to the URI so the next call gets a new random ID by default.

That is a valuable implementation boundary for crash-safe financial automation: **provider-native duplicate protection is only useful if the logical effect ID is durably persisted outside the SDK and explicitly restored after restart.** Reconstructing a fresh SDK context after an ambiguous timeout/process death silently creates a new provider request identity.

### Evidence verified beyond README
- `ipp-v3-java-devkit/.../core/Context.java`: `getRequestID()` generates a random UUID-derived value when null; `setRequestID()` permits a caller-supplied stable ID.
- `ipp-v3-java-devkit/.../interceptors/PrepareRequestInterceptor.java`: QBO URI includes `requestid=<context.getRequestID()>`, then immediately calls `context.setRequestID(null)` so subsequent operations receive a fresh identity unless the caller sets it again.
- `PrepareRequestInterceptorTest.java`: executable test sets `anyRequestID` and verifies the generated QBO URI contains `requestid=anyRequestID`.
- Official SDK schema includes `VendorCredit`, and the inspected source files carry Apache-2.0 license headers.
- Current official-repo issue `intuit/QuickBooks-V3-PHP-SDK#563` (2025-09-26) points to Intuit's Request ID docs and describes `requestid` as the idempotent write parameter for Add/Update/Void/SendEmail; the PHP SDK still lacks first-class support, illustrating inconsistent SDK ergonomics even though the provider capability exists.

### Independent implementation triangulation
`simstudioai/sim@a2c9756113a13debfa1c6b5b1503700fae9007d9` has a production-shaped QuickBooks adapter that:
- supports native `VendorCredit` as a purchasing transaction;
- adds an optional Intuit `requestid` (validated to <=50 chars) to create URLs;
- creates a vendor credit at the native `/vendorcredit` resource;
- explicitly sets `retry: { enabled: false }` for vendor-credit creation rather than blindly retrying a money-bearing POST;
- parses the returned native record ID and SyncToken, enabling exact record-level follow-up once a response is obtained;
- exposes vendor-credit read/query support separately.

This is a materially safer adapter shape than an SDK wrapper that auto-generates a fresh request identity on every reconstructed call.

### Provider semantics / unresolved retention
The current Intuit developer documentation URL for Basic ID and field definitions is public but its rendered Request ID section was not machine-readable in this run. Current integration material describes QuickBooks `requestId` as the idempotency identifier, while an official Intuit repository issue cites the first-party Request ID docs for idempotent writes.

**However, I did not verify a current first-party published retention/expiry horizon for QBO Accounting `requestid`.** Therefore the provider must be treated as replay-capable only inside a documented/validated horizon; after that horizon is unknown, an ambiguous write must stay `UNKNOWN` until authoritative business-record reconciliation resolves it.

### AP commercial wedge
QuickBooks Online is directly relevant to a first Safe ERP/Accounting Writeback Gateway because `VendorCredit` is a native AP object. A safe adapter contract can be:

`reserve exact reverse capacity -> persist logical counter-event ID -> set the exact same QBO requestid -> create VendorCredit -> capture returned Id+SyncToken if response arrives -> timeout/process death => UNKNOWN -> replay only with the identical persisted requestid while replay authority is known-valid -> exact VendorCredit read/reconciliation -> APPLIED / proven NOT_APPLIED / UNKNOWN`

The immediate buyer is an AP recovery/audit vendor or mid-market finance team that wants approved recoveries posted back to QBO without duplicate vendor credits after network/process failure.

### Strongest objection
QBO request ID itself is not rare technology, and this run did not execute a live crash/replay against an authorized QuickBooks tenant. The key commercial/technical value is the integration invariant plus the source-verified SDK failure mode, not the existence of `requestid` alone. The unknown first-party retention horizon prevents classification as fully replay-addressable across arbitrary delays.

### 2. Sage Intacct REST — unresolved parity, keep XML sidecar for now
Fresh Sage sources confirm REST has been GA since 2025 Release 1 and is the recommended API for new client applications. But the public Sage XML AP Adjustment reference still labels create/update AP adjustment as **Legacy**, and this run did not verify a Sage Intacct REST AP-adjustment endpoint carrying a provider-native replay/idempotency contract equivalent to XML `function controlid + uniqueid=true`.

Therefore the previous live question remains partially negative: **do not retire the XML sidecar for crash-safe AP adjustment yet.** The XML contract remains the verified Sage path until REST mutation identity + AP adjustment coverage + retention semantics are demonstrated from the current Intacct REST OpenAPI or a live authorized tenant.

Important non-equivalence: Sage's separate Embedded Accounting/Embedded Services APIs visibly use `X-Idempotency-Key`, but those are different Sage products/surfaces and must not be transferred to Sage Intacct REST by analogy.

### 3. Intuit CLI `--idempotency-tag` — negative control
The newer Intuit CLI's `--idempotency-tag` is an attribution marker appended to Notes/PrivateNote rather than provider-native QBO `requestid`. It is useful audit metadata but is not crash-safe duplicate suppression. Do not let naming such as "idempotency tag" satisfy the launch gate without inspecting the actual wire-level identity primitive.

## CLAIMS TESTED
1. **Official SDK support means a stable retry identity survives restart automatically:** falsified for the inspected QBO Java SDK. The request ID is cleared after URI construction and regenerated when absent.
2. **QBO has a native AP counter-event object:** supported; `VendorCredit` is present in the official schema and in an independent current adapter.
3. **A modern adapter should blindly retry a money-bearing QBO POST:** challenged; Sim explicitly disables retry on VendorCredit creation and exposes optional provider request identity instead.
4. **Sage Intacct REST can replace the XML crash-safe AP-adjustment sidecar today:** not verified. Current public material establishes REST as preferred/GA, but this run did not establish equivalent AP-adjustment replay semantics.
5. **Sage Embedded Accounting `X-Idempotency-Key` proves Sage Intacct REST idempotency:** falsified as an inference; they are distinct products/API surfaces.

## EMERGING TECHNOLOGY SIGNALS

A provider may offer a safe primitive while its official SDK's convenience defaults still defeat that primitive after restart.

## FAILURES / NEGATIVE KNOWLEDGE
- SDK-generated UUIDs are not durable logical effect identity unless persisted before dispatch.
- An SDK clearing its request ID after each call is appropriate for ordinary use but dangerous if a crash/restart path reconstructs a write without restoring the original provider key.
- A field or CLI flag named "idempotency" is not proof of provider-side duplicate suppression; inspect the wire call.
- `SyncToken` is record-version/concurrency state, not create-request deduplication identity.
- Do not infer Sage Intacct REST semantics from Sage Embedded Accounting headers.
- Do not release reverse capacity because a provider idempotency retention horizon is unknown or expired.
