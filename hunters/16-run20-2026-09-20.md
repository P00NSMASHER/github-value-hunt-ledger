# Hunt 09 Run 20 — Xero bounded replay-cache semantics for AP writeback

Date: 2026-09-20
Node: 09 — Data Moats
Target: CAP-016 / CAP-019 / EXP-002 AP Leakage Assurance

## Summary

The strongest new evidence is Xero's first-party idempotency contract plus its current official Node SDK. Xero provides a real provider-side duplicate-suppression mechanism for mutating Accounting API calls, including `createCreditNotes`, but the protection is deliberately short-lived: **idempotency keys are stored for 6 minutes from the first call**. Reusing the same key during that window returns the cached original response instead of reprocessing the request. Reusing the same key after expiry is treated as a new key and may execute the mutation again.

This is the clearest provider-side evidence found so far for EXP-002's previously generic "idempotency retention expiry" hazard. It creates a new provider class distinct from NetSuite's recoverable async-job identity and Sage Intacct's replay-suppressed function identity:

- `REPLAY_ADDRESSABLE`: same provider identity recovers the original provider job/result (NetSuite exemplar).
- `REPLAY_SUPPRESSED`: same provider-recognized function identity prevents repeat execution but readback is separate (Sage Intacct XML exemplar).
- **`REPLAY_CACHED_BOUNDED`: same key returns the original cached response only inside a documented TTL; after expiry the same key becomes a new mutation (Xero exemplar).**
- `RECONCILABLE`: unsafe to replay, but authoritative readback can resolve outcome.
- `UNSAFE_MANUAL`: neither safe replay nor bounded authoritative reconciliation is proven.

For Xero AP credit notes, the six-minute boundary matters even more because the official generated `CreditNote` model does not expose an obvious client-controlled unique operation identity for `ACCPAYCREDIT`: `CreditNoteID` is Xero-generated, while `CreditNoteNumber` and `Reference` are documented as `ACCRECCREDIT`-only fields. If the create response is lost and the six-minute idempotency window expires before the caller recovers the generated `CreditNoteID`, exact automatic negative proof is not established by the inspected contract.

## Evidence inspected

### 1. First-party Xero idempotency contract — VERIFIED

Source: https://developer.xero.com/documentation/guides/idempotent-requests/idempotency/

Current Xero documentation states:
- Include `Idempotency-Key` on mutating POST, PUT, and PATCH requests.
- Xero caches the response to the first keyed request.
- Subsequent identical requests with the same key are not reprocessed; the cached response is returned.
- Concurrent requests using the same key are handled so that the first call processes and the cached response is returned to the rest.
- Reusing the same key with a different URL/body/method returns an error.
- Keys are stored **for 6 minutes from the first call**.
- After expiry, repeating the same key is processed as a **new key**; Xero explicitly says this should be avoided.
- Internal error responses are cached too. Xero recommends GET/readback to inspect whether a resource exists before using a new key after an error.
- If Xero cannot safely process idempotency keys, it returns HTTP 500 rather than silently proceeding without the guarantee.

Evidence label: VERIFIED first-party protocol behavior.

### 2. Credit-note endpoint is explicitly idempotency-enabled — VERIFIED

Official generated Node SDK docs expose:

`createCreditNotes(xeroTenantId, creditNotes, summarizeErrors, unitdp, idempotencyKey)`

for `/CreditNotes`, with the `Idempotency-Key` documented as allowing safe retry without duplicate processing and capped at 128 characters.

Source: https://xeroapi.github.io/xero-node/accounting/

This is directly relevant to an AP counter-event because the payload supports credit-note type `ACCPAYCREDIT`.

Evidence label: VERIFIED generated first-party SDK/API surface.

### 3. Generated SDK implementation serializes idempotency headers — IMPLEMENTED

Repository-wide source search at the inspected revision finds current generated API clients serializing the caller-supplied `idempotencyKey` into `Idempotency-Key` request headers. Accounting API source is generated from the same OpenAPI release and the current generated Accounting API docs expose the parameter on `createCreditNotes`.

Evidence label: IMPLEMENTED/generated SDK pattern; exact 1.19 MB Accounting source file was too large for the connector's file fetch, so endpoint-specific wire behavior is additionally anchored by the official generated docs.

### 4. AP credit-note identity boundary — IMPLEMENTED / VERIFIED

`src/gen/model/accounting/creditNote.ts` at the exact revision documents:
- `creditNoteID`: **Xero generated unique identifier**.
- `creditNoteNumber`: documented for **ACCRECCREDIT** and auto-generated if missing.
- `reference`: documented as **ACCRECCREDIT only**.

Therefore the inspected AP credit type (`ACCPAYCREDIT`) does not expose an obvious client-chosen unique credit-note identity in this model. The API can retrieve one exact credit note by `CreditNoteID`, but after a lost create response the caller may not know that generated ID.

`getCreditNotes` supports broad retrieval/filtering (`where`, date, page, ordering), but the inspected current endpoint does not expose a dedicated client operation-ID lookup for AP credits.

Evidence label: IMPLEMENTED schema + VERIFIED generated API surface.

Evidence label: VERIFIED.

### RED-TEAMER

1. **Is Xero idempotency indefinite?** No. First-party docs explicitly cap storage at six minutes.
2. **Can the gateway safely use the same key after expiry?** No. Xero says it is processed as a new key after expiry.
3. **Can expiry be interpreted as NOT_APPLIED?** No. Expiry says only that replay protection is gone, not whether the first request executed.
4. **Can a generic GET prove an AP credit does not exist?** Not automatically. The created `CreditNoteID` is Xero-generated, and the inspected AP model lacks an obvious caller-supplied unique operation ID. Broad queries can support reconciliation but do not establish uniqueness by themselves.
5. **Can a new key be minted after an error?** Only after authoritative readback has established that the intended resource was not created. Xero's own guidance recommends GET-before-new-key after repeated keyed errors.
6. **Does SDK/API documentation equal a live-tenant crash test?** No. This run did not execute against an authorized live Xero tenant. Runtime confirmation remains a valuable experiment.

VERIFIER VERDICT: **STRONG component / experiment correction. The six-minute replay TTL is authoritative and directly changes EXP-002. Post-expiry AP-credit negative proof remains unresolved and must fail closed.**

## Proposed EXP-002 fixtures

### `XERO-IDEMPOTENCY-WINDOW-PROBE`

Precondition:
- one approved AP credit intent
- one reserved reverse-capacity edge
- one durable logical effect ID
- one Xero `Idempotency-Key`

Fixture A — response lost, recovery inside replay window:
1. Send `createCreditNotes(ACCPAYCREDIT)` with key K.
2. Simulate loss of response after possible provider execution.
3. Restart worker while K is still inside the documented six-minute window.
4. Replay the byte-equivalent request with K.
5. Expected provider contract: cached original response, no second credit-note creation.
6. Gateway resolves provider-generated `CreditNoteID` and records APPLIED.

Fixture B — recovery after replay window expiry:
1. Same setup, but do not recover until the provider replay key has expired.
2. Attempted automatic resend with K must be blocked by the gateway **before network dispatch** because Xero would process K as a new key.
3. Reverse capacity remains reserved and effect state remains UNKNOWN until authoritative reconciliation or manual review.

Fixture C — same key, different payload inside window:
- Gateway must reject locally before send.
- If sent, Xero contract returns a key-conflict error.

Fixture D — cached internal provider error:
- Same key may keep returning the cached error even after the underlying provider issue clears.
- Gateway must inspect the resource before considering a new key.

Fixture E — idempotency subsystem unavailable:
- Xero documents 500 when it cannot honor idempotency processing.
- Gateway must remain UNKNOWN / no fresh key.

## Capability / graph impact

### CAPABILITY DELTA

Adds a **bounded replay-cache provider contract** with a first-party exact TTL. The authority layer now needs `provider_replay_expires_at`, not only `provider_operation_id`.

### GRAPH EDGE

Strengthens CAP-016 and EXP-002 downstream of serialized reverse-capacity reservation and durable effect identity. CAP-019 remains the upstream source-authority gate.

### RADAR SIGNAL

Strengthens RAD-006 qualitatively: provider mutation safety is not binary. Replay mechanisms differ materially in whether they recover an original job, merely suppress a duplicate, cache an original response for a finite TTL, or offer no safe replay at all.

### EXPERIMENT IMPACT

Converts the generic idempotency-retention-expiry case into a concrete vendor fixture with a documented six-minute window. EXP-002 should treat provider replay expiry as a hard state transition from `replay_safe` to `replay_forbidden_until_reconciled`.

### COMMERCIAL IMPACT

A provider-neutral Safe ERP/Accounting Writeback Gateway becomes more defensible if it exposes an endpoint registry such as:

`provider | operation | identity primitive | replay class | retention | same-key result | post-expiry behavior | exact readback | SDK retry behavior | proof for NOT_APPLIED`

Xero is a strong example because its six-minute limit forces the gateway to prove it understands time-bounded safety rather than simply claiming "idempotency support."

### NEGATIVE KNOWLEDGE

- Never treat idempotency-key expiry as evidence of failure.
- Never automatically reuse a Xero key after six minutes; the provider says it becomes a new mutation.
- Never mint a fresh key while the previous effect is UNKNOWN without authoritative negative proof.
- Never assume a vendor-generated record ID is recoverable after a lost response unless another exact lookup identity was persisted.
- Never treat a broad `where` query as exact negative proof unless uniqueness of the queried operation marker is itself enforced.

## Search method outcome

The productive method was **provider retention-contract triangulation**:
1. start from the highest-value unresolved failure mode (idempotency expiry),
2. search first-party provider protocol docs for explicit TTL / same-key semantics,
3. confirm the target financial mutation supports that identity in an official SDK,
4. inspect the mutation's data model for exact post-timeout readback identity,
5. classify the provider by replay capability rather than by generic "supports idempotency" language.

This produced substantially more value than another generic outbox/saga search.

## Strongest objection

No live authorized Xero tenant crash/replay was executed. The six-minute replay contract is first-party and explicit, but the exact operational behavior of AP-credit reconciliation after a lost create response remains unproven in a real tenant, especially once the caller no longer has the generated `CreditNoteID` and the idempotency TTL has elapsed.
