# Hunt 09 Run 21 — Xero AP positive reconciliation after bounded replay expiry

Date: 2026-09-20
Node: 09 — Data Moats
Target: CAP-016 / CAP-019 / EXP-002 AP Leakage Assurance

## Summary

Run 20 established Xero as a `REPLAY_CACHED_BOUNDED` provider: Accounting API idempotency keys are retained for six minutes, after which the same literal key may execute as a new mutation. The unresolved question was whether a lost-response `ACCPAYCREDIT` could be reconciled after that replay window without unsafe redispatch.

This run found a meaningful partial answer in current first-party Xero source and documentation:

1. Xero's current official command-line client deliberately accepts a caller `reference` on a Credit Note and sends that field on an `ACCPAYCREDIT` create.
2. The exact current official Accounting OpenAPI contains an `ACCPAYCREDIT` create example with `Reference: HelloWorld`, and the response echoes that reference, even though the generic `CreditNote.Reference` field description still says `ACCRECCREDIT only`.
3. Xero introduced Credit Note webhooks on 2026-03-04. A Credit Note event carries the provider-generated `CreditNoteID` (`resourceId`/`resourceUrl`), credit type and status; current webhook delivery semantics retain events generated while the subscription is Retry/Disabled for up to 31 days and replay them in order once healthy again.

Combined, these primitives create a stronger **positive reconciliation** path after the six-minute replay TTL:

`durable logical effect L -> reserve reverse capacity -> put L-derived marker in ACCPAYCREDIT Reference -> send with idempotency key K -> lost response -> if K still valid, replay K -> if K expired, do not resend -> later Credit Note webhook yields CreditNoteID -> GET exact CreditNoteID -> require Reference marker + expected tenant/contact/type/amount/currency/line semantics -> APPLIED`.

This does **not** establish authoritative `NOT_APPLIED`. `Reference` is not documented as provider-unique for AP credits, and absence of a webhook or broad search match is not proof of absence. The provider class therefore refines to:

**`REPLAY_CACHED_BOUNDED + POSITIVE_RECONCILABLE`**

rather than fully `RECONCILABLE`.

## Evidence inspected

### 1. Exact current OpenAPI schema has a documentation/behavior contradiction — VERIFIED SOURCE CONTRACT

At `XeroAPI/Xero-OpenAPI@448060d...`, the generic `CreditNote` schema says:
- `CreditNoteID`: Xero-generated unique identifier.
- `CreditNoteNumber`: described as `ACCRECCREDIT` unique alpha-numeric code.
- `Reference`: described as `ACCRECCREDIT only` additional reference number.

However the same first-party OpenAPI contains an explicit request example creating:
- `Type: ACCPAYCREDIT`
- `Status: AUTHORISED`
- `Reference: HelloWorld`

and an example response for the resulting `ACCPAYCREDIT` retains `Reference: HelloWorld`.

Evidence label: **VERIFIED first-party source contract/examples, but live-tenant behavior not independently executed.**

Commercially important conclusion: schema prose alone is too weak to decide whether a financial mutation field is actually usable. Current official executable clients/examples must also be inspected.

### 2. Xero's current official CLI intentionally sends Reference on ACCPAYCREDIT — IMPLEMENTED

`src/commands/credit-notes/create.ts` at `XeroAPI/xero-command-line@ae346db...`:
- exposes a `reference` CLI flag;
- validates/parses the supplied field;
- constructs `CreditNote.TypeEnum.ACCPAYCREDIT`;
- sets `reference: parsed.data.reference`;
- sends the object through `xero.accountingApi.createCreditNotes(...)`;
- prints the provider-generated `creditNoteID` returned by Xero.

The validator accepts the reference as part of the Credit Note create path.

Evidence label: **IMPLEMENTED first-party client behavior.**

Caveat: the inspected repository does not have a dedicated Credit Note create command regression test proving a real API round trip. Do not silently upgrade this to TESTED live provider behavior.

### 3. Official CLI readback does not establish a unique AP-reference query — IMPLEMENTED NEGATIVE BOUNDARY

The current CLI's `credit-notes list` command filters by exact ContactID or `CreditNoteNumber`; it does not expose a dedicated `Reference` filter. The underlying Accounting API has a generic `where` surface, but this run did not establish provider-enforced uniqueness of `Reference` for `ACCPAYCREDIT`.

Therefore the logical-effect marker is useful for **positive attribution after an exact provider record ID is known**, not as authoritative negative proof that no credit exists.

Evidence label: IMPLEMENTED boundary / negative knowledge.

### 4. Credit Note webhooks create a post-response provider-ID recovery plane — VERIFIED FIRST-PARTY DOCS

Xero's changelog says Credit Note webhook events were introduced on **2026-03-04** for near-real-time create/update notification.

Current Credit Note webhook documentation says each event includes:
- `ResourceID` — the changed CreditNoteID;
- `ResourceURL` — exact resource URL;
- event time/type/category;
- tenant identity;
- `Data.Type` including `ACCPAYCREDIT`;
- `Data.Status`.

Sources:
- https://developer.xero.com/changelog
- https://developer.xero.com/documentation/guides/webhooks/credit-notes

Evidence label: VERIFIED current first-party protocol behavior.

### 5. Webhook outage retention is useful positive evidence but not completeness proof — VERIFIED

Current Xero webhook overview documents:
- immediate retry after failed delivery;
- later retries roughly every 15 minutes;
- Retry state for an overall period up to 24 hours;
- Disabled after persistent failure;
- events occurring while Retry/Disabled are retained for **up to 31 days** and replayed in order once the subscription becomes healthy again;
- consumers must implement idempotency/replay handling.

Source:
- https://developer.xero.com/documentation/guides/webhooks/overview/

This materially extends the positive observation horizon beyond the six-minute mutation replay TTL. It does not prove that event absence is authoritative absence. A disabled/unhealthy subscription, delivery delay, finite retention, consumer failure or source outage can all produce missing local observations.

Evidence label: VERIFIED first-party delivery semantics; **no complete negative-observation proof**.

### 6. Prior run's six-minute idempotency boundary still governs replay — VERIFIED

Current Xero idempotency documentation states that an Idempotency-Key protects a mutation only inside a six-minute retention window. Reusing the same key after expiration is processed as a new request. Therefore the webhook/reference path must never be misused as permission to resend after expiry.

Source:
- https://developer.xero.com/documentation/guides/idempotent-requests/idempotency/

Evidence label: VERIFIED current first-party protocol behavior from Run 20; retained as a hard invariant.

### RED-TEAMER

1. **Is `Reference` provider-unique?** No evidence found. Do not claim it.
2. **Can the gateway search Reference and infer absence?** No. Search/list absence is not provider-completeness evidence.
3. **Does a webhook prove the intended operation?** A webhook proves a provider CreditNoteID/event. The adapter must fetch the exact resource and verify the durable logical marker plus tenant/contact/type/amount/currency/line semantics before attributing it to one local operation.
4. **Can an accidental reference collision create a false APPLIED attribution?** Yes in principle. Use a high-entropy, domain-scoped marker generated from the durable effect identity and require full semantic equality; the provider still does not enforce uniqueness.
5. **Can no webhook after 31 days prove NOT_APPLIED?** No. The documented retention window is not a gap-free completeness certificate.
6. **Can the same idempotency key be resent after six minutes?** No; Xero documents that it is treated as a new request.
7. **Does schema prose saying AR-only invalidate the AP marker?** It is a serious documentation inconsistency. Current first-party CLI and OpenAPI AP examples independently support AP Reference usage, but a live authorized test remains required before production launch.

VERIFIER VERDICT: **STRONG experiment correction / adapter component. Positive APPLIED recovery after replay expiry is plausible and first-party-source-backed; authoritative NOT_APPLIED remains unresolved.**

## Proposed EXP-002 fixtures

### `XERO-POST-TTL-POSITIVE-RECONCILIATION`

Precondition:
- exact approved AP counter-event E;
- exact reverse-capacity reservation R;
- durable logical effect ID L;
- compact high-entropy reference marker M derived from L;
- Xero idempotency key K and persisted `provider_replay_expires_at`.

Case A — lost create response, recovery within six minutes:
1. create ACCPAYCREDIT with M + K;
2. drop response after possible provider apply;
3. replay identical K while still safe;
4. require cached original response and exact provider CreditNoteID;
5. fetch and validate exact CreditNoteID;
6. mark APPLIED.

Case B — lost create response, replay window expires, webhook later arrives:
1. same dispatch, response lost;
2. wait beyond replay expiry;
3. gateway must block any automatic resend;
4. receive Credit Note webhook with provider CreditNoteID;
5. GET exact resource;
6. require ACCPAYCREDIT, expected tenant/contact, M, amount/currency/line semantics;
7. mark APPLIED without redispatch.

Case C — post-expiry no webhook / zero search result:
- remains UNKNOWN;
- reverse capacity stays reserved;
- no new provider key is minted;
- no NOT_APPLIED verdict.

Case D — subscription unhealthy then recovers:
- webhook/source health must be UNAVAILABLE/INCOMPLETE during unhealthy interval;
- replayed event can later prove APPLIED;
- lack of event during outage cannot become VERIFIED_EMPTY.

Case E — marker collision/adversary:
- a different provider CreditNote carries the same Reference but differs in contact/amount/line semantics;
- attribution must fail/review, never auto-APPLIED.

Case F — schema-drift acceptance:
- launch test against an authorized Xero development/demo tenant must prove ACCPAYCREDIT persists/returns Reference at the pinned API/SDK revision;
- if not, disable the marker-based recovery path and keep UNKNOWN fail-closed.
