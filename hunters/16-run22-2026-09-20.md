## Summary

Run 21 established that Xero AP Credit Notes can be positively reconciled after the six-minute mutation-replay window by combining a durable caller marker with a later Credit Note webhook, exact `CreditNoteID` readback and full semantic verification. The remaining question was whether webhook sequence metadata plus bounded API reads can ever turn post-expiry silence into authoritative `NOT_APPLIED`.

This run finds a strong **negative boundary**:

> Current Xero first-party contracts support proving that an observation channel is incomplete, but do **not** establish a bounded completeness certificate strong enough for silence or a zero-match Credit Note read to prove that an ambiguous AP credit was never applied.

Xero's signed webhook envelope carries `firstEventSequence` and `lastEventSequence`, and its delivery system exposes health states plus bounded retry/retention. These are valuable observation receipts. However neither the current public webhook documentation nor the exact official OpenAPI specifies sequence scope, mandatory contiguity, reset/re-enable behavior, gap semantics, or a theorem that a gap-free local sequence covers every relevant Credit Note mutation. The Accounting API can enumerate Credit Notes with `If-Modified-Since`, filters and pagination, but no first-party contract found in this run elevates an exhausted zero-result query into an authoritative absence certificate after an ambiguous write.

The correct source-health model is therefore **asymmetric**:

- bad signature / disabled subscription / explicit sequence discontinuity / incomplete paging -> can prove `INCOMPLETE` or `UNAVAILABLE`;
- apparently healthy delivery + locally contiguous sequence + zero query matches -> can at most prove `OBSERVED_EMPTY`, **not** `VERIFIED_EMPTY`;
- exact provider CreditNoteID + full expected economics -> can prove `APPLIED`;
- post-expiry absence without an authoritative provider operation ledger -> remains `UNKNOWN`, keeping reverse capacity reserved.

No new MASTER repository is warranted. This is a strong EXP-002 correction and a reusable CAP-019 source-observation invariant.

## Evidence inspected

### 1. Xero webhook sequence fields are real, signed observation metadata — VERIFIED

At `XeroAPI/Xero-OpenAPI@448060d...`, `xero-webhooks.yaml` requires `firstEventSequence`, `lastEventSequence`, `events` and `entropy` in the webhook envelope. The Credit Note example carries sequence 76/76, exact provider `resourceId`/`resourceUrl`, tenant identity, event type/category, and `Data.Type: ACCPAYCREDIT`.

The generic schema defines `firstEventSequence` only as "the sequence number of the first event in the list" and `lastEventSequence` only as "the sequence number of the last event in the list." The official webhook documentation likewise describes them as the first/last sequence numbers in the payload.

The payload is authenticated with `x-xero-signature` using HMAC-SHA256. Therefore a valid payload can be treated as a provider-authenticated observation receipt for the included events and sequence metadata.

Evidence label: **VERIFIED first-party contract.**

### 2. Current first-party material does not define a negative-completeness theorem — VERIFIED ABSENCE FROM INSPECTED CONTRACT

This run specifically searched current Xero first-party documentation and the exact webhook OpenAPI for semantics that would allow a consumer to say:

`all Credit Note events for tenant T between sequence/time bounds X..Y were delivered; therefore no event means no mutation`.

No such documented guarantee was found. In particular, the inspected contract does not specify:
- sequence namespace/scope (per app, per tenant, per category, or broader);
- whether consecutive delivered payloads must be numerically contiguous;
- what sequence behavior occurs when subscriptions are re-enabled or URLs change;
- whether retained/replayed events preserve a provable gap-free sequence stream;
- whether every relevant accounting mutation emits exactly one observable Credit Note event;
- whether reaching a particular sequence constitutes a provider watermark covering all mutations before some time.

Evidence label: **NEGATIVE CONTRACT FINDING, bounded to current inspected first-party surfaces.** It is not a claim that Xero internally lacks stronger semantics; only that the public contract inspected does not authorize a financial negative-proof inference.

### 3. Delivery-health states can prove incompleteness, not completeness — VERIFIED

Current Xero webhook documentation defines states including OK, Retry and Disabled. Failed webhook deliveries are retried for an overall period up to 24 hours; after continued failure the subscription is disabled. Events occurring while Retry/Disabled are retained for up to 31 days and replayed in order once the subscription becomes healthy again.

This is useful source-health evidence:
- Retry or Disabled means the local consumer cannot claim current complete observation;
- a gap or failed signature can force a non-green observation state;
- events replayed after recovery can later establish positive APPLIED evidence.

But the documented 31-day retention horizon is not a completeness certificate. It does not state that absence after the retention/replay process proves a particular mutation never happened.

Source: https://developer.xero.com/documentation/guides/webhooks/overview/

Evidence label: **VERIFIED first-party delivery semantics.**

### 4. Accounting API supports bounded enumeration, but zero-match is still not authoritative NOT_APPLIED — VERIFIED SURFACE / NEGATIVE AUTHORITY BOUNDARY

At the same exact OpenAPI revision, `GET /CreditNotes` supports:
- `If-Modified-Since`;
- generic `where` filters;
- `order`;
- `page`, with up to 100 Credit Notes returned per call with line items;
- `pageSize` and `unitdp`.

A reconciler can therefore exhaustively paginate the API surface it is authorized to query and record a bounded observation receipt.

However two missing guarantees prevent this from becoming authoritative `NOT_APPLIED` after a response-lost write:
1. the caller marker (`Reference`) is not documented as provider-enforced unique for `ACCPAYCREDIT`;
2. no current first-party contract found states a read-after-write/eventual-consistency upper bound or that a completed zero-match query is an absence certificate for a mutation whose response was lost.

Thus an empty completed query is `OBSERVED_EMPTY` at a stated observation time, not `VERIFIED_EMPTY`.

Evidence label: **VERIFIED API surface; negative proof NOT VERIFIED.**

### 5. Public implementations parse sequence fields but do not upgrade their semantics — ECOSYSTEM CORROBORATION

Broad GitHub search found multiple Xero webhook consumers that model `firstEventSequence` and `lastEventSequence`, including Nango and several language libraries/app integrations. The inspected search results did not surface a Xero first-party implementation or independent provider-authority contract using those fields to certify gap-free accounting-event coverage or a `NOT_APPLIED` financial verdict.

This is corroborating evidence only; ecosystem behavior cannot define Xero's provider contract.

## Red-team / falsification

### Tempting design A — contiguous signed webhook sequence means no missing Credit Note

**REJECT.** A signature authenticates what Xero sent; it does not add undocumented semantics to the sequence numbers. Even locally contiguous numbers cannot establish global/per-tenant/per-category completeness without a defined namespace and watermark contract.

### Tempting design B — webhook status `OK` means all relevant historical events were observed

**REJECT.** `OK` documents current successful delivery state. It does not certify historical absence or prove that every mutation relevant to one ambiguous AP operation has been observed.

### Tempting design C — paginate `GET /CreditNotes` after the write and treat zero results as NOT_APPLIED

**REJECT.** A bounded query can be a useful observation, but the current contract does not provide the uniqueness + bounded consistency semantics needed to turn no match into proof that the lost-response create did not commit.

### Tempting design D — 31-day retained webhook horizon gives a final absence deadline

**REJECT.** Retention governs how long events are saved while the subscription is unhealthy. It is not documented as a provider-side nonexistence proof or a guarantee that one client can infer an unobserved mutation never existed.

### Strong positive path

Still valid from Run 21:
- exact later Credit Note webhook -> exact `CreditNoteID` -> fetch exact resource -> require durable marker plus tenant/contact/type/amount/currency/line semantics -> `APPLIED`.

Strengthens RAD-006 qualitatively. The provider registry now needs three separate axes:
1. mutation replay safety;
2. positive effect observability;

A provider can be strong on the first two and still have no automated safe negative verdict.

### EXPERIMENT IMPACT

The EXP-002 launch gate should explicitly require `negative_observation_authority != NONE` before any post-timeout zero result can release reverse capacity. Xero currently fails that gate for post-expiry automatic NOT_APPLIED.

### COMMERCIAL IMPACT

This reduces the risk of duplicate AP credits in a Safe Accounting Writeback Gateway. The value is conservative: Xero can automate positive recovery while ambiguous negatives remain manual instead of gambling with a second vendor credit.

The broader moat is a provider-by-provider **mutation + observation safety registry** with exact evidence for what can prove APPLIED, what can prove incomplete observation, and what—if anything—can prove NOT_APPLIED.

### NEGATIVE KNOWLEDGE

- Authenticated sequence metadata is not automatically a completeness certificate.
- A healthy webhook channel does not imply complete historical observation.
- Event retention is not an absence guarantee.
- Exhaustive pagination of an eventually consistent/non-uniqueness-bound read model is observation, not negative authority.
- `no evidence of a gap` must not be rewritten as `evidence of no gap`.
