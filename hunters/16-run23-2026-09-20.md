### Concrete capability
A real provider can expose **phase-qualified provider outcome states** strong enough to distinguish a class of true no-apply outcomes from ambiguous or partially-applied outcomes. The safe rule is not `status == failed => NOT_APPLIED`; it is:

`provider identity + documented processing phase + terminal state + no target-processing phase entered => NOT_APPLIED`

while any state that may have entered target/business processing remains `UNKNOWN` or requires record-level reconciliation.

### SAP S/4HANA evidence
Current SAP S/4HANA Cloud Public Edition documentation for `SupplierInvoiceS4Request_In` says:
- the asynchronous inbound service creates supplier invoices;
- a separate outbound confirmation reports **success and error messages when posting an invoice**;
- if an error occurs during service processing, an SAP administrator can inspect it and decide whether the **inbound request must be canceled**;
- when the administrator cancels that inbound request, `InvoiceStatusUpdateNotification_Out` sends an outbound message with error entries, after which a corrected inbound request can be sent.

Current `InvoiceStatusUpdateNotification_Out – InvoiceStatus` documentation exposes a provider invoice number/fiscal year, document reference, supplier-invoice status and log messages. Documented status descriptions include **Canceled, Rejected, Processing, Reconciled, Paid/Paying** plus structured log message code/class/severity/text.

A separate current/official SAP invoice-processing description makes the posting boundary explicit: error-free invoices can be posted automatically; invoices with errors can be **saved with errors** for later manual processing. An SAP integration administration guide maps a rejected status to deletion/discard of the invoice-with-errors case and maps processing to an invoice that is **not posted**, while reconciled corresponds to posted. This is important because it proves that pre/posting states are semantically distinct rather than all being generic HTTP failures.

**Safe interpretation for EXP-002:** a target-specific SAP confirmation that an exact inbound request was canceled/rejected **before posting** is qualitatively stronger than absence and can be represented as a provider negative receipt. Generic `Processing`, timeout, transport error, or a business `Canceled` status without phase/correlation proof must not be collapsed into `NOT_APPLIED`.

### Microsoft Dynamics 365 evidence
Current Microsoft Finance & Operations recurring-integration docs expose a durable message ID and explicit status machine:
- `Enqueued`
- `Dequeued`
- `Preprocessing`
- `Processing`
- `Processed`
- **`PreProcessingError` — import/export operation failed in the preprocessing stage**
- `ProcessedWithErrors`
- `PostProcessingFailed`

The service can map `messageId -> executionId` via `GetExecutionIdByMessageId` and return execution errors. Data Management package APIs separately return an execution ID / Job ID and statuses `Unknown`, `NotRun`, `Executing`, `Succeeded`, `PartiallySucceeded`, `Failed`, `Canceled`.

The official Microsoft sample `PackageImporter.cs` at revision `fef1173a479968dcf79bce5a5f7e93dc74c2d0d1` verifies the concrete workflow beyond docs/README: it calls `ImportFromPackage`, retains the returned execution ID, then repeatedly calls `GetExecutionSummaryStatus(executionId)` until the execution leaves `NotRun` / `Executing`.

Microsoft's current data-management documentation also exposes record-level failure artifacts, including keys for records that failed staging-to-target, and demonstrates that partial success is normal: a single import may create/update some rows while other rows fail.

**Safe interpretation for EXP-002:** `PreProcessingError` is a valuable negative-proof exemplar because the provider says failure occurred in the preprocessing phase, before the normal processing state. By contrast, generic `Failed`, `ProcessedWithErrors`, `PostProcessingFailed`, or `PartiallySucceeded` must not be treated as economic `NOT_APPLIED` without target-record reconciliation. A job-level terminal status can coexist with record-level effects.

## OTHER STRONG CANDIDATES / COMPARATORS

### Oracle NetSuite REST asynchronous jobs — strong comparator, not a new promotion
Current Oracle docs continue to support a `REPLAY_ADDRESSABLE` pattern: asynchronous requests return a provider job; same-key duplicate submission returns the prior job location; job/task status and task results can be queried. The important red-team result this run is that **job-level success/failure should still be reconciled at task/item level where batching/partial outcomes exist**. A terminal provider job is not automatically one economic result.

### SAP S/4HANA Journal Entry - Post (Asynchronous) — watch / adjacent
Current SAP docs require a message-header ID and support outbound confirmation plus AIF/SRT monitoring. Cloud docs explicitly discuss reprocessing only entries with errors; on-prem docs say failed items cannot be reprocessed through AIF. This confirms that asynchronous financial operations can have item-granular outcome semantics. I did not establish a public source-backed rule that every failure confirmation means zero journal effects, so it stays a comparator rather than the canonical NOT_APPLIED source.

### SAP Transportation Management Carrier Invoice — useful domain oracle
SAP documentation states that a carrier invoice can be rejected only while **not yet posted to MM** and exposes a confirmation status `Invoice Posting Failed` when posting could not be completed. It also separately defines `Carrier invoice posted`. This is strong domain evidence that ERP workflows can explicitly separate *business object exists* from *financial posting happened*. It is especially relevant to Freight Recovery, but I did not validate an external API/readback contract sufficient to use it directly as the EXP-002 writeback adapter this run.

## CLAIMS TESTED

### Claim: any terminal `Failed` status can free reserved financial authority
**FALSIFIED.** Dynamics explicitly supports partial success and record-level failure keys. A job-level terminal state is not enough.

### Claim: a provider can expose stronger negative evidence than absence/search-zero
**SUPPORTED.** Dynamics `PreProcessingError` is explicitly phase-scoped before processing; SAP exposes request cancellation/error flows tied to posting semantics. These are provider-issued negative receipts, not inferred absence.

### Claim: `Canceled` is universally equivalent to `NOT_APPLIED`
**FALSIFIED / unsafe generalization.** In financial systems, `Canceled` can also describe reversal/cancellation of a previously posted business document. `NOT_APPLIED` is allowed only when the status is bound to the **original operation/request** and a documented pre-apply phase.

### Claim: message/job identity alone proves the economic result
**FALSIFIED.** Identity is necessary for correlation, but phase and item/effect scope determine whether the outcome is safe to classify.

## COMBINATIONS DISCOVERED

Upgrade the EXP-002 provider adapter contract from three outcome labels to an **evidence-bearing outcome receipt**:

```text
ProviderOutcomeReceipt {
  logical_effect_id,
  provider_operation_id,
  provider_phase,
  provider_status,
  effect_scope,              // whole operation vs item/record
  terminal,
  partial_effect_possible,
  evidence_source,
  observed_at,
  retention_expires_at?,
  classification: APPLIED | NOT_APPLIED | UNKNOWN
}
```

Classification rule:
- `NOT_APPLIED` only if provider evidence proves the exact effect never entered/apply phase or was explicitly rejected/canceled before posting.
- `APPLIED` only from positive provider/business evidence.
- everything else, including generic `Failed`, post-processing failure, partial success, timeout, missing record, expired replay identity, remains `UNKNOWN` until reconciled.

This composes directly with `effect-broker` and CAP-019 source-health semantics: the adapter returns a typed, provenance-bearing receipt instead of a naked status string.

## EMERGING TECHNOLOGY SIGNALS

**RAD-006 Authority-aware money assurance strengthens conceptually.** The provider mutation-safety registry now needs a sixth axis beyond identity/replay/retention/positive observation/negative completeness: **processing-phase semantics and partial-effect scope**.

The more important emerging pattern is `PROOF-CARRYING WRITEBACK`: consequential mutations are not considered resolved from transport results; the adapter emits an independently inspectable outcome receipt describing exactly what provider evidence justifies the economic classification.

## FAILURES / NEGATIVE KNOWLEDGE

1. Do not map `Failed` -> `NOT_APPLIED` generically.
2. Do not map `Canceled` -> `NOT_APPLIED` unless it is the exact original operation canceled **before apply/posting**.
3. Do not use job-level status when item/record-level partial success is possible.
4. `PostProcessingFailed` can occur after target processing; it is not safe negative proof.
5. `ProcessedWithErrors` and `PartiallySucceeded` explicitly require per-record reconciliation.
6. Preprocessing failure is promising only when the provider contract clearly defines that preprocessing precedes target mutation.
7. Provider message retention and business-record retention are different; expiry must preserve `UNKNOWN` if evidence can no longer be obtained.
8. An ERP business object may exist in a saved/error state while the financial posting did not occur; distinguish object creation from economic posting.
