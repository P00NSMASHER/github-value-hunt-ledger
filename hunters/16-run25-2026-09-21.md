## First-party contract verified

Microsoft's current recurring-integration documentation defines a durable message-status interface and distinguishes:

- `PreProcessingError`: the operation failed in the preprocessing stage.
- `ProcessedWithErrors`: processing completed with errors.
- `PostProcessingFailed`: failure occurred during post-processing.
- `Processed`: processing completed successfully.

The same interface maps the enqueued message ID to an execution ID and exposes execution errors. Source: [Microsoft recurring integrations documentation](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/data-entities/recurring-integrations), last updated January 22, 2026.

The separate package REST API requires callers to retain the returned execution ID and later query `GetExecutionSummaryStatus`; its terminal values include `Succeeded`, `PartiallySucceeded`, `Failed` and `Canceled`. It also provides source-to-staging and staging-to-target error artifacts. Source: [Microsoft Data management package REST API](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/data-entities/data-management-api), last updated April 3, 2026.

The official archived integration sample corroborates the executable identity lifecycle: it calls `ImportFromPackage`, retains the returned execution ID and polls `GetExecutionSummaryStatus(executionId)` until the job leaves `NotRun` / `Executing`. Exact source: [`microsoft/Dynamics-AX-Integration@fef1173a.../PackageImporter.cs`](https://github.com/microsoft/Dynamics-AX-Integration/blob/fef1173a479968dcf79bce5a5f7e93dc74c2d0d1/FileBasedIntegrationSamples/ConsoleAppSamples/DataPackageHandler/PackageImporter.cs).

## Safe classification rule implemented

The fixture admits `NOT_APPLIED` only when all of these are true:

1. A nonempty provider operation ID is bound to the expected logical effect.
2. The receipt is terminal.
3. Its scope is exactly one economic effect, not a batch or unknown scope.
4. The documented phase is `PRE_APPLY`.
5. The raw provider status is exactly `PreProcessingError`.
6. Partial application is impossible under the adapter's validated scope contract.

`ProcessedWithErrors`, `PostProcessingFailed`, generic `Failed`, ambiguous `Canceled`, mismatched logical identity and batch-scoped `PreProcessingError` all classify as `UNKNOWN`. They keep reverse capacity reserved.

`Processed` classifies as `APPLIED` only for the exact single effect after the economic fingerprint also agrees. A success-like job status without record-level semantic agreement cannot post the reversal.

## Planted lifecycle proof

The new test reserves an entire vendor-credit capacity, simulates an abandoned dispatch, supplies an exact singleton `PreProcessingError` receipt and verifies that the ledger moves to `NOT_APPLIED`. Only then can a replacement effect reserve the released capacity.

The replacement then receives each unsafe status and identity/scope mismatch as a planted negative. None is allowed to produce `NOT_APPLIED`. Finally, an exact `Processed` receipt with matching economic fingerprint produces one `REVERSAL_APPLIED` event and no duplicate.

## Claims tested

- **“A terminal provider failure proves nothing was applied” — falsified.** The package API explicitly includes `PartiallySucceeded`; recurring integration distinguishes errors after processing from preprocessing failure.
- **“Any failed recurring-integration message can be retried safely” — rejected for financial writeback.** Microsoft says a client may retry or take another action after a failed status, but only the documented pre-processing failure is eligible for this fixture's negative receipt, and only under exact single-effect binding.
- **“PreProcessingError alone is enough” — rejected.** A status detached from provider operation identity, logical effect identity or effect scope remains `UNKNOWN`.
- **“Processed proves the intended economic effect” — rejected.** Exact business semantics and fingerprint agreement are still required.
