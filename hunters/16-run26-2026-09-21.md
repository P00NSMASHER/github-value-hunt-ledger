## First-party evidence

At documentation revision `b81257fa8c6f2e0599f477653b740f4565649276`, Microsoft documents:

1. `VendorInvoiceHeader` / `VendorInvoiceHeaders` and `VendorInvoiceLine` / `VendorInvoiceLines` as public OData entities. The header creates or updates vendor-invoice headers; the line entity follows it; updates apply only before invoice posting. The header documentation describes pending/open vendor invoices, not a credit-note posting contract.
2. Vendor credit notes as real Dynamics Finance business documents. The current August 5, 2026 procedure supports purchase-order, invoice-journal, invoice-register and general-journal credit notes, uses the Credit invoicing function to reference the original invoice and then posts the credit note.
3. Recurring integration statuses including `PreProcessingError`, `ProcessedWithErrors`, `PostProcessingFailed` and `Processed`, with message-to-execution identity lookup.

Sources:

- [Vendor invoice header entity](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/data-entities/entity-vendor-invoice-header-vendorinvoiceheader)
- [Vendor invoice line entity](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/data-entities/entity-vendor-invoice-line-vendorinvoiceline)
- [Reference original invoices in vendor credit notes](https://learn.microsoft.com/en-us/dynamics365/finance/accounts-payable/gbl-original-invoice-numbers-credit-notes-ap), updated August 5, 2026
- [Recurring integrations](https://learn.microsoft.com/en-us/dynamics365/fin-ops-core/dev-itpro/data-entities/recurring-integrations), updated January 22, 2026

The inspected public sources do **not** state that the vendor-invoice header/line import entities create the documented vendor credit note, post that credit note, bind it to the original invoice, or make recurring-import preprocessing the last boundary before financial posting. The generic phase status is therefore insufficient for an AP `NOT_APPLIED` receipt.

## Fixture change

Added `ProviderEndpointContract` with these required facts:

- provider and exact interface;
- intended economic action;
- named posting boundary;
- verified credit-note capability;
- bound provider operation identity;
- verified phase-to-posting-boundary semantics.

`ProviderOutcomeReceipt.classify()` now requires this reviewed endpoint contract in addition to exact logical/provider identity, terminality, single-effect scope and phase/status semantics.

The new planted case proves:

- Exact singleton `PreProcessingError` with no endpoint contract → `UNKNOWN`.
- The documented `VendorInvoiceHeaders/VendorInvoiceLines` interface represented as invoice-only / credit capability unverified → `UNKNOWN`.
- Only a planted exact credit-capable endpoint contract with verified pre-posting semantics permits `PreProcessingError → NOT_APPLIED`.

The prior positive rule is also tightened: `Processed` cannot become `APPLIED` without both the endpoint contract and exact economic-fingerprint agreement.

## Claims tested

- **“A provider-wide status definition automatically applies to every financial endpoint” — falsified.** Phase semantics and economic endpoint semantics are separate authorities.
- **“Vendor invoice import implies vendor-credit posting support” — not supported by the inspected public documentation.** The docs separately establish invoice data entities and credit-note workflows but do not bind them.
- **“PreProcessingError is enough to free money authority” — falsified.** Without a reviewed endpoint-to-posting-boundary contract, it remains `UNKNOWN`.
- **“Current public Dynamics documentation is enough to call the adapter AP-credit ready” — rejected.** An authorized sandbox or stronger endpoint-specific contract is still required.
