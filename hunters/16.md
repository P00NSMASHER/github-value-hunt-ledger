### kinryukii/us-tech-quant-v21 — point-in-time SEC ingestion/provenance reference

- Exact commit / revision: c9a2e8e7a09876ec4f672b3f6945451a0b45051c
- Date inspected: 2026-09-19
- Status: watch
- What it contains: Research code for strict point-in-time SEC financial-statement ingestion and feature construction. The inspected pipeline keys facts to accession filings, makes them usable only after EDGAR acceptance time, fingerprints bulk Company Facts/Submissions snapshots, keeps manifest/hash provenance, writes atomically to JSON/Parquet, and maps multiple XBRL concepts into canonical financial categories.
- Rare or undernoticed value: The useful idea is not the trading model; it is the careful anti-lookahead data engineering around EDGAR. Point-in-time availability, accession/amendment identity, source hashing and atomic derived artifacts are exactly the details that distinguish a defensible historical financial dataset from a silently restated one.
- Monetization path: Clean-room implement the provenance/PIT design for financial diligence, research-data APIs, accounting analytics, issuer intelligence or audit-support products that need to answer “what was knowable on this date?” rather than only “what does the latest filing say?”
- Likely buyer / user: Quant/research teams, investment-data vendors, forensic accounting products, credit/risk teams, diligence platforms and financial-data engineering groups.
- Build-time or data advantage: Approximately 2–4 weeks of design/edge-case discovery can be compressed by studying its accession-time, amendment, concept-priority, snapshot-manifest and atomic-output patterns; direct code reuse is not authorized.
- Concrete evidence inspected: `scripts/v22/a2_pit_sec_fundamental_acceleration_alpha_r1.py` documents strict PIT semantics, bulk `companyfacts.zip`/`submissions.zip` contracts with SHA-256 and entry/byte counts, SEC URLs/rate limits, accession-aware availability, concept-priority maps, stable hashes and atomic JSON/Parquet writes. Search also surfaced data-layer documentation describing versioned `companyfacts.parquet`/`submissions.parquet` outputs with input file and manifest hashes.
- License / rights: No license detected in repository metadata at inspection. SEC public-source data has separate public-source terms, but this repository's source code remains copyrighted absent a license.
- Reuse classification: Inspect / learn / clean-room implementation only unless permission is established.
- Why it is not already obvious / crowded: The repository is presented as a quant-research project, so its reusable value as a PIT/provenance ETL reference is hidden inside strategy scripts and data-layer notes rather than packaged as a data-engineering library.
- Combination opportunities: Use the design concepts with a separately implemented SEC ingestion layer and `goldenmatch`/`dedupe` for issuer/entity identity. Could enrich federal-contractor or supplier intelligence where public-company linkage matters, but it is secondary to the cleaner USAspending/SAM opportunity stack.
- Next action: Extract a clean-room PIT ingestion specification—source snapshot manifest, accession/amendment keys, availability timestamp rules, immutable raw layer and deterministic derived Parquet—and validate it against a small set of amended 10-Q/10-K filings before considering a product use.

### OpenLineage/OpenLineage — cross-system lineage event standard and clients
- URL: https://github.com/OpenLineage/OpenLineage
- Exact commit / revision: e248b98e3146ff4437df76fcb07c83913d41f727
- Date inspected: 2026-09-19
- Status: strong
- What it contains: A production-scale Apache-2.0 lineage standard plus multi-language clients, integration modules, JSON schemas, generated models and a proxy. The inspected specification has first-class dataset/job/run identity plus facets for column lineage, schema, dataset versions, lifecycle changes, ownership, source-code location, input/output statistics, data-quality metrics/assertions, extraction errors and parent/child run relationships.
- Rare or undernoticed value: The repository is popular, but its value to the hunt is easy to underuse: it removes the need to invent a proprietary provenance envelope separately for every extraction, ETL and audit product. The extensible facet model can carry source/version/quality/error evidence while preserving a standard event graph across services.
- Monetization path: Embed it as the lineage/evidence plumbing beneath higher-value products rather than sell generic lineage itself. First paid wedge: use OpenLineage-compatible events inside a freight/AP recovery pilot or CaptureBrief ingestion pipeline so every derived finding can be traced to the exact input dataset/document version and processing run; later expose that evidence as audit/debug/compliance value.
- Likely buyer / user: Data-platform teams, regulated SaaS, finance/audit products, GovCon intelligence, scientific/lab platforms and any vertical product whose customer needs to defend how a derived result was produced.
- Build-time or data advantage: Roughly 2–4 months of schema/client/versioning/integration work avoided versus building a credible cross-service lineage protocol from scratch; incremental adoption can be much smaller because only the relevant event/facet subset is needed initially.
- Concrete evidence inspected: The repository root at the inspected revision contains `spec`, `client`, `integration`, `generator` and `proxy` subsystems plus a large changelog and release machinery. The `spec` tree contains `OpenLineage.json/.yml` and explicit facets including `ColumnLineageDatasetFacet`, `DatasetVersionDatasetFacet`, `LifecycleStateChangeDatasetFacet`, `SchemaDatasetFacet`, `DataQualityAssertionsDatasetFacet`, `DataQualityMetricsDatasetFacet`, `ExtractionErrorRunFacet`, `InputStatisticsInputDatasetFacet`, `OutputStatisticsOutputDatasetFacet`, `SourceCodeLocationJobFacet` and `ParentRunFacet`.
- License / rights: Apache-2.0 with root license/notice; directly reusable subject to license and notice obligations. External systems instrumented through integrations retain their own terms.
- Reuse classification: Directly reusable permissive infrastructure.
- Value score: A3 + B4 + C5 + D4 + E5 + F5 = **26/30**. Revenue speed is indirect because lineage is enabling infrastructure, but completeness, standards leverage and rights clarity are excellent.
- Why it is not already obvious / crowded: It is well-known in data engineering, so the opportunity is not obscurity; the non-obvious value is using it as a common evidence contract across multiple vertical products instead of independently designing provenance tables for each one.
- Combination opportunities: Freight recovery (`open_tms`/InvoiceKit/Docpipe/Assay) can emit document→extraction→normalized contract/invoice→finding lineage; CaptureBrief can trace SAM/USAspending inputs into scored briefs; FlowCept/lab automation can bridge computational and instrument evidence; Evidentia can consume the resulting lineage as compliance evidence.
- Next action: Implement one narrow OpenLineage event adapter around a synthetic freight-audit job and verify that source document hash/version, parser/ruleset version, normalized artifact and recovery finding can all be reconstructed from the emitted lineage without adding a new proprietary lineage schema.

### NiclasOlofsson/sqllens — lossless multi-dialect SQL parser, semantic analyzer and column-lineage engine
- URL: https://github.com/NiclasOlofsson/sqllens
- Exact commit / revision: ae24f646c0abf2b8ff1bcfac92432bd761c5afc0
- Date inspected: 2026-09-19
- Status: strong / Master contender
- What it contains: A TypeScript SQL parser and static analyzer that lowers SQL into a dialect-neutral IR, resolves scopes and names, qualifies fields from schemas, infers types, extracts references and traces column lineage across Databricks/Spark, T-SQL, Snowflake, BigQuery, Redshift, PostgreSQL, DuckDB, Trino/Presto/Athena, SQLite and MySQL/MariaDB. It also understands unrendered dbt/minijinja templates while preserving source spans.
- Rare or undernoticed value: Only three stars despite unusually deep semantics. Its design is evidence-friendly: “never wrong” means returning unknown instead of guessing, while “lossless” preserves every token and exact source span even for broken/incomplete input. Lineage records intermediate hops through CTEs/subqueries/joins rather than only source/destination pairs, making it useful for defensible transformation provenance and impact analysis.
- Monetization path: Embedded static-lineage engine or fixed-price lineage/impact diagnostic for data teams; alternatively use it internally to make higher-value finance/GovCon/recovery products explain exactly which source fields and SQL transformations produced a derived result.
- Likely buyer / user: Data-platform teams, regulated analytics/SaaS vendors, consultancies, governance/catalog vendors, dbt-heavy warehouses, finance/audit data teams and AI/data tooling companies needing reliable SQL context.
- Build-time or data advantage: Roughly 4–8+ months saved compared with independently building error-tolerant multi-dialect parsing, semantic resolution, type inference, templating-aware spans and column-lineage traversal.
- Concrete evidence inspected: Exact-revision README documents the AST→dialect-neutral IR→semantic pipeline, fail-closed/unknown behavior, lossless exact spans, multi-dialect support, dbt/minijinja parsing without rendering and lineage through CTEs/subqueries/joins. The tree contains substantial `src/lineage/hops.ts`, `src/lineage/lineage.ts`, per-dialect parser/IR implementations, type inference, scope/name resolution and broad tests: lineage/hops, batch parity/conservation, dialect corpora and known-bad corpora, minijinja, IR source spans and broken/incomplete SQL.
- License / rights: MIT, copyright Niclas Olofsson, verified from root `LICENSE` at the inspected revision.
- Reuse classification: Directly reusable permissive infrastructure subject to MIT notice/copyright terms.
- Value score: A4 + B5 + C5 + D5 + E5 + F5 = **29/30**. The only reason revenue speed is not a 5 is that the clearest near-term value is embedded infrastructure/consulting rather than a standalone end-user product.
- Why it is not already obvious / crowded: Created in June 2026 with only three stars; the name looks like a small SQL helper, while the source/test surface is closer to a serious compiler/static-analysis subsystem.
- Combination opportunities: Pair with OpenLineage so sqllens supplies static source-span/column-hop evidence and OpenLineage supplies cross-job/run/dataset transport. CaptureBrief and freight/AP pipelines can record SQL-derived feature/recovery lineage; compliance/restore-proof products gain transformation impact analysis without needing runtime instrumentation for every query.
- Next action: Benchmark sqllens on the actual SQL used by one current product and emit an OpenLineage-compatible column-lineage facet containing exact transformation/source-span references; measure unknown/unsupported cases rather than only successful parses.

### lpraat/inbq — BigQuery-native schema-aware lineage parser with procedural-query support
- URL: https://github.com/lpraat/inbq
- Exact commit / revision: 917a2715e3825cbe2cdf6fb26b848ffa6f39b74a
- Date inspected: 2026-09-19
- Status: strong
- What it contains: A Rust parser/lineage engine with lightweight Python bindings specifically for BigQuery SQL. It handles nested structs/arrays, schema-aware column lineage, referenced-column context, side inputs from WHERE/JOIN clauses, multi-statement queries and procedural constructs. Its pipeline API can capture errors instead of silently returning fabricated lineage and can parallelize batches.
- Rare or undernoticed value: Only three stars, but the exact-revision source contains a ~289 KB lineage engine, ~220 KB function semantics, ~216 KB parser and large declarative lineage/parsing test corpora. The BigQuery specialization is a strength where generic parsers often miss structs, arrays, UNNEST and procedural semantics.
- Monetization path: BigQuery lineage/impact-analysis service or embedded governance/evidence component for warehouse-heavy customers. First paid wedge: fixed-price warehouse lineage diagnostic that maps sensitive/revenue-critical output columns to source columns and filter/join dependencies before migrations or audit work.
- Likely buyer / user: BigQuery data teams, analytics consultancies, regulated SaaS, finance/data audit groups, migration teams and products whose decision outputs are computed in BigQuery.
- Build-time or data advantage: Approximately 3–6 months saved for a BigQuery-specific parser/lineage engine, especially nested data, procedural SQL and function semantics.
- Concrete evidence inspected: README demonstrates an `INSERT` driven by a declared variable, joins and nested struct fields and emits direct inputs, side inputs and referenced-column locations. Exact-revision tree contains `crates/inbq/src/lineage/engine.rs` (~289 KB), `functions.rs` (~220 KB), `parser.rs` (~216 KB), benchmarks plus `lineage_tests.toml` (~113 KB), `parsing_tests.toml` (~35 KB) and Rust/Python packaging/release workflows.
- License / rights: MIT in repository metadata and root license; dependencies retain their own licenses.
- Reuse classification: Directly reusable permissive infrastructure.
- Value score: A4 + B4 + C5 + D4 + E5 + F5 = **27/30**. It is narrower than sqllens but unusually deep inside its BigQuery scope.
- Why it is not already obvious / crowded: Three stars and a terse project name hide a substantial Rust implementation and unusually large semantic test corpus.
- Combination opportunities: Use as a BigQuery-specific oracle beside sqllens rather than forcing a single parser everywhere; discrepancies can become regression cases. Emit results through OpenLineage. Strong fit for CaptureBrief or finance/recovery analytics if their warehouse lands on BigQuery.
- Next action: Build a shared lineage conformance corpus from real-but-sanitized project SQL and cross-check inbq versus sqllens on BigQuery semantics, especially UNNEST, structs, arrays, scripts and side-input dependencies.
