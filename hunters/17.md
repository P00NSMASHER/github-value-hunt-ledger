### NewFan-TakashiHatakeyama/ai-ocr-agents
- URL: https://github.com/NewFan-TakashiHatakeyama/ai-ocr-agents
- Exact commit / revision: a06b5d980673084fa3451563b86e8d1e1aae2929
- Date inspected: 2026-09-19
- Status: strong
- What it contains: A functioning human-in-the-loop document extraction workflow with tenant-scoped review queues, page-image retrieval, OCR/extraction runs, engine-version reporting, spans with bounding boxes, field/table results, corrections, optimistic locking, review priority, reviewer locks with TTL, schema versioning, exclusion regions, batch extraction and explicit confirmed/exported state protections.
- Rare or undernoticed value: The valuable asset is not another OCR model; it is the operational review/control plane around extraction. The DTOs and tests encode many failure-prone details that teams often discover late: superseding an in-review run without overwriting confirmed/exported values, versioned corrections, reviewer locking, page-coordinate normalization, schema versioning and keeping correction context for later learning.
- Monetization path: Clean-room implement this workflow around a permissively licensed extractor to sell auditable document intake/review for AP invoices, freight documents, claims, permits, procurement packets or other high-value back-office workflows. The money is in reducing human review time while preserving traceable corrections rather than in commodity OCR itself.
- Likely buyer / user: AP and finance operations, freight-audit teams, insurers, permit/compliance processors, BPOs, accounting firms and vertical SaaS companies handling semi-structured documents.
- Build-time or data advantage: Roughly 3–6 weeks of product/workflow design can be compressed by independently reimplementing the observed state model, review queue, correction/version semantics and reviewer-locking behavior.
- Concrete evidence inspected: `services/gateway/src/newfan_gateway/dto.py` defines document/page metadata, extraction options, batch handling, `ResultResponse` with engine versions/fields/tables/review summary/fallback pages, `RunSpanDto` with text+bbox, corrections with original/corrected values and learning context, review queue priority and lock state. Searches located `/review/queue`, correction APIs in the web client, tenant-scoped queue reads, and `services/gateway/tests/test_extract_review.py` tests for correction optimistic locking and review queues.
- License / rights: No license detected in repository metadata at inspection. Public visibility does not authorize copying or commercial redistribution.
- Reuse classification: Inspect / learn / clean-room implementation only unless permission is established.
- Why it is not already obvious / crowded: Zero stars and no repository description, while the useful capability is buried in gateway DTOs, routes and tests rather than advertised as a document-ops platform.
- Combination opportunities: Reimplement the review/control-plane concepts around `getomni-ai/zerox` or another permissive extractor; pair with `microsoft/RulesEngine` for deterministic validation and `goldenmatch`/`dedupe` for supplier/entity normalization. Particularly relevant to the evidence-first freight/AP recovery stack.
- Next action: Produce a clean-room state diagram and API contract from observed behavior only, then validate it against synthetic invoices: upload → extract → needs_review → lock → correct → confirm → export, including concurrent-review and stale-version failure cases.
