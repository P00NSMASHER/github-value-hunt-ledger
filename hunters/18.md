### benseverndev-oss/goldenmatch
- URL: https://github.com/benseverndev-oss/goldenmatch
- Exact commit / revision: d3516270570fc648759a3cc64ed24d80392d0b50
- Date inspected: 2026-09-19
- Status: strong
- What it contains: A substantial entity-resolution and durable identity platform rather than only a fuzzy-match library. The inspected Python core implements Fellegi-Sunter matching with EM-trained m/u probabilities, log-likelihood weights, posterior/linear calibration modes, prior-aware evidence thresholds, positive-evidence safeguards, missing-value semantics, optional semi-supervised label anchors, and blocking-aware scoring. The repository also contains an identity-control-plane architecture for stable IDs, merge/split, provenance and audit, plus Python/Rust/SQL/WASM-oriented surfaces and parity/out-of-core tests.
- Rare or undernoticed value: The unusual part is the combination of statistically grounded match scoring with durable identity-state concepts. Most open ER libraries stop at pair scores/clusters; this project explicitly models stable identity, merge/split and provenance, which is closer to a commercial MDM/customer-360/vendor-master substrate.
- Monetization path: Package the matching/control plane as a shared entity-resolution service for vendor/customer mastering, AP duplicate prevention, permit/property normalization, procurement intelligence, CRM cleanup or public-record joins. Charge for managed matching pipelines, per-record processing, or high-value data cleanup/migration projects.
- Likely buyer / user: Finance/AP teams, procurement organizations, data-platform teams, B2B SaaS vendors, public-data intelligence products, systems integrators and companies consolidating messy CRM/ERP records.
- Build-time or data advantage: Estimated 2–5+ months saved versus building/calibrating probabilistic linkage, clustering guards, provenance and identity-state behavior from scratch. Particularly valuable as an alternate or complement to the already-cataloged dedupeio/dedupe when stable IDs and audit/provenance matter.
- Concrete evidence inspected: `packages/python/goldenmatch/goldenmatch/core/probabilistic.py` implements Fellegi-Sunter/EM, calibration, priors, evidence gates and missing-value policy. Repository searches located active tests including `test_fs_disagree_route_parity.py`, `test_fs_out_of_core.py`, `test_spark_fs_parity.py`, CI coverage, and architecture/docs describing stable IDs, merge/split, provenance, audit and field-level provenance. Repository metadata at inspection showed active development, 132 stars, 14 forks and MIT licensing.
- License / rights: MIT at the inspected repository state. Normal MIT notice/copyright obligations apply. Performance and quality claims in repository documentation should not be repeated commercially without independent benchmarking.
- Reuse classification: Directly reusable subject to MIT terms.
- Why it is not already obvious / crowded: It is newer than the canonical ER projects and has modest attention relative to its breadth. Its highest-value identity-control-plane work is easy to miss if evaluating it only as another fuzzy-matching package.
- Combination opportunities: Benchmark beside `dedupeio/dedupe`; use as the entity spine behind `DominicFinn/open_tms`, AP/recovery stacks, PermitPlate, CaptureBrief and USASpending/SAM.gov joins. GoldenMatch's provenance/stable-ID layer could sit downstream of OCR/document extraction so extracted supplier/customer identities remain traceable across revisions.
- Next action: Run an independent benchmark on lawful synthetic/public vendor/company data against `dedupeio/dedupe` and a simple exact/fuzzy baseline, emphasizing precision at auto-link thresholds, cluster stability across incremental updates, split recovery and provenance completeness rather than repository headline performance.

- Exact commit / revision: df9bc75ba63f93fed71b21d2c30c8c1cd06a2d57
- Date inspected: 2026-09-19
- Status: strong
- What it contains: A mature MIT probabilistic record-linkage engine with multiple SQL backends and a large implementation/test surface for blocking, comparison levels, probabilistic parameter estimation, accuracy analysis, connected components and clustering. The inspected package exposes DuckDB, PostgreSQL, Spark and SQLite backends; internals include substantial blocking, blocking-analysis, comparison, connected-components and clustering modules rather than delegating the core problem to an external model.
- Rare or undernoticed value: Splink is not obscure, but it materially strengthens the hunt's identity stack because it operationalizes statistically grounded linkage at SQL-scale and provides a mature test corpus around blocking and clustering. GoldenMatch is more interesting for durable identity/merge-split control-plane semantics; Splink is the stronger reference when the immediate bottleneck is high-volume probabilistic linkage over warehouse-sized data.
- Monetization path: Use it as the matching engine in paid supplier/vendor master cleanup, customer/CRM consolidation, public-record joins or recurring identity-quality SaaS. First paid wedge: a fixed-price AP/vendor-master diagnostic that ingests two or more ERP/vendor lists, produces high-confidence auto-links plus a review band, quantifies duplicate/vendor fragmentation, and then converts into a managed recurring master-data service.
- Likely buyer / user: Finance/AP and procurement teams, data-platform teams, public-data intelligence products, systems integrators, insurers, healthcare/regulated data teams and enterprises consolidating CRM/ERP/customer records.
- Build-time or data advantage: Roughly 3–6+ months of probabilistic linkage, blocking, SQL-backend and clustering engineering avoided compared with building an industrial-scale engine from scratch; the main remaining work is domain-specific comparison design, evaluation, governance and durable identity semantics.
- Concrete evidence inspected: The current package tree includes large `internals/blocking.py`, `blocking_analysis.py`, `comparison_level_library.py`, `comparison_library.py`, `connected_components.py` and `clustering.py` implementations plus DuckDB/Postgres/Spark/SQLite backend modules. The test tree contains broad fixtures and tests including `test_accuracy.py`, `test_analyse_blocking.py`, `test_array_based_blocking.py`, `test_chunking.py`, `test_cluster_at_multiple_thresholds.py`, `test_cluster_using_single_best_links.py`, `test_clustering.py` and compatibility/parameter-history datasets. Repository metadata identifies entity-resolution, EM-algorithm and deduplication topics and active development.
- License / rights: MIT with an explicit root `LICENSE`; directly reusable subject to MIT notice/copyright terms. Test datasets/third-party dependencies retain their own terms and should be reviewed before redistribution.
- Reuse classification: Directly reusable permissive infrastructure.
- Value score: A4 + B5 + C5 + D4 + E5 + F5 = **28/30**. Revenue can be fast through a services-first data-cleanup wedge, while the mature implementation and permissive rights materially reduce technical risk.
- Why it is not already obvious / crowded: It is a known linkage project, so the value is not obscurity; the underused opportunity is treating it as immediately sellable infrastructure for expensive master-data cleanup and cross-dataset intelligence rather than as a research/data-science library.
- Combination opportunities: Pair with GoldenMatch's stable-ID/provenance/merge-split layer and benchmark against `dedupeio/dedupe`. Use it for USAspending↔SAM↔company linkage in CaptureBrief, carrier/vendor identity in freight recovery, owner/property/entity joins in PermitPlate and supplier normalization across AP/audit products.
