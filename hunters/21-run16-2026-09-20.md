## Search direction
EXP-007, CAP-017 and SEARCH_QUEUE identify one concrete missing edge before more broad lab-device discovery: an ambiguous physical action must enter `UNKNOWN`/recovery and must not be blindly redispatched. This run therefore audited the **dispatch → lost response → same-action readback → UNKNOWN → retry** transition rather than adding another generic LIMS/device framework.

## Starting hypothesis
A production-shaped lab orchestrator may already implement the safe first half of an ambiguous-action contract: if a physical action may have been accepted but the dispatch response is lost, preserve one action identity, query that same action, and fail closed to `UNKNOWN` if the outcome cannot be recovered. The decisive red-team question is whether later retry/resume APIs preserve that identity/reconcile physical state or silently create a new action and redispatch.

# BEST NEW FIND / EVIDENCE DELTA

## AD-SDL/MADSci
- Canonical URL: https://github.com/AD-SDL/MADSci
- Exact revision: `6b1ab6a70ce8b15af7aa8968479c90d9138753d0`
- Status: **STRONG COMPONENT for in-session ambiguity handling; NOT safe exactly-once/retry authority**
- Score: **25/30** — A4 B4 C5 D3 E5 F4
- Public license/provenance: MIT, UChicago Argonne LLC.

### What is actually implemented
The Workcell Manager creates a single `ActionRequest` and therefore a single generated `action_id` for a dispatch attempt. If `send_action(..., await_result=False)` throws before the manager receives a response, current source does **not immediately call `send_action` again**. Instead it constructs a `RUNNING` response with the same request/action identity specifically so `monitor_action_progress()` can query `get_action_result(action_id)` in case the node created the action but the response was lost.

`monitor_action_progress()` then polls that same action ID with capped exponential backoff. A recovered terminal result is accepted. If repeated result queries fail beyond the configured retry count, the request is converted to `UNKNOWN`; `finalize_step()` treats `UNKNOWN` as a workflow failure and ends the workflow rather than advancing downstream steps.

The persisted runtime step also records the returned `ActionResult` and an action-history sequence keyed by `action_id` and status, so the identity is not merely a local log string during normal execution.

### Tests / history
Current tests include both critical branches:
- `send_action` throws, `get_action_result` subsequently returns `SUCCEEDED` → step finishes `SUCCEEDED`.
- `send_action` throws and `get_action_result` also fails → step/result finish `UNKNOWN`.

History is particularly strong. Commit `5c62a070c8dcbc62bc91077cd133a62e45949691` (2025-03-23), titled **“Add tests for failures in the send_action->get_action_result cycle”**, introduced explicit result-query retries and ambiguity handling. At exact head, GitHub Actions include successful workflows for the revision, and the repository labels itself beta rather than production-certified.

### Independent RED-TEAM / VERIFIER verdict
**STRONG for the narrow in-session lost-response invariant, but the full EXP-007 no-blind-redispatch invariant is NOT yet satisfied.**

The important loophole is the generic workflow retry endpoint. `finalize_step()` converts an unresolved action to workflow `failed`, making it terminal. `/workflow/{workflow_id}/retry` accepts any terminal workflow, resets its status to the failed step, re-enqueues it, and does not require physical-state reconciliation or special handling for a prior `UNKNOWN`. On the next `run_step()`, the engine constructs a **new `ActionRequest` whose `action_id` uses a fresh ULID default**. Therefore an operator/API retry after an unresolved physical action can create a new identity and redispatch the same physical step.

The checked retry test proves retrying a terminal/cancelled workflow is intentionally supported, but there is no inspected test that blocks retry after an `UNKNOWN` physical action until the original action is reconciled. Targeted search also found no startup/restart reconciliation path that scans persisted running/UNKNOWN action identities and deterministically re-queries them before replay.

### Why this matters
The system already contains most of the right ingredients—stable per-attempt action IDs, same-action readback, `UNKNOWN`, persisted step history, terminal fail-closed behavior—but the **recovery gate is at the wrong boundary**. `UNKNOWN` is safe only if all subsequent control surfaces honor it. A generic retry button that creates a fresh action can reintroduce the double-actuation risk the original ambiguity logic was designed to prevent.

### Commercial implication
This sharpens the first paid wedge into a concrete **Physical-Action Ambiguity Acceptance Test** for laboratory automation. Fault-inject one instrument action so the device applies the side effect but the response is lost. PASS requires: one dispatch identity; same-action readback; unresolved outcome becomes `UNKNOWN`; downstream actions remain blocked; retry is disabled until independent device/state reconciliation; and process restart preserves enough identity to make the same decision. This is a stronger, sellable commissioning/upgrade regression pack than generic “lab orchestration QA.”

# COMBINATIONS DISCOVERED

The installed-base lab stack now has a precise recovery contract:

`LIMS/workflow identity → one physical action identity → vendor/device actuation → independent same-action readback → SUCCEEDED/FAILED/UNKNOWN → recovery gate → downstream workflow → provenance evidence`.

MADSci can supply the action/workflow state machine, `ot2_module` supplies a concrete vendor-native run identity for fault injection, `simlab` can supply a no-hardware physical-action surrogate, and Flowcept can record the evidence trajectory. The critical missing component is **not another orchestrator**; it is a recovery gate that prevents `UNKNOWN → generic retry → new physical action` until original-state reconciliation is complete.

# CLAIMS TESTED

### Verified
- Lost dispatch response can be recovered by querying the same MADSci action ID rather than immediately redispatching.
- Repeated result-query failure becomes `UNKNOWN`.
- `UNKNOWN` fails the workflow and does not advance the step.
- Step result/history persist action IDs/statuses during normal execution.
- Generic workflow retry resets a terminal workflow and re-enqueues the same failed index.
- A new run-step attempt constructs a new `ActionRequest`, whose action ID defaults to a fresh ULID.
- MADSci has explicit tests/history for send→result failure handling.

### Not verified / falsified
- **Falsified as a system-wide guarantee:** “MADSci prevents blind redispatch after an ambiguous physical action.” It prevents it in the immediate monitor loop, but the generic retry surface can create a new action without mandatory reconciliation.
- No restart-durable exactly-once physical-action reconciliation was verified.
- No inspected real-hardware test proves the ambiguity branch against an actual instrument.
- Local world-state mutation is not independent physical verification (`plr-lab-robot` negative oracle).

# EMERGING TECHNOLOGY SIGNALS

# FAILURES / NEGATIVE KNOWLEDGE

1. Do not credit “UNKNOWN” as safe merely because the immediate worker stops. Trace every retry/resubmit/operator path after UNKNOWN.
2. A fresh request/action ID on retry is dangerous for non-idempotent physical actions unless the previous action has been independently reconciled.
3. Device/client polling that swallows exceptions indefinitely is not evidence of safe recovery.
4. A postcondition derived from state the command itself mutated is not independent physical verification.
5. Simulation becomes materially valuable only when it can plant ambiguous outcomes, not merely reproduce happy-path motion.
