# BEST NEW FIND / EVIDENCE DELTA

## AD-SDL/MADSci — restart converts unresolved execution into local CANCELLED without physical reconciliation
- Canonical URL: https://github.com/AD-SDL/MADSci
- Exact revision: `6b1ab6a70ce8b15af7aa8968479c90d9138753d0`
- Status: **STRONG COMPONENT for same-session ambiguity handling; FAIL for restart-safe exactly-once physical-action authority**
- Existing portfolio score: **25/30** for the useful component, unchanged. No score inflation from this negative finding.
- Public provenance: MIT repository code. Device/vendor runtimes, customer records and physical equipment remain independently governed.

### Source-level restart path
At WorkcellManager engine construction, `Engine.__init__()` initializes the state handler and then immediately calls `cancel_active_workflows(state_handler)` before the normal scheduler loop begins.

`cancel_active_workflows()` applies `cancel_workflow()` to every workflow whose status is active. `cancel_workflow()` sets the workflow to `cancelled`, stops `running`, and mutates the current step to `ActionStatus.CANCELLED`. Critically, it assigns:

`step.result = ActionResult(status=ActionStatus.CANCELLED)`

without passing the original action ID.

`ActionResult.action_id` has its own `default_factory=new_ulid_str`. Therefore a manager restart can replace the current step result with a **new local result identity** that is unrelated to the physical action that may still have executed or may still be executing. This transition is based on local process lifecycle, not independent device state.

The prior action identity can survive in `step.history` if it was persisted before the interruption, because `Step` stores a latest `result` plus a list of `ActionResult` history and `set_active_workflow()` serializes the workflow. But startup does not inspect that history and re-query unresolved action IDs before it emits local `CANCELLED` state.

### Retry after restart
The generic retry endpoint accepts any terminal workflow, calls `wf.status.reset(index)`, restores it to active state, deletes the archived copy and re-enqueues the failed/cancelled step. It has no guard for a prior physical `UNKNOWN`, no requirement to recover an original vendor-native run/command ID, and no reconciliation disposition.

On the next execution, `run_step()` constructs a brand-new `ActionRequest`. `ActionRequest.action_id` also uses a fresh ULID default. The resulting sequence can therefore be:

`physical side effect may have happened -> manager/process interruption -> startup marks local CANCELLED with a different result ID -> operator/API retry -> new ActionRequest ID -> physical step may be dispatched again`.

This is stronger negative evidence than Run 16's generic UNKNOWN-retry loophole because **restart itself creates a false local-finality transition before any independent physical readback**.

### Resubmit is an even wider escape hatch
`/workflow/{workflow_id}/resubmit` intentionally creates a new workflow from the original definition and inputs and queues it as a new run. That behavior is reasonable for ordinary software jobs, but it cannot be treated as safe recovery for a non-idempotent unresolved physical action unless an external recovery gate prevents use while the prior effect is ambiguous.

### Tests and roadmap evidence
`test_retry_workflow` explicitly proves that a cancelled terminal workflow can be reset and retried at the same workflow ID. The test is a positive API-behavior test; it does not require physical reconciliation or preserve an original external action identity.

MADSci's own 1.0 roadmap independently confirms that recovery semantics are still an active hardening area. Issue #322, **Error Recovery: Recovery workflow framework + retry/cooldown/circuit-breaker primitives**, remains open and is labeled a **1.0 blocker**. Issue #321 plans rule-driven actions including retry-workflow-step/restart-node/recovery-workflow, and #247 contemplates autonomous troubleshooters authorized to retry workflows. Issue #363 describes an operational failure path where a terminal-run workflow presents an operator with the option to retry from the failed step. These roadmap items make ambiguity-safe retry a practical, not merely theoretical, boundary.

### Independent RED-TEAM / VERIFIER verdict
**FAIL for restart-safe exactly-once physical execution. STRONG remains justified only for the narrower same-session behavior already verified in Run 16.**

The verifier tried to rescue the claim using persisted `step.history`, but failed: persisted historical identity is not enough when startup does not consult it before mutating the workflow to local CANCELLED, current `step.result` is overwritten with a fresh ID, and the retry surface can issue a fresh `ActionRequest` without a reconciliation record. No inspected source/test proved startup same-ID/device-ID reconciliation or an UNKNOWN/CANCELLED-specific retry block.

This does **not** prove the physical device is double-actuated in production. It proves the current orchestrator state machine does not establish the invariant required to rule that out.

# REQUIRED EXP-007 RESTART FIXTURE

The synthetic acceptance corpus should now include a hard manager-restart cut between external side effect and safe local finality:

1. Create a synthetic/non-PHI node action with a durable external `device_operation_id` and a side-effect counter.
2. Dispatch once and apply the simulated physical side effect.
3. Drop/withhold the dispatch response or result so the manager cannot prove success.
4. Persist enough workflow state to contain the original MADSci action identity, then terminate the WorkcellManager before reconciliation completes.
5. Restart against the same durable/cache state.
6. Assert startup does **not** convert ambiguity into authoritative `CANCELLED` or create a substitute result identity for recovery purposes.
7. Assert the original MADSci `action_id` and vendor/device operation ID remain first-class recovery keys.
8. Recovery branch A: same-ID/device-ID readback proves `CONFIRMED_APPLIED`; downstream may continue without redispatch.
9. Recovery branch B: readback remains unresolved; state remains `UNKNOWN/RECONCILIATION_REQUIRED`; retry/resubmit is blocked.
10. Recovery branch C: independent device/state evidence proves `CONFIRMED_NOT_APPLIED / SAFE_TO_REISSUE`; only then may a new attempt ID be created, linked explicitly to the original ambiguous attempt.

### Minimal durable recovery record
A defensible implementation should preserve at least:
- workflow ID and step ID;
- orchestration action ID;
- vendor/device-native operation/run/command ID when available;
- immutable intent fingerprint over action + material args/files/locations/version;
- dispatch/observation timestamps;
- last independently observed device state/result and evidence source;
- ambiguity reason;
- recovery disposition (`RECONCILIATION_REQUIRED`, `CONFIRMED_APPLIED`, `CONFIRMED_NOT_APPLIED`, `SAFE_TO_REISSUE`);
- any replacement attempt ID with an explicit parent/original edge.

The exact schema can vary; the invariant cannot: **process restart is not physical cancellation, and local retry is not proof that the previous physical effect did not occur.**

# COMBINATIONS DISCOVERED

The installed-base lab stack should now distinguish **three identities** instead of one:

`workflow/step identity -> orchestration action-attempt identity -> vendor/device-native operation identity`.

Flowcept-like provenance can preserve the lineage, but provenance is not the recovery authority by itself. A vendor-native run/command ID from an adapter such as the Opentrons surface is especially valuable because it gives the recovery gate something independent to query after manager restart.

The corrected control contract is:

`intent fingerprint -> one dispatch attempt -> external operation identity -> independent readback -> CONFIRMED_APPLIED / CONFIRMED_NOT_APPLIED / RECONCILIATION_REQUIRED -> governed continuation or linked reissue`.

# CLAIMS TESTED

### Verified
- MADSci same-session lost-response handling preserves one request action ID and queries that same ID before declaring `UNKNOWN`.
- On engine startup, MADSci calls `cancel_active_workflows()`.
- Active workflows are converted to local `CANCELLED` without a device-result reconciliation step in that startup path.
- The current step's `result` is replaced by a newly constructed `ActionResult(CANCELLED)` whose action ID defaults to a new ULID.
- Prior action IDs may survive in `step.history`, but the startup path does not use them to reconcile the physical action before cancellation.
- Generic retry resets a terminal workflow and re-enqueues the step.
- Re-execution creates a fresh `ActionRequest` and therefore a fresh action ID.
- The current MADSci roadmap still treats retry/recovery primitives as 1.0 hardening work.

### Falsified / not verified
- **Falsified as an established invariant:** manager restart preserves the authoritative original physical-action identity and reconciles it before changing state.
- **Falsified as an established invariant:** local `CANCELLED` after manager restart proves the external physical action was cancelled/not applied.
- **Not verified:** retry/resubmit is blocked while any prior physical effect remains unresolved.
- **Not verified:** a real instrument or simulator has passed a kill/restart ambiguity acceptance test at this exact revision.
