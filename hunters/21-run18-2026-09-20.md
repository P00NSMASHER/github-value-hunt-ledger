# BEST NEW FIND

## Opentrons/opentrons — Robot Server run/action persistence is the missing independent recovery plane
- URL: https://github.com/Opentrons/opentrons
- Exact revision: `03b991fb263b97b6bb767ce311ca56e103d635e4` (`edge`, verified 2026-09-20)
- Status: **STRONG COMPONENT / EXP-007 challenger**
- Score: **27/30** — A4 B4 C5 D4 E5 F5
- Public license: Apache-2.0. Physical robots, customer protocols/data, third-party labware/assets and commercial support terms remain independently governed.

### What is concretely implemented
The official Robot Server assigns every run a stable `run_id`. `POST /runs/{runId}/actions` creates typed run-control actions (`play`, `pause`, `stop`, recovery resumes). `RunAction` has a unique server-generated action ID and timestamp. The public `Run` resource includes status, whether it is current, started/completed timestamps, and the complete client-initiated action list ordered oldest to newest.

`RunStore` persists runs and actions in SQL. `insert_action()` commits an action row against the run, and `GET` reconstruction selects those rows in order. This makes the robot server a materially more independent state plane than MADSci's local workflow status.

### Restart evidence
Official integration tests explicitly stop and restart the Robot Server process. They verify:
- runs persist after restart;
- a run started through the actions router persists with its final state;
- run subresources including run actions persist through restart;
- run commands can be re-fetched by their original command IDs after restart;
- started/completed timestamps survive restart.

This is the first inspected public component in the current EXP-007 thread that provides a tested external run identity plus restart-persistent action/state evidence.

### Why it closes part of EXP-007
For an MADSci-controlled Opentrons run, MADSci can persist the `run_id` before issuing `play`. If the `play` HTTP response is lost and only MADSci restarts, the recovery path can query `GET /runs/{run_id}` instead of trusting MADSci's restart-created local `CANCELLED` result.

A returned run with a recorded `play` action and status such as running/succeeded/failed/stopped is independent evidence that prevents blind creation of a second run merely because MADSci lost its local response.

### Important asymmetry: proving APPLIED is easier than proving SAFE_TO_REISSUE
The verifier found a boundary that prevents a full exactly-once claim:
- `RunActionCreate` accepts only `actionType`; the client does not supply the action ID/idempotency key.
- The action ID is generated server-side by the router.
- `RunController.create_action()` initiates the side effect (`task_runner.run(...)` for first play, or `play()` for resume) and only afterward calls `RunStore.insert_action()`.

Therefore there is a narrow Robot-Server crash window where the side effect may begin before the `RunAction` record is committed. More generally, after an ambiguous network outcome, **absence of a persisted play action is weaker evidence than presence of one**. The run-level status and command state can still help, but a universal `SAFE_TO_REISSUE` conclusion needs stronger device-specific proof or a client-supplied idempotency/receipt contract.

### Independent RED-TEAM / VERIFIER verdict
**STRONG as an external reconciliation component; NOT sufficient by itself for end-to-end exactly-once physical execution.**

The positive branch is strong: stable run identity, persisted actions/status, and restart tests allow independent confirmation that an action/run exists or completed. The negative branch is intentionally narrower: there is no inspected client-defined idempotency key for `play`, action persistence follows side-effect initiation, and the restart tests are Robot Server/dev-server integration tests rather than a physical Flex/OT-2 kill/restart ambiguity campaign.

This calibration materially improves EXP-007 because it tells us exactly what can be proven today and what must remain `RECONCILIATION_REQUIRED`.

# FAILURES / NEGATIVE KNOWLEDGE

1. `run_id` persistence alone is not exactly-once execution.
2. Server-generated action IDs are less useful for response-loss idempotency than client-supplied request IDs because the client may never receive them.
3. Persisting an action after initiating its side effect leaves a crash-ordering window; action-history absence cannot universally prove no effect.
4. A wrapper that catches/prints ambiguous POST or polling errors without a terminal recovery state must not authorize replay.
5. Dev-server restart tests are strong software evidence but do not replace a physical-robot HITL fault campaign.
6. `CONFIRMED_APPLIED` and `CONFIRMED_NOT_APPLIED` require different proof burdens; do not infer the latter merely by negating the former.
