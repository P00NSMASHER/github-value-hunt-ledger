### STANDARD / SCIENCE VALIDATOR
Official SiLA 2 Specification v1.1 was used as the protocol authority.

**Part A — observable commands:** after command initiation and acceptance, the SiLA Server returns the `Command Execution UUID` to the SiLA Client; that UUID is then used for execution-info, intermediate-response, and final-response queries. The UUID's validity is scoped to the lifetime of the server/execution as defined by the protocol.

**Part B — mapping:** the command-initiation request contains the generated `<CommandIdentifier>_Parameters`; the response is `CommandConfirmation`, which contains the `CommandExecutionUUID` (plus optional execution lifetime). The standard initiation request does not contain a field for the client to choose the `CommandExecutionUUID`.

This matters because MADSci's design document currently says:
> SiLA assigns a `CommandExecutionUUID` to every observable command. MADSci's `ActionRequest.action_id` (a ULID) is the canonical client-side ID; we map it 1:1 onto the SiLA UUID by passing the action_id at command-create time.

The current standard initiation contract does not provide that direct client-selected execution-UUID field, and a ULID string is not literally the RFC-4122 UUID form specified for `CommandExecutionUUID`. A custom MADSci server could add correlation metadata or custom logic, but that would be an application-specific extension—not the standard behavior implied by "pass action_id at command-create time."

## Search-policy lesson
**Candidate local lesson:** `Server-Assigned Receipt Persistence Boundary`.

WHEN TO USE: a lab/device protocol assigns the durable operation identifier only after accepting a mutating command.

PROCEDURE:
1. locate the request/confirmation boundary;
2. determine whether the client can preselect an idempotency/correlation identifier;
3. persist `(client intent, server identity, operation receipt)` before declaring the action safely trackable;
4. fault-inject before receipt, after receipt but before local commit, client restart, and server restart separately;
5. require UNKNOWN/RECONCILIATION_REQUIRED unless independent evidence makes reissue safe.

WHY IT WORKED: it exposed a gap hidden by both a client-generated `action_id` and a standard server-generated `CommandExecutionUUID`—each exists, but continuity across the acknowledgment seam is the safety property.

FAILURE MODES: assuming equal IDs solve correlation; treating transport exception as "not applied"; treating durable history as recovery unless startup uses it; treating server restart as equivalent to client restart; treating a standards-compliant UUID as an idempotency token.

STATUS: local only. This is one EXP-007 hunt family and is **not** eligible for promotion to `SEARCH_SKILLS.md` yet.
