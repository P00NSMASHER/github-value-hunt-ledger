### PROTOCOL / SCIENCE VALIDATOR — official SiLA semantics
The SiLA 2 v1.1 protocol establishes three important facts:

1. An observable command is initiated with its **parameters**; after acceptance the server returns a `CommandConfirmation` containing the `CommandExecutionUUID` and optional `LifetimeOfExecution`.
2. The `CommandExecutionUUID` is the handle used for subsequent execution-info/intermediate/result calls.
3. The execution UUID is unique **within one instance / lifetime of a SiLA Server**. The specification separately defines `ServerUUID` as a globally unique server identifier that is generated once and remains the same even after a SiLA Server lifetime ends.

This yields a critical identity-scope distinction:

- `ServerUUID` = stable logical server identity across restarts/lifetimes.
- `CommandExecutionUUID` = operation identity scoped to a particular server execution lifetime.

Therefore `same ServerUUID after restart` is **not** proof that an old command receipt is still queryable or authoritative.

**Evidence labels:** protocol identity/lifetime semantics **VERIFIED from authoritative specification**.

### CURRENT PACKAGE / IMPLEMENTATION VALIDATOR
Current `sila2` 0.14.0 documentation exposes a public `ClientObservableCommandInstance` constructor that accepts an already-known `execution_uuid`. This is precisely the client-side primitive required to rebind after a **client-only** restart: recreate the client/feature/command objects, construct an observable-command instance with the saved execution UUID, and query the same operation rather than sending a new command.

The historical 0.10.4 reference source independently shows how this works internally:
- `ClientObservableCommand.__call__()` receives `CommandConfirmation`, extracts `(exec_id, lifetime)`, and creates `ClientObservableCommandInstance(..., exec_id, lifetime)`.
- `ClientObservableCommandInstance` stores `execution_uuid`, subscribes to `..._Info` using that UUID, and calls `..._Result` with the same UUID.
- The reference server allocates `uuid.uuid4()` for each observable command and holds managers in an in-memory map keyed by that UUID.

This historical source matches the current documented constructor/API shape, but it remains a reference implementation oracle rather than proof of current 0.14.0 server internals.

- Concrete rebind mechanism in old 0.10.4 source: **IMPLEMENTED historically**.

## Search-policy lesson
**Candidate local lesson:** `Execution-Identity Scope Audit`.

**WHEN TO USE:** a physical-control protocol exposes both a stable endpoint/server identifier and a separate operation/execution identifier.

**PROCEDURE:**
1. identify client intent ID, endpoint/server ID and external operation ID;
2. write the exact uniqueness/lifetime scope of each identifier;
3. locate where the external operation ID is allocated and when the client can durably capture it;
4. find a supported API to rebind/query by that ID after **client** restart;
5. test **server/service** restart separately;
6. treat stable endpoint identity as insufficient whenever operation identity is lifetime-scoped;
7. trace every retry/resubmit surface before granting `SAFE_TO_REISSUE`.

**WHY IT WORKED:** this run found that SiLA's `ServerUUID` is intentionally stable across server lifetimes while `CommandExecutionUUID` is scoped to a server lifetime. Without a scope audit, a system could falsely trust “same server” after restart even though the operation receipt is no longer authoritative.

**FAILURE MODES:** conflating endpoint and operation identity; converting invalid/expired operation ID into NOT_APPLIED; testing client restart but not server restart; assuming a public constructor implies live restart proof; transferring semantics across SDK implementations.

**STATUS:** local only, evidence count 1 distinct hunt family. Do **not** promote to `SEARCH_SKILLS.md` yet.
