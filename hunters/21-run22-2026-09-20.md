## Proposed EXP-007 normalization acceptance contract
Every case should persist:
1. source URL/dataset accession and per-file license evidence;
2. immutable raw bytes plus SHA-256 (retain chromConverter’s source SHA-1 too, but add SHA-256 externally);
3. vendor family, file format/version where detectable and instrument model where authoritative;
4. exact chromConverter commit/package version, external parser versions and OS/runtime;
5. normalized object/open-format output;
6. independent oracle tool/version and its own output hash;
7. field-level preservation results with explicit tolerances;
8. `PASS / DISAGREE / UNSUPPORTED / RIGHTS_BLOCKED / ORACLE_UNAVAILABLE`, never silent coercion.

### Minimum preservation checks
- time/retention axis and units;
- signal/channel identity and intensity values/units;
- dimensions/scan or point count;
- sample/instrument/detector metadata when present in source;
- for MS data: m/z, MS level and polarity where available;
- source hash, source format and parser identity;
- missing source metadata remains UNKNOWN/absent rather than being invented.

### Negative controls
- source-hash mismatch;
- truncated/corrupt input;
- wrong/unsupported format version;
- optional dependency missing;
- independent oracle disagreement outside declared tolerance;
- required provenance field lost during export/round-trip;
- fixture with missing/unclear dataset rights;
- test skipped because a fixture/dependency is absent.

None of those states may become green. A skipped parser path is **INCOMPLETE**, not PASS.

**Verdict: strong methodology, but oracle independence must be declared per field.** A converted mzML is a useful independent representation for m/z, scan identity and some metadata, but vendor preprocessing can change profile intensities. Where the converter and parser share vendor libraries or a common implementation, the comparison is correlated evidence and should be supplemented with file-internal invariants or a second engine.

## SEARCH POLICY UPDATE
### Candidate local lesson: Rights-Annotated Fixture Lineage Audit
**WHEN TO USE:** scientific parsers/converters whose test corpus mixes contributor files, external repositories and public datasets.

**PROCEDURE:**
1. inventory each load-bearing fixture separately;
2. trace it to original source/dataset and pin revision/accession;
3. verify per-file/dataset rights independently of repository code rights;
4. trace the fixture into exact numerical/metadata tests;
5. identify oracle generation path and correlated assumptions;
6. replace unclear-rights fixtures with separately licensed equivalents before calling the benchmark commercially reusable.

**WHY IT WORKED:** it exposed that the companion corpus is simultaneously unusually well documented and still not uniformly rights-clean; it also found a CC0 MassIVE Thermo RAW replacement candidate without weakening the negative rule.

**FAILURE MODES:** treating package license as file license; assuming public-dataset defaults apply without dataset-specific evidence; mistaking an oracle conversion for raw truth; counting skipped tests as coverage.

**NEXT IMPROVEMENT:** execute the four-vendor corpus and measure whether this method prevents a rights/evidence false-green in a second distinct scientific-parser family.
