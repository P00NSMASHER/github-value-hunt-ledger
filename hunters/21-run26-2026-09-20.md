## SPECIALIST PASSES

### CODE INSPECTOR

`chromConverter@ddf959.../R/read_thermoraw.R` does not decode Thermo RAW itself. It calls ThermoRawFileParser and then re-reads its mzML output. The parser path is manually installed/configured. On non-Windows the checked-in shell wrapper is:

`mono ~/software/ThermoRawFileParser/ThermoRawFileParser.exe "$@"`

On Windows it directly executes the configured parser path. There is no inspected check binding a specific ThermoRawFileParser version, release digest or binary hash to a normalized result.

The current ThermoRawFileParser release tag `v.2.0.0-dev` resolves to commit `a30bbac3dd4398a41262cee921685ad33e771311`. Its project targets `net8.0`, reports version `2.0.0-dev`, and references `ThermoFisher.CommonCore.RawFileReader` version `8.0.6`. The release notes explicitly say code migrated fully to .NET 8 and Mono dependency is obsolete. Release assets expose SHA-256 digests, so an acceptance harness can and should pin an exact platform artifact rather than trusting an arbitrary local executable.

### TEST / SCHEMA INSPECTOR

ThermoRawFileParser exact-tag CI has a successful `buildtest` workflow run for `a30bbac...`. Its checked-in writer tests exercise real `small.RAW` fixtures, create mzML, assert a 48-spectrum result for the test fixture, assert m/z and intensity binary arrays, and exercise profile output and other writer modes.

ThermoRawFileParser's mzML writer embeds source-file SHA-1, Thermo RAW source-format metadata, instrument model/serial data, software version, scan/spectrum data and TIC-related fields. This makes the raw mzML useful as a receipt, but EXP-007 should still independently capture the external decoder artifact SHA-256 and command/runtime configuration.

OpenTFRaw's pinned Python API exposes a clean comparison intersection before shared normalization: `num_scans`, scan number, MS level, retention time, filter string, TIC, base-peak m/z/intensity, low/high m/z, precursor m/z, isolation width, collision energy, and centroid m/z/intensity arrays. Its profile API is separately typed and explicitly unavailable for flat-peak SRM format. Therefore the acceptance ledger must compare only semantics supported by both decoders rather than forcing every field into equality.

### SCIENCE VALIDATOR

Scientific agreement must be field-semantic rather than file-byte equality. A valid comparator set is scan count/range, RT, MS order, TIC/BPC, centroid m/z/intensity or declared aggregates, and precursor/isolation fields only where both decoders represent the same concept. Profile data, peak-picking choices, unsupported DIA isolation semantics and representation-specific metadata must remain `UNSUPPORTED` or `DISAGREE`, not be normalized into apparent agreement.

### COMMERCIAL / RIGHTS ANALYST

The top-level ThermoRawFileParser repository is Apache-2.0, but its production dependency chain is not governed solely by that license. The checked-in `THERMO_LICENSE` for RawFileReader states that commercial exploitation of the software or products incorporating it requires prior written consent from Thermo. The `.csproj` references `ThermoFisher.CommonCore.RawFileReader` 8.0.6 directly.

Under the hunt's standing rule, repository-code permission does not extend to independently governed vendor SDKs. Therefore:

- ThermoRawFileParser is **technically strong evidence**, but **not a rights-clean default production dependency** for a paid migration product unless separate Thermo permission/terms establish that use.
- OpenTFRaw remains materially more attractive as the candidate commercial Thermo production decoder because its inspected parser path directly decodes RAW bytes and does not depend on Thermo RawFileReader.
- ThermoRawFileParser may remain a valuable comparator in an environment where the customer/operator has appropriate rights, or after separate commercial permission is established.

This is a product-architecture/reuse classification, not legal advice.

### ECOSYSTEM ANALYST

The current ThermoRawFileParser release is widely downloaded and exact-tag CI is green, so the finding is not that the tool is weak. The key issue is **role assignment**: technically mature vendor-SDK-backed software can be an excellent reference while still being a poor default dependency for a commercial product whose license boundary has not been cleared.

## SEARCH POLICY UPDATE

Local candidate lesson: **Dependency-Chain Rights + Runtime Pin Audit**.

WHEN TO USE: a scientific/industrial wrapper delegates consequential parsing/control to an external executable, SDK or service.

PROCEDURE:
1. Trace the actual load-bearing runtime dependency below the wrapper.
2. Pin exact dependency release/commit/artifact digest, not only wrapper commit.
3. Inspect platform launcher/runtime compatibility.
4. Separate repository license from bundled SDK/data/service rights.
5. Record exact decoder/runtime identity in the acceptance receipt.
6. If commercial rights are unclear/restricted, find a rights-clean alternate production path and keep the restricted tool only as separately authorized comparator.

WHY IT WORKED: it exposed both an unpinned parser/runtime-currentness seam and a commercially material third-party license boundary hidden beneath an otherwise Apache wrapper.

FAILURE MODES: treating transitive dependency terms as inherited from the top-level repo; treating a configured filesystem path as a version pin; over-reading a bundled historical license when a deployment-specific current agreement may supersede it.

NEXT IMPROVEMENT: validate this method on a second distinct scientific/device integration before proposing promotion to `SEARCH_SKILLS.md`.
