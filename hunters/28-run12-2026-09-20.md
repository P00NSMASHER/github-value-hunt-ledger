## Concrete implementation evidence

Hyperswitch has real payout-sync and reversal machinery rather than README-only claims:

1. `crates/router/src/workflows/payout_sync.rs`
   - `PayoutSyncWorkFlow` retrieves the payout from the configured connector with `force_sync: Some(true)`.
   - While the payout status is non-terminal, the process tracker schedules another sync.
   - When the payout status is terminal, `process_terminal_task()` marks the process tracker complete and emits the terminal merchant webhook; no next payout-sync retry is scheduled by this workflow.

2. `crates/router/src/core/payouts/helpers.rs`
   - `should_call_retrieve(status)` returns true only for `Pending | Initiated`.
   - Therefore the generic `force_sync` retrieve path itself refuses connector readback once a payout is already `Success`, `Reversed`, `Failed`, etc. This is stronger than merely saying the background scheduler stops: even an ordinary forced retrieve does not re-query a locally successful payout through this helper.

3. `crates/common_enums/src/enums.rs`
   - `Reversed` is a terminal payout state.

4. `crates/hyperswitch_connectors/src/connectors/wise/transformers.rs`
   - Wise `OutgoingPaymentSent` maps to Hyperswitch `PayoutStatus::Success`.
   - Wise `FundsRefunded` maps to Hyperswitch `PayoutStatus::Reversed`.
   - Incoming webhook mapping also recognizes the corresponding payout success/reversal classes.

5. Other connector mappings independently show that the platform understands reversal semantics: PayPal `Refunded | Returned -> Reversed`, Trustly credit webhook -> `Reversed`, and GoTyme reversed -> `Reversed`.

6. `crates/router/tests/connectors/wise.rs`
   - Connector tests exercise successful Wise payout fulfillment and assert `PayoutStatus::Success`.
   - I did not locate an equivalent end-to-end regression proving `Success -> later FundsRefunded/Reversed` is independently rediscovered after the terminal sync job has stopped.

## External provider reality check

Wise's current first-party transfer-status documentation states that `outgoing_payment_sent` means Wise has sent the payout but does **not** guarantee the beneficiary bank has credited it. The documented unhappy path can move from `outgoing_payment_sent -> bounced_back -> ... -> funds_refunded`, and bounce-backs may occur weeks after the transfer was sent. Wise also documents that payout failures do not always produce the same state-change event and recommends separate payout-failure/refund handling.

Sources:
- https://docs.wise.com/guides/product/send-money/tracking/transfer-statuses
- https://docs.wise.com/guides/product/send-money/use-cases/correspondent/correspondent-track-transfers
- https://docs.wise.com/guides/product/send-money/tracking/payout-failures

## Why this matters

This is a concrete EXP-003 false-finality fixture:

`Wise outgoing_payment_sent -> Hyperswitch Success -> payout sync workflow terminates -> later Wise bounced_back/funds_refunded -> Hyperswitch generic force-sync gate will not query the provider because local status is no longer Pending/Initiated`.

A delivered reversal webhook can still correct the state, so this is **not** evidence that Hyperswitch cannot process a reversal. The narrower and commercially important finding is that the inspected generic polling/readback path does not independently rediscover a late reversal after terminal success if that webhook is permanently lost.

That exactly matches CAP-018's remaining failure class: a system can model `Reversed` correctly while still being blind to the event if its observation horizon ends at the first terminal state.

## Commercial interpretation

A buyer-facing diagnostic can identify payout systems whose reconciliation jobs only watch in-flight records and quantify exposure to missed late bank/provider returns, stale paid states, unsafe reissues and close-period misclassification.

## EXP-003 test delta

Add a provider-specific fixture using Wise semantics:
1. Original earning fixed under plan version V1.
2. Send payout; provider reaches `outgoing_payment_sent`; local system records `Success`.
3. Allow ordinary in-flight sync job to terminate.
4. Suppress the later reversal/refund webhook completely.
5. Provider moves to `bounced_back`, then `funds_refunded` after the local success state.
6. Run the application's ordinary scheduled/manual reconciliation path.
7. Expected acceptance-test result: **FAIL** if no provider/bank re-read occurs because local success blocks retrieve.
8. A safe remediation path must reobserve the exact original provider payout/transfer identity after success, classify still-owed vs clawback, append one economic counter-event, and only the still-owed branch may reopen the original immutable earning.

## Negative knowledge

- A connector supporting `Reversed` does not imply a system can rediscover reversal after success.
- A `force_sync` flag is not meaningful finality protection if status gating excludes successful rows.
- A process tracker that polls only until the first terminal state is an **in-flight reconciler**, not a **post-success finality observer**.
- Webhook correctness and independent readback redundancy are separate capabilities.
- Provider terminal success remains distinct from beneficiary-bank finality.
