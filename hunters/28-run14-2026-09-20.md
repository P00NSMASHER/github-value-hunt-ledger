### What was verified beyond README
**Status-independent provider listing.** `djstripe/management/commands/djstripe_sync_models.py` can sync all supported Stripe models or a named model such as `Payout`. Eligibility is based on the model having a Stripe class/list operation, not on the local object's payout status. The sync path iterates the provider list and feeds every returned object into `sync_from_stripe_data()`.

**Existing local objects are actually updated.** `tests/test_stripe_model.py::TestSyncFromStripeData::test_updates_an_existing_instance` is a regression test proving that syncing the same Stripe object ID again updates the persisted row rather than returning stale state or creating a duplicate. This is the key primitive needed for a local `paid` payout to become `failed` on a later provider rescan.

**Cron/CI-visible source failure exists, but must be enabled correctly.** The management command counts model/key and object sync failures. On the CLI it defaults to fail loudly; with `--fail-on-error` it raises `CommandError`. `tests/test_sync.py` verifies this. It also verifies that restricted-key sync performs real listing work rather than silently succeeding with an empty account set.

**Important fail-open caveat.** Programmatic `call_command()` defaults `fail_on_error` to false so admin/programmatic callers do not throw. Therefore a product using this as a finality observer must explicitly request fail-on-error behavior and persist a scan receipt/freshness state. A logged provider-sync error cannot be converted into `VERIFIED_EMPTY` or settlement finality.

**Payout/reversal data shape is present.** The Payout model includes Stripe payout state plus `failure_balance_transaction`, `original_payout` and `reversed_by` relationships. Payout sync tests validate the relationship surface, but the test file explicitly still has a TODO for payout reverse-operation tests. Do not overclaim economic reversal execution from this repository.

**Exact-revision maintenance evidence.** Current main resolves to `40882bb...`; GitHub Actions records exist on that exact SHA and include successful completed runs. The repository is mature and actively maintained, but this hunt did not independently reproduce the full suite locally.

### First-party external verification
Stripe's current official SDK model says payout status may be `paid`, `pending`, `in_transit`, `canceled` or `failed`; importantly, some payouts that fail can initially show as `paid` and later change to `failed`. The same model exposes a beneficiary-bank trace ID whose availability can lag `arrival_date` by up to 10 days. This independently validates the need for post-success observation rather than terminal-success immunity.

## RED-TEAM VERDICT
**Useful missing-edge component, not a complete Commission Payout Assurance engine.**

Strongest objections:
- `djstripe_sync_models` is an operator/management primitive, not an installed scheduler or defined finality-horizon policy by itself.
- Programmatic calls can be non-throwing unless `fail_on_error=True`; source-health/freshness must be elevated into an explicit receipt.
- Provider object truth is not beneficiary-bank truth.
- The repository does not join a payout failure back to a commission earning, distinguish `BANK_RETURN_STILL_OWED` from refund/clawback-not-owed, or reopen/re-pay the original earning under historical rate authority.
- Payout reverse-operation semantics are not directly covered by the inspected payout test.

## COMMERCIAL EVALUATION
BUYER: RevOps, finance, payroll, marketplace/partner-finance teams running Stripe Connect or Stripe payout workflows.

PAINFUL PROBLEM: a local system can mark a rep/partner payout paid and then miss a late provider transition to failed, especially when the webhook is permanently lost. This creates false paid states, unsafe manual reissues and close/reconciliation drift.

FIRST PAID WEDGE: add a **Terminal Payout Drift** section to the Commission Payout Acceptance Test: independently rescan a bounded historical payout population from Stripe, compare current provider truth with local paid state, and report contradictions without automatically creating repayment.

MONEY PATH: prevented duplicate payouts, corrected unpaid-but-marked-paid liabilities, reduced manual reconciliation and safer close.

BUILD COMPRESSION: several weeks of provider-model persistence/listing/connected-account sync/error handling; much more mature than writing a bespoke Stripe mirror.

MOAT: not dj-stripe itself. The moat is the joined proof system: historical entitlement authority + status-independent provider observation + independent bank/payroll observation + exact economic classification + idempotent compensation/reopen.
