### Concrete capability verified
`coordinator/api/stripe_payouts_webhooks.go` explicitly handles a payout that was already marked `paid` and later receives `payout.failed` / `payout.canceled` because the beneficiary bank bounced it. The handler:

1. resolves the withdrawal by the exact Stripe payout ID;
2. accepts the late failure even when the local withdrawal is already `paid`;
3. atomically reopens the withdrawal to `transferred` for the automatic sweep to retry;
4. detaches the dead payout ID so an old event cannot keep controlling the row;
5. refunds the instant-delivery fee exactly once when applicable;
6. preserves `transfer.reversed` as the stronger terminal accounting outcome when a concurrent reversal has already refunded principal;
7. routes the ambiguous legacy `paid + refunded` state to manual review rather than automatically making another money movement.

The code comments correctly distinguish bank-payout failure from platform-transfer reversal: a failed payout returns funds to the connected account balance, so principal is not re-credited to the platform ledger; `transfer.reversed` is the event that can return principal to the platform. This is a useful cash-location invariant for Commission Payout Assurance.

### Tests inspected beyond README
`coordinator/api/stripe_payout_events_test.go` contains `TestConnectWebhookPayoutBounceAfterPaidReopens`:
- seeds a withdrawal in `Status: "paid"` with payout ID `po_pb`;
- delivers a failed payout event for that exact ID;
- asserts status becomes `transferred`;
- asserts the dead payout ID is removed;
- asserts the instant fee is refunded once;
- redelivers the same event and proves there is no second credit and no state regression.

The same file also includes:
- stale unmatched payout failure must leave an unrelated paid row untouched;
- `paid + refunded` is treated as ambiguous/manual-review, not auto-reopened;
- a late `payout.paid` cannot overwrite a withdrawal already terminalized/refunded by `transfer.reversed`.

Store-level evidence exists for both memory and PostgreSQL implementations of `ReopenStripeWithdrawalAfterPayoutFailure`; the interface contract requires the transition to be guarded so concurrent `transfer.reversed` wins instead of being overwritten by a stale payout-failure handler.

### Independent provider semantics
Current Stripe API documentation independently says payout status can be `paid` and later change to `failed` for some failing payouts. Stripe also exposes `failure_balance_transaction`, payout trace information and retrieval/list APIs. This supports the repository's late-bounce state-machine premise but does not make Stripe object state equivalent to beneficiary-bank finality.

### Critical negative finding — the lost-webhook branch is still open
`coordinator/api/stripe_reconcile.go` runs an hourly stuck-withdrawal reconciler, but its observation population is only:
- stale `pending` withdrawals; and
- stale `transferred` withdrawals.

It never selects locally `paid` withdrawals for independent post-success provider re-read. The reconciler can heal a manual payout schedule and alert on stuck non-terminal rows, but once a row is `paid`, a permanently lost late `payout.failed` webhook leaves it outside this scheduled observer.

The codebase already has a provider `GetPayout(connectedAcctID, payoutID)` primitive and uses it to protect automatic-sweep reconciliation from an out-of-order stale `payout.paid` event. Therefore the missing capability is unusually narrow: **status-independent post-success observation over a bounded finality horizon**, not the economic repair transition itself.

### Commercial value
This enables a precise buyer-facing exception class:

`PAID_PAYOUT_NOT_REOBSERVED`

and a derived high-dollar failure:

`LATE_BANK_BOUNCE_STILL_MARKED_PAID`

A Commission Payout Acceptance Test can distinguish systems that merely have correct `payout.failed` handlers from systems that can still discover the failure when that handler never receives the event.

### Strongest objection
This is not a complete commission-entitlement system and not an independent bank-feed oracle. The successful repair depends on receiving the provider counter-event. A provider-wide or exact-ID post-success scan still needs a coverage/freshness receipt, and beneficiary-bank truth remains a separate evidence plane.

### What was verified
`convex/payouts.ts` applies Stripe transfer snapshots against exact amount/currency/destination/platform/correlation evidence. When `amount_reversed` increases, it appends a `transfer_reversal` settlement entry with positive available balance and negative paid balance, keyed by a deterministic reversal reference, then marks a full reversal `reversed`. The projection is cumulative/delta-based, so replay does not double-unwind the transfer.

`convex/billing.ts` retrieves the actual Stripe transfer on `transfer.failed` / `transfer.reversed` before projecting it. The repository also includes a provider-proof harness that checks Stripe test-mode provider objects and compensation evidence.

### Why it did not beat Layr-Labs for the current gap
The admin/provider reconciliation path returns immediately when a transfer is already `succeeded` or `reversed`, so it likewise does not supply the needed state-independent post-success observer. The core reversal accounting is valuable, but it does not close the late lost-webhook edge.

## Comparison to current CAP-018 leaders

The current ledger already has a complementary post-success sensor (`stripe-connect-reckon`) that lists provider payouts independently of local terminal status, plus Modern Treasury / ACHInterbank for provider-to-bank return evidence. Layr-Labs supplies the strongest newly verified **economic correction side** of the seam:

`paid withdrawal -> exact late payout failure -> reopen to transferred -> retry via sweep -> fee refunded once -> concurrent principal reversal wins`.

The remaining composition is therefore concrete rather than conceptual:

**status-independent terminal payout scan** + **exact payout identity** + **Layr-style guarded paid→transferred reopen** + **independent bank/return evidence** + **historical commission earning authority**.

## Claims tested

1. **Late payout failure can safely reopen a previously paid local obligation. — VERIFIED in source/tests.**
2. **The reopen can be replay-safe and race-safe against a stronger transfer reversal. — VERIFIED by test cases and guarded store contract.**
3. **Having an hourly reconciler proves lost late-return webhooks will self-heal. — FALSIFIED.** The scheduled reconciler selects only `pending` / `transferred`, not `paid`.
4. **Provider `paid` is immutable finality. — FALSIFIED independently by current Stripe documentation.** Some failing payouts can initially appear `paid` and later become `failed`.
5. **Provider failure alone proves bank finality or repayment authority. — NOT VERIFIED and should remain false as a product assumption.** Provider object state, independent bank observation and commission entitlement are separate planes.

## Experiment impact — EXP-003
Add a dedicated two-stage late-bounce branch:

1. create/seed the historical earning under plan/rate V1;
2. pay it and mark the payout locally `paid`;
3. suppress the late `payout.failed` webhook permanently;
4. make the provider object become `failed` after the local success;
5. require a status-independent post-success observer to rediscover the exact payout within its declared finality horizon;
6. require the same guarded transition that the tested webhook path uses: local obligation becomes payable/observable again exactly once;
7. replay the same provider failure and prove no duplicate fee/principal credit;
8. concurrently inject the stronger transfer/bank reversal and require that terminal economic state to win;
9. only after still-owed vs clawback classification may the original historical earning be repaid, without rerating under current commission policy;
10. independent bank/payroll observation remains required for realized-money finality.
