### getaero-io/gtm-signal-scoring
- URL: https://github.com/getaero-io/gtm-signal-scoring
- Exact commit / revision: `9b89a185532fecc2800eb7edf381e60977045d9d`
- Date inspected: 2026-09-19
- Status: **strong**
- What it contains: A functioning Next.js/Postgres GTM signal-scoring application with person/contact qualification, domain-level account aggregation, engagement/velocity signals, webhook ingestion, identity resolution, account tiering, scheduled scoring, and CRM sync/routing surfaces for HubSpot, Attio and Notion.
- Rare or undernoticed value: The valuable part is not another generic CRM UI; it is the operational glue between contact-level ICP fit, multi-channel engagement, company fit, coverage, account scoring and downstream CRM routing. The account scorer exposes an explicit 0–100 formula and returns auditable component-derived account features instead of hiding qualification behind an opaque model.
- Monetization path: White-label RevOps signal layer / account-prioritization service over existing CRMs; configurable ICP + engagement scoring; agency-managed lead qualification; product-led sales routing. A higher-value variant would benchmark the scoring model against closed-won/lost outcomes and sell measurable pipeline-lift rather than raw enrichment.
- Likely buyer / user: B2B SaaS RevOps leaders, SDR/BDR teams, GTM agencies, founders using HubSpot/Attio/Notion, teams with fragmented behavioral signals.
- Build-time or data advantage: Estimated **4–10+ weeks** saved on a production-shaped scoring/routing substrate: persistence, account rollups, cron scoring, webhook ingest, CRM synchronization, identity-linking patterns and tests already exist. Customer-specific weights and outcome calibration still need independent validation.
- Concrete evidence inspected: Latest commit adds account-level scoring, engagement velocity, CRM integrations, Attio sync, identity resolution and webhook ingestion. `lib/outbound/engine/account-scorer.ts` implements a deterministic formula: best-contact ICP 40%, engagement 30%, company fit 20%, contact coverage 10%; engagement includes touchpoints, velocity, positive intent, meeting request, active conversation and channel count. `tests/account-scorer.test.ts` exists; account-score persistence and qualification cron routes are present; CRM/Attio webhook code calls identity-resolution logic and links email/LinkedIn/company-domain fields. Root tree contains a real app/API/config/docs structure rather than a README-only concept.
- License / rights: MIT license, copyright 2026 Deepline. Public visibility was not treated as ownership of any third-party CRM data. No credentials or accidental disclosures were retained.
- Reuse classification: **Directly reusable** under MIT, with required copyright/license notice; integration-provider terms remain separate.
- Why it is not already obvious / crowded: The repository name sounds like a narrow scoring demo, while the source reveals a broader RevOps execution layer with account rollups, identity linking and CRM routing. Its value is the assembled workflow more than any single scoring formula.
- Combination opportunities: Pair with `dedupeio/dedupe` from MASTER for stronger entity resolution before account aggregation; add an evidence/provenance ledger so each score can cite the specific signals that produced it; combine with public-company/change-signal hunters to create a higher-signal account-prioritization product.
- Next action: Extract the scoring/routing data model into a vendor-neutral schema and design an offline backtest harness that learns/calibrates weights from a customer's historical opportunities instead of shipping the CPG-specific weights unchanged.

### migace/hvac-cpq
- URL: https://github.com/migace/hvac-cpq
- Exact commit / revision: `badc5284685352f9feaaf9a19e3136b3a05fc207`
- Date inspected: 2026-09-19
- Status: **strong clean-room/domain reference; rights-blocked for direct reuse**
- What it contains: A substantive FastAPI/PostgreSQL CPQ prototype for configurable HVAC products. It models product families and dynamic attributes, EAV configuration values, family-specific validation rules, separate pricing rules, technical calculations, order-code generation and quote snapshots that preserve the configuration/pricing state used when the quote was created.
- Rare or undernoticed value: Most small CPQ repos stop at a form and a total. This one encodes the harder product-modeling boundary between dynamic attributes, compatibility/business rules, price rules, engineering calculations, order-code generation and immutable historical quotes. That is useful architecture for manufacturers whose quoting knowledge lives across PDFs, spreadsheets and engineering know-how.
- Monetization path: Clean-room a vertical CPQ accelerator for HVAC/specialty manufacturers, sold as a paid product-data normalization + quoting implementation. A sharper wedge is “catalog/PDF/Excel to validated quote engine” rather than a generic CPQ replacement, with implementation fees plus recurring hosting/support.
- Likely buyer / user: HVAC manufacturers, industrial distributors, specialty equipment makers, sales-engineering teams and implementation partners with complex configurable catalogs.
- Build-time or data advantage: Estimated **1–3 months** of domain-model/requirements acceleration even without source reuse; the repository already exposes a coherent schema for configurable families, rule/pricing separation, historical quote snapshots and tests for pricing behavior.
- Concrete evidence inspected: Exact commit and recent history; README architecture/data model; repository root and deployment structure; `apps/backend/app/db/models.py` and pricing-rule schemas; `apps/backend/app/services/pricing_engine.py` implements base/fixed/percentage price rules and validation; `apps/backend/tests/test_pricing.py` exercises conditional percentage surcharges; seed data includes multiple fire-damper families and conditional price rules. Recent commits also fix Decimal handling and make technical-calculation dispatch data-driven rather than hardcoded to one family.
- License / rights: **No LICENSE file was found at the inspected revision.** Public visibility is not a license grant. Any manufacturer catalog/product data would have separate rights as well.
- Reuse classification: **Inspect / learn / clean-room implementation only** unless the author later grants permission/license.
- Why it is not already obvious / crowded: Low-attention “weekend project” positioning hides a surprisingly coherent industrial CPQ domain model and testable pricing/quote workflow.
- Combination opportunities: Pair its clean-room CPQ architecture with `microsoft/RulesEngine` for a permissively licensed execution layer, `getomni-ai/zerox` for lawful customer-provided catalog extraction, and GoldenMatch/dedupe for SKU/vendor normalization. Could become a document-to-quote vertical implementation service before becoming SaaS.
- Next action: Independently model one synthetic configurable industrial product with 15–25 attributes, compatibility constraints and tiered surcharges using permissive components, then measure quote time/error reduction against a spreadsheet workflow.
