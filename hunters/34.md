### danielrosehill/Freight-Vol-Calculator
- URL: https://github.com/danielrosehill/Freight-Vol-Calculator
- Exact commit / revision: `ac2590e2599f9ccf0e7090155cc92524d9b5795a`
- Date inspected: 2026-09-19
- Status: strong
- What it contains: A deterministic stdlib-Python freight geometry engine for pallet quantity, container/trailer loading, floor-loaded versus palletized plans, payload caps, volumetric/chargeable weight, carton-option enumeration, per-unit freight costing from a supplied rate, and an input verifier that checks inconsistent CBM/dimensions/units/gross-vs-net/physical pack counts. It includes 45 self-tests and validates placements for overlap/overhang.
- Rare or undernoticed value: It attacks a different false-recovery source than ordinary rate engines: bad physical shipment facts. A billed dimensional/reweigh discrepancy is only defensible if carton, cube, packing and payload arithmetic are internally plausible. The engine makes those checks deterministic instead of trusting invoice dimensions blindly.
- Monetization path: Add a dimensional/reweigh/reclass evidence module to the freight-audit stack; use it to flag physically impossible carton claims, recompute chargeable weight, and quantify whether a disputed reweigh actually changes contracted freight.
- Likely buyer / user: Parcel/LTL/air shippers, freight-audit/payment teams, importers and 3PLs handling dimensional-weight disputes.
- Likely first paid wedge: Audit a customer sample for dimensional-weight/reweigh leakage and return source dimensions plus reproducible geometry evidence alongside each finding.
- Build-time or data advantage: Roughly 1–2 months of geometry, packing, validation and edge-case work compressed into one tested engine; more valuable as an evidence oracle than as a standalone calculator.
- Concrete evidence inspected: actual `LICENSE`; `README.md`; `scripts/freight.py`; latest commit message expanding verification and self-tests. Source implements bounded lane/pinwheel packing, placement validation and explicit freight-mode divisors while refusing to invent a rate.
- License / rights: Software is MIT. README says bundled reference dimensions are compiled from published standards/carrier specification sheets; this run did not independently clear every reference-data row, so code rights are clear but external reference-data provenance should be verified before redistribution or contractual use.
- Reuse classification: Directly reusable MIT software; treat bundled reference data as verify-before-redistribute/contract against.
- Why it is not already obvious / crowded: Small Claude-plugin-branded repository; the valuable part is a deterministic geometry/audit kernel rather than the plugin wrapper.
- Combination opportunities: Kareya/Qatoto contract rating + this physical-fact oracle + open_tms invoice normalization can separate rate errors from dimension/reweigh errors. It also supplies stronger benchmark cases for reweigh/reclass and dimensional disputes.
- Value score: A 3/5, B 4/5, C 4/5, D 4/5, E 5/5, F 4/5 = **24/30**.
- Next action: Build synthetic invoice cases where billed dimensions, carton count and stated CBM disagree; require the recovery engine to route impossible/ambiguous geometry to REVIEW and only price a discrepancy after physical facts are consistent.
