### notrinos/NotrinosERP
- URL: https://github.com/notrinos/NotrinosERP
- Exact commit / revision: `93221b3314149f1e9d3c01682e9539307c205d28`
- Date inspected: 2026-09-19
- Status: watch
- What it contains: A functioning ERP purchasing stack with explicit supplier/vendor evaluation infrastructure: configurable quality/delivery/price/service/compliance categories, manual/calculated scoring, tiers, recommendations, evaluation periods, performance events, supplier pricing and broader purchase-order/AP controls.
- Rare or undernoticed value: Vendor scoring is implemented as operational database logic inside a live ERP rather than presented as a standalone scorecard demo; the code has explicit performance-event types such as late delivery, quality issue, price change, complaint and resolution.
- Monetization path: Supplier-performance / procurement-control product or service for SMB/midmarket buyers; alternatively use the module as a GPL reference implementation for clean-room vendor scoring inside a proprietary product.
- Likely buyer / user: Procurement teams, manufacturers, distributors and ERP implementers.
- Painful problem: Vendor performance is often anecdotal and disconnected from purchasing history, leaving sourcing teams unable to quantify service/quality/price tradeoffs.
- Build-time or data advantage: Roughly 1–3 months of procurement-domain workflow and scoring-model implementation guidance.
- Concrete evidence inspected: `purchasing/includes/db/vendor_evaluation_db.inc`, README vendor-management section, latest repository commit.
- License / rights: GNU GPL v3; source file headers state GPL v3 or later.
- Reuse classification: Reusable with GPL conditions; direct incorporation into distributed proprietary software can trigger copyleft obligations, so clean-room reimplementation may be preferable for a closed-source SaaS/product.
- Why it is not already obvious / crowded: Procurement value is buried inside a general ERP rather than marketed as vendor-intelligence software.
- Combination opportunities: Combine vendor performance scoring with freight carrier scorecards, spend analysis and invoice-recovery findings to build a carrier/vendor negotiation cockpit.
- Scores: technical 8/10; commercial 8/10; rarity 7/10; completeness 9/10; build-time saved 8/10; data advantage 5/10; high-ticket potential 8/10.
- Next action: Inspect its three-way matching/bill-control modules next run and determine whether a clean-room supplier-performance layer can share evidence with freight carrier scorecards.

### ajithalex2004/Fleet360 logistics marketplace
- URL: https://github.com/ajithalex2004/Fleet360
- Exact commit / revision: `de9dd8b2b1792efb81ee91f19ed52aa1677b30e9`
- Date inspected: 2026-09-19
- Status: watch
- What it contains: A substantial carrier-procurement domain model inside a fleet platform: carrier onboarding/compliance/capacity, negotiated lane rate contracts with effective dates, minimum charges, fuel percentage and accessorial rules, shipment-linked freight RFQs, carrier bids with amount/transit/validity/charge breakdown, and carrier scorecards covering on-time, acceptance, cancellation, claim and compliance metrics plus preferred/blacklist state.
- Rare or undernoticed value: It joins the full carrier sourcing loop—contract rate, spot RFQ, bid, operational performance and preferred/blacklist decision—in one coherent schema rather than treating carrier scorecards as a detached dashboard.
- Monetization path: Clean-room carrier-procurement/tendering cockpit that chooses between contracted and spot capacity, ranks bids with service history, and feeds accepted economics into freight audit/payment controls.
- Likely buyer / user: 3PLs, brokers, shippers with transportation procurement teams and private fleets using outside carriers.
- Painful problem: Carrier sourcing, negotiated rates, spot bids and performance history are commonly fragmented across TMS, email and spreadsheets, weakening negotiation and tender decisions.
- Build-time or data advantage: Roughly 1–3 months of carrier-procurement schema/workflow design guidance.
- Concrete evidence inspected: `backend/models/logistics_marketplace.go`; exact latest commit and repository metadata. Source implements `LogisticsCarrier`, `LogisticsRateContract`, `LogisticsFreightRFQ`, `LogisticsCarrierBid` and `LogisticsCarrierScorecard` rather than only documenting them.
- License / rights: Repository metadata reports no license; no project-level reuse grant was established.
- Reuse classification: Inspect / learn / clean-room only unless permission is established.
- Why it is not already obvious / crowded: Zero-star broad fleet application; procurement functionality is hidden in backend marketplace models and does not appear in the repository description.
- Combination opportunities: Combine its sourcing-loop requirements with deterministic negotiation from freight-pilot, Apache-licensed Kareya tariff economics, and Notrinos-style vendor scoring to create a carrier procurement + audit feedback loop.
- Next action: Do not copy code. Search next for a permissively licensed RFQ/bid-award implementation with tests; use Fleet360 only as a clean-room requirements map until rights improve.
