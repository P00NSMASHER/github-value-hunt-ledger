### Emma-V/support-triage
- URL: https://github.com/Emma-V/support-triage
- Exact commit / revision: `f12f682eda87ddbf1593200ad515b464b04c00ff`
- Date inspected: 2026-09-19
- Status: **strong research/evaluation artifact; no-license code**
- What it contains: A rigorous 27-way customer-support intent-classification project comparing Qwen3-1.7B + LoRA, TF-IDF/logistic regression, majority and zero-shot baselines, with explicit dataset leakage measurement, template-family deduplication, controlled splits, confidence/abstention analysis and error inspection.
- Rare or undernoticed value: The biggest commercial value is the **evaluation protocol**, not the headline model. It demonstrates how templated support datasets can create misleadingly high random-split scores and supplies a disciplined method for deduplication, size-matched leakage controls, metric-resolution checks and abstention thresholds. It also shows a cheap TF-IDF baseline can already be near ceiling for a constrained intent taxonomy.
- Monetization path: High-confidence ticket-routing/triage layer with explicit abstention to humans; benchmark/audit service for companies evaluating support-routing models; low-cost routing where a linear model handles easy traffic and an LLM only handles ambiguous cases.
- Likely buyer / user: Support operations teams, helpdesk vendors, BPOs and contact centers with repeatable intent taxonomies and costly misrouting.
- Build-time or data advantage: Roughly **2–6 weeks** saved on benchmark design, leakage controls and routing-evaluation methodology. The direct code is not reusable without permission, but the scientific lessons can be independently implemented.
- Concrete evidence inspected: README reports 26,872 raw rows / 27 intents, removes 2,318 exact duplicates, clusters near-duplicates into template families, creates clean/naive/size-matched splits with hashed manifests, measures a metric resolution floor, compares TF-IDF and LoRA, and records all five clean-test errors. It reports 10.49% exact leakage and 52.02% >=0.90 similarity in the naive validation setup before cleaning, while the cleaned split reduces >=0.90 overlap to 0.24%. It includes confidence/coverage analysis and an abstention example. Notebook map documents the reproducible pipeline.
- License / rights: **No repository LICENSE file found** at inspected revision. The referenced Bitext dataset and Qwen model have separate third-party terms that must be checked independently before commercial use.
- Reuse classification: **Inspect / learn / clean-room implementation only** for repository code; do not assume dataset/model commercial rights.
- Why it is not already obvious / crowded: It is presented as a course project, but the evaluation design is substantially more commercially useful than many polished ticket-classifier demos because it exposes exactly how support benchmarks can lie.
- Combination opportunities: Pair a clean-room classifier/abstention layer with `pyworkforce`: predicted per-intent ticket volume and handling time can become skill-specific staffing demand. Also combine with QA/audit tooling to measure routing precision, deferral rate and downstream transfer cost.
- Next action: Recreate only the methodology on a permissively licensed or customer-owned support dataset and compare a cheap sparse baseline, small classifier and LLM under the same deduplicated gold set with dollar-weighted misroute costs.

These are prompt/workflow specifications rather than a tested standalone application.
- License / rights: README displays an Apache-2.0 badge, but **no LICENSE file exists at the inspected revision**. A badge is not sufficient evidence of a license grant.
- Reuse classification: **Inspect / learn / clean-room only unless licensing is clarified.** Composio and connected-service terms are separate.
- Why it is not already obvious / crowded: The repo looks like a prompt pack; its useful part is the breadth of operational workflows it enumerates, not unique algorithms.
- Combination opportunities: Convert the workflow taxonomy into evaluation scenarios for a real support-ops agent, then combine with the high-confidence triage methodology above and staffing optimization from the workforce lane.
