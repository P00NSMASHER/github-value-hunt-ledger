### Ahmad-Mujtaba-09/demand-forecasting-agent
- URL: https://github.com/Ahmad-Mujtaba-09/demand-forecasting-agent
- Exact commit / revision: `0f8db23e01a7c1239a8836994675a83f00f6e294`
- Date inspected: 2026-09-19
- Status: strong
- What it contains: Evaluation-heavy retail-demand forecasting core for M5-format data with deterministic model routing by intermittency, Croston/SBA sparse-demand comparators, LightGBM L2/Poisson/Tweedie/quantile models, rolling-origin validation, leakage-safe horizon-lagged features, uncertainty intervals, branch calibration, a critic gate, provenance manifests and machine-readable model contracts. The planned LLM/agent wrapper is not the value; the forecasting/evaluation core is already implemented.
- Rare or undernoticed value: The strongest feature is disciplined decision alignment rather than another forecasting model. The repository explicitly detects that daily WMAPE is degenerate on zero-heavy demand, demonstrates that a zero forecast can beat fitted models, and switches evaluation to horizon-aggregated WMAPE_28 because replenishment consumes 28-day totals. It also records commit/package/seed/thread/feature-list provenance so results are reproducible.
- Monetization path: Productize a sparse-demand forecasting and replenishment decision service for spare parts, MRO, wholesale/distribution, or long-tail retail; charge for inventory reduction / service-level improvement rather than forecast dashboards. A lighter wedge is an audit/benchmark service that identifies where a customer's existing KPI or forecast objective rewards economically useless zero forecasts.
- Likely buyer / user: MRO/spare-parts distributors, multi-SKU wholesalers, inventory-planning teams, retail data-science groups with intermittent/long-tail demand.
- Build-time or data advantage: Months of leakage-safe backtesting, sparse-demand routing, model bake-off, uncertainty and reproducibility plumbing are already represented. The project has 141 tests according to the inspected README and separates deterministic modeling rules from any future agent layer.
- Concrete evidence inspected: Pinned README covering branches B1/B2/B4, rolling-origin folds, frozen features, Croston/SBA, LightGBM objectives, baseline/zero-forecast comparison, metric pathology and machine-readable contract; root tree with `src/`, `tests/`, artifacts/docs and LICENSE; actual `src/dfa/manifest.py`, which hashes series IDs and order-sensitive feature columns and stamps git SHA, package versions, seed and fixed LightGBM thread count into artifacts.
- License / rights: MIT, verified from root `LICENSE` at the inspected revision. The M5 dataset itself has separate dataset rights/terms and should not be assumed covered by the software license.
- Reuse classification: Directly reusable subject to MIT terms; dataset reuse must be evaluated separately.
- Why it is not already obvious / crowded: The repository name and planned “agent” framing make it look like another AI wrapper, while the real value is unusually careful forecasting methodology, negative-result handling and reproducibility discipline.
- Combination opportunities: Pair with a licensed inventory optimizer / multi-echelon planner to move from better forecast selection to direct reorder/safety-stock decisions. Could also supply a benchmarking/evaluation harness for broader forecasting products.
- Next action: Run the router/metric suite on a second lawful non-M5 intermittent-demand dataset, preferably spare parts, to test whether the calibrated architecture generalizes and whether horizon-aggregated scoring tracks stockout/holding-cost outcomes.

### etaia/kernel-change-point-detection
- URL: https://github.com/etaia/kernel-change-point-detection
- Exact commit / revision: `b2f714033d90bf009bea371869e1019365832b16`
- Date inspected: 2026-09-19
- Status: strong
- What it contains: PyPI-packaged offline multivariate kernel change-point detection library (`kcpdi`) based on Arlot et al. (2019), plus a post-hoc explainability routine that decomposes the linear-kernel criterion by individual time series/sensor and ranks contributors around each detected shared change point. It also converts sparse change-point locations to dense decayed anomaly scores for TADkit compatibility.
- Rare or undernoticed value: In high-dimensional operational telemetry, detecting a regime shift is less valuable than identifying which sensors/series drove it. `kcp_v.py` implements exactly that contributor-ranking workflow instead of stopping at a changepoint index.
- Monetization path: Embed in industrial/SRE/process-monitoring software as an offline root-cause triage layer: detect system regime changes and rank the channels most responsible, reducing analyst time during incident/postmortem or process-change investigations.
- Likely buyer / user: Industrial process analytics, fleet/asset monitoring, SRE/observability vendors, scientific instrumentation analytics, quality/process engineering teams.
- Build-time or data advantage: Saves substantial algorithm implementation and validation effort for multidimensional change-point detection plus interpretable contributor attribution; already packaged, documented, CI-tested and published to PyPI.
- Concrete evidence inspected: Pinned README, root tree showing package/tests/docs/coverage and publishing workflows, MPL license, and actual `kcpdi/kcp_v.py`. The source computes the global kernel criterion, per-series criterion contributions, sorts series at the detected global minimum, and visualizes the most important contributors.
- License / rights: Mozilla Public License 2.0, verified from `LICENSE`.
- Reuse classification: Reusable with MPL-2.0 file-level copyleft conditions; keep covered-file modifications under MPL and preserve required notices. A larger proprietary work can generally remain separate when MPL-covered files remain distinct, subject to legal review for the intended distribution architecture.
- Why it is not already obvious / crowded: Small research-origin package; the commercially useful explainability feature is buried in `kcp_v.py` rather than a polished incident-management product.
- Combination opportunities: Pair with time-series ingestion and alerting to create a “what changed and which signals caused it?” service; pair with forecasting/decision systems to trigger model recalibration after statistically detected regime shifts.
- Next action: Benchmark detection delay, false positives and contributor ranking on one lawful industrial/public multivariate telemetry dataset with known interventions/failures, and profile `kcp_v` runtime because its current per-series/per-candidate loops note parallelization opportunities.
