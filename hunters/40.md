### DNYoussef/guardspine-spec
- URL: https://github.com/DNYoussef/guardspine-spec
- Exact commit / revision: `4b21006daa82af52647c5b6e4288d995ccbaf401`
- Date inspected: 2026-09-20
- Category: Reusable Component / Interoperability Specification / Business Opportunity
- Status: **strong component / watch boundary**
- Score: **24/30** — A3 speed to revenue, B3 ceiling, C4 build/domain compression, D4 rarity, E5 evidence/completeness, F5 rights clarity. It is not a standalone evidence collector, but it is a strong portable-verification contract for a multi-engine assurance service.
- Concrete capability: Apache-2.0 stable v0.2.1 vendor-neutral evidence-bundle specification designed for offline verification without trusting the issuing system. A bundle binds canonical JSON content with SHA-256 hashes, an ordered hash chain, root hash and optional Ed25519/RSA-SHA256/ECDSA-P256 signatures. Verification rules require version validity, 1:1 item/chain binding, contiguous sequence, correct previous-chain linkage, root/content hashes and valid signatures. The repository includes golden cross-language vectors and malformed vectors that implementations MUST reject. v0.2.1 also adds a sanitization attestation carrying redaction engine/version/method/token format/count/status plus a crypto-field registry so intentional hashes/signatures are not mistaken for accidental high-entropy secrets.
- Rare / undernoticed value: The useful asset is not another internal hash ledger; it is an **interoperability and falsification contract**. Multiple evidence producers can be required to emit the same externally verifiable shape, and a customer/auditor can test the package offline. The explicit sanitization attestation is also useful for proving how evidence was redacted before it entered downstream audit workflows.
- Buyer / painful problem: compliance/recovery MSPs and assurance platforms using several collectors/restore engines whose evidence packages otherwise have incompatible schemas, signatures and redaction conventions; auditors/customers need portable verification outside the producer's own UI.
- Monetization / first paid wedge: **Evidence Bundle Interop Gate** as part of Continuous Assurance Evidence Operations: normalize selected cloud/recovery evidence into a portable bundle, ship an offline verifier plus monthly/quarterly signed packages, and treat verifier failure as non-pass before any audit report is issued.
- Build-time/domain advantage: roughly 2–3 months saved on canonicalization rules, signature/hash-chain structure, schemas, cross-language golden vectors, malformed rejection fixtures, sanitization metadata and offline-verifier contract design.
- Evidence inspected: exact revision README/spec summary, verification rules, bundle schema description, sanitizer contract, cryptographic field registry, retention/export semantics and golden/malformed fixture inventory. The project explicitly states that its evidence infrastructure supports audits but is not itself compliance certification.
- Actual public license / third-party rights: Apache-2.0 for repository-owned specification/code material. External standards/regulatory text, GitHub/Jira/Slack/Microsoft/DLP integrations and any customer evidence retain separate rights/terms.
- User-asserted commercial-permission posture: separate commercial permission assumed for repository-owned public code/content only.
- Combination opportunities: epack/OpenWright/PRC produce and bind evidence → GuardSpine-style schema/golden vectors enforce portable offline verification and sanitization attestation → Evidentia/C2P expresses control state → external RFC3161 + SiVa-style trust validates independent time/certificate state. Its strongest role is a compatibility/falsification layer rather than replacing existing collectors or OSCAL engines.
