- Exact commit / revision: 894a3e0d36dea6d3dc086d066881d9a691b20882

The inspected tests exercise cross-syntax equivalence, rule conformance, ZUGFeRD hybrid-PDF extraction and robustness against arbitrary rule-query input.

That is much more valuable than a one-format XML parser because downstream AP/audit logic can target a canonical invoice representation instead of multiplying format-specific code.
- Monetization path: Use as the structured-invoice path in an AP/audit/recovery gateway, e-invoice validation/conversion API, supplier-onboarding checker or regional compliance adapter. Structured invoices can bypass OCR entirely, improving accuracy and evidence quality.
- Likely buyer / user: AP automation vendors, accounting platforms, multinational finance teams, e-invoice networks, B2B SaaS vendors, procurement systems and compliance service providers serving Europe.
- Build-time or data advantage: Estimated 1–3 months saved on standards modeling, syntax conversion and validation plumbing, before counting the ongoing cost of maintaining multiple invoice syntaxes independently.
- Concrete evidence inspected: Repository metadata showed Apache-2.0 and only 3 stars. `crates/en16931-cli/tests/cli.rs` contains a test asserting the same invoice represented in two syntaxes converts identically; `crates/en16931/tests/conformance.rs` exercises validator rule firing; `crates/en16931-formats/tests/zugferd.rs` tests extracting business terms from hybrid ZUGFeRD PDFs; robustness/property tests exist; the source includes XRechnung-specific validation and explicit separation of syntax-independent versus syntax-binding rules.
- License / rights: Apache-2.0 at the inspected revision. Standards/rules may have their own authoritative publication/update cadence; do not market certification or guaranteed regulatory compliance solely from repository presence.
- Reuse classification: Directly reusable subject to Apache-2.0 notice/license terms.
- Why it is not already obvious / crowded: Very new repository, only 3 stars, but unusually deep standards scope and tests. Search by “invoice parser” would understate that it is a semantic-model and validation substrate.
- Combination opportunities: Put ahead of `getomni-ai/zerox` in document routing: native UBL/CII/ZUGFeRD → exact parser/canonical model; image/PDF without embedded structured data → OCR. Pair with `microsoft/RulesEngine` for customer-specific audit rules and with `open_tms`/AP-recovery systems for structured billing evidence.
- Next action: Build a small adapter from the canonical EN16931 model into the current freight/AP evidence schema and run official/public conformance samples plus intentionally malformed invoices; pin the ruleset/version in every result.
