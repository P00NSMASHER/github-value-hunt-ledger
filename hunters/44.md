# Hunter 44 — Archived enterprise-grade open-source systems

## Mission
Search public GitHub broadly for obscure, undernoticed, rare, unusually valuable, and monetizable public software, datasets, algorithms, workflows, schemas, standards, research code, or technical/business infrastructure relevant to **Archived enterprise-grade open-source systems**.

## Catalog rule
Record every meaningful candidate inspected in this file. For strong candidates, include detailed evidence. For weak/rejected candidates, record a concise reason so future runs do not repeat the work.

## Rights and safety
- Publicly visible is not automatically public domain.
- Respect repository/data licenses and copyright.
- No-license code is inspect/learn/clean-room only unless permission is established.
- Do not collect, reproduce, preserve, or exploit credentials, private/personal data, authentication material, accidentally exposed confidential information, or leaked trade secrets.
- Do not exploit vulnerabilities or unauthorized access paths.

### AOT-Technologies/m8flow-lgpl — archived multi-tenant BPMN/DMN workflow stack
- URL: https://github.com/AOT-Technologies/m8flow-lgpl
- Exact commit / revision: `257d3fb0adad7760ec51d4620104748811c3beae`
- Date inspected: 2026-09-19
- Status: strong
- What it contains: A Python workflow platform derived from the SpiffWorkflow/Spiff Arena ecosystem, with BPMN 2.0 execution, DMN, Camunda-form extraction, Python/JSON workflows, a frontend/backend, database migrations, Celery workers and Flower, Docker infrastructure, Redis, Keycloak, tenant APIs/login, tenant-aware auth patches, MinIO and production-oriented environment/configuration machinery.
- Rare or undernoticed value: The valuable part is not merely BPMN execution; the archived fork contains the unglamorous enterprise plumbing needed to turn workflow execution into a multi-tenant product. The inspected terminal commit still modifies tenant-aware Keycloak/OIDC behavior, cookie/cache handling and JWKS/discovery-cache TTL logic.
- Monetization path: Use as a rights-compliant substrate/reference for vertical case-management, compliance, approval or back-office workflow products; alternatively offer migration/modernization accelerators for organizations leaving Camunda 7-style stacks, without claiming drop-in compatibility until validated.
- Likely buyer / user: Government/SLED vendors, regulated back-office SaaS teams, systems integrators, enterprises with BPMN-heavy workflows.
- Build-time or data advantage: Potentially months of workflow-runtime, tenancy, auth, worker and deployment plumbing versus building a BPMN/DMN SaaS substrate from scratch.
- Concrete evidence inspected: README feature/deployment documentation; Docker/Keycloak/MinIO/Celery stack; `extensions/m8flow-backend` auth patch changes in exact terminal commit; root LICENSE and production/dev tooling.
- License / rights: GitHub metadata/root licensing indicate LGPL-2.1. It is a fork/derivative ecosystem, so dependency and upstream license boundaries must be reviewed component-by-component before distribution.
- Reuse classification: Copyleft / conditional reuse. Suitable for evaluation and potentially commercial use under LGPL terms, but modifications, linking/distribution model and bundled dependencies need legal/engineering review.
- Why it is not already obvious / crowded: Only ~2 stars, archived, and branded as a workflow-engine fork; most of the commercial value sits in deployment/tenant/auth integration rather than a novel README feature.
- Combination opportunities: Pair with `microsoft/RulesEngine` for explicit policy decisions, `zerox` for document intake, and `sam-search` for evidence lookup to create vertical human-in-the-loop case systems.
- Next action: Isolate which AOT-specific modules are genuinely additive to current upstream SpiffWorkflow/Spiff Arena, inventory their licenses, and prototype one vertical case flow before treating the whole archived stack as reusable product infrastructure.

That horizontal “case + evidence + configurable forms + history + reporting” substrate maps directly onto claims, audits, compliance investigations, grant monitoring and recovery workflows without requiring a BPMN engine for every customer process.
- Monetization path: Clean-room vertical case-workbench for freight recovery, denial appeals, government grants/compliance, investigations or evidence-heavy back-office operations; monetize per seat/case/entity or as implementation software for specialist service firms.
- Likely buyer / user: Government contractors, compliance/claims service firms, regulated back-office teams, nonprofits/program-monitoring organizations, audit/recovery operators.
- Build-time or data advantage: Potentially months of product/domain discovery around configurable case types, activity/history/document models, form collection, role administration and embedded analytics. Direct code reuse is not assumed because explicit rights were not found.
- Concrete evidence inspected: Root Docker/test setup and README; `src/api/application.py` is ~109 KB; API package is split into `activities`, `activity_definitions`, `case_definitions`, `case_statuses`, `cases`, `files`, auth, Metabase integration and model schemas; tests include unit/integration/regression directories and a ~9 KB `conftest.py`; the 2020 user manual documents case creation/editing, activity/document/note/history/status/assignment workflows, custom fields, configurable forms, response exports, analytics, roles/permissions and case-type configuration.
- License / rights: No explicit repository license was present in the inspected root. The documentation states the system was produced by IMPAQ International under a U.S. Department of Labor cooperative agreement; that funding context does not by itself establish an unrestricted software license.
- Reuse classification: INSPECT / LEARN / CLEAN-ROOM ONLY unless reuse rights are independently established. Do not assume public-domain status merely because the repository is under a federal-agency organization.
- Why it is not already obvious / crowded: Archived “prototype” naming and a program-specific child-labor monitoring origin obscure a broadly reusable horizontal case/evidence/forms architecture with substantial implementation and documentation depth.
- Combination opportunities: Strong conceptual pairing with `m8flow-lgpl` when explicit BPMN/DMN is needed, `DocuRule` for evidence extraction/provenance, and existing recovery products such as freight audit or ClaimJumper-style denial work queues. It may be a cleaner product-model reference than forcing every vertical workflow into BPMN.
- Next action: Map its case/activity/document/form/history/permission concepts into a fresh clean-room schema and compare that schema against m8flow for one existing revenue wedge (freight recovery or denial recovery) before choosing a workflow substrate.
