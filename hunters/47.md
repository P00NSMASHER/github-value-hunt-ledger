- Monetization path: Offer an offline-first GST reconciliation/recovery workstation or accountant-facing batch service that identifies missing GSTR-2B invoices, value/tax mismatches and potentially unclaimed ITC for review. Monetize per GSTIN/entity, monthly seat, or a fixed diagnostic engagement; do not promise tax recovery without current tax-rule validation and human review.
- Likely buyer / user: Indian SMEs, outsourced bookkeeping/accounting firms, chartered-accountant practices, finance shared-services teams.
- Build-time or data advantage: Several weeks of file-ingestion, normalization, duplicate-safe matching, report generation, GUI and portable-build plumbing are already implemented. The narrow GSTR-2B workflow makes it closer to a sellable vertical tool than a generic reconciliation library.
- Concrete evidence inspected: Repository/license metadata; exact terminal commit; root with MIT `LICENSE`, `rekvia.py`, package structure, build script and committed pytest output; `rekvia/core/engine.py` (~11 KB) implementing Excel ingestion, alias mapping, GSTIN/invoice normalization, tax aggregation, unique occurrence keys, deterministic outer merge, fuzzy matching with row-consumption guard, status/risk assignment and Excel report sheets.
- License / rights: MIT for repository code. Tax forms, government portal data and any third-party dependencies still require their own terms/compliance review.
- Reuse classification: Permissive / reusable under MIT terms, subject to dependency and regulatory validation.
- Why it is not already obvious / crowded: Only two stars and distributed as a small Windows desktop utility rather than a tax-tech SaaS; the valuable workflow sits in a compact local matching engine rather than a marketed API/platform.
- Combination opportunities: Combine the deterministic matching core with `dedupeio/dedupe` for carefully validated entity matching, `RulesEngine` for versioned tax-control rules, and evidence/document intake from `zerox`; alternatively keep the founding product fully local/offline to exploit privacy as a differentiator.
- Next action: Validate the engine on synthetic edge cases and current GSTR-2B schemas, remove/disable automatic self-update for controlled enterprise deployments, then measure incremental ITC/exceptions found versus a CA firm's existing spreadsheet process before making recovery/savings claims.

### europeanplaice/subset_sum — permissive many-to-many reconciliation kernel across Rust/Python/WASM
- URL: https://github.com/europeanplaice/subset_sum
- Exact commit / revision: `62fe41b4c8f5d287d1904f573a9594cac254d340`
- Date inspected: 2026-09-19
- Status: strong
- What it contains: A six-star MIT dynamic-programming library whose `sequence_matcher` handles many-to-many transaction matching rather than only one-payment/one-invoice lookup. It supports negative values, configurable maximum group lengths, unmatched remainders, sparse/parallel native computation, Python and Rust packages, browser/WASM artifacts, CLI usage and an MCP-oriented reconciliation demo.
- Rare or undernoticed value: This is a rights-clean implementation of the hard allocation primitive seen in proprietary reconciliation systems: one bank-side amount may correspond to several ledger rows and vice versa. The library exposes matched groups plus remainders instead of forcing every transaction into a one-to-one identity. Its March 2026 hardening commit added empty-input/bounds validation and stricter minor-unit normalization.
- Monetization path: Use as the mathematical allocation layer inside B2B cash application, freight/payment evidence matching, GST reconciliation, processor settlement reconciliation or recovery products; wrap it with entity/reference/date constraints and human ambiguity handling rather than sell subset-sum itself.
- Likely buyer / user: AR/shared-service teams, accounting automation vendors, distributors/manufacturers, payment operations and recovery/audit products.
- Build-time or data advantage: Saves several weeks of designing/optimizing a many-to-many allocation kernel and maintaining wrappers across Python/Rust/WASM. The product layer still needs domain-specific candidate generation, explainability and ambiguity controls.
- Concrete evidence inspected: MIT repository metadata; exact hardening commit; recursive tree with Rust core, Python/MCP normalization, docs, examples and browser/WASM package; packaged README explicitly documents `find_subset` and `sequence_matcher` for many-to-many bank/account reconciliation, group-size controls and unmatched remainders.
- License / rights: MIT.
- Reuse classification: Permissive reuse subject to MIT terms and normal dependency review.
- Why it is not already obvious / crowded: Only six stars and a generic algorithm name. The commercially interesting reconciliation API is buried behind “subset sum” framing rather than marketed as a finance engine.
- Combination opportunities: This is a particularly useful permissive replacement for the many-to-many allocation concept learned from proprietary `reconcileai`; combine with `dedupe` for entity/reference constraints, CasePro for exception workflow, Rekvia or freight recovery for a vertical use case, and versioned deterministic rule packs for financial controls.
- Next action: Benchmark it on synthetic ambiguous/split/partial/negative/FX-like transaction sets and require domain constraints before accepting a grouping; quantify false-match rate versus one-to-one and greedy baselines.
