# Hunter Learning Engine

## Purpose

Add compounding learning to the GitHub Value Hunt **without weakening the existing evidence, benchmark, safety, verification, or promotion gates**.

This layer borrows the strongest mechanisms found in current experimental agent systems while keeping the repository's existing deterministic authority model:

- MemRL-style value-weighted memory;
- SkillHone-style runtime failure capture and regression repair;
- AgentHER-style salvage of verified useful outcomes from otherwise failed trajectories;
- GEPA/AutoSkill-style train/dev versus promotion-test skill evolution;
- FederatedSkill-style personalized peer-skill transfer;
- GEA-style performance × behavioral-novelty fleet selection;
- HarnessEvoGym-style immutable evaluator/controller boundaries for deeper self-modification;
- Agent Lightning/ATLAS-compatible clean trajectory export for a later model-training phase.

No third-party runtime is required for the first layer. The production engine is dependency-free Python and can later accept candidate variants generated by GEPA/DSPy or another optimizer.

## Highest-leverage sequence implemented

### 1. Value-scored memory — active, observe-first

Value is learned at both global and search-objective scope. Objective-conditioned priors prevent success in one problem class from being blindly generalized to unrelated lanes. Search moves are credited from their own observed hit/yield telemetry rather than inheriting the whole hunt's reward, and repeated uses of the same move type within one hunt collapse to one averaged update.

`production/learning_engine.py::ValueMemory` maintains a bounded Q-value per strategy, query family, search move, salvaged trajectory, or local skill.

`tools/ti_learning_state.py` rebuilds those values from canonical `search_runs.jsonl` plus linked `outcomes.jsonl`.

The reward is deliberately grounded in measured evidence only:

- retained/deep-inspected yield;
- actual MASTER promotion counts;
- new capability creation;
- measured duplicate-inspection avoidance;
- linked downstream experiment outcomes;
- realized revenue/customer value when those fields are actually observed, with bounded log-scale magnitude weighting;
- a penalty for repeated deep inspection producing no retained candidate.

Unknown denominators remain unknown. Non-search fixture/artifact work is excluded. Retrospective records do not train this layer.

The generated `intelligence/LEARNING_STATE.json` is advisory. It does **not** automatically expand/retire strategies or override assignment/STOP/verification rules.

Existing policy evidence gates remain unchanged: at least **5 train runs and 20 train deep inspections**, followed by **2 independent confirm runs and 6 confirm deep inspections with non-negative mean confirm reward**, before a strategy/query family becomes eligible for policy consideration.

### 2. Failure capture → regression repair — queue implemented

`intelligence/learning_failure_spool/` accepts immutable, reproducible hunter-system failures.

A repair candidate is not accepted merely because an agent proposes a better prompt. It must have:

- an eligible non-sensitive/non-contaminated source failure;
- at least one regression test;
- every linked regression test passing;
- a content-addressed diff;
- durable decision history;
- no unrelated file changes.

Passing this gate yields only `READY_FOR_SKILL_EVAL`.

### 3. Failed-trajectory salvage — local only

A failed hunt can become useful experience only when the trajectory produced a **verified alternate outcome with evidence**.

The reward is capped and the memory scope is:

`LOCAL_ONLY_UNTIL_INDEPENDENTLY_VALIDATED`

This prevents "failed but interesting" from silently becoming global truth while preserving serendipitous discoveries that would otherwise be thrown away.

### 4. Skill evolution — staged mutation gate implemented

Optimizers may mutate a search skill or prompt using a `mutate_dev` split, but promotion is measured on a separate `promotion_test` split.

A candidate is rejected for:

- insufficient dev or promotion examples;
- split leakage;
- missing provenance;
- any hard regression;
- no dev improvement;
- insufficient held-out delta against the current champion.

A passing candidate reaches only `STAGED_MUTATION`. Separately, any strategy/query-family that is train-ready but becomes negative on sufficient confirm evidence is labeled `overfit_signal`, suppressed from live priors, and surfaced for falsification/repair. The pre-existing production rule still controls GLOBAL promotion:

2 distinct successes → STAGED → >=5 held-out tasks at 100% with zero regressions + adversarial + adjacent-domain transfer + curator approval → CANARY → >=3 hunters with zero regressions → GLOBAL.

### 5. Personalized peer transfer — implemented

A skill learned by Hunter A is not blindly copied to Hunter B.

Transfer requires:

- source skill already STAGED/VERIFIED/CANARY/GLOBAL;
- at least two distinct source successes;
- zero known source regressions;
- evidence refs;
- adequate target compatibility;
- evidence that the target actually has a related failure/need.

Same-runtime, strongly compatible VERIFIED+ skills may be `ABSORB_LOCAL`; otherwise the allowed positive decision is `ADAPT_LOCAL`.

Neither decision bypasses the global skill gate.

### 6. Fleet evolution with diversity pressure — implemented

`select_fleet_parents` uses the GEA-style idea:

`performance × sqrt(behavioral novelty)`

Novelty is the mean cosine distance to nearest peers using a task-success vector.

This prevents all hunters converging on one search behavior merely because it currently has the best average yield. Different high-value behavior can survive and seed later fleet variants.

This mechanism is staged for controlled/shadow use; it does not rewrite current automation assignments.

### 7. Harness self-modification — canary-only gate implemented

A deeper harness mutation is rejected when it:

- writes outside the leased mutable region;
- changes the evaluator;
- changes the controller;
- opens the sealed final set;
- touches credentials;
- lacks enough selection tasks;
- introduces any regression;
- fails to improve the selection score;
- lacks a frozen diff hash.

A passing mutation is only `CANARY_ONLY`.

### 8. Future RL/distillation export — eligibility implemented, training not activated

`build_training_manifest` emits only verified, evidence-linked, immutable-payload trajectories with finite rewards and no sensitive/benchmark contamination.

This creates a clean future handoff to systems such as Agent Lightning or ATLAS without making model training a prerequisite for current learning.

## Generated live artifact

Run:

```bash
python tools/ti_learning_state.py --write intelligence/LEARNING_STATE.json
python tools/ti_learning_state_validate.py
```

The shared build executes both steps automatically.

Hunters consume only evidence-sufficient value priors exposed through `NETWORK_PRIORS.md`. Insufficient evidence remains visible as "observe first"; it is not converted into an apparent winner.

## Safety and benchmark boundaries

This learning layer never:

- reads benchmark gold to improve remaining benchmark work;
- treats a predicted score as realized commercial value;
- trains on non-search work as if it were search yield;
- learns from sensitive/accidental/confidential material;
- lets a repair agent rewrite its own audit history;
- permits peer transfer to bypass local validation;
- lets an evolving harness modify its evaluator/controller;
- globally promotes a skill automatically.

The frozen benchmark and `production/STATUS.md` cutover gates remain authoritative.

## Next activation after merge

The first useful live effect is deliberately small:

1. canonical runs/outcomes produce Q-values on every build;
2. evidence-sufficient strategy/query-family values appear in NETWORK_PRIORS;
3. hunters may use those as one retrieval prior, never as authority;
4. reproducible hunter-system failures can enter the immutable repair queue;
5. once enough failure/holdout evidence exists, an external optimizer can generate skill variants for the existing staged-mutation gate.

Fleet evolution, harness evolution, and model training remain shadow/canary operations until the current benchmark and production launch gates permit them.

### 9. Hunter database training environment — implemented

`production/training_environment.py` converts canonical measured search telemetry into deterministic offline episodes:

`state -> action -> observation -> reward`

Prospective runs are deterministically split into train and confirm partitions by `sha256(search_run_id)`. Benchmark records are evaluation-only. Outcome credit never crosses a split, and mixed-origin outcomes spanning train and confirm are excluded.

Downstream reward is intentionally multi-stage. Discovery yield and technical validation can teach search behavior now, but technical-only evidence is capped below commercially grounded evidence. Realized revenue/customer value, when actually observed, receives the strongest reward weight.

Long-horizon credit can flow backward only through explicit ledger provenance: direct origin search IDs, shared experiment IDs, contributed capability IDs and explicitly retained repositories. Each credited outcome conserves total credit at exactly 1.0. This is training/accounting attribution, not a causal claim.

Generated artifacts:

- `intelligence/TRAINING_ENVIRONMENT.json`;
- `intelligence/training_episodes.jsonl`.

The training environment remains `policy_effect=none`. Optimizers may use the train partition to propose variants, but only confirm/evaluation evidence plus the existing held-out/canary/global promotion gates may authorize later policy changes.
