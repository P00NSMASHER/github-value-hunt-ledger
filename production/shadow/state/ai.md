# AI / agent infrastructure shadow state

This is lane-local shadow state. It is evidence-backed working memory, not authoritative MASTER/Search-Skills promotion.

## Current hypotheses
- ACTIVE — **Compositional effect-safety hypothesis.** High-risk agent runtimes need at least four distinct proof planes: (1) source-bound deterministic replay for already-known effects; (2) multi-worker ownership/fencing plus durable effect identity before dispatch; (3) provider/system-of-record reconciliation for effects whose remote outcome is unknown; and (4) exact bounded authority plus qualification evidence proving which implementation/configuration was allowed to act. Chidori is strongest on strict no-live replay; Feedling/Zebra on fenced effect dispatch; WriteGuard/Auths on provider-aware reconciliation; Orka adds model-submission ambiguity and provider publication recovery. No inspected project proves every layer for arbitrary third-party APIs.
- ACTIVE — **Qualification-currentness hypothesis.** Provider/action evidence is trustworthy for current routing only when the retained proof subject is compared against the currently shipped behavior-bearing source/configuration subject. A Git SHA or historical qualified release is provenance, not currentness by itself.
- ACTIVE — **Qualification-closure precision hypothesis.** A useful currentness gate must be selectively invalidating: covered behavior/configuration drift withdraws qualification, while demonstrably irrelevant out-of-closure drift preserves it. Under-scoped closures create stale-proof risk; over-scoped closures create unnecessary expensive requalification.
- ACTIVE — **Commercial wedge hypothesis.** The nearest sellable unit is a bounded consequential-action/qualification retrofit around an existing agent stack: stable action identity, durable UNKNOWN, provider readback, conservative economic reservation where money is involved, crash-window evidence, and source/configuration currentness. Full orchestration replacement is not required.

## Validated local lessons
- Evaluate durability at the **side-effect boundary**, not by the presence of checkpoint/resume APIs.
- Strict replay needs source identity, function/argument divergence, complete journal consumption, no unexpected live calls, completed-state requirements and output equality.
- Crash/retry safety, multi-writer ownership, source provenance and provider truth are separate axes; do not infer one from another.
- **Unknown remote outcome is a first-class state, not a retry condition.** Definitive no-effect requires proof that the effect did not happen; definitive success requires authoritative evidence.
- Persist-before-act is necessary but insufficient. Non-idempotent/irreversible actions need explicit retry admissibility and an independent resolution path for uncertainty.
- Model output must never be an authorization channel for gated consequential actions.
- Uniqueness constraints are weaker than ownership/fencing. External I/O requires a valid owner/fence before dispatch, not merely duplicate terminal-row protection afterward.
- Fenced effect state machines should distinguish at least `PENDING`, `CLAIMED`, `SUCCEEDED`, `FAILED_NO_EFFECT`, and `UNCERTAIN/NEEDS_RECONCILIATION`.
- “Exactly once” must name its boundary. Local sink ledgers do not create exactly-once semantics for arbitrary remote providers.
- Provider reconciliation is strongest as a **separate read path**, not a disguised repeat mutation.
- Live E2E, a qualification harness, and trusted qualification are three different evidence classes. A provider workflow/report schema does not count as provider proof until retained evidence says the provider was actually exercised and passed.
- `NOT_EXERCISED` is a valuable fail-closed evidence state and must not be converted into a partial pass.
- Generic transport errors are not evidence that no remote effect occurred. Catch-all `NETWORK_ERROR -> failed` is unsafe when the request may have crossed the remote boundary.
- Unknown money must remain reserved/conservatively counted against limits until provider truth resolves it.
- Provider idempotency retention is a recovery horizon, not a permanent business-operation ledger.
- Safe stopping is not full reconciliation. If a create acknowledgement and provider object ID are both lost, the system needs read-only object discovery plus exact semantic correlation or deliberate human review.
- Stable business-effect identity should be independent of transient framework/tool-call IDs.
- Reconciliation should distinguish `found`, `not_found`, `ambiguous`, and `unavailable`; zero or multiple matches are not success.
- **Provider exercised != source qualified.** A dated real/sandbox provider drill must not silently bless later behavior-bearing source/configuration.
- `gitRevision` inside a report is provenance labeling; currentness requires comparing the retained proof subject to the current subject at route/build admission.
- Qualification scope inheritance needs a machine-defined equivalence/closure relation. “Shared lifecycle” plus fixtures can be sensible operational evidence but is not exact-current-source qualification by itself.
- Qualification currentness has two independent failure modes: **under-scoped closure** lets stale proof survive behavior change; **over-scoped closure** invalidates proof after irrelevant change and can make qualification economically impractical.
- A whole-repository tracked-tree hash is robust anti-staleness but not automatically a good semantic qualification closure.
- Exact phrase/code search for qualification terms can surface superseded historical designs. Current status headers, current extension docs and commit/history verification are mandatory before crediting implementation.

## Failed / low-yield search patterns
- Broad repository-name/product searches around `checkpoint`, `durable agent`, `agent replay`, `Stripe + Temporal + idempotency`, or `live provider attestation` mostly return commodity checkpointing, retry-with-same-key examples, harnesses and report schemas.
- Higher-yield implementation nouns include `effect_outbox`, `LeaseFence`, `claim_token`, `needs_reconciliation`, `OutcomeUnknown`, `SubmittedUnknown`, `provider_operation_id`, `provider truth`, `refund_operations`, `provider_reference`, `real_refund_verified`, `throwAfterExternalSuccess`, `reconciled_after_unknown_outcome`, qualification index/report state and source/configuration digest checks.
- README or workflow presence is not run evidence. Inspect retained reports/artifacts, explicit exercise status, route advertisement and current production configuration.
- Provider-specific header names in code/comments are not proof that the provider supports that contract; cross-check current first-party provider documentation when the claim depends on it.
- Search hits from historical architecture/design documents can be false positives when the current tree explicitly marks them superseded or removed.
- Local clone/test execution remains blocked by the sandbox's outbound DNS restriction; committed tests are therefore distinguished from independently rerun tests unless another execution path exists.
