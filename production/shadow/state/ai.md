## Validated local lessons
- Run 1: a durable-agent claim should be evaluated at the **side-effect boundary**, not at the presence of a checkpoint API. High-signal evidence is a journal that can prevent previously completed external effects from executing again during replay, coupled with tests that prove this behavior in a fresh runtime.
- Run 1: replay becomes verification-grade only when it has a strict posture: source identity/fingerprints, function + argument divergence, journal completeness/consumption, no unexpected live calls, completed-state requirement and output equality. A best-effort replay/debug mode is weaker than a dedicated fail-closed verifier.
- Run 1: crash/retry safety and multi-writer safety are separate. A runtime can replay correctly in one process while still allowing concurrent continuations to corrupt durable state. Inspect the lease/transaction semantics of each storage backend before claiming exactly-once or distributed safety.
- Run 1: history archaeology is essential for runtime maturity. Chidori's current code contains strong regression controls, but its v3.8.1 release commit also documents an engine panic, package-version drift and previously red CI in v3.8.0. A strong architecture does not erase release-operability risk.
- Run 1: comparator breadth and candidate depth should remain distinct. Atmosphere provides strong adjacent evidence for cross-runtime governance/capability contracts, but it was not credited with Chidori-level deterministic-replay depth without equivalent source/test inspection.
- Run 2: **unknown outcome is a first-class state, not a retry condition.** If a non-idempotent effect was marked started before process death but no terminal outcome was durably recorded, safe recovery requires parking the run and obtaining authoritative external evidence. Absence of a local success row does not prove remote failure.
- Run 2: “persist before act” is only half the safety story. The runtime must also classify side effects (`read_only` / idempotent / non-idempotent / irreversible), define which classes may be replayed after uncertainty, and provide a separate resolution path for indeterminate writes.
- Run 2: model output must not be an authorization channel. `agent-runtime`'s tests show that even model-supplied fields claiming approval cannot bypass a registry-level gate; malformed model output also must not silently become terminal success.
- Run 2: append uniqueness is weaker than ownership. A `(run_id, seq)` uniqueness constraint can expose a direct journal collision but does not prove that two processes cannot both reach external I/O. Multi-worker safety needs a lease/fencing/transaction mechanism evaluated independently from replay correctness.
- Run 2: manual recovery metadata is not automatically authoritative evidence. Requiring `actor` and `evidence` fields is useful, but the verifier should separately ask whether the actor is authenticated and whether the evidence can be reconciled against the actual external system of record.
- Run 2: strict replay libraries and durable runtimes are complementary. `davccavalcante/agenticstash` is stronger on framework-neutral input divergence, missing/extra-call reporting and tamper-evident recordings; `agent-runtime` is stronger on crash/approval/indeterminate external-write semantics. Neither alone establishes the full production reliability contract.
- Run 3: **fencing must exist before external dispatch, not merely at terminal write.** Feedling's owner-fenced enqueue and Zebra's `LeaseFence`/claim path show the useful pattern: stale owners should be unable to create or claim new effects, and a later owner must reconcile an abandoned claim instead of simply reissuing it.
- Run 3: an effect state machine should distinguish at least `PENDING`, `CLAIMED`, `SUCCEEDED`, `FAILED_NO_EFFECT`, and `UNCERTAIN/NEEDS_RECONCILIATION`. Feedling and Zebra independently encode the key asymmetry: retry is permitted only after the system has evidence that no external effect occurred; uncertainty is not eligible for automatic retry.
- Run 3: “exactly once” must always name its boundary. Feedling's tests strongly prove exactly-one write across crash recovery **inside its sink-ledger contract**, but that does not imply exactly-once behavior for an arbitrary remote API whose commit status cannot be read back. Future writeups must explicitly name the local boundary and the external authority.
- Run 3: source/version provenance and worker ownership are orthogonal. Runtime generation, owner epochs and fencing tokens protect who may write; they do not prove that the tool implementation being replayed is the same code/version that produced the prior result.
- Run 3: PostgreSQL fault tests that force crashes at multiple points around claim/write/status transitions are much more probative than generic retry tests. The most useful cases make “write failed” and “write may have committed” produce different durable recovery states.
- Run 4: **provider-backed reconciliation should be a separate read path, not a disguised retry.** Auths' Stripe qualification adapter separates execute from reconcile and describes reconciliation as observing the original idempotent refund without another mutation. That is stronger evidence than merely reusing the same idempotency key on another POST.
- Run 4: **qualification state is part of the claim, not deployment metadata.** A sophisticated source tree with crash matrices and provider adapters does not earn “production proven” status if the trusted qualification index is empty or the production route test refuses advertisement. Always inspect the attestation/index and route availability directly.
- Run 4: exact authority, effect safety and evidence provenance are distinct planes. Auths commits exact money/action/configuration inputs, holds ambiguous capacity, observes provider truth with separate read credentials, and binds qualification to a semantic source closure. None of those should be inferred from the others.
- Run 4: a self-denying production route is positive evidence of fail-closed governance. `auths-node` tests explicitly require no production provider profiles when qualification is absent. This is more probative than README language claiming “production ready.”
- Run 4: mainstream durable orchestration plus provider idempotency is a strong commodity baseline. The Temporal comparator can durably resume a refund activity and reuse one Stripe idempotency key; a stronger candidate must add something measurable beyond that baseline, such as provider-truth reconciliation, exact bounded authority, source/configuration closure or qualification evidence.
- Run 5: **model-provider ambiguity and tool/provider ambiguity are distinct reliability boundaries.** Orka's durable `SubmittedUnknown` and external-effect `OutcomeUnknown` states show that a model request can become indeterminate before any business tool runs, while an external mutation can independently become indeterminate after dispatch. Recovery logic should not collapse these into one generic retry state.
- Run 5: provider reconciliation is most convincing when a repository contains an actual readback/recovery implementation plus duplicate-avoidance tests. Orka's GitHub PR publication recovery is materially stronger evidence than an `OutcomeUnknown` enum alone because it interrogates provider-side state to resolve an ambiguous publication.
- Run 5: **live E2E CI and trusted qualification are different evidence classes.** A successful `Live GitHub OIDC PR E2E` at the pinned revision supports operability of one live-provider path, but it does not prove source-bound attestation, crash-matrix qualification or transferability to other providers.
- Run 5: tool/configuration drift must be tested as a recovery hazard. Orka's MCP broker drift tests independently support the Run-4 lesson that execution/recovery assumptions should be invalidated when the tool contract changes rather than silently inheriting old authority/evidence.
- Run 5: commit-history archaeology can reveal the real reliability surface. Orka's repeated fixes for ambiguous PR recovery, URL corruption, provider lookup failures, number collisions and terminal-outcome invariants are evidence that the hard cases live in recovery semantics, not in the happy-path dispatcher.
- Run 6: **qualification reports need a first-class `NOT_EXERCISED` state.** Threvo's Stripe report schema distinguishes `PASSED`, `FAILED` and `NOT_EXERCISED`, and its missing-input path records provider/database participation as false rather than converting absence of credentials into a green result. This is evidence-quality plumbing, not provider proof.
- Run 6: safe retry semantics should be inspectable at the durable state boundary, not only in application code. Threvo's PostgreSQL transition/claim rules allow `failed_unknown -> verification_pending` while effect-claim transfer is limited to `failed_known` or `stale`, making “unknown is not retryable” visible in database-enforced invariants.
- Run 6: financial action governance is emerging as a separable layer between agent frameworks and provider SDKs. Threvo independently converges with Auths on exact approval/effect identity, state re-resolution, provider-aware ambiguity, authoritative verification and explicit qualification evidence while remaining framework-neutral.
- Run 7: **generic transport errors are not evidence of no remote effect.** Railguard catches every `httpx.HTTPError` as one `NETWORK_ERROR`, and its gateway converts every provider error into `failed` plus “No money moved.” For a request that may have crossed the remote boundary, that is an epistemic bug even when the local intent was persisted first.
- Run 7: **financial policy accounting must be uncertainty-aware.** If an ambiguous remote mutation is written locally as `failed`, any velocity/cap query that sums only `executed` rows can understate actual money movement and authorize further spend from a false ledger. Unknown money should remain reserved/conservatively counted until authoritative reconciliation.
- Run 7: a local idempotency TTL is not an ambiguity resolver. Railguard intentionally permits an identical money action again after its local window expires; that is safe only when the prior outcome is known or the provider's idempotency-retention/readback contract is sufficient and verified. Retry eligibility must be evidence-based, not merely age-based, while outcome is unknown.
- Run 7: a tamper-evident audit chain preserves **integrity of recorded claims**, not truth of those claims. Hash-chaining a misclassified `failed` outcome can increase false confidence unless provider outcome authority is modeled separately.
- Run 8: **uncertain money must consume the same economic capacity as successful money until truth is known.** AgentCart's refund reservation query subtracts every refund operation except `failed`/`canceled`, so `reserved`, `pending`, `requires_action` and other unresolved states block additional refunds against the same verified payment. This is the positive counterpart to Railguard's Run-7 cap-understatement bug.
- Run 8: **provider idempotency retention is a recovery horizon, not a permanent guarantee.** AgentCart deliberately refuses to resubmit an unresolved Stripe refund after 23 hours because current Stripe documentation says idempotency keys may be pruned after at least 24 hours, after which reuse can create a new request. A safe hold is better than an unbounded retry, but the hold is operationally incomplete without provider readback.
- Run 8: **a safe stop is not the same as completed reconciliation.** Once a Stripe refund ID is known, AgentCart retrieves provider status and verifies amount/currency/payment identity. If the create acknowledgement was lost before that ID was persisted and the idempotency horizon expires, the code only blocks. Current Stripe `refunds.list` supports filtering by `payment_intent`, showing a plausible provider-truth path the candidate has not yet implemented.
- Run 8: read-only provider reconciliation can be composed separately from mutation control. `tonytonycoder11/stripe-connect-reckon@deb30aabfed84c7b0b2e5ae28c92cc9f85f79193` reads Stripe refunds and flags provider refunds missing from application state, but exact automation still requires correlating that provider object to the semantic action/request before treating it as authoritative resolution.
- Run 8: README claims of live test-mode verification remain a weaker evidence class than a retained qualification artifact. Stripe Connect Reckon claims live test-mode reads were exercised, while AgentCart explicitly says its payment-provider integration drills use fixtures; neither supplied the exact retained live money-action qualification packet targeted by the current hypothesis.
