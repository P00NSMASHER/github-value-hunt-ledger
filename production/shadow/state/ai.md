# AI / agent infrastructure shadow state

## Current hypotheses
- ACTIVE — Compositional effect-safety hypothesis: high-risk agent runtimes need **three distinct proof layers** that are often implemented separately: (1) source-bound deterministic replay for already-known effects; (2) multi-worker ownership/fencing plus durable effect identity before dispatch; and (3) provider/system-of-record reconciliation for effects whose remote outcome is unknown. Supporting evidence: `ThousandBirdsInc/chidori@223bb8779f63822c3e63a9a4347dda7483a02158` is strongest on strict source/argument-aware no-live replay; `teleport-computer/feedling-mcp@c37e3db0dcc4f08cf69aa3c73cf87a911377b02f` and `LogicStormINC/zebra@efd4e2938d14c6598e9c60503830abf5360fa0bf` independently implement fenced effect/outbox state machines with explicit uncertain/reconciliation states; `prathamesh-git9/agent-runtime@3d4c3bf58b4262cf523e78655ff0bf1c9453830e` independently demonstrates the same ambiguous-effect fail-closed rule in a compact agent runtime. Contrary evidence: these are established distributed-systems ideas, mature workflow engines may already offer stronger primitives, and no inspected project yet proves all three layers against arbitrary third-party APIs. NEXT TEST: find a production-shaped agent/tool adapter that combines source/version binding, multi-worker fencing, and a real provider idempotency/status-readback API; fault-inject “remote commit succeeded, acknowledgement lost” and verify automatic reconciliation without duplicate I/O. CONFIDENCE: HIGH on the three-layer semantic requirement, MEDIUM on whether a distinct agent-specific product category exists.

## Validated local lessons
- Run 1: a durable-agent claim should be evaluated at the **side-effect boundary**, not at the presence of a checkpoint API. High-signal evidence is a journal that can prevent previously completed external effects from executing again during replay, coupled with tests that prove this behavior in a fresh runtime.
- Run 1: replay becomes verification-grade only when it has a strict posture: source identity/fingerprints, function + argument divergence, journal completeness/consumption, no unexpected live calls, completed-state requirement and output equality. A best-effort replay/debug mode is weaker than a dedicated fail-closed verifier.
- Run 1: crash/retry safety and multi-writer safety are separate. A runtime can replay correctly in one process while still allowing concurrent continuations to corrupt durable state. Inspect the lease/transaction semantics of each storage backend before claiming exactly-once or distributed safety.
- Run 1: history archaeology is essential for runtime maturity. Chidori's current code contains strong regression controls, but its v3.8.1 release commit also documents an engine panic, package-version drift and previously red CI in v3.8.0. A strong architecture does not erase release-operability risk.
- Run 1: comparator breadth and candidate depth should remain distinct. Atmosphere provides strong adjacent evidence for cross-runtime governance/capability contracts, but it was not credited with Chidori-level deterministic-replay depth without equivalent source/test inspection.
- Run 2: **unknown outcome is a first-class state, not a retry condition.** If a non-idempotent effect was marked started before process death but no terminal outcome was durably recorded, safe recovery requires parking the run and obtaining authoritative external evidence. Absence of a local success row does not prove remote failure.
- Run 2: “persist before act” is only half the safety story. The runtime must also classify side effects (`read_only` / idempotent / non-idempotent / irreversible), define which classes may be replayed after uncertainty, and provide a separate resolution path for indeterminate writes.
- Run 2: model output must not be an authorization channel. `agent-runtime`'s tests show that even model-supplied fields claiming approval cannot bypass a registry-level gate; malformed model output also must not silently become terminal success.
- Run 2: append uniqueness is weaker than ownership. A `(run_id, seq)` uniqueness constraint can expose a direct journal collision but does not prove that two processes cannot both reach external I/O. Multi-worker safety needs a lease/fencing/transaction mechanism evaluated independently from replay correctness.
- Run 2: manual recovery metadata is not automatically authoritative evidence. Requiring `actor` and `evidence` fields is useful, but the verifier should separately ask whether the actor is authenticated and whether the evidence can be reconciled against the actual external system of record.
- Run 2: strict replay libraries and durable runtimes are complementary. `davccavalcante/agenticstash` is stronger on framework-neutral input divergence, missing/extra-call reporting and tamper-evident recordings; `agent-runtime` is stronger on crash/approval/indeterminate external-write semantics. Neither alone establishes the full production reliability contract.
- Run 3: **fencing must exist before external dispatch, not merely at terminal write.** Feedling's owner-fenced enqueue and Zebra's `LeaseFence`/claim path show the useful pattern: stale owners should be unable to create or claim new effects, and a later owner must reconcile an abandoned claim instead of simply reissuing it.
- Run 3: an effect state machine should distinguish at least `PENDING`, `CLAIMED`, `SUCCEEDED`, `FAILED_NO_EFFECT`, and `UNCERTAIN/NEEDS_RECONCILIATION`. Feedling and Zebra independently encode the key asymmetry: retry is permitted only after the system has evidence that no external effect occurred; uncertainty is not eligible for automatic retry.
- Run 3: “exactly once” must always name its boundary. Feedling's tests strongly prove exactly-one write across crash recovery **inside its sink-ledger contract**, but that does not imply exactly-once behavior for an arbitrary remote API whose commit status cannot be read back. Future writeups must explicitly name the local boundary and the external authority.
- Run 3: source/version provenance and worker ownership are orthogonal. Runtime generation, owner epochs and fencing tokens protect who may write; they do not prove that the tool implementation being replayed is the same code/version that produced the prior result.
- Run 3: PostgreSQL fault tests that force crashes at multiple points around claim/write/status transitions are much more probative than generic retry tests. The most useful cases make “write failed” and “write may have committed” produce different durable recovery states.

## Candidate skills
- EFFECT-JOURNAL RELIABILITY AUDIT — STAGED-ELIGIBLE, 3 distinct shadow successes (Run 1 Chidori; Run 2 agent-runtime; Run 3 Feedling/Zebra). WHEN TO USE: agent runtimes claiming durability, resumability, deterministic execution or safe human-in-the-loop. PROCEDURE: trace every external effect to its durable identity; inspect record→fresh-process replay; force a pre-frontier source/argument change; inspect strict/no-live verification; inspect crash frontier persistence; inspect approval continuation; inspect storage-specific concurrent-writer behavior; classify started-without-outcome semantics; then read release history for failures that tests later fixed. WHY IT WORKED: it separated Chidori's genuinely unusual replay verifier from ordinary checkpoint orchestration, exposed `agent-runtime`'s ambiguous-effect handling plus missing lease/source binding, and then distinguished Feedling/Zebra's stronger fenced effect boundaries from source-bound replay. FAILURE MODES: frameworks may hide effects inside third-party runtimes; a replay can be deterministic yet still lack authoritative source identity or distributed exclusion; documentation can overstate backend guarantees; “idempotent” may be developer-declared without provider proof. NEXT IMPROVEMENT: apply to a provider-integrated runtime and require an actual remote status/readback reconciliation seam. Keep lane-local; do not promote to global SEARCH_SKILLS from shadow state.
- AMBIGUOUS EFFECT OUTCOME AUDIT — STAGED-ELIGIBLE, 2 distinct shadow successes (Run 2 agent-runtime; Run 3 Feedling/Zebra). WHEN TO USE: any agent/workflow system that can issue money-mutating, irreversible or customer-visible external actions. PROCEDURE: locate the durable pre-dispatch marker; identify the exact crash interval between remote commit and local acknowledgement; determine whether retry policy differs by side-effect class; require an explicit INDETERMINATE/UNKNOWN state for non-idempotent writes; inspect the resolution API for actor identity, evidence provenance, duplicate resolution prevention and provider-side status lookup; then test a cold restart before resolution. WHY IT WORKED: `agent-runtime` made the ambiguity window explicit; Feedling and Zebra independently showed that production-shaped multi-worker runtimes need the same state under fencing and real-DB concurrency. FAILURE MODES: a system can park safely but accept unauthenticated/fabricated resolution evidence; a provider may lack a status/idempotency API; distributed workers may duplicate the call before the indeterminate state is observed. NEXT IMPROVEMENT: validate against a real provider sandbox or a synthetic provider that models “commit succeeded, acknowledgement lost.”
- FENCED EFFECT BOUNDARY AUDIT — LOCAL, 1 shadow success. WHEN TO USE: multi-worker agent/workflow runtimes claiming exactly-once or crash-safe external actions. PROCEDURE: verify a stable effect identity; verify owner/epoch/fence authority before enqueue and claim; force stale-owner and concurrent-claim cases; inspect atomic intent/terminal writes; expire or replace a claim; require reconciliation rather than pending reset; verify retries are only created from `FAILED_NO_EFFECT`; then identify the external authority needed to resolve `UNCERTAIN`. WHY IT WORKED: Feedling and Zebra exposed nearly identical correctness structure despite different implementations. FAILURE MODES: local fencing can still lose against a remote provider with no idempotency/status API; an outbox may be transactionally strong while source provenance is weak; lease heartbeats can protect ownership without protecting already-issued remote I/O. NEXT IMPROVEMENT: combine this audit with a provider-status adapter and Chidori-style source fingerprints.
