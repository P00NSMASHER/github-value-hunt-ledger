# AI / agent infrastructure shadow state

## Current hypotheses
- ACTIVE — Compositional effect-safety hypothesis: high-risk agent runtimes need **three distinct effect-proof layers plus an orthogonal authority/evidence gate**: (1) source-bound deterministic replay for already-known effects; (2) multi-worker ownership/fencing plus durable effect identity before dispatch; (3) provider/system-of-record reconciliation for effects whose remote outcome is unknown; and (4) exact bounded authority plus source/configuration qualification proving which implementation was allowed to act. Supporting evidence: `ThousandBirdsInc/chidori@223bb8779f63822c3e63a9a4347dda7483a02158` is strongest on strict source/argument-aware no-live replay; `teleport-computer/feedling-mcp@c37e3db0dcc4f08cf69aa3c73cf87a911377b02f` and `LogicStormINC/zebra@efd4e2938d14c6598e9c60503830abf5360fa0bf` implement fenced effect/outbox state machines with explicit uncertain/reconciliation states; `prathamesh-git9/agent-runtime@3d4c3bf58b4262cf523e78655ff0bf1c9453830e` independently demonstrates the same ambiguity rule; `auths-dev/auths-proof@34fa1f33cf365fa54075a2002710aee52ab42394` adds an exact Stripe action, deterministic provider idempotency, durable `OutcomeUnknown`, read-only provider reconciliation, provider-truth observation, semantic source closure and a machine gate that refuses production advertisement while qualification is absent; `orka-agents/orka@7cffe130efa74f505d66dce561ade6c18901ba6e` independently adds durable `SubmittedUnknown` model-call state, `OutcomeUnknown` external-effect state, GitHub PR provider readback/recovery, tool-drift blocking and a successful live GitHub OIDC PR E2E at the pinned head; and `BlackPigIndustries/threvo-actions@f50d568e8d67d1806a122b3151048f038832dcf9` adds a framework-neutral financial consequential-action lifecycle with exact authority, live state re-resolution, semantic-effect admission, `failed_unknown` recovery, authoritative verification and a versioned Stripe qualification-report schema, while explicitly recording that the live provider cases remain `not_exercised`. Contrary evidence: these are established distributed-systems/security ideas assembled in different proportions; Auths and Threvo both remain unqualified against live Stripe at the inspected revisions; Orka's strongest provider readback is specialized to GitHub publication; and no inspected project yet proves all layers for arbitrary third-party APIs at production scale. NEXT TEST: find or independently produce a **qualified live-provider evidence packet** for one high-risk money-mutating action where exact source/config closure, worker authority, provider idempotency, crash-after-write ambiguity and independent provider readback all survive a retained attestation and cold restart. CONFIDENCE: HIGH on the semantic requirement, HIGH that provider-aware governed action runtimes are an emerging category, MEDIUM on whether they command a standalone software budget versus an implementation/service wedge.

## Validated local lessons
- Run 1: a durable-agent claim should be evaluated at the **side-effect boundary**, not at the presence of a checkpoint API. High-signal evidence is a journal that can prevent previously completed external effects from executing again during replay, coupled with tests that prove this behavior in a fresh runtime.
- Run 1: replay becomes verification-grade only when it has a strict posture: source identity/fingerprints, function + argument divergence, journal completeness/consumption, no unexpected live calls, completed-state requirement and output equality. A best-effort replay/debug mode is weaker than a dedicated fail-closed verifier.
- Run 1: crash/retry safety and multi-writer safety are separate. A runtime can replay correctly in one process while still allowing concurrent continuations to corrupt durable state. Inspect the lease/transaction semantics of each storage backend before claiming exactly-once or distributed safety.
- Run 1: history archaeology is essential for runtime maturity. Chidori's current code contains strong regression controls, but its v3.8.1 release commit also documents an engine panic, package-version drift and previously red CI in v3.8.0. A strong architecture does not erase release-operability risk.
- Run 1: comparator breadth and candidate depth should remain distinct. Atmosphere provides strong adjacent evidence for cross-runtime governance/capability contracts, but it was not credited with Chidori-level deterministic-replay depth without equivalent source/test inspection.
- Run 2: **unknown outcome is a first-class state, not a retry condition.** If a non-idempotent effect was marked started before process death but no terminal outcome was durably recorded, safe recovery requires parking the run and obtaining authoritative external evidence. Absence of a local success row does not prove remote failure.
- Run 2: “persist before act” is only half the safety story. The runtime must also classify side effects (`read_only` / idempotent / non-idempotent / irreversible), define which classes may be replayed after uncertainty, and provide a separate resolution path for indeterminate writes.
- Run 2: model output must not be an authorization channel. `agent-runtime`'s tests show that even model-supplied fields claiming approval cannot bypass a registry-level gate; malformed model output also must not silently become terminal success.
- Run 2: append uniqueness is weaker than ownership. A `(run_id, seq)` uniqueness constraint can expose a direct journal collision but does not prove that two processes cannot both reach external I/O. Multi-worker safety needs a lease/fencing/transaction mechanism evaluated independently from replay correctness.
- Run 2: manual recovery metadata is not automatically authoritative evidence. Requiring `actor` and `evidence` fields is useful, but the verifier should separately ask whether the actor is authenticated and whether the evidence can be reconciled against the actual external system of record.
- Run 2: strict replay libraries and durable runtimes are complementary. `davccavalcante/agenticstash` is stronger on framework-neutral input divergence, missing/extra-call reporting and tamper-evident recordings; `agent-runtime` is stronger on crash/approval/indeterminate external-write semantics. Neither alone establishes the full production reliability contract.
- Run 3: **fencing must exist before external dispatch, not merely at terminal write.** Feedling's owner-fenced enqueue and Zebra's `LeaseFence`/claim path show the useful pattern: stale owners should be unable to create or claim new effects, and a later owner must reconcile an abandoned claim instead of simply reissuing it.
- Run 3: an effect state machine should distinguish at least `PENDING`, `CLAIMED`, `SUCCEEDED`, `FAILED_NO_EFFECT`, and `UNCERTAIN/NEEDS_RECONCILIATION`. Feedling and Zebra independently encode the key asymmetry: retry is permitted only after the system has evidence that no external effect occurred; uncertainty is not eligible for automatic retry.
- Run 3: “exactly once” must always name its boundary. Feedling's tests strongly prove exactly-one write across crash recovery **inside its sink-ledger contract**, but that does not imply exactly-once behavior for an arbitrary remote API whose commit status cannot be read back. Future writeups must explicitly name the local boundary and the external authority.
- Run 3: source/version provenance and worker ownership are orthogonal. Runtime generation, owner epochs and fencing tokens protect who may write; they do not prove that the tool implementation being replayed is the same code/version that produced the prior result.
- Run 3: PostgreSQL fault tests that force crashes at multiple points around claim/write/status transitions are much more probative than generic retry tests. The most useful cases make “write failed” and “write may have committed” produce different durable recovery states.
- Run 4: **provider-backed reconciliation should be a separate read path, not a disguised retry.** Auths' Stripe qualification adapter separates execute from reconcile and describes reconciliation as observing the original idempotent refund without another mutation. That is stronger evidence than merely reusing the same idempotency key on another POST.
- Run 4: **qualification state is part of the claim, not deployment metadata.** A sophisticated source tree with crash matrices and provider adapters does not earn “production proven” status if the trusted qualification index is empty or the production route test refuses advertisement. Always inspect the attestation/index and route availability directly.
- Run 4: exact authority, effect safety and evidence provenance are distinct planes. Auths commits exact money/action/configuration inputs, holds ambiguous capacity, observes provider truth with separate read credentials, and binds qualification to a semantic source closure. None of those should be inferred from the others.
- Run 4: a self-denying production route is positive evidence of fail-closed governance. `auths-node` tests explicitly require no production provider profiles when qualification is absent. This is more probative than README language claiming “production ready.”
- Run 4: mainstream durable orchestration plus provider idempotency is a strong commodity baseline. The Temporal comparator can durably resume a refund activity and reuse one Stripe idempotency key; a stronger candidate must add something measurable beyond that baseline, such as provider-truth reconciliation, exact bounded authority, source/configuration closure or qualification evidence.
- Run 5: **model-provider ambiguity and tool/provider ambiguity are distinct reliability boundaries.** Orka's durable `SubmittedUnknown` and external-effect `OutcomeUnknown` states show that a model request can become indeterminate before any business tool runs, while an external mutation can independently become indeterminate after dispatch. Recovery logic should not collapse these into one generic retry state.
- Run 5: provider reconciliation is most convincing when a repository contains an actual readback/recovery implementation plus duplicate-avoidance tests. Orka's GitHub PR publication recovery is materially stronger evidence than an `OutcomeUnknown` enum alone because it interrogates provider-side state to resolve an ambiguous publication.
- Run 5: **live E2E CI and trusted qualification are different evidence classes.** A successful `Live GitHub OIDC PR E2E` at the pinned revision supports operability of one live-provider path, but it does not prove source-bound attestation, crash-matrix qualification or transferability to other providers.
- Run 5: tool/configuration drift must be tested as a recovery hazard. Orka's MCP broker drift tests independently support the Run-4 lesson that execution/recovery assumptions should be invalidated when the tool contract changes rather than silently inheriting old authority/evidence.
- Run 5: commit-history archaeology can reveal the real reliability surface. Orka's repeated fixes for ambiguous PR recovery, URL corruption, provider lookup failures, number collisions and terminal-outcome invariants are evidence that the hard cases live in recovery semantics, not in the happy-path dispatcher.
- Run 6: **qualification reports need a first-class `NOT_EXERCISED` state.** Threvo's Stripe report schema distinguishes `PASSED`, `FAILED` and `NOT_EXERCISED`, and its missing-input path records provider/database participation as false rather than converting absence of credentials into a green result. This is evidence-quality plumbing, not provider proof.
- Run 6: safe retry semantics should be inspectable at the durable state boundary, not only in application code. Threvo's PostgreSQL transition/claim rules allow `failed_unknown -> verification_pending` while effect-claim transfer is limited to `failed_known` or `stale`, making “unknown is not retryable” visible in database-enforced invariants.
- Run 6: financial action governance is emerging as a separable layer between agent frameworks and provider SDKs. Threvo independently converges with Auths on exact approval/effect identity, state re-resolution, provider-aware ambiguity, authoritative verification and explicit qualification evidence while remaining framework-neutral.

## Failed search patterns

- Run 1: generic `checkpoint` / `resume` is too commodity to rank reliability. Future triage should quickly discard projects that persist conversation/graph state but cannot show what prevents duplicate live effects, how divergence is detected, and how concurrent resume is serialized.
- Run 1: an attempted local clone/test execution was blocked by the execution sandbox's outbound-DNS restriction. Until a repository is otherwise materialized locally, distinguish inspected committed tests from independently rerun tests.
- Run 2: generic `agent replay` search produces many observability/debugging libraries that replay model outputs but say nothing about the crash window around irreversible external writes. Search exact state-machine terms such as `execution_started`, `outcome_unknown`, `indeterminate`, `awaiting_recovery`, provider reconciliation and non-idempotent retry policy.
- Run 2: a repository's claim that UNIQUE sequence numbers provide concurrency safety should not be accepted as run-level mutual exclusion. Search specifically for run leases, fencing tokens, owner generations, compare-and-swap transitions or transaction boundaries that exist before external dispatch.
- Run 3: broad searches combining `agent`, `idempotency`, `lease` and `replay` still return design documents and generic framework prose. Exact implementation nouns (`effect_outbox`, `LeaseFence`, `claim_token`, `needs_reconciliation`, `provider_proved_no_effect`, `FOR UPDATE SKIP LOCKED`) were materially higher signal.
- Run 3: a final provider-specific reconciliation search was blocked by a transient GitHub code-search rate limit. Do not infer absence of provider-backed adapters from this run; the unanswered question remains active.
- Run 4: searching only for `Stripe + Temporal + idempotency` mostly finds the commodity pattern “retry with same key.” Higher-signal terms were `outcome-unknown`, `provider truth`, `reconcile transport`, `read permissions`, `semantic closure`, and qualification/attestation files.
- Run 4: design documents that specify live-provider crash qualification are not sufficient evidence that qualification occurred. Check machine state (`release/.../index.json`, attestation directory, generated route roster, production advertisement tests) before crediting the claim.
- Run 5: broad public searches for `live provider attestation`, refund reconciliation and agent idempotency produced many application-level retry/idempotency fragments but no verified **non-empty trusted provider-qualification artifact**. Do not substitute a successful live E2E workflow for that missing evidence class.
- Run 5: transient GitHub code-search rate limits interrupted some late broadening searches. This is negative search-process evidence only, not evidence that stronger provider-qualified implementations do not exist.
- Run 6: the presence of a protected provider-qualification workflow, real sandbox test code, or an artifact-upload step is still not evidence that qualification ran. Search the retained report/artifact state and inspect its explicit status/participation fields before crediting live-provider proof.

## Candidate skills
- EFFECT-JOURNAL RELIABILITY AUDIT — STAGED-ELIGIBLE, 5 distinct shadow successes (Run 1 Chidori; Run 2 agent-runtime; Run 3 Feedling/Zebra; Run 4 Auths; Run 5 Orka). WHEN TO USE: agent runtimes claiming durability, resumability, deterministic execution or safe human-in-the-loop. PROCEDURE: trace every external effect to its durable identity; inspect record→fresh-process replay; force a pre-frontier source/argument change; inspect strict/no-live verification; inspect crash frontier persistence; inspect approval continuation; inspect storage-specific concurrent-writer behavior; classify started-without-outcome semantics; identify provider-side reconciliation; then read release/qualification history. WHY IT WORKED: it separated Chidori's replay verifier from ordinary checkpoint orchestration, exposed `agent-runtime`'s ambiguity semantics and missing lease/source binding, distinguished Feedling/Zebra's stronger fencing, found Auths' provider-backed recovery plus qualification gate, and then surfaced Orka's dual model/effect ambiguity plus GitHub provider reconciliation. FAILURE MODES: frameworks may hide effects inside third-party runtimes; a replay can be deterministic yet lack authoritative source identity or distributed exclusion; documentation can overstate backend/provider guarantees; “idempotent” may be developer-declared without provider proof; a qualification harness can exist without a qualified route; a live E2E can be mistaken for a trusted qualification artifact. NEXT IMPROVEMENT: require an imported live-provider attestation and replay a real crash-after-write case against that exact source closure. Keep lane-local; do not promote to global SEARCH_SKILLS from shadow state.
- AMBIGUOUS EFFECT OUTCOME AUDIT — STAGED-ELIGIBLE, 5 distinct shadow successes (Run 2 agent-runtime; Run 3 Feedling/Zebra; Run 4 Auths; Run 5 Orka; Run 6 Threvo). WHEN TO USE: any agent/workflow system that can issue money-mutating, irreversible or customer-visible external actions. PROCEDURE: locate the durable pre-dispatch marker; identify the exact crash interval between remote commit and local acknowledgement; determine whether retry policy differs by side-effect class; require an explicit INDETERMINATE/UNKNOWN state for non-idempotent writes; inspect the resolution API for actor identity, evidence provenance, duplicate resolution prevention and provider-side status lookup; then test a cold restart before resolution. WHY IT WORKED: `agent-runtime` made the ambiguity window explicit; Feedling/Zebra added multi-worker fencing; Auths adds a provider-specific read-only reconcile path and provider-truth contract; Orka independently adds `OutcomeUnknown` plus a concrete GitHub publication readback path; Threvo independently encodes `failed_unknown -> verification_pending` and prevents semantic-effect transfer from an unknown owner while its Stripe qualification test asserts one provider submission across injected lost acknowledgement. FAILURE MODES: a system can park safely but accept unauthenticated/fabricated resolution evidence; a provider may lack a status/idempotency API; distributed workers may duplicate the call before the indeterminate state is observed; provider readback can itself be stale or insufficiently correlated; a committed live-provider test can still be unexercised. NEXT IMPROVEMENT: validate the full matrix against an imported live-provider qualification record.
- FENCED EFFECT BOUNDARY AUDIT — LOCAL, 1 shadow success. WHEN TO USE: multi-worker agent/workflow runtimes claiming exactly-once or crash-safe external actions. PROCEDURE: verify a stable effect identity; verify owner/epoch/fence authority before enqueue and claim; force stale-owner and concurrent-claim cases; inspect atomic intent/terminal writes; expire or replace a claim; require reconciliation rather than pending reset; verify retries are only created from `FAILED_NO_EFFECT`; then identify the external authority needed to resolve `UNCERTAIN`. WHY IT WORKED: Feedling and Zebra exposed nearly identical correctness structure despite different implementations. FAILURE MODES: local fencing can still lose against a remote provider with no idempotency/status API; an outbox may be transactionally strong while source provenance is weak; lease heartbeats can protect ownership without protecting already-issued remote I/O. NEXT IMPROVEMENT: combine this audit with a provider-status adapter and Chidori-style source fingerprints.
- LIVE-PROVIDER QUALIFICATION GATE AUDIT — STAGED-ELIGIBLE, 2 distinct shadow successes (Run 4 Auths; Run 6 Threvo). WHEN TO USE: agent/action systems claiming provider-safe execution, formally qualified profiles or production-grade recovery. PROCEDURE: freeze exact revision; inspect the provider mutation and reconcile paths; identify independent provider-truth reads and credential scopes; inspect crash/failpoint coverage; locate semantic/source/configuration closure where present; inspect the qualification workflow/report schema; then inspect the trusted qualification index/retained report/artifact and actual production route advertisement. Classify “implemented harness,” “provider exercised,” “qualified provider,” and “advertised production route” separately. WHY IT WORKED: Auths looked unusually complete in source, but its empty qualification index and fail-closed production test prevented an inflated production claim; Threvo independently looked provider-ready in source yet its explicit current-status document and `NOT_EXERCISED` report state prevented a false live-Stripe qualification claim. FAILURE MODES: generated artifacts may look like attestations without a trusted import; testkit routes may be mistaken for production; a protected workflow may exist but never run; a report can exist with `provider_exercised=false`; source closure can be specified but not enforced at build/route time. NEXT IMPROVEMENT: find a candidate with a retained `PASSED` report/attestation for the exact source/provider versions and independently verify that behavior-bearing source drift removes the qualified route. Keep lane-local; do not promote globally from shadow state.
- SOURCE/TOOL DRIFT GATE AUDIT — STAGED-ELIGIBLE, 2 distinct shadow successes (Run 4 Auths semantic source/configuration closure; Run 5 Orka MCP/tool drift blocking). WHEN TO USE: a durable runtime claims recovery/replay remains safe across deploys, tool registry changes or provider adapter updates. PROCEDURE: identify the code/config/tool identity committed into the prior run; mutate one behavior-bearing dependency or tool contract; attempt resume/recovery; require stale qualification or stale execution assumptions to be rejected before another external effect can occur; distinguish a semantic closure/fingerprint from a mere release/version label. WHY IT WORKED: Auths made route qualification dependent on a source/configuration closure, while Orka independently demonstrated that tool/broker drift can block unsafe continuation. FAILURE MODES: version strings can change without semantic drift and semantic behavior can change without version strings; drift detection may stop replay but not invalidate production credentials/routes; a config hash is weaker than a complete behavior-bearing closure. NEXT IMPROVEMENT: combine drift invalidation with a non-empty live-provider attestation and prove that changing one covered source/config input withdraws the production route. Keep lane-local.
