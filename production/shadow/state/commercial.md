## Failed search patterns
- Broad `revenue leakage` queries overproduce dashboards, synthetic CRM/warehouse reconciliations and unsupported headline-dollar claims. Require source authority, effective dates, fail-closed unknown states, deterministic evidence or outcome settlement beyond README.
- Generic payment/AP matching without authority or negative-control semantics is usually a component, not a complete money-assurance oracle.
- Generic `credit note` / `refund` searches over-select systems that can reverse money but cannot prove what should have been billed. Require structural linkage to contract/rating authority when making recovery claims.
- Effective-dated catalog pricing is not equivalent to versioned customer contract authority.
- Internally generated payment facts plus all-green reconciliation do not prove PSP/bank settlement.
- `PaymentIntent.retrieve`, `Refund.retrieve`, webhooks or provider idempotency by themselves do not prove safe recovery. Require explicit post-entry ambiguity, stable action identity, no-new-action invariants and a terminal reconciliation rule.
- Test-mode provider API calls and qualification harness code are not equivalent to completed qualification; inspect launch/attestation state.
- Live smoke is insufficient if the dangerous post-dispatch row is skipped.
- Mutate-then-throw plus a fresh provider adapter is not literal process restart; require process boundary and durable restart state before awarding tier 5B.
- Literal SIGKILL plus exactly one provider object is not economic settlement proof; inspect final provider status, accounting application and later reversals/disputes.
- A provider-native credit consumed on a paid invoice is stronger than object existence, but it is still not cash/bank settlement. Do not use `invoice.status=paid`, `starting_balance`, or `applied_to_invoice` alone to claim refund payout/bank finality.
- **Run-9 failure rule:** Stripe `payout.status=paid`, `payout.paid` and provider/application balance parity do not prove crash-safe payout execution. Require an effect-boundary fault seam around that same payout before awarding crash-safety. Conversely, a crash-safe refund object must not inherit payout/balance terminality from a different repository.
- **Run-9 revision rule:** do not automatically inspect only HEAD for provider qualification. Pin the strongest successful exact workflow revision and then inspect later changes for regressions; a later stricter payout commit can fail its sandbox workflow.
- **Run-10 durability rule:** a cache/lease lock with finite TTL is concurrency protection, not durable ambiguity proof. If a provider effect can exist after local persistence loss, never release economic capacity merely because the lock expires; require a durable action identity plus authoritative provider readback or explicit operator resolution.
- **Run-10 provider-contract rule:** application code cannot infer that all payment providers honor idempotency identically. Provider-specific idempotency and readback semantics must be externally qualified; generic multi-provider abstractions are not evidence of exactly-once provider behavior.
- **Run-11 WAL rule:** `intent durably logged before effect` is not enough if the provider/result identity needed to compensate is born only after the effect. Require either a pre-dispatch provider-discoverable business/action identity or explicit fail-closed orphan handling; never upgrade a WAL alone into crash-safe external recovery.
- **Run-11 idempotency-identity rule:** amount-derived keys can collapse two legitimate equal-amount partial refunds into one logical action. Prefer a durable business refund/action ID that is stable across retries and distinct across legitimate repeated operations.
- **Run-12 replay-window rule:** a locally durable idempotency identity does not create permanent provider exactly-once semantics. If provider dedupe expires, exact replay may become a second effect; record the provider replay horizon and fail closed after it unless another authoritative lookup path exists.
- **Run-13 durable-execution-owner rule:** a workflow engine can safely regenerate a provider idempotency key only while the durable workflow/run identity owner remains authoritative. Source code and rehearsal instructions are not equivalent to a frozen completed provider run, and provider dedupe retention must still be recorded separately; do not infer indefinite replay safety from deterministic key derivation alone.
- Historical CI run IDs can expire; prefer evidence records that stand on their own in-repo but lower confidence when underlying runs are no longer independently retrievable.
